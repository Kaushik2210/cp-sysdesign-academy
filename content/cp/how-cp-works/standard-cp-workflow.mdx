## Intuition

Strong competitors do not solve each problem from scratch each time. They follow the **same loop** every time: understand, brute force, optimise, test, submit, review. The loop is boring on purpose. It reduces cognitive load so your brain can spend its energy on the one hard step that differs per problem: the key idea.

This lesson walks through that loop on a concrete problem, shows how to use the samples as a first (not last) test, and sets up a mistake log you will actually use.

## The loop

1. **Understand** (the five-pass reading from the previous lesson).
2. **Brute force on paper.** State a correct, slow algorithm and its complexity.
3. **Optimise.** Compare the complexity with the constraints; find the property that removes the redundant work.
4. **Implement.** Choose types after computing the worst-case values.
5. **Test.** Samples, then your own edge cases, then (when unsure) a randomised comparison against the brute force.
6. **Submit** only when you can argue it is correct.
7. **Review.** After the verdict, log what happened.

## Worked example: Best Window

**Statement (informal).** Given `n` readings and a number `k`, find the maximum sum of exactly `k` consecutive readings.

**Brute force.** For every start index `i`, add up `a[i..i+k-1]`. That is `(n-k+1) * k` additions, at most about `n^2 / 4`. For `n = 2 * 10^5` this is `10^10`, too slow, but perfectly good for `n <= 5000` and, more importantly, **an excellent reference to compare against later**.

**Where is the redundancy?** Window `i` and window `i+1` share `k-1` elements. Going from one to the next, exactly one element enters (`a[i+k]`) and one leaves (`a[i]`). So the new sum is the old sum plus `a[i+k] - a[i]`.

**Optimised.** One pass, `O(n)`:

<CodeRunner language="python" code={`def brute(a, k):
    return max(sum(a[i:i + k]) for i in range(len(a) - k + 1))

def fast(a, k):
    s = sum(a[:k])
    best = s
    for i in range(k, len(a)):
        s += a[i] - a[i - k]
        best = max(best, s)
    return best

a = [4, -1, 2, 1, -7, 5, 3]
for k in range(1, len(a) + 1):
    assert brute(a, k) == fast(a, k)
    print(k, fast(a, k))
`} />

The assertion loop above is a miniature version of the stress test you will build in module 2: the slow, obviously-correct version checks the fast one.

## Using the samples well

- A passing sample proves almost nothing. A failing sample proves the program is wrong. Treat samples as a smoke test.
- **Add your own cases** at the boundaries of every constraint: `n = 1`, `k = n`, `k = 1`, all values negative, all values equal, values at `10^9`. For this problem, the all-negative case is the one that breaks `best = 0` initialisation.
- Check the **largest** possible answer against your type: here `n * 10^9` up to `2 * 10^14` in a real contest, so `long long`.

## The mistake log

Keep one plain text file or spreadsheet. One line per *verdict that was not AC*:

```text
date | problem | verdict | root cause category | one-line fix habit
2026-03-02 | CF 1234B | WA 5 | missed-edge-case (n=1) | always test n=1 and all-equal
2026-03-05 | CSES 1643 | WA 3 | overflow | choose type from worst-case value
2026-03-09 | CF 1301C | TLE 12 | wrong-complexity | check n against 1e8 budget first
```

Categories to start with: *misread statement*, *edge case*, *overflow*, *off-by-one*, *wrong complexity*, *wrong idea*, *implementation slip*. Review it on a fixed day each week and turn the top category into a checklist item.

<Callout type="warning" title="Do not resubmit blindly">
Resubmitting after a WA without changing your reasoning teaches you nothing and, in rated contests, costs penalty. Before each resubmission, name the specific test case you believe was failing.
</Callout>
