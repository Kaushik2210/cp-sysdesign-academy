## Intuition

The **convex hull trick** speeds up DP transitions of the form `dp[i] = min over j of (m_j * x_i + b_j)`: each earlier state `j` is a **line** `y = m_j * x + b_j`, and the query asks for the lowest line at the point `x_i`. If lines arrive in sorted slope order and queries are sorted too, a deque handles it in `O(n)`. When they are **not** sorted, you would need a balanced structure that maintains the **hull** of the lines, which is fiddly.

The **Li Chao tree** is a much simpler alternative that needs **no ordering at all**. It is a segment tree over the possible query points where **each node stores one line**: the line that is best at the **midpoint** of the node's interval. Adding a line, or asking for the best line at a point, takes `O(log C)` for a domain of `C` points. You can add lines in any order, and the code is about 25 lines.

## Definition

The tree covers the integer interval `[LO, HI]` of possible query points. Each node covers a sub-interval `[lo, hi]` and stores at most one line.

**Invariant:** for every point `x`, the best line at `x` among all lines inserted so far is stored in some node on the path from the root to the leaf of `x`.

### Inserting a line `L` (maximum version)

Start at the root. At each node with interval `[lo, hi]` and `mid = (lo + hi) // 2`:

1. Compare `L` with the stored line `S` **at `mid`**. The better one stays in the node; call the other one `W` (the loser). If the node was empty, store `L` and stop.
2. Two different lines cross **at most once**. So `W` can beat `S` on at most one side of `mid`:
   - if `W` beats `S` at `lo`, it can only win on the **left** half: continue into the left child with `W`;
   - else if `W` beats `S` at `hi`, continue into the **right** child;
   - else `W` is worse everywhere in this interval: **discard** it.
3. Create the child when it does not exist and place `W` there; stop.

Each step goes one level down, so insertion is `O(log C)`.

### Querying a point `x`

Walk from the root to the leaf containing `x` (go left if `x <= mid`, otherwise right), evaluate the line stored in each visited node at `x`, and keep the **best value**. `O(log C)`.

For **minimum** queries, flip the comparisons (or store negated lines). A line `y = m x + b` can also be replaced by a **segment** valid only on an interval: insert it into the `O(log C)` nodes covering that interval (each insertion then costs `O(log^2 C)`).

```python
LO, HI = -10**6, 10**6
slope, icpt, left, right = [], [], [], []

def new(m, b):
    slope.append(m); icpt.append(b); left.append(-1); right.append(-1)
    return len(slope) - 1

def add(m, b):
    if not slope:
        new(m, b); return
    node, lo, hi = 0, LO, HI
    while True:
        mid = (lo + hi) >> 1
        if m * mid + b > slope[node] * mid + icpt[node]:          # the new line is better at the midpoint: swap
            slope[node], m = m, slope[node]
            icpt[node], b = b, icpt[node]
        if lo == hi:
            return
        if m * lo + b > slope[node] * lo + icpt[node]:            # the loser can still win on the left half
            side, hi = left, mid
        elif m * hi + b > slope[node] * hi + icpt[node]:          # or on the right half
            side, lo = right, mid + 1
        else:
            return                                                # it is worse everywhere here
        if side[node] == -1:
            side[node] = new(m, b); return
        node = side[node]

def query(x):
    node, lo, hi, best = 0, LO, HI, None
    while node != -1:
        v = slope[node] * x + icpt[node]
        if best is None or v > best:
            best = v
        mid = (lo + hi) >> 1
        if x <= mid: node, hi = left[node], mid
        else: node, lo = right[node], mid + 1
    return best
```

## Using it in a DP

Take the DP `dp[i] = min over j < i of ( dp[j] + (h_i - h_j)^2 ) + C` (a frog choosing stones). Expanding gives `dp[j] + h_j^2 - 2 h_j * h_i + h_i^2 + C`: for fixed `j` this is a **line in the variable `h_i`** with slope `-2 h_j` and intercept `dp[j] + h_j^2`. So the DP is

```text
dp[i] = h_i^2 + C + min over j < i of line_j(h_i)
```

Insert line `j` into the Li Chao tree once `dp[j]` is known, and query at `h_i`. With the **maximum** version, store negated lines (slope `2 h_j`, intercept `-(dp[j] + h_j^2)`) and negate the answer. The heights need not be sorted and the slopes need not be monotone: the Li Chao tree does not care.

What it shows:

- With **1,000 random lines and 1,000 queries** over `x` between `-10^6` and `10^6`, every answer equals the maximum over all lines. Random lines are mostly dominated, so the tree needs only **16 nodes** and an insertion takes about **2.9 steps**, a query about **3.0**.
- The opposite extreme: **1,000 lines tangent to a parabola**, every one of which is the maximum somewhere. All answers are still correct; the tree uses **993 nodes** (at most one per line), an insertion takes about **8.3 steps** and a query about **9.6**, below the depth limit of 18 for a range of 200,001 points.
- In the **1,000-stone DP**, the Li Chao version equals the quadratic DP. The quadratic one makes **499,500 transitions**; the tree needs about **42,000 steps** (two operations per stone times at most 21 levels).

The counts come from seeded runs; the agreement with brute force is the correctness evidence.

## Li Chao tree versus the other tools

| tool | needs sorted slopes | needs sorted queries | handles arbitrary insertion order | segments | code size |
| --- | --- | --- | --- | --- | --- |
| deque convex hull trick | yes | yes (or binary search) | no | no | short |
| binary search on a hull | yes | no | no | no | medium |
| dynamic hull with a `std::set` | no | no | yes | no | long and error-prone |
| **Li Chao tree** | **no** | **no** | **yes** | **yes** (with extra log) | **short** |
| divide and conquer on time (offline) | no | no | offline only | yes | medium |

The Li Chao tree costs `O(log C)` per operation where `C` is the number of possible query points; compress the offline query coordinates to make `C` equal to the number of queries.

## Pitfalls

1. **Overflow in `m * x + b`.** With `|m|, |x| <= 10^9` the product is `10^18`: use 64-bit and check the range; reduce the domain by compressing queries.
2. **Querying outside the domain.** Choose `[LO, HI]` to cover every query point.
3. **Midpoint of negative ranges.** Use a floor division (`>> 1` or `floorDiv`), not truncation towards zero; and be consistent about whether the left child is `[lo, mid]` and the right `[mid + 1, hi]`.
4. **Forgetting to compare at both ends** after the midpoint swap, or comparing the wrong line (the loser, not the original new line).
5. **Ties.** Use strict comparisons when swapping so equal lines do not loop; equal lines may be discarded.
6. **Minimum versus maximum.** Do not mix them: a tree built for maximum cannot answer minimum queries without negating the lines.
7. **Storing nodes in an array indexed by heap position** (`2 * node + 1`) for a huge domain: use dynamic node creation instead.
8. **Querying an empty tree.** Handle "no lines yet" explicitly (the problem here promises a line exists).
