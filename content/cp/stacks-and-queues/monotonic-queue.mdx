## Intuition

You slide a window of width `k` over an array and want the maximum inside it at every step. Recomputing is `O(nk)`. But when the window slides by one:

- one element **leaves** on the left,
- one element **arrives** on the right.

An element that is smaller than a newer element **in the same window** will never be the maximum again: the newer one is bigger *and* leaves the window later. So it can be discarded the moment the bigger one arrives. What remains are candidates whose values decrease from oldest to newest, the biggest being the oldest.

## Definition: the monotonic queue

Maintain a deque of **indices** of the current window such that their values are strictly decreasing from front to back. For each new index `i`:

1. **Push with cleanup (back):** pop from the back while `a[back] <= a[i]`, then push `i`.
2. **Expire (front):** if the front index is `<= i - k`, pop it from the front.
3. **Answer:** once `i >= k - 1`, the maximum of the window is `a[front]`.

```python
dq = deque()
for i in range(n):
    while dq and a[dq[-1]] <= a[i]:
        dq.pop()
    dq.append(i)
    if dq[0] <= i - k:
        dq.popleft()
    if i >= k - 1:
        out.append(a[dq[0]])
```

### Invariant and proof

> After handling index `i`, the deque holds exactly the indices `j` in the window `(i-k, i]` that are **not dominated**, meaning no later index `j' in (j, i]` has `a[j'] >= a[j]`. They appear in increasing index order, hence in strictly decreasing value order.

- *Safe to discard:* a dominated `j` is never a window maximum from now on, since `j'` is at least as large and stays in the window at least as long.
- *Front is the maximum:* the front is the oldest non-dominated index, hence the largest of the candidates, and every non-candidate is dominated by some candidate, so the front is the window maximum.
- *Expiry:* indices leave the window in index order, so only the front can expire, and at most one per step (the window moves by one).

### Complexity

Each index is pushed once and popped at most once (from the back or the front): **`O(n)` total, independent of `k`**.

## Sliding window minimum, and checking against brute force

For the minimum, flip the comparison (`a[back] >= a[i]`). The snippet below tests both against a naive implementation on random input.

<CodeRunner language="python" code={`import random
from collections import deque

def sliding(a, k, better):
    # better(x, y) is True if x should evict y (>= for max, <= for min)
    dq, out = deque(), []
    for i, x in enumerate(a):
        while dq and better(x, a[dq[-1]]):
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(a[dq[0]])
    return out

random.seed(5)
for _ in range(500):
    n = random.randint(1, 15)
    k = random.randint(1, n)
    a = [random.randint(-5, 5) for _ in range(n)]
    mx = sliding(a, k, lambda x, y: x >= y)
    mn = sliding(a, k, lambda x, y: x <= y)
    assert mx == [max(a[i:i + k]) for i in range(n - k + 1)]
    assert mn == [min(a[i:i + k]) for i in range(n - k + 1)]
print("500 random cases agree with brute force")
`} />

## Application: DP over a sliding range

A common pattern: `dp[i] = cost[i] + min(dp[j] for j in [i-k, i-1])`. The inner minimum is a sliding window minimum **over the dp values themselves**, which are produced online. Keep a monotonic deque of indices with increasing `dp` values; the front gives the best predecessor.

<CodeRunner language="python" code={`from collections import deque

def min_cost_path(cost, k):
    # start at index 0, reach index n-1, each jump moves 1..k steps,
    # paying cost of every index landed on (including the first).
    n = len(cost)
    dp = [0] * n
    dp[0] = cost[0]
    dq = deque([0])            # indices with increasing dp
    for i in range(1, n):
        while dq[0] < i - k:
            dq.popleft()
        dp[i] = cost[i] + dp[dq[0]]
        while dq and dp[dq[-1]] >= dp[i]:
            dq.pop()
        dq.append(i)
    return dp[-1]

print(min_cost_path([1, 100, 1, 1, 100, 1], 2))   # 4
print(min_cost_path([5, 1, 1, 1, 5], 3))         # 11
`} />

With `k = 2` the first call prints `4` (path `0 -> 2 -> 3 -> 5`, each jump at most 2 steps, landing on costs `1 + 1 + 1 + 1`). The second prints `11`: the ends cost `10` and one cheap cell in between costs `1`.

<Callout type="note" title="Same idea, other aggregates">
The window aggregate must be *selective* (max, min). For sum or count you simply keep a running total. For gcd, or any associative non-invertible operation, use the "two stacks" queue: see [amortized analysis](/cp/stacks-and-queues/amortized-analysis/).
</Callout>

## Pitfalls

1. **Expiry check uses the index, not the value.** The deque must store indices (or `(index, value)` pairs); otherwise you cannot tell what has left the window.
2. **`<` versus `<=` when evicting.** Both are correct for the maximum value; `<=` keeps the deque strictly decreasing and slightly shorter. If you need the *position* of the leftmost/rightmost maximum, the choice matters.
3. **Reading the answer before the first full window** (`i < k - 1`).
4. **Off-by-one in expiry.** The window ending at `i` contains `i-k+1 .. i`, so an index is expired when `idx <= i - k`.
5. **Using a heap** gives `O(n log n)` with lazy deletion. It works but is slower and needs deletion care. The deque is simpler *and* faster.
6. **Variable-width windows.** The same structure handles windows where the left end only moves right (two pointers): expire by index whenever the left pointer passes the front.
