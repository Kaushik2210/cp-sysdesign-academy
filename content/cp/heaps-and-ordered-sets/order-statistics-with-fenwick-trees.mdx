## Intuition

A heap answers "what is the smallest?". Many problems ask for something in the **middle** of a collection that keeps **changing**:

- "What is the **k-th smallest** number right now?" (the median is a special case)
- "How many numbers are **smaller than** `x`?" (the rank of `x`)
- "Insert a number, remove a number, ask again."

These are **order statistics**. A sorted array answers them in `O(log n)` but takes `O(n)` to insert or remove. A balanced search tree with subtree sizes (an *order statistic tree*) does everything in `O(log n)`, but few standard libraries expose it: C++ `std::set` and Java `TreeSet` give you ordering and neighbours but **no k-th element or rank**, and Python and JavaScript have no ordered set at all.

A **Fenwick tree** (binary indexed tree) over **counts** gives the same operations in about 10 lines of code, in every language. The idea: if the possible values are `1..m`, keep an array where position `v` holds **how many copies of `v`** are currently in the collection. Rank queries become **prefix sums** of that array, and the k-th smallest becomes **"the first position where the prefix sum reaches `k`"**.

## Definition

When values are large or arbitrary (up to `10^9`, negative, or not integers), first **compress** them: collect every value that will ever be inserted or queried, sort and deduplicate them, and replace each by its rank `1..m`. This needs the operations in advance (*offline*). For an online problem with unknown values use a balanced tree or a dynamically sized structure instead.

Over the compressed values keep a Fenwick tree of counts `T`. Then:

| operation | how | cost |
| --- | --- | --- |
| insert `v` | add `+1` at position `v` | `O(log m)` |
| erase `v` | add `-1` at position `v` (check that it is present first: keep a plain count array) | `O(log m)` |
| count of values `<= v` | prefix sum up to `v` | `O(log m)` |
| rank of `v` (how many are smaller) | prefix sum up to `v - 1` | `O(log m)` |
| **k-th smallest** | **binary descent** (below) | `O(log m)` |
| size | keep a running total | `O(1)` |

### Binary descent for the k-th smallest

The smallest position whose prefix count reaches `k` could be found by binary search on the answer with a prefix sum inside (`O(log^2 m)`). But the Fenwick tree's structure lets you do it in **one pass**. Let `top` be the largest power of two not above `m`. Start with `pos = 0` and for `step = top, top/2, ..., 1`:

```text
if pos + step <= m and T[pos + step] < k:
    pos += step
    k  -= T[pos]
```

At the end `pos` is the **largest position whose prefix count is below the original `k`**, so `pos + 1` is the rank (compressed position) of the k-th smallest. Why it works: `T[pos + step]` (with `pos` a multiple of `2 * step`) covers exactly the block of `step` positions that follows `pos`, so the test asks "does the whole next block still leave the answer further right?" It is a binary search that reads the tree directly.

# vals = sorted distinct values, tree = Fenwick tree of counts over positions 1..size
def kth(k):                        # k-th smallest (1-indexed); the caller checks k <= total
    pos, step = 0, top             # top = largest power of two <= size
    while step:
        nxt = pos + step
        if nxt <= size and tree[nxt] < k:
            pos = nxt
            k -= tree[nxt]
        step >>= 1
    return vals[pos]               # vals is 0-indexed, so vals[pos] is the value at position pos + 1

## Experiment

The program wraps these ideas in a small class over values `0..m-1` and checks them against a sorted list and brute force.

<CodeRunner language="python" timeoutMs={30000} code={`import bisect
import random


class OrderStatistics:
    """A multiset over the values 0..m-1 with insert, erase, rank and k-th smallest, all in O(log m), using a Fenwick tree of counts."""
    def __init__(self, m):
        self.m = m
        self.tree = [0] * (m + 1)
        self.top = 1
        while self.top * 2 <= m:
            self.top *= 2
        self.size = 0
        self.steps = 0

    def add(self, v, d):                          # v in 0..m-1
        i = v + 1
        while i <= self.m:
            self.tree[i] += d
            self.steps += 1
            i += i & -i
        self.size += d

    def count_below(self, v):                     # how many stored values are smaller than v: the rank of v, minus one
        i, total = v, 0
        while i > 0:
            total += self.tree[i]
            self.steps += 1
            i -= i & -i
        return total

    def kth(self, k):                             # the k-th smallest value (k starts at 1)
        pos = 0
        step = self.top
        while step:
            nxt = pos + step
            self.steps += 1
            if nxt <= self.m and self.tree[nxt] < k:
                pos = nxt
                k -= self.tree[nxt]
            step >>= 1
        return pos                                # pos + 1 is the 1-based rank of the answer, so pos is the 0-based value


def count_inversions(a):
    """Pairs i < j with a[i] > a[j]. Compress the values, then for each element count how many earlier ones are larger."""
    vals = sorted(set(a))
    rank = {v: i for i, v in enumerate(vals)}
    os_ = OrderStatistics(len(vals))
    inv = 0
    for x in a:
        r = rank[x]
        inv += os_.size - (os_.count_below(r + 1))           # earlier elements strictly larger than x
        os_.add(r, 1)
    return inv, os_.steps


def window_medians(a, k):
    vals = sorted(set(a))
    rank = {v: i for i, v in enumerate(vals)}
    os_ = OrderStatistics(len(vals))
    out = []
    for i, x in enumerate(a):
        os_.add(rank[x], 1)
        if i >= k:
            os_.add(rank[a[i - k]], -1)
        if i >= k - 1:
            out.append(vals[os_.kth((k + 1) // 2)])
    return out, os_.steps

What the output shows:

- Over **20,000 random inserts, erases and queries** the Fenwick structure agrees with a plain sorted list on every k-th and every rank query.
- The cost is **independent of how many values are stored**: with 1,000 stored values or 100,000 among `2^20` possible values, a k-th query takes **21 tree steps** (the loop runs once per power of two from `2^20` down to 1). It depends only on the size of the **value range**, which is why compressing values keeps `m` at most the number of operations.
- **Counting inversions** (pairs `i < j` with `a[i] > a[j]`) in 3,000 numbers: for each element, count how many earlier elements are larger. The Fenwick answer, **2,317,351**, equals the brute force over **4,498,500** pairs, with about **35,000 tree steps** instead of 4.5 million pair checks. Inversions measure how far an array is from sorted, and the same count gives the number of swaps bubble sort needs.
- The **sliding window median** of 5,000 numbers with a window of 101 (add the new value, remove the expired one, ask for the `(k + 1) / 2`-th smallest) equals the brute force over every window, with no lazy deletion and no heap bookkeeping: just 129,639 tree steps in total.

The counts are from one seeded run; the agreement with brute force is the correctness evidence.

## Where else this appears

| task | how |
| --- | --- |
| Count of smaller (or larger) numbers before or after each element | process in order; for each element ask the rank before inserting it |
| Inversions, and the minimum adjacent swaps to sort | sum of those counts |
| k-th smallest in a sliding window, window median | add the new value, erase the expired one, query |
| Order statistics in a **subrange of an array** (offline) | sort the queries and sweep, or use a persistent or wavelet structure |
| **Ordered set with k-th and rank** where only ordering exists | compress, then Fenwick |
| Selecting the best `k` items under changing conditions | a Fenwick tree over values holding counts (and a second one holding sums) lets you add "the sum of the k smallest" |

Many languages offer shortcuts: C++ has the policy-based `tree` (`__gnu_pbds`) with `find_by_order` and `order_of_key`, but it is a GNU extension and not available everywhere; Java's `TreeMap` has no rank. The Fenwick tree is portable and short enough to write from memory in a contest.

## Pitfalls

1. **Forgetting to compress** (or compressing without including every queried value). The tree must cover every value that is ever inserted or erased.
2. **Erasing an absent value.** A blind `-1` drives a count negative and corrupts later answers. Keep a separate count (or test the point count) and ignore the erase when it is zero.
3. **Off-by-one between 0-indexed values and a 1-indexed tree.** Fenwick trees are 1-indexed; the descent returns `pos` such that the answer is at position `pos + 1`, which is `vals[pos]` for a 0-indexed value array.
4. **Asking for `k` larger than the size.** Check against the running total first and print the required sentinel (here `-1`).
5. **Using `top` that is too large or too small.** `top` must be the largest power of two **not exceeding** `m`; the guard `nxt <= m` handles the rest.
6. **Binary search with prefix sums** inside a loop: correct but `O(log^2)`; fine for small limits, slow at large ones.
7. **Forgetting duplicates.** A multiset counts copies, and rank can mean "number strictly smaller" or "number at most". Decide which the problem needs.
8. **Using 32-bit counts** when sums of values (not counts) are stored in a second tree.
