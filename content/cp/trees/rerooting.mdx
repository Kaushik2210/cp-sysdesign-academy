## Intuition

[Tree DP](/cp/trees/tree-dp-and-diameter/) answers a question **for the root**: you compute something for each subtree and combine children upward. But many problems want the answer **for every vertex as if it were the root**: "for each house, the total distance to all the others", "for each city, how far is the farthest city".

Running the tree DP once per vertex costs `O(n^2)`. The trick is to notice that **moving the root across one edge changes very little**. If you already know the answer for the parent `p`, the answer for its child `v` differs only by what happens on the single edge `p-v`: the vertices on `v`'s side get one step closer, the vertices on `p`'s side get one step farther. So: solve once for a fixed root bottom-up, then **push answers down** from the root, fixing each child with an `O(1)` correction.

## Definition

Root the tree at vertex 1 and fix an order where every parent comes before its children (BFS order works and avoids recursion).

**Pass 1, bottom-up** (reverse BFS order): for every vertex `v` compute

```text
size[v]  = number of vertices in the subtree of v
down[v]  = sum of distances from v to the vertices inside its own subtree
         = sum over children c of ( down[c] + size[c] )        # each vertex of c's subtree is 1 farther from v than from c
```

Then `ans[root] = down[root]`.

**Pass 2, top-down** (BFS order): moving the root from `p` to its child `v`:

```text
ans[v] = ans[p] - size[v] + (n - size[v])
```

The `size[v]` vertices of `v`'s subtree each get 1 closer, and the other `n - size[v]` vertices each get 1 farther.

Both passes are linear, so everything is `O(n)`.

## Example, step by step

Tree with 5 vertices, edges `1-2, 1-3, 3-4, 3-5`, rooted at 1.

```text
      1
     / \
    2   3
       / \
      4   5
```

**Bottom-up:**

| vertex | `size` | `down` | why |
| --- | --- | --- | --- |
| 2 | 1 | 0 | leaf |
| 4 | 1 | 0 | leaf |
| 5 | 1 | 0 | leaf |
| 3 | 3 | 2 | children 4 and 5: `(0 + 1) + (0 + 1)` |
| 1 | 5 | 6 | child 2: `0 + 1`; child 3: `2 + 3` |

So `ans[1] = 6`: distances `1 + 1 + 2 + 2`.

**Top-down**, `n = 5`:

| vertex | formula | `ans` |
| --- | --- | --- |
| 1 | `down[1]` | 6 |
| 2 | `6 - 1 + (5 - 1)` | 9 |
| 3 | `6 - 3 + (5 - 3)` | 5 |
| 4 | `ans[3] - 1 + (5 - 1) = 5 - 1 + 4` | 8 |
| 5 | `ans[3] - 1 + 4` | 8 |

Check vertex 3 by hand: distances to 1, 2, 4, 5 are `1, 2, 1, 1`, total 5. ✓.

## The general pattern

Not every answer reroots as neatly as a sum. The recipe for a general reroot:

1. Define what a vertex needs from each **neighbour direction** (a "message"): for a child it is the answer for that child's subtree, for the parent it is the answer for *everything else*, the part of the tree above.
2. Compute the **down** messages bottom-up as in ordinary tree DP.
3. Compute the **up** message for child `v` of `p` by combining `p`'s own up message with the down messages of all of `p`'s **other** children. For sums and counts you can subtract `v`'s contribution; for **max** and **min** you need *prefix and suffix* combinations (or keep the best two values per vertex), because you cannot subtract a maximum.
4. The answer for `v` combines its up message and all its down messages.

Typical problems: the farthest vertex from each vertex (keep the top two down depths), the number of valid colourings with each vertex as the root, the best centre of the tree.

<Callout type="tip" title="A shortcut for one special case">
For "distance to the farthest vertex" there is a shortcut: the farthest vertex from any vertex is one of the two diameter endpoints. Rerooting is the technique that keeps working when the quantity is not a distance.
</Callout>

## Pitfalls

1. **Subtracting a maximum.** The `- size[v] + (n - size[v])` trick works because sums are invertible. For max, min or gcd you need prefix/suffix aggregates or the best two child values.
2. **Wrong order.** The top-down pass needs `ans[parent]` first, so use BFS order (or DFS preorder), never an arbitrary order.
3. **Mixing `size` and `n - size`.** On a move `p -> v`, the vertices on `v`'s side are `size[v]`, the others are `n - size[v]`; swapping them gives answers off by a lot, yet still plausible-looking on small trees.
4. **Recursion depth.** A path graph has depth `n`; recursive DFS overflows the stack in Python and in Java's default stack. Use BFS order as above.
5. **Overflow.** Distance sums reach about `n^2 / 2`, which is `2·10^10` for `n = 2·10^5`: use 64-bit integers.
6. **Forgetting the root's answer.** `ans[root] = down[root]` is the seed; everything else is derived from it.
