## Intuition

Given `n` points, which two are closest? Checking every pair costs `O(n²)`, hopeless for `n = 2·10^5`. The structure of the plane lets you do it in `O(n log n)`, with two classic ideas that reach far beyond this one problem:

1. **Divide and conquer.** Split the points by a vertical line, solve each half, then handle the pairs that *straddle* the line. The trick is that straddling pairs can only matter near the line, and "near" turns out to contain only a handful of candidates per point.
2. **Sweep line.** Slide a vertical line across the plane from left to right, and maintain a small set of "active" points in a sorted structure. Each new point only needs to look at a few neighbours in that set.

## Divide and conquer

1. **Sort** the points by `x`.
2. **Recurse** on the left half and the right half. Let `δ` be the smaller of the two best distances found.
3. A pair with one point in each half can beat `δ` only if **both points lie within `δ` of the dividing line**. Collect those points into the **strip**.
4. **Sort the strip by `y`.** For each point, compare it only with the following points whose `y` is within `δ`. Update `δ` when a closer pair appears.

**Why step 4 is cheap: the packing argument.** Take a point `p` in the strip and look at the rectangle `δ` wide on each side of the line (width `2δ`) and `δ` high above `p`. Every point inside it is at least `δ` away from every other point *of the same half*, so at most four points fit in each `δ × δ` square, at most **8 points** in the whole rectangle, and only about 7 of them can be other points. So each strip point is compared with a constant number of successors. The strip pass is linear after sorting.

```text
T(n) = 2 T(n/2) + O(n log n)   when the strip is sorted each time   ->  O(n log^2 n)
T(n) = 2 T(n/2) + O(n)         when you merge by y like merge sort  ->  O(n log n)
```

**Work with squared distances.** Compare `dx² < best` instead of taking square roots; everything stays an exact integer.

```python
def closest_pair_sq(points):                       # squared distance of the closest pair (n >= 2)
    pts = sorted(points)
    def solve(l, r):
        if r - l <= 3:                             # brute force on tiny ranges
            return min((pts[i][0] - pts[j][0]) ** 2 + (pts[i][1] - pts[j][1]) ** 2
                       for i in range(l, r) for j in range(i + 1, r))
        m = (l + r) // 2
        midx = pts[m][0]
        best = min(solve(l, m), solve(m, r))
        strip = sorted((p for p in pts[l:r] if (p[0] - midx) ** 2 < best), key=lambda p: p[1])
        for i in range(len(strip)):
            j = i + 1
            while j < len(strip) and (strip[j][1] - strip[i][1]) ** 2 < best:
                d = (strip[i][0] - strip[j][0]) ** 2 + (strip[i][1] - strip[j][1]) ** 2
                if d < best: best = d
                j += 1
        return best
    return solve(0, len(pts))
```

```cpp
        ll best = LLONG_MAX;
        for (int i = l; i < r; i++) for (int j = i + 1; j < r; j++) best = min(best, d2(pts[i], pts[j]));
```

## Sweep lines

A **sweep line** replaces a 2D problem with a 1D problem that changes over time: imagine a vertical line moving left to right. Events happen at specific `x` values; between events nothing changes. You keep a data structure for what the line currently crosses.

| problem | events | structure for the active set |
| --- | --- | --- |
| **closest pair** | each point | a set ordered by `y`; look at the few points with `y` within `δ`, discard those with `x` more than `δ` behind |
| do any two segments **intersect**? (Shamos-Hoey) | segment start and end | a set ordered by the `y` at the sweep position; only **adjacent** segments need testing |
| **area of a union of rectangles** | rectangle left and right edges | a segment tree over `y` that counts covered length |
| **skyline** or maximum overlap | interval starts and ends | a multiset of active heights, or a counter |
| nearest **neighbour queries** offline | points and queries, sorted by `x` | an ordered set keyed by `y` |

### The sweep version of closest pair

Process points in order of `x`. Keep an ordered set `active` of the points whose `x` is within `δ` of the current point, keyed by `y`. For each new point `p`:

1. Remove points from `active` whose `x` is more than `δ` behind `p` (they can never help again).
2. Look up the points in `active` with `y` in `[p.y − δ, p.y + δ]`: at most a constant number by the same packing argument.
3. Update `δ` with any closer pair, then insert `p`.

It is the same idea as the divide and conquer strip, seen from a moving viewpoint, and runs in `O(n log n)` with a balanced tree.

## Pitfalls

1. **Taking square roots.** Compare squared distances: `dx² < best` is exact. A `sqrt` followed by a floating-point comparison invites off-by-epsilon errors.
2. **Forgetting duplicates.** Two identical points give distance `0`; make sure the strip logic and the base case do not skip them (the strict `<` against `best` still keeps `0` as the minimum).
3. **Using `<=` in the strip filter incorrectly.** Points with `dx² = best` cannot improve a squared distance of `best`; `<` is enough and keeps the strip small.
4. **Sorting by `y` inside the strip but comparing `x` too.** Use the sort only to bound the `y` window; the actual distance uses both coordinates.
5. **Degenerate inputs.** If all points share an `x`, the strip contains everything; the `y`-window cut still keeps the pass cheap, but a naive implementation without it degrades to `O(n²)`.
6. **Recursion depth.** The depth is `log n`, fine; but copying subarrays at every level (as in the Python version) costs memory, so slice sparingly for big inputs.
7. **Overflow.** Squared distances reach `8·10^12` for coordinates up to `10^6`, so use 64-bit integers.
