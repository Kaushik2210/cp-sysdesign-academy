## Intuition

Geometry problems feel different from graph or DP problems because the input is *continuous* and the answers depend on edge cases: points that touch, lines that coincide, three points that are almost in a row. The cure is one small tool and one rule:

- **The tool:** the **cross product**. It turns "is this point to the left or right of that line?" into the sign of a single integer expression.
- **The rule:** **stay in exact integers.** No angles, no slopes, no square roots, no division, as long as the problem allows. Every decision becomes the sign of an integer, which is either exactly right or exactly wrong, never "almost".

Almost everything in this module (segment intersection, polygon area, convex hulls, closest pairs) is built from the cross product.

## Definition

For vectors `u = (ux, uy)` and `v = (vx, vy)`:

```text
cross(u, v) = ux * vy - uy * vx         (a single number)
dot(u, v)   = ux * vx + uy * vy
```

- `cross(u, v) > 0`: turning from `u` to `v` is a **counter-clockwise** turn (`v` is to the left of `u`).
- `cross(u, v) < 0`: clockwise (right). `cross(u, v) = 0`: `u` and `v` are **parallel** (collinear if they share a point).
- `|cross(u, v)|` is the area of the parallelogram spanned by `u` and `v`, so half of it is the area of the triangle.
- `dot(u, v) = 0` means perpendicular; the sign tells whether the angle is acute or obtuse.

**Orientation** of three points `a, b, c`: the sign of `cross(b - a, c - a)`.

```text
orient(a, b, c) = +1   c is to the left of the directed line a -> b   (counter-clockwise turn)
orient(a, b, c) = -1   c is to the right                                (clockwise turn)
orient(a, b, c) =  0   a, b, c are collinear
```

With coordinates up to `10^6` a cross product is below `8 * 10^12`: safe in 64-bit integers (and in JavaScript numbers). With coordinates up to `10^9`, products reach `10^18`, so you need 128-bit arithmetic or care.

## Segment intersection

Do segments `p1 p2` and `p3 p4` share a point? Compute

```text
d1 = orient(p3, p4, p1)    d2 = orient(p3, p4, p2)
d3 = orient(p1, p2, p3)    d4 = orient(p1, p2, p4)
```

1. **Proper crossing:** `d1 * d2 < 0` **and** `d3 * d4 < 0`. Each segment's endpoints lie strictly on opposite sides of the other's line. They cross at a single interior point.
2. **Touching or collinear:** if some `d_i = 0`, that endpoint is collinear with the other segment. It is a common point exactly when it lies **inside the other segment's bounding box**: for a point already known to be on the line through `a` and `b`, being between `a` and `b` is the same as `min(ax, bx) <= px <= max(ax, bx)` and the same for `y`.
3. Otherwise the segments do not touch.

This handles every special case in one structure: T-junctions (an endpoint on the middle of the other segment), shared endpoints, overlapping collinear segments, collinear but disjoint segments. A test using only bounding boxes, or only "do the signs differ", is wrong in some of those cases.

## Polygon area: the shoelace formula

For a simple polygon with vertices `p0, p1, ..., p(n-1)` in order:

```text
2 * area = sum over i of cross(p_i, p_(i+1))   (indices modulo n)
```

The result is **positive for counter-clockwise** order and negative for clockwise. Work with **twice the area**: it is an integer whenever the coordinates are, which avoids all fractions. It also works for non-convex polygons.

## Point in polygon

Cast a ray from point `p` to the right and count how many polygon edges it crosses: odd means inside. To stay exact:

- Handle a point **on the boundary** first (collinear with an edge and in its bounding box).
- Count an edge only if it **straddles** the horizontal line through `p` using the half-open rule `(a.y > p.y) != (b.y > p.y)`. This avoids double counting when the ray passes exactly through a vertex.
- Decide "is the crossing to the right of `p`" with `orient`, not with a division.

## Pick's theorem

For a polygon whose vertices have integer coordinates, with `I` lattice points strictly inside and `B` lattice points on the boundary:

```text
area = I + B/2 - 1          so    I = (2*area - B + 2) / 2
```

`B` is the sum of `gcd(|dx|, |dy|)` over the edges. This gives the number of interior lattice points with no enumeration.

## Example, step by step

Segments `(0,0)-(4,4)` and `(4,4)-(6,6)`.

- `d1 = orient((4,4), (6,6), (0,0)) = 0`, `d2 = orient((4,4), (6,6), (4,4)) = 0` (everything is on the same line `y = x`).
- `d3 = orient((0,0), (4,4), (4,4)) = 0`: collinear, and `(4,4)` is inside the bounding box of the first segment `[0,4] x [0,4]`: **they touch** at `(4,4)`.
- With the third segment `(5,5)-(6,6)` instead: the endpoint `(5,5)` is collinear but outside `[0,4] x [0,4]`, and `(4,4)` is outside `[5,6] x [5,6]`: no contact.

For the L-shaped polygon `(0,0), (4,0), (4,2), (2,2), (2,4), (0,4)`: `2 * area = 24`, area `12`; boundary points `B = 4 + 2 + 2 + 2 + 2 + 4 = 16`; Pick gives `I = (24 - 16 + 2) / 2 = 5` interior lattice points.

```python
def orient(ax, ay, bx, by, cx, cy):
    v = (bx - ax) * (cy - ay) - (by - ay) * (cx - ax)
    return (v > 0) - (v < 0)

def on_segment(ax, ay, bx, by, px, py):             # p already collinear with a-b
    return min(ax, bx) <= px <= max(ax, bx) and min(ay, by) <= py <= max(ay, by)

def touch(s, t):
    x1, y1, x2, y2 = s
    x3, y3, x4, y4 = t
    d1 = orient(x3, y3, x4, y4, x1, y1); d2 = orient(x3, y3, x4, y4, x2, y2)
    d3 = orient(x1, y1, x2, y2, x3, y3); d4 = orient(x1, y1, x2, y2, x4, y4)
    if d1 * d2 < 0 and d3 * d4 < 0:
        return True
    return ((d1 == 0 and on_segment(x3, y3, x4, y4, x1, y1)) or
            (d2 == 0 and on_segment(x3, y3, x4, y4, x2, y2)) or
            (d3 == 0 and on_segment(x1, y1, x2, y2, x3, y3)) or
            (d4 == 0 and on_segment(x1, y1, x2, y2, x4, y4)))

def area2(poly):                                      # twice the signed area, an integer
    n = len(poly)
    return sum(poly[i][0] * poly[(i + 1) % n][1] - poly[(i + 1) % n][0] * poly[i][1] for i in range(n))
```

```cpp
    int d1 = orient(x3, y3, x4, y4, x1, y1), d2 = orient(x3, y3, x4, y4, x2, y2);

    if (d1 * d2 < 0 && d3 * d4 < 0) return true;
    return (d1 == 0 && on_segment(x3, y3, x4, y4, x1, y1)) || (d2 == 0 && on_segment(x3, y3, x4, y4, x2, y2)) ||

ll area2(const vector<pair<ll,ll>>& p) {
    ll s = 0; int n = p.size();
    for (int i = 0; i < n; i++) s += p[i].first * p[(i+1)%n].second - p[(i+1)%n].first * p[i].second;
    return s;
}
```

## Formulas at a glance

| question | exact integer formula |
| --- | --- |
| which side of line `a -> b` is `c` on | sign of `cross(b - a, c - a)` |
| are `a, b, c` collinear | `cross(b - a, c - a) == 0` |
| twice the area of triangle `abc` | `abs(cross(b - a, c - a))` |
| twice the area of a polygon | shoelace sum of `cross(p_i, p_(i+1))` |
| is `p` on segment `ab` | collinear, and inside the bounding box |
| do two segments touch | the four-orientation test above |
| angle acute, right or obtuse at `b` | sign of `dot(a - b, c - b)` |
| squared distance between points | `dx*dx + dy*dy` (compare squared distances, avoid `sqrt`) |
| lattice points on a segment | `gcd(abs(dx), abs(dy)) + 1` including both ends |
| interior lattice points of a polygon | Pick: `I = (2*area - B + 2) / 2` |

## Pitfalls

1. **Floating point where integers suffice.** Collinearity and touching tests with floats fail on near-degenerate input (the demo shows a genuine miss at coordinates near `10^8`). Stay in integers; if you must use floats, compare with a tolerance `eps` and choose it deliberately.
2. **Overflow.** Coordinates `10^9` make a cross product `10^18`: use 128-bit integers (C++ `__int128`) or reduce the problem.
3. **Skipping collinear cases.** A proper-crossing test alone misses T-junctions and overlaps; a bounding-box test alone claims touching for segments that merely have overlapping boxes.
4. **Bounding-box check on non-collinear points.** `on_segment` is only valid after you know the point is collinear with the segment.
5. **Counting a vertex twice in point-in-polygon.** Use the half-open straddle rule `(a.y > p.y) != (b.y > p.y)`.
6. **Forgetting the boundary** when the problem distinguishes inside, outside and on the edge.
7. **Taking `abs` too early or too late** for signed areas; the sign tells the orientation of the polygon, which the convex hull and the other algorithms need.
8. **Comparing `sqrt` of distances.** Compare squared distances instead, exactly.
