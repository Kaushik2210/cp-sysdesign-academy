## Intuition

Some students dislike each other. Can you split the class into two teams so that **nobody shares a team with someone they dislike**? Graph language: students are vertices, "dislike" is an edge, and you ask whether the vertices can be painted with **two colours** so that every edge joins different colours.

Try it by hand. Pick a student and put them in team A. Everyone they dislike must go to team B. Everyone *those* students dislike must go back to team A. The choice is forced all the way through the group. A contradiction can only appear if the forcing runs into a student who would need both colours.

## Definition

A graph is **bipartite** when its vertices split into two sets with every edge between the sets.

> A graph is bipartite exactly when it has **no cycle of odd length**.

Why: along a cycle the colours must alternate, so an odd cycle would need the first vertex to have two different colours. Conversely, if there is no odd cycle, the BFS colouring below never meets a conflict.

### Checking by BFS

1. Give every vertex the colour "unknown".
2. For each unknown vertex (a graph may have several **components**), colour it `0` and start a BFS.
3. When you reach a new neighbour, give it the **opposite** colour of the current vertex.
4. If a neighbour already has the **same** colour as the current vertex, the graph is not bipartite.

Time `O(n + m)`. A DFS works as well, and so does union-find with a "parity" per vertex.

<Callout type="note" title="Layers of BFS">
BFS visits vertices in layers of equal distance from the start. Colouring by the parity of the layer is the same thing as the 2-colouring, which explains why an edge inside a layer (or between layers of equal parity) reveals an odd cycle.
</Callout>

```python
from collections import deque

def is_bipartite(n, adj):                # vertices 1..n
    color = [-1] * (n + 1)
    for s in range(1, n + 1):
        if color[s] != -1:
            continue
        color[s] = 0
        q = deque([s])
        while q:
            u = q.popleft()
            for v in adj[u]:
                if color[v] == -1:
                    color[v] = color[u] ^ 1
                    q.append(v)
                elif color[v] == color[u]:
                    return False, None
    return True, color
```

```cpp
    for (int s = 1; s <= n; s++) {
        if (color[s] != -1) continue;
```

## What bipartite graphs are good for

1. **Two-team and conflict problems** (this lesson's exercise, scheduling with exclusions).
2. **Matching:** in a bipartite graph the maximum matching can be found with augmenting paths (Kuhn's algorithm), and by König's theorem it equals the minimum vertex cover.
3. **Bounding structure:** grids and trees are bipartite (colour by the parity of `row + column`, or by depth), which is the idea behind chessboard-colouring arguments.
4. **Parity constraints** such as "these two must differ" or "these two must be equal" are solved with the same colouring, with union-find carrying a parity bit.

## Pitfalls

1. **Starting only from vertex 1.** A graph with several components needs a BFS from each uncoloured vertex.
2. **Treating a self-loop as fine.** An edge `a - a` joins a vertex to itself, so it is an odd cycle (length 1) and the answer is "not bipartite".
3. **Checking only tree edges.** The conflict appears on a non-tree edge, so examine every edge from the visited vertex.
4. **Directed graphs.** Bipartiteness ignores direction; build the adjacency both ways.
5. **Recursive DFS on a deep path** overflows in Python; use BFS or an explicit stack.
6. **Confusing bipartite with tree.** Every tree is bipartite, but a bipartite graph may have even cycles.
