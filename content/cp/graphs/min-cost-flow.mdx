## Intuition

[Maximum flow](/cp/graphs/maximum-flow/) answers "how much can I send?" but ignores a question that matters in practice: **what does it cost?** A shipping network may have cheap slow routes and expensive fast ones. Two plans can both carry 10 parcels per day, one for 40 coins and one for 400.

**Minimum-cost flow** asks for the cheapest way to send a given amount, or the cheapest way to send the *most* that is possible (min-cost max-flow). It also solves **assignment** problems: match workers to jobs when each pairing has a price, not merely "allowed or not".

The method is a small upgrade of what you already know. Keep the residual graph with twin edges, and instead of augmenting along *any* path, always augment along the **cheapest** one.

## Definitions

Each edge `u → v` has a capacity `c` and a cost `w` per unit of flow. The cost of a flow is the sum of `w × flow` over all edges. In the residual graph every edge has a twin that carries the flow backwards:

```text
edge e:     u -> v     capacity c      cost  +w
twin e^1:   v -> u     capacity 0      cost  -w         (undoing a unit refunds its cost)
```

Sending `d` units along `e` does `cap[e] -= d`, `cap[e ^ 1] += d`, exactly as in max flow, and the cost bookkeeping is automatic because the twin has cost `−w`.

## Successive shortest paths

```text
repeat:
    find the cheapest path from s to t in the residual graph (edges with cap > 0, weighted by cost)
    if there is none: stop
    push the bottleneck amount f along it
    flow += f;   total_cost += f * (cost of that path)
```

**Why it is correct.** If you always augment along a shortest path, the current flow is a minimum-cost flow *for its value* after every step. The reason is that a flow has minimum cost if and only if its residual graph has **no negative-cost cycle**. A shortest-path augmentation never creates one. So when the algorithm ends, the flow is maximum, and among all maximum flows it is the cheapest.

**Negative edges.** The residual graph contains twin edges of cost `−w`, so shortest paths must cope with negative weights. Two standard tools:

| tool | idea | time per search |
| --- | --- | --- |
| **SPFA** (Bellman-Ford with a queue) | relax edges, re-queue improved vertices | `O(V · E)` worst case, usually near `O(E)` |
| **Dijkstra with potentials** | keep a potential `h[v]` so reduced costs `w + h[u] − h[v]` stay non-negative | `O(E log V)` |

SPFA is short and reliable for contest sizes. Use potentials when the graph is big or when an adversary can build a bad SPFA case.

```python
from collections import deque

def min_cost_flow(n, edges, s, t):                 # edges: (u, v, capacity, cost); vertices 1..n
    to, cap, cost = [], [], []
    adj = [[] for _ in range(n + 1)]
    for u, v, c, w in edges:
        adj[u].append(len(to)); to.append(v); cap.append(c); cost.append(w)
        adj[v].append(len(to)); to.append(u); cap.append(0); cost.append(-w)
    INF = 10 ** 18
    flow = total = 0
    while True:
        dist = [INF] * (n + 1); dist[s] = 0
        inq = [False] * (n + 1); pe = [-1] * (n + 1)
        q = deque([s])
        while q:                                   # SPFA
            v = q.popleft(); inq[v] = False
            for e in adj[v]:
                if cap[e] > 0 and dist[v] + cost[e] < dist[to[e]]:
                    dist[to[e]] = dist[v] + cost[e]; pe[to[e]] = e
                    if not inq[to[e]]:
                        inq[to[e]] = True; q.append(to[e])
        if dist[t] == INF:
            return flow, total
        f = INF; v = t
        while v != s:
            e = pe[v]; f = min(f, cap[e]); v = to[e ^ 1]
        v = t
        while v != s:
            e = pe[v]; cap[e] -= f; cap[e ^ 1] += f; v = to[e ^ 1]
        flow += f
        total += f * dist[t]
```

```cpp
typedef long long ll;
struct MCMF {
    int n;
    vector<int> to;
    vector<ll> cap, cost;
    vector<vector<int>> adj;
    MCMF(int n) : n(n), adj(n + 1) {}
    void addEdge(int u, int v, ll c, ll w) {
        adj[u].push_back(to.size()); to.push_back(v); cap.push_back(c); cost.push_back(w);
        adj[v].push_back(to.size()); to.push_back(u); cap.push_back(0); cost.push_back(-w);
    }
    pair<ll, ll> run(int s, int t) {
        const ll INF = LLONG_MAX / 4;
        ll flow = 0, total = 0;
        while (true) {
            vector<ll> dist(n + 1, INF);
            vector<int> pe(n + 1, -1);
            vector<bool> inq(n + 1, false);
            queue<int> q;
            dist[s] = 0; q.push(s);
            while (!q.empty()) {
                int v = q.front(); q.pop(); inq[v] = false;
                for (int e : adj[v])
                    if (cap[e] > 0 && dist[v] + cost[e] < dist[to[e]]) {
                        dist[to[e]] = dist[v] + cost[e]; pe[to[e]] = e;
                        if (!inq[to[e]]) { inq[to[e]] = true; q.push(to[e]); }
                    }
            }
            if (dist[t] == INF) return {flow, total};
            ll f = INF;
            for (int v = t; v != s; v = to[pe[v] ^ 1]) f = min(f, cap[pe[v]]);
            for (int v = t; v != s; v = to[pe[v] ^ 1]) { cap[pe[v]] -= f; cap[pe[v] ^ 1] += f; }
            flow += f; total += f * dist[t];
        }
    }
};
```

## Min-cost flow for assignment

The classic application: `n` workers, `n` jobs, and a price `cost[i][j]` for worker `i` doing job `j`. Find the cheapest complete assignment.

```text
source -> worker i     capacity 1, cost 0
worker i -> job j      capacity 1, cost cost[i][j]
job j -> sink          capacity 1, cost 0
```

A max flow of value `n` is a perfect matching; the min-cost one is the cheapest. This is exactly [bipartite matching](/cp/graphs/bipartite-matching/) with prices. It is the weighted version, and the Hungarian algorithm solves it directly in `O(n³)`, but the flow model is far more flexible: add capacities greater than 1 (a worker can take 3 jobs), forbid pairs by omitting edges, or add intermediate nodes for rules.

## What min-cost flow can model

| problem | modelling |
| --- | --- |
| **assignment** with prices | the bipartite network above |
| **transportation**: factories with supplies, shops with demands, route prices | source → factories (supply), shops → sink (demand), routes with cost per unit |
| **k edge-disjoint cheapest paths** | capacity 1 on each edge, push exactly `k` units |
| cheapest way to send **exactly F** units | stop after `F` units (the last augmentation may be partial) |
| **k-th best** pairing structure, flows with lower bounds | extra nodes and edges (circulations with demands) |
| **maximum weight** instead of minimum | negate the costs (the graph has negative edges, so use SPFA or add a constant) |

## Pitfalls

1. **Forgetting the twin cost `−w`.** Without negative costs on twins, undoing a choice is treated as free or impossible and the cost is wrong.
2. **Dijkstra without potentials.** Plain Dijkstra fails on the negative residual edges. Use SPFA or Johnson-style potentials.
3. **Infinite loops from negative cycles.** If the input itself has a negative-cost cycle, successive shortest paths is not valid; remove it or use cycle-cancelling.
4. **Confusing max flow with min-cost max flow.** The algorithm stops when no augmenting path exists, giving the *maximum* flow; to send only `F` units, cap the total pushed.
5. **Overflow.** Costs multiply by flow: use 64-bit integers and a large `INF` such as `10^18`, never `INT_MAX`.
6. **Counting the cost of each augmentation wrongly.** Add `f × dist[t]`, where `dist[t]` is the *residual path* cost (it can be smaller than the sum of original edge costs when it cancels earlier flow).
7. **Worst-case SPFA.** Adversarial graphs can make SPFA slow; switch to potentials with a heap when `n` and `m` are large.
