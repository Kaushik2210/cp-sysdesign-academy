## Intuition

A company's servers are joined by cables. Some cables are a single point of failure: cut it and part of the network is stranded. Others have a backup route around them. A cable of the first kind is called a **bridge**.

Testing every cable by removing it and re-checking connectivity works, but costs `O(m (n + m))`. A single DFS can answer for all cables at once, using one question per vertex: *"how high up the DFS tree can this vertex's subtree reach by taking one shortcut?"* If the subtree can climb back above the edge that leads into it, that edge has a backup. If not, the edge is a bridge.

## Definition

In a connected undirected graph, an edge is a **bridge** if deleting it increases the number of connected components. (In a disconnected graph, apply this to the component the edge lives in.)

Run a DFS and record for every vertex:

- `tin[v]`: the time `v` was first reached (0, 1, 2, ...).
- `low[v]`: the smallest `tin` reachable from the **subtree** of `v` using tree edges downwards plus **at most one** non-tree (back) edge:

```text
low[v] = min( tin[v],
              tin[w]   for every back edge (v, w),
              low[c]   for every DFS child c of v )
```

**Bridge test.** A tree edge from `p` to its child `c` is a bridge exactly when

```text
low[c] > tin[p]
```

Nothing in the subtree of `c` can reach `p` or anything earlier than `p` except through this very edge, so cutting it strands the subtree. Non-tree edges close a cycle with the tree and are never bridges.

## Example, step by step

Graph with 6 vertices and 7 cables, numbered in input order:

```text
1: 1-2   2: 2-3   3: 3-1   4: 3-4   5: 4-5   6: 5-6   7: 6-4
```

It is two triangles, `{1,2,3}` and `{4,5,6}`, joined by cable 4. DFS from vertex 1, taking neighbours in input order:

| vertex | `tin` | `low` | why |
| --- | --- | --- | --- |
| 1 | 0 | 0 | root |
| 2 | 1 | 0 | child 3 has `low = 0` |
| 3 | 2 | 0 | back edge 3-1 reaches `tin = 0` |
| 4 | 3 | 3 | the triangle below only reaches back to 4 itself |
| 5 | 4 | 3 | back edge 6-4 gives `low[6] = 3` |
| 6 | 5 | 3 | back edge 6-4 reaches `tin = 3` |

Now test each tree edge `p -> c` with `low[c] > tin[p]`:

- `4 -> 5`: `low[5] = 3`, `tin[4] = 3`, not greater. Not a bridge.
- `5 -> 6`: `low[6] = 3 > tin[5] = 4`? No.
- `3 -> 4`: `low[4] = 3 > tin[3] = 2`. **Yes: cable 4 is the only bridge.**
- `2 -> 3`: `low[3] = 0 > tin[2] = 1`? No. `1 -> 2`: `low[2] = 0 > tin[1] = 0`? No.

## The detail that breaks most solutions

When scanning the neighbours of `v`, you must not treat the edge you **arrived by** as a back edge, or every vertex would see its parent and `low` would collapse. But skip it by **edge id**, not by "the neighbour is my parent":

```text
cables:  1-2 (id 0),  1-2 (id 1),  2-3 (id 2)
```

The two parallel cables between 1 and 2 are a backup for each other, so neither is a bridge. If you skipped *every* edge to the parent vertex, vertex 2 would never see the second cable and cable 1 would be reported wrongly. Skipping only the edge with `id == parent_edge` lets the other parallel cable count as a way back.

## Code

The recursive form is the shortest. It uses an adjacency list of `(neighbour, edge id)` pairs.

```python
import sys
sys.setrecursionlimit(10000)         # fine for a few thousand vertices; see the pitfalls for larger graphs

tin = [-1] * (n + 1)
low = [0] * (n + 1)
timer = 0
bridges = []

def dfs(v, parent_edge):
    global timer
    tin[v] = low[v] = timer
    timer += 1
    for to, e in adj[v]:
        if e == parent_edge:
            continue
        if tin[to] != -1:
            low[v] = min(low[v], tin[to])          # back edge
        else:
            dfs(to, e)
            low[v] = min(low[v], low[to])
            if low[to] > tin[v]:
                bridges.append(e)

for s in range(1, n + 1):
    if tin[s] == -1:
        dfs(s, -1)
```

def components(n, edges, skip):
    par = list(range(n + 1))
    def find(x):
        while par[x] != x:
            par[x] = par[par[x]]
            x = par[x]
        return x
    c = n
    for i, (u, v) in enumerate(edges):
        if i == skip:

        a, b = find(u), find(v)
        if a != b:

            c -= 1

## What bridges give you

- **2-edge-connected components.** Delete all bridges; the remaining components are the groups of vertices that survive any single cable failure. Contract each group to one vertex and the graph becomes a **tree** (the bridge tree), which turns many "robust network" questions into tree problems.
- **Articulation points** (cut vertices) use the same DFS with a slightly different test: a non-root vertex `p` is a cut vertex if some child `c` has `low[c] >= tin[p]` (with `>=`, because removing a vertex also removes the edge that would have been the backup). The root is a cut vertex only if it has two or more DFS children.
- **Directed graphs** are a different problem (strongly connected components); do not reuse this test there.

## Pitfalls

1. **Skipping the parent by vertex instead of by edge id.** It hides parallel cables and reports them as bridges. Always pass the edge id down.
2. **Not starting from every vertex.** A disconnected graph needs the outer loop `for s in 1..n`.
3. **Using `>=` for bridges.** Bridges use strict `low[c] > tin[p]`. The non-strict version is the articulation-point test and reports too many edges.
4. **Updating `low` from a child's `tin`.** A child contributes `low[c]`; a back edge contributes `tin[w]`. Mixing them makes `low` too small.
5. **Recursion depth.** A path of `2·10^5` vertices overflows the stack in Python, and in Java without a larger thread stack. Use an explicit stack with a per-vertex "next neighbour" pointer, as in the practice problem's reference solution.
6. **Reporting vertex pairs instead of edge ids.** With parallel cables the pair is ambiguous; keep edge ids if the output asks for cables.
