## Intuition

A set of Russian dolls: to count the dolls, open the biggest one, count itself as one, and ask "how many dolls are inside?". The inside is the same problem, only smaller. When you reach a doll that opens to nothing, you stop and start adding up on the way back.

Recursion is exactly that: **solve a problem by solving smaller copies of the same problem, plus a tiny amount of extra work.** Two things must be true for it to work:

1. There is a **base case** that is answered directly, with no further calls.
2. Every recursive call moves **strictly closer** to a base case.

If you trust that the recursive call returns the right answer for the smaller input (the "recursive leap of faith"), then you only have to check these two things and the combine step.

## Anatomy of a recursive function

```python
def solve(problem):
    if is_base(problem):          # 1. base case
        return direct_answer(problem)
    parts = shrink(problem)       # 2. reduce
    results = [solve(p) for p in parts]
    return combine(results)       # 3. combine
```

Concrete and tiny: `factorial(n) = n * factorial(n - 1)` with `factorial(0) = 1`. Correctness is a proof by induction on `n`: the base case is right, and if `factorial(n-1)` is right then so is `factorial(n)`.

## The call stack

Each call gets its own **frame** holding its parameters, local variables and the place to return to. Frames are stacked: the newest call is on top, and it must finish (pop) before the caller continues.

For `factorial(3)` the stack grows to depth 4 (`3, 2, 1, 0`), then the answers flow back: `1`, `1*1`, `2*1`, `3*2`.

Two consequences matter in contests:

- **Time** is the number of calls times the work done inside each call (excluding the sub-calls).
- **Memory** is the maximum **depth**, not the total number of calls. A recursion with `2^n` calls but depth `n` (like towers of Hanoi) uses only `O(n)` stack.

Typical recurrences you should recognise on sight:

- `T(n) = T(n-1) + O(1)` gives `O(n)` (a chain, e.g. factorial, sum of a list).
- `T(n) = T(n/2) + O(1)` gives `O(log n)` (binary search, fast power).
- `T(n) = 2T(n/2) + O(n)` gives `O(n log n)` (merge sort: `log n` levels, `n` work per level).
- `T(n) = 2T(n-1) + O(1)` gives `O(2^n)` (towers of Hanoi: exactly `2^n - 1` moves; subsets).
- `T(n) = T(n-1) + T(n-2) + O(1)` gives `O(phi^n)`, about `1.618^n` (naive Fibonacci).

Let the machine count the calls for you:

<CodeRunner language="python" code={`calls = 0

def fib(n):

    calls += 1
    if n < 2:

    return fib(n - 1) + fib(n - 2)

`fib(20)` makes 21,891 calls, in general `2*F(n+1) - 1`. The fix is to **remember answers** (memoization), which turns the tree into a DAG of only `n + 1` distinct states. This is the doorway to dynamic programming.

## Worked example: fast exponentiation

Computing `x^n` by `n` multiplications is `O(n)`. Halve the exponent instead: `x^n = (x^(n/2))^2`, and one extra factor of `x` if `n` is odd. The recurrence is `T(n) = T(n/2) + O(1)`, so `O(log n)` multiplications and recursion depth only about `log2 n`.

<CodeRunner snippets={{ python: `def power(x, n, mod):
    if n == 0:
        return 1 % mod          # base case
    half = power(x, n // 2, mod)
    result = half * half % mod
    if n % 2 == 1:
        result = result * x % mod
    return result

print(power(2, 10, 1000000007))
print(power(3, 10**18, 1000000007))
`, javascript: `function power(x, n, mod) {
  if (n === 0n) return 1n % mod;
  const half = power(x, n / 2n, mod);
  let result = half * half % mod;
  if (n % 2n === 1n) result = result * x % mod;
  return result;
}
console.log(power(2n, 10n, 1000000007n).toString());
console.log(power(3n, 10n ** 18n, 1000000007n).toString());
` }} />

Notice the call `power(x, n // 2, mod)` is made **once** and stored in `half`. Writing `power(...) * power(...)` would make two calls per level and quietly turn `O(log n)` back into `O(n)`.

## Depth limits: when recursion crashes

Every frame costs memory, and each language caps the depth:

- **Python** raises `RecursionError` at depth 1000 by default. `sys.setrecursionlimit(10**6)` raises the cap, but a deep recursion can still crash the interpreter by exhausting the real C stack. On contest judges, running the solve function in a `threading.Thread` with a larger `threading.stack_size` is the usual trick.
- **Java** defaults to a stack of roughly 512 KB to 1 MB per thread, which is often only 10,000 to 20,000 frames. The fix is to run the work in `new Thread(null, runnable, "", 1 << 28)`.
- **C++** has no fixed frame limit; the OS stack (commonly 8 MB on Linux, judge-dependent) is the limit, so depth around `10^5` is usually fine and `10^6` may not be.
- **JavaScript** engines allow roughly 10,000 frames by default.

<CodeRunner language="python" code={`import sys

def depth(n):
    return 0 if n == 0 else 1 + depth(n - 1)

print("limit", sys.getrecursionlimit())
try:
    print(depth(3000))
except RecursionError:
    print("RecursionError at depth 3000")

sys.setrecursionlimit(5000)
print(depth(3000))
`} />

When depth can reach `10^5` or more (a path-shaped tree, a long linked list), convert to an explicit stack or a loop. The rule of thumb: recursion depth should be about `log n` or at most a few thousand unless you control the stack size.

## Code: towers of Hanoi

To move `k` disks from `a` to `b` using `c` as spare: move `k-1` disks to `c`, move the big disk, move the `k-1` disks onto it. That is a recursion that is easy to write and hopeless to do in your head.

<Tabs>
<Tab label="Python">

```python
def hanoi(k, a, b, c, out):
    if k == 0:
        return
    hanoi(k - 1, a, c, b, out)
    out.append((a, b))
    hanoi(k - 1, c, b, a, out)
```

</Tab>
<Tab label="C++">

```cpp
void hanoi(int k, int a, int b, int c, vector<pair<int,int>>& out) {
    if (k == 0) return;
    hanoi(k - 1, a, c, b, out);
    out.push_back({a, b});
    hanoi(k - 1, c, b, a, out);
}
```

</Tab>
<Tab label="Java">

```java
static void hanoi(int k, int a, int b, int c, List<int[]> out) {
    if (k == 0) return;
    hanoi(k - 1, a, c, b, out);
    out.add(new int[]{a, b});
    hanoi(k - 1, c, b, a, out);
}
```

</Tab>
</Tabs>

## Pitfalls

<Callout type="pitfall" title="Classic recursion bugs">
1. **Missing or wrong base case** gives infinite recursion (and a crash at the depth limit). Test the smallest input first (`n = 0`, empty list).
2. **Not shrinking:** a call that sometimes passes the same arguments never terminates.
3. **Slicing in the recursion:** `solve(a[1:])` copies the list each call, turning `O(n)` into `O(n^2)`. Pass indices `lo, hi` instead.
4. **Shared mutable state** (a global counter, a list you forgot to restore) that makes different branches interfere. Prefer returning values, or undo changes after the call.
5. **Duplicate sub-calls:** if the same arguments recur, memoize.
6. **Python integers vs fixed width:** other languages overflow in intermediate values such as `half * half`.
</Callout>
