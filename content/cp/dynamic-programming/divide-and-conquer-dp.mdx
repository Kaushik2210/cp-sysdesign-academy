## Intuition

Many DPs have the shape

```text
dp[g][i] = min over j < i of  dp[g-1][j] + cost(j, i)
```

"Split the first `i` items into `g` groups; the last group is `j+1 .. i`." Filling the table costs `O(k · n²)`: for each of `k` layers, each of `n` positions tries up to `n` split points. Too slow when `n` is large.

But often there is a pattern in *where the best split point is*. If you cut a row of crates into batches, then as the right end `i` moves right, the best place to start the last batch also moves right (or stays), never left. The best split `opt(i)` is **monotone non-decreasing in `i`**.

Knowing that, you do not need to scan every `j` for every `i`. Compute `opt` for the *middle* `i` first. That tells you the left half of the positions only need splits `≤ opt(mid)`, and the right half only need splits `≥ opt(mid)`. Recurse, and the scans shrink dramatically.

## Definition

Let `opt(i)` be the (smallest) `j` achieving the minimum for position `i` in one layer. The technique requires

```text
opt(i) <= opt(i + 1)          (monotone optimum)
```

A sufficient condition is that the cost function satisfies the **quadrangle inequality**:

```text
for  a <= b <= c <= d :     cost(a, c) + cost(b, d)  <=  cost(a, d) + cost(b, c)
```

Intuition: nesting two ranges is never cheaper than overlapping them. Squared sums `(pre[i] − pre[j])²`, "sum of pairwise distances in a group", and "number of distinct values in a group" are standard examples.

## The algorithm

For one layer, define `compute(lo, hi, optLo, optHi)`: fill `dp[g][lo..hi]`, knowing every best split lies in `[optLo, optHi]`.

```text
compute(lo, hi, optLo, optHi):
    if lo > hi: return
    mid = (lo + hi) / 2
    best = infinity;  bestK = optLo
    for j in optLo .. min(mid - 1, optHi):
        value = dp[g-1][j] + cost(j, mid)
        if value < best: best = value; bestK = j
    dp[g][mid] = best
    compute(lo,      mid - 1, optLo, bestK)       # smaller positions: splits <= bestK
    compute(mid + 1, hi,      bestK, optHi)       # larger positions:  splits >= bestK
```

**Why it is fast.** At each depth of the recursion the split ranges `[optLo, optHi]` of the different calls overlap only at their endpoints, so all the scans at one depth add up to `O(n)`. There are `O(log n)` depths, so one layer costs `O(n log n)` and all `k` layers `O(k · n log n)`. Only the previous layer is needed, so memory is `O(n)`.

Call it with `compute(g, n, g − 1, n − 1)` for layer `g`: at least `g` items are needed for `g` groups, and the last group starts at `j ≥ g − 1`.

## Example

Crates `[1, 2, 3, 4, 5]` into `k = 2` consecutive batches, batch cost = (weight)². Try every cut:

```text
[1] [2 3 4 5]      1²  + 14² = 197
[1 2] [3 4 5]      3²  + 12² = 153
[1 2 3] [4 5]      6²  +  9² = 117
[1 2 3 4] [5]     10²  +  5² = 125
best = 117
```

Divide and conquer reaches the same answer while looking at far fewer cuts when `n` is large.

```python
def split_cost(a, k):
    n = len(a)
    pre = [0] * (n + 1)
    for i, x in enumerate(a): pre[i + 1] = pre[i] + x
    INF = 1 << 62
    prev = [INF] * (n + 1); prev[0] = 0          # prev[i]: i items in g - 1 groups
    for g in range(1, k + 1):
        cur = [INF] * (n + 1)
        def compute(lo, hi, olo, ohi):
            if lo > hi: return
            mid = (lo + hi) // 2
            best, bk = INF, olo
            for j in range(olo, min(mid - 1, ohi) + 1):
                v = prev[j] + (pre[mid] - pre[j]) ** 2
                if v < best: best, bk = v, j
            cur[mid] = best
            compute(lo, mid - 1, olo, bk)
            compute(mid + 1, hi, bk, ohi)
        compute(g, n, g - 1, n - 1)
        prev = cur
    return prev[n]
```

## When can you use it?

| check | meaning |
| --- | --- |
| the recurrence has the form `dp[g][i] = min_j dp[g-1][j] + cost(j, i)` | one layer depends only on the previous layer |
| `cost` satisfies the **quadrangle inequality** (or you can argue `opt` is monotone) | the optimum moves only one way |
| `cost(j, i)` is computable in `O(1)` after preprocessing | each candidate is cheap; otherwise maintain a sliding structure |

If `cost(j, i)` is expensive, see Codeforces 868F, where the cost is the number of distinct values in a range and a Mo-style pointer is maintained as `j` and `i` move; the divide and conquer order keeps the pointer movement `O(n log n)` per layer.

## Relatives of this technique

| technique | requirement | time per layer |
| --- | --- | --- |
| **divide and conquer** | monotone `opt` | `O(n log n)` |
| **Knuth's optimisation** (interval DP) | `opt(i, j-1) ≤ opt(i, j) ≤ opt(i+1, j)` | total `O(n²)` instead of `O(n³)` |
| **convex hull trick** | cost splits into a product of a function of `j` and a function of `i` (lines) | `O(n)` or `O(n log n)` |
| **Aliens trick** (lambda optimisation) | answer is convex in the number of groups `k` | binary search on a penalty, one `O(n)` or `O(n log n)` pass per step |
| plain DP | none | `O(n²)` |

Divide and conquer is the most forgiving: it asks for monotonicity only, and needs no special data structure.

## Pitfalls

1. **Applying it without monotonicity.** If `opt(i)` is not monotone, the pruned ranges can miss the true optimum and the answer is silently wrong. When in doubt, compare with the `O(k n²)` DP on random small inputs before trusting it.
2. **Wrong candidate range.** The split `j` must satisfy `g − 1 ≤ j ≤ mid − 1`. A range that allows `j = mid` makes an empty last group.
3. **Infinity arithmetic.** `prev[j]` may be infinite for unreachable states; add carefully, or restrict to reachable ranges so no `INF + cost` overflows.
4. **Ties.** Choosing the smallest or the largest optimal `j` consistently is fine, but mixing the two can break the monotone bound. Use strict `<` as above.
5. **Recursion depth.** The depth is `O(log n)`, so recursion is safe even for `n = 10^5`.
6. **Forgetting that layers are sequential.** Each layer needs the finished previous layer; do not reuse the array being written.
7. **Overflow.** Costs like squared sums can reach `(n · max a)²`; use 64-bit integers.
