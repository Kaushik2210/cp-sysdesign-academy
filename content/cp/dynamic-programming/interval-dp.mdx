## Intuition

Some problems ask you to combine **neighbouring** items again and again: merge adjacent piles, split a string into palindromes, parenthesise a product of matrices, play a game from both ends of a row. The cost of the whole depends on the **order** of the steps, and trying all orders is exponential.

The way out: look at the **last** step instead of the first. The last merge joins two blocks that were built independently, one from the left part of the interval and one from the right. So the answer for an interval is made from answers for two **shorter** intervals. That is a DP whose states are intervals.

## Definition

State: `dp[i][j]` = the best value for the items `i .. j`.

Transition: try every split point `k` between the two final blocks:

```text
dp[i][j] = min over k in [i, j-1] of ( dp[i][k] + dp[k+1][j] ) + cost(i, j)
dp[i][i] = 0
```

For **merging piles** `cost(i, j)` is the total weight `w[i] + ... + w[j]`, since the last merge pays for the whole interval. A prefix-sum array `pre` gives it in `O(1)`: `pre[j+1] - pre[i]`.

**Order of evaluation.** `dp[i][j]` needs shorter intervals, so loop over the **length** first (2, 3, ..., n), then over the start `i`:

```text
for length in 2..n:
    for i in 0..n-length:
        j = i + length - 1
        ...
```

There are `O(n^2)` states and `O(n)` transitions each: `O(n^3)` time, `O(n^2)` memory. That is comfortable for `n` up to about 400.

## Example

Piles `[2, 2, 1, 2]`. The tempting rule "always merge the lightest neighbouring pair" merges `(2,1)` first (3), giving `[2, 3, 2]`, then `(2,3)` (5), then `(5,2)` (7): total 15. The DP finds 14: merge `(1,2)` (3) to get `[2, 2, 3]`, then `(2,2)` (4), then `(4,3)` (7).

## Other interval DPs, same skeleton

| problem | `dp[i][j]` means | transition |
| --- | --- | --- |
| merge piles | cheapest way to merge `i..j` | split at `k`, add `sum(i..j)` |
| matrix-chain product | fewest multiplications for `A_i ... A_j` | split at `k`, add `p[i] * p[k+1] * p[j+1]` |
| optimal game from both ends (CSES *Removal Game*) | best score difference for the current player on `i..j` | take `a[i]` or `a[j]`, then the opponent plays `dp[i+1][j]` or `dp[i][j-1]` |
| palindrome partitioning | is `s[i..j]` a palindrome | `s[i] == s[j]` and `dp[i+1][j-1]` |
| burst balloons | max coins for `i..j` where `k` is the **last** one burst | `a[i-1]*a[k]*a[j+1] + dp[i][k-1] + dp[k+1][j]` |

When the natural split is the first or last item (the game), the transition has only two options and the whole DP is `O(n^2)`.

## Speeding it up

If the best split point is monotone (`opt[i][j-1] <= opt[i][j] <= opt[i+1][j]`), **Knuth's optimisation** restricts the loop over `k` and brings the total to `O(n^2)`. It holds for merging piles and optimal binary search trees; verify the condition before using it.

## Pitfalls

1. **Wrong loop order.** Looping `i` then `j` reads intervals you have not computed yet; iterate by **length**.
2. **Off-by-one in the split.** `k` ranges over `i .. j-1`, and the two parts are `[i, k]` and `[k+1, j]`.
3. **Forgetting the merge cost.** Without `+ sum(i..j)` the DP returns 0.
4. **Overflow.** Costs add up to about `n` times the total weight; use 64-bit integers.
5. **Trusting a greedy.** Local choices (lightest pair first) fail; if you cannot prove it with an exchange argument, use the DP.
6. **Memory at large `n`.** The table is `n^2` entries; for `n = 5000` that is 25 million, so keep the array flat and use 32-bit values when possible.
