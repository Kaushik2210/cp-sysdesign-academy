## Intuition

Some problems let you shrink a row by repeatedly acting on **neighbours**: merge two adjacent piles, burst a balloon, parenthesise a product. The order matters a great deal, and there are exponentially many orders. But look at the **last** action. Whatever you did before, that final action splits the row into a left part and a right part which were handled **independently**, each as a smaller copy of the same problem.

So the natural sub-problem is not a prefix (as in knapsack or LIS) but a **contiguous segment** `[i, j]`. The answer for a long segment is assembled from answers for shorter segments inside it. That is interval DP.

## Definition

State: `dp[i][j]` is the best value for the segment `i..j` considered on its own.

Transition: try every **split point** `k` (or every choice of "which element is handled last") and combine the two halves:

```text
dp[i][j] = best over k in [i, j-1] of  combine( dp[i][k], dp[k+1][j] )  + cost(i, j)
dp[i][i] = base case (often 0)
```

**Order of evaluation.** `dp[i][j]` needs strictly shorter segments, so iterate by increasing **length**:

```text
for length in 2..n:
    for i in 0..n-length:
        j = i + length - 1
        compute dp[i][j]
```

Cost: `O(n^2)` states and `O(n)` transitions each, so `O(n^3)` time and `O(n^2)` memory, fine for `n` up to a few hundred.

## Example, step by step

**Merging crates.** Crates weigh `4 1 1 4`. Merging two neighbouring piles costs their combined weight. Find the cheapest way to end with one pile.

Let `W(i, j)` be the total weight of segment `i..j`. The last merge of any segment joins a left and a right pile and costs `W(i, j)`, so

```text
dp[i][j] = min over k of ( dp[i][k] + dp[k+1][j] ) + W(i, j)
```

| segment | splits tried | result |
| --- | --- | --- |
| `[4,1]` | single split | `0 + 0 + 5 = 5` |
| `[1,1]` | single split | `0 + 0 + 2 = 2` |
| `[1,4]` | single split | `0 + 0 + 5 = 5` |
| `[4,1,1]` | `0 + dp[1,1]=2`, `5 + 0` | `min(2, 5) + 6 = 8` |
| `[1,1,4]` | `0 + 5`, `2 + 0` | `min(5, 2) + 6 = 8` |
| `[4,1,1,4]` | `0 + 8`, `5 + 5`, `8 + 0` | `min(8, 10, 8) + 10 = 18` |

The answer is `18`: merge the two 1s (cost 2), then the 4 with that pile (cost 6), then the last 4 (cost 10). The weights are easy to get wrong by hand, which is why `W` comes from [prefix sums](/cp/arrays-and-windows/prefix-sums/) in `O(1)`.

A second shape of interval DP peels from **both ends** instead of splitting: the **longest palindromic subsequence** of a string.

```text
dp[i][j] = dp[i+1][j-1] + 2          if s[i] == s[j]      (both ends match; if i+1 > j-1 the middle is empty, so just 2)
         = max(dp[i+1][j], dp[i][j-1])   otherwise        (drop one end)
```

Here there is no loop over `k`: each state has `O(1)` transitions, so the whole table is `O(n^2)`.

## Recognising interval DP

| signal in the statement | typical state and transition |
| --- | --- |
| merge or combine **adjacent** items, cost depends on the group | `dp[i][j]`, split at `k` (this lesson) |
| parenthesise an expression, matrix-chain multiplication | `dp[i][j]`, split at the top-level operator `k` |
| remove or burst items, reward depends on current neighbours | `dp[i][j]`, `k` is the item removed **last** |
| string reducible from both ends (palindromes) | `dp[i][j]`, compare `s[i]` and `s[j]` |
| two players alternately take from either end | `dp[i][j]` = best score difference for the player to move |

For merge-type problems whose cost satisfies the **quadrangle inequality**, the best split `opt[i][j]` is monotone: `opt[i][j-1] <= opt[i][j] <= opt[i+1][j]`. Searching only that window brings the total to `O(n^2)` (Knuth's optimisation). You rarely need it at `n <= 500`; it matters at `n = 5000`.

## Pitfalls

1. **Wrong evaluation order.** Filling `i` then `j` in plain nested loops reads cells that are not computed yet. Go by increasing length, or by `i` descending and `j` ascending.
2. **Off-by-one in the split.** With `dp[i][k] + dp[k+1][j]`, `k` runs from `i` to `j - 1`. Using `j` reads `dp[j+1][j]`, an empty segment.
3. **Forgetting the merge cost.** `cost(i, j)` depends on the *whole* segment, not on how the halves were built; compute it from prefix sums.
4. **Infinity arithmetic.** Initialising unused cells with `INF` and adding two of them overflows in C++ and Java; use a large-but-safe constant (`10^18` for `long long`) and only combine valid states.
5. **Overflow of the answer.** Costs add up per merge level, so 200 crates of weight `10^6` exceed 32 bits. Use 64-bit integers.
6. **Treating a segment as a prefix.** The sub-problem must be closed: the answer for `[i, j]` may not depend on what lies outside it. If it does, the state needs another dimension.

## Problem ladder

- [Removal Game](https://cses.fi/problemset/task/1097) (CSES): two players take from the ends, `dp[i][j]` is the best score difference.
- [Minimum Cost to Merge Stones](https://leetcode.com/problems/minimum-cost-to-merge-stones/) (LeetCode 1000, hard): this lesson with `k` piles per merge.
- [Burst Balloons](https://leetcode.com/problems/burst-balloons/) (LeetCode 312, hard): `k` is the balloon popped **last**.

- [Zuma](https://codeforces.com/problemset/problem/607/B) (Codeforces 607B, rating about 1900): minimum seconds to delete a palindromic row, a classic interval DP.
