## Intuition

Some DP transitions look like

```text
dp[i] = min over j < i of  ( dp[j] + b[j] * a[i] )
```

Notice that for a fixed `j`, the term `b[j] * a[i] + dp[j]` is a **straight line** in the variable `a[i]`: slope `b[j]`, intercept `dp[j]`. Each earlier index `j` contributes one line, and `dp[i]` is the **lowest of all those lines at the point `x = a[i]`**.

So the DP turns into a geometry question: maintain a set of lines, support "add a line" and "what is the minimum value at `x`?". Trying every line costs `O(n)` per query, `O(n²)` overall. But most lines are never the lowest anywhere. Only the **lower envelope** matters, and a few clever structures keep just that.

## Lines and the lower envelope

Plot all lines `y = m·x + c`. The pointwise **minimum** of all of them is a piecewise-linear *concave* curve: the lower envelope. Each line that appears on it is minimal on one contiguous interval of `x`, and as `x` moves right, the minimal line has smaller and smaller slopes.

```text
y
|         ________          the lower envelope: an arch, steep lines on the left,
|       /          \         flatter ones in the middle, falling lines on the right
|     /              \
|   /                  \
+------------------------- x
```

If you keep only the lines on the envelope in order of slope, then:

- a **query** at `x` is the line that is minimal at `x`: found by binary search over the envelope, or by a moving pointer when queries come in sorted order;
- an **insertion** of a new line may make some envelope lines useless and removes them.

## Monotone version: a deque in O(n)

When **slopes arrive sorted** (say strictly decreasing, for a minimum) **and queries are sorted** (increasing `x`), you need no search at all:

```text
add(line l3):
    while the deque has two lines l1, l2 at its back and l2 is useless given l3:   pop l2
    push l3 to the back

query(x):
    while the front line is not better than the next one at x:   advance the front
    return value of the front line at x
```

A line `l2` between `l1` and `l3` (slopes `m1 > m2 > m3`) is **useless** when the intersection of `l1` and `l3` is to the left of the intersection of `l1` and `l2`:

```text
(c3 - c1) * (m1 - m2)  <=  (c2 - c1) * (m1 - m3)
```

Each line is pushed once and popped once, so the total is amortised `O(n)`. **Caution: overflow.** That cross-multiplication can be about `(value) × (value)`; with `10^5`-sized slopes and `10^13`-sized intercepts it exceeds 64 bits. Use 128-bit integers (`__int128` in C++), Python's big integers, or avoid the comparison altogether with a Li Chao tree.

## Li Chao tree: any order, O(log n)

A **Li Chao tree** stores one line per node over a range of `x` values and needs no monotonicity at all.

- **Insert** a line `L` at a node covering `[lo, hi]`: compare `L` with the node's line at the midpoint; keep the better one in the node. The *loser* can only be better on one side (two lines cross at most once), so push it down to **that one** child, or drop it if it wins nowhere.
- **Query** at `x`: walk from the root to the leaf for `x`, evaluating the line at each node, and take the minimum.

Both walk one root-to-leaf path: `O(log n)`. Build the tree over the **sorted distinct query points** (coordinate compression) so the range is small; if queries are online with huge `x`, use a dynamic tree over the full range. Only line *evaluations* are needed, so there is no cross-multiplication and values stay within `k·x + c`.

```text
insert(line):
    at the node for [lo, hi]: keep whichever line is lower at mid
    the other line is lower, if anywhere, only left of mid or only right of mid
    go to that child and continue
```

```python
import bisect

class LiChao:                                  # minimum of lines at the points xs (sorted, distinct)
    def __init__(self, xs):
        self.xs = xs
        self.m = len(xs)
        self.K = [0] * (4 * self.m)
        self.C = [None] * (4 * self.m)

    def add(self, k, c):
        xs, K, C = self.xs, self.K, self.C
        node, lo, hi = 1, 0, self.m - 1
        while True:
            if C[node] is None:
                K[node], C[node] = k, c
                return
            mid = (lo + hi) // 2
            if k * xs[mid] + c < K[node] * xs[mid] + C[node]:     # keep the better line at mid
                K[node], k = k, K[node]
                C[node], c = c, C[node]
            if lo == hi:
                return
            if k * xs[lo] + c < K[node] * xs[lo] + C[node]:        # the loser may win on the left only...
                node, hi = 2 * node, mid
            elif k * xs[hi] + c < K[node] * xs[hi] + C[node]:      # ...or on the right only
                node, lo = 2 * node + 1, mid + 1
            else:
                return

    def query(self, x):
        i = bisect.bisect_left(self.xs, x)
        node, lo, hi = 1, 0, self.m - 1
        best = None
        while True:
            if self.C[node] is not None:
                v = self.K[node] * x + self.C[node]
                if best is None or v < best:
                    best = v
            if lo == hi:
                return best
            mid = (lo + hi) // 2
            if i <= mid:
                node, hi = 2 * node, mid
            else:
                node, lo = 2 * node + 1, mid + 1
```

```cpp
typedef long long ll;
struct LiChao {                                // minimum of lines at the points xs (sorted, distinct)
    vector<ll> xs, K, C;
    vector<bool> has;
    int m;
    LiChao(vector<ll> pts) : xs(move(pts)), m(xs.size()), K(4 * xs.size(), 0), C(4 * xs.size(), 0), has(4 * xs.size(), false) {}
    void add(ll k, ll c) {
        int node = 1, lo = 0, hi = m - 1;
        while (true) {
            if (!has[node]) { has[node] = true; K[node] = k; C[node] = c; return; }
            int mid = (lo + hi) / 2;
            if (k * xs[mid] + c < K[node] * xs[mid] + C[node]) { swap(K[node], k); swap(C[node], c); }
            if (lo == hi) return;
            if (k * xs[lo] + c < K[node] * xs[lo] + C[node]) { node = 2 * node; hi = mid; }
            else if (k * xs[hi] + c < K[node] * xs[hi] + C[node]) { node = 2 * node + 1; lo = mid + 1; }
            else return;
        }
    }
    ll query(ll x) {
        int i = lower_bound(xs.begin(), xs.end(), x) - xs.begin();
        ll best = LLONG_MAX;
        int node = 1, lo = 0, hi = m - 1;
        while (true) {
            if (has[node]) best = min(best, K[node] * x + C[node]);
            if (lo == hi) return best;
            int mid = (lo + hi) / 2;
            if (i <= mid) { node = 2 * node; hi = mid; } else { node = 2 * node + 1; lo = mid + 1; }
        }
    }
};
```

    def __init__(self):

        L = self.lines
        while len(L) >= 2:

## Turning a recurrence into lines

The art is rewriting `dp[i] = min_j ( ... )` so that the part depending on `j` and the part depending on `i` multiply:

| recurrence | rewrite | lines |
| --- | --- | --- |
| `dp[j] + b[j] · a[i]` | already a line | slope `b[j]`, intercept `dp[j]`, query `x = a[i]` |
| `dp[j] + (S[i] − S[j])² + C` | expand: `S[i]² − 2 S[i] S[j] + S[j]² + dp[j] + C` | slope `−2 S[j]`, intercept `dp[j] + S[j]²`; add `S[i]² + C` after the query |
| `dp[j] + (i − j) · h[j]` | `i · h[j] + (dp[j] − j · h[j])` | slope `h[j]`, intercept `dp[j] − j h[j]` |
| maximisation | negate everything, or flip the comparisons | upper envelope |

The second row is the same "split into batches" cost as the [divide and conquer DP](/cp/dynamic-programming/divide-and-conquer-dp/) lesson, now with an extra fixed fee per batch. When both techniques apply, the hull is `O(n)`, divide and conquer is `O(n log n)` but simpler to code.

## Choosing a structure

| situation | use |
| --- | --- |
| slopes sorted **and** queries sorted | deque with a pointer, `O(n)` |
| slopes sorted, queries arbitrary | deque with **binary search** on the hull, `O(log n)` per query |
| anything else, or you fear overflow | **Li Chao tree**, `O(log n)` |
| cost is not a product of an `i` part and a `j` part | divide and conquer DP or Knuth, if monotone |
| the answer is convex in the number of groups | the "Aliens trick" (a binary search on a penalty) |

## Pitfalls

1. **Overflow in the intersection test.** The cross-multiplication can exceed 64 bits. Use `__int128`, big integers, or a Li Chao tree that only evaluates lines.
2. **Wrong direction for maximum.** For a maximum the upper envelope has *increasing* slopes as `x` grows; the useless-line test flips its inequality.
3. **Equal slopes.** Two lines with the same slope: keep only the one with the better intercept, or the division-free test can misbehave.
4. **Pointer past the end.** After popping lines from the back, make sure the query pointer is not beyond the last line.
5. **Querying outside the compressed points.** A Li Chao tree built on a point set can only answer at those points; compress *all* query coordinates first.
6. **Adding a line before its `dp` is known.** Compute `dp[i]` with a query first, then insert the line for `i`.
7. **Assuming monotonicity that is not there.** If slopes or queries are not sorted, the simple deque gives wrong answers silently; check, or use the Li Chao tree.
