## Intuition

A vending machine has coin kinds of various values and an endless supply of each. How few coins make exactly `T`?

Greedy ("always take the largest coin that fits") feels natural and is correct for real currencies, but not for every coin system. With coins `1, 3, 4` and `T = 6` greedy gives `4 + 1 + 1` (three coins), while `3 + 3` uses two.

The dynamic programming view: whatever the best payment of `c` is, **its last coin** is one of the kinds `k`, and what remains is a best payment of `c - k`. So the answers for smaller amounts are all you need.

## Definition

Let `dp[c]` be the fewest coins summing to exactly `c`.

```text
dp[0] = 0
dp[c] = 1 + min( dp[c - k] )   over coin values k <= c with dp[c - k] reachable
```

Unreachable amounts hold infinity. The answer is `dp[T]` (or `-1` if infinity). With `n` kinds and amount `T` the time is `O(nT)` and memory `O(T)`.

This is the **unbounded knapsack**: unlike the [0/1 version](/cp/dynamic-programming/knapsack/), an item can be reused. In the one-array formulation the capacity loop therefore goes **upwards**, so `dp[c - k]` may already include the same coin. (In the 0/1 case going upwards was the bug; here it is the feature.)

The `1, 3, 4` row shows the gap (dp 2, greedy 3). The `[5, 7]` row shows that greedy may even claim impossibility for an amount that is payable (`24 = 5 + 5 + 7 + 7`).

## Counting instead of minimising

A close cousin asks **how many ways** to pay `T`. The order of the two loops decides what you count.

| goal | loops | counts |
| --- | --- | --- |
| combinations (order of coins ignored) | outer: coins, inner: amounts upwards | `1+2` and `2+1` count once |
| sequences (order matters) | outer: amounts, inner: coins | `1+2` and `2+1` count twice |

<CodeRunner language="python" code={`def combinations(coins, T):
    ways = [1] + [0] * T
    for k in coins:                  # coins outermost: each multiset counted once
        for c in range(k, T + 1):
            ways[c] += ways[c - k]
    return ways[T]

def sequences(coins, T):
    ways = [1] + [0] * T
    for c in range(1, T + 1):        # amounts outermost: order matters
        for k in coins:
            if k <= c:
                ways[c] += ways[c - k]
    return ways[T]

print("combinations of 4 from {1,2,3}:", combinations([1, 2, 3], 4))
print("sequences of 4 from {1,2,3}:   ", sequences([1, 2, 3], 4))
`} />

For `T = 4` there are 4 combinations (`1111`, `112`, `22`, `13`) and 7 sequences (the 4 combinations arranged in every distinct order: 1 + 3 + 1 + 2).

<Callout type="pitfall" title="Swapping the loops changes the problem">
If the question says "different orders count as different ways", the amount loop goes outside. If it says "multisets" or "combinations", the coin loop goes outside. Reading the statement carefully here is worth more than any optimisation.
</Callout>

## Related problems

| twist | change |
| --- | --- |
| print the coins used | store `choice[c] = k` and walk back from `T` |
| minimum cost with a cost per coin | `dp[c] = min(dp[c - k] + cost[k])` |
| ways modulo `10^9 + 7` | reduce after each addition |
| huge `T`, tiny coins | matrix exponentiation or the Frobenius structure (a later topic) |
| each coin at most once | the 0/1 knapsack (loop downwards) |

## Pitfalls

1. **Greedy by largest coin** without proof. Check the coin system or use the DP.
2. **`dp[c - k]` unreachable but used.** Skip infinite states; otherwise `INF + 1` can overflow or be mistaken for an answer.
3. **Initialising `dp[0]` wrongly.** `dp[0] = 0` coins for the minimum, `1` way for counting.
4. **Mixing up the loop order** when counting combinations versus sequences.
5. **Forgetting the unreachable case.** Print `-1` (or whatever the statement says) when `dp[T]` is still infinite.
6. **Time limit with `T` up to `10^9`.** The table must fit in memory; with huge `T` this approach does not apply.
