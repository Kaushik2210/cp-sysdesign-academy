## Intuition

Comparing two strings of length `L` takes `O(L)`. Suppose you must answer `10^5` queries of the form "are `s[l1..r1]` and `s[l2..r2]` equal?" on a string of length `10^5`. Naively that is `10^10` character comparisons.

A **fingerprint** fixes this. Give every string a small number, its *hash*, such that:

1. equal strings always get equal hashes;
2. different strings *almost always* get different hashes;
3. the hash of **any substring** can be computed in `O(1)` after `O(n)` preprocessing.

Then comparing strings means comparing two integers. The price: the answer is only *probably* right, and we must quantify "probably".

## Definition: polynomial hash

Pick a modulus `M` (a prime) and a base `B` with `1 < B < M`. Map characters to numbers `c(x)` in `1..` (use `x - 'a' + 1`; never `0`). For `s = s_0 s_1 ... s_{n-1}`:

`H(s) = c(s_0) * B^(n-1) + c(s_1) * B^(n-2) + ... + c(s_{n-1}) * B^0   (mod M)`

Read it as `s` interpreted as a number written in base `B`.

### Prefix hashes and the substring formula

Define `P[0] = 0` and `P[i+1] = P[i] * B + c(s_i)  (mod M)`. So `P[i]` is the hash of the first `i` characters. For the half-open range `[l, r)`:

`H(s[l..r)) = P[r] - P[l] * B^(r-l)   (mod M)`

*Why:* `P[r]` is `P[l]` shifted left by `r - l` places plus the substring's digits. Subtracting the shifted prefix leaves exactly the substring's number.

## How reliable is it?

### One comparison

Fix two different strings `x != y` of the **same length** `n`. Their hash difference `H(x) - H(y)` is a polynomial in `B` of degree at most `n - 1`, and it is not the zero polynomial (the strings differ somewhere). Over the field `Z_M` (`M` prime) a nonzero polynomial of degree `d` has at most `d` roots. If `B` is chosen **uniformly at random**, then

`Pr[H(x) = H(y)] <= (n - 1) / M`.

This is a *guarantee* for any fixed pair of strings, as long as the base is random and unknown to whoever produced the strings.

### Many comparisons: the union bound and the birthday paradox

- **Union bound.** With `q` comparisons of strings of length up to `n`, the chance that *any* comparison is wrong is at most `q * (n - 1) / M`. With `M = 10^9 + 7`, `q = n = 10^5`, that is `10`, which is a vacuous bound (the typical collision probability is nearer `1 / M`, but you can no longer *prove* safety).
- **Birthday paradox.** If you put `k` different strings into a hash set, any *pair* may collide. Expected number of colliding pairs is about `k(k - 1) / (2M)`. One collision is likely once `k` is about `sqrt(M)`: for `M ~ 10^9`, around `3.2 * 10^4` strings give a `1 - e^(-1/2)`, about `39%`, chance of a collision.

| modulus size | strings `k` | expected colliding pairs `k^2 / 2M` |
| --- | --- | --- |
| `~10^9` | `10^5` | `~5` |
| `~10^9` | `10^6` | `~500` |
| `~10^18` (two mods or `2^61 - 1`) | `10^6` | `~5 * 10^-7` |
| `~10^18` | `10^7` | `~5 * 10^-5` |

So **a single `10^9` modulus is not enough** whenever you store many hashes, but a `~10^18` combined space is.

## Choosing the modulus and base

| choice | verdict |
| --- | --- |
| prime near `10^9` (`10^9 + 7`, `998244353`) | products fit in signed 64-bit; **combine two** such moduli for safety |
| prime `2^61 - 1` | about `2.3 * 10^18` space with one hash; needs 128-bit multiplication (`__int128`) or a split multiply |
| `2^64` via unsigned overflow | fast, but **breakable** by Thue-Morse strings for every odd base; never use it where adversarial tests exist |
| non-prime modulus | the polynomial can have more roots; avoid |
| base `B` | random in `[256, M - 1]` chosen at run time; avoid tiny bases (`B = 2`), and avoid `B = 0, 1` |
| character map | `c(x) >= 1`, otherwise `"a"` and `"aa"` can hash equal when `c(a) = 0` |

<Callout type="warning" title="Randomise the base">
A fixed `(B, M)` in your source can be attacked by anyone who reads it (on Codeforces, other participants during the hacking phase). Derive `B` from a clock, `random_device` or a per-run RNG so no fixed input is bad for you.
</Callout>

## Worked example: palindromic substring queries

A substring `s[l..r)` is a palindrome iff it equals its reverse. Build prefix hashes for `s` and for `rev(s)`. The reverse of `s[l..r)` is `rev(s)[n-r .. n-l)`, so the check is two `O(1)` hash comparisons after `O(n)` preprocessing. (Manacher's algorithm answers every centre in `O(n)` deterministically; the hash version generalises to "almost palindromes" and to queries on updated strings.)

## Pitfalls

1. **Negative remainder.** In C++/Java `(a - b) % M` may be negative; add `M` and take `% M` again.
2. **Overflow.** `P[l] * pw[k]` is a product of two residues below `M`: it needs `M < 3 * 10^9` for signed 64-bit. With `M ~ 10^18` use `__int128` or `unsigned __int128`.
3. **Comparing different lengths** without including the length: always compare hashes of equal-length ranges (or store `(hash, length)`).
4. **Zero character value** makes strings of different lengths indistinguishable.
5. **Off-by-one in half-open vs inclusive ranges.** Pick `[l, r)` internally and convert once at the input boundary.
6. **Trusting a hash match as proof.** Hash equality means "equal with high probability"; when exactness is cheap (a single verified comparison), verify.
7. **Fixed base in public code.** See above; randomise.
