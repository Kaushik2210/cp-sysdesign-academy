## Intuition

A phone book sorted by name lets you binary-search in `O(log n)`. A **hash table** goes further: it computes, from the key alone, the *address* where the entry must be stored, so the lookup is a single jump. No comparisons, no ordering, just "where would this key live?".

In contests this turns "have I seen this value before?", "how many times did it occur?" and "what is stored for this key?" into `O(1)` operations (expected), and with them whole `O(n^2)` solutions into `O(n)`.

## Definition

A **hash map** (dictionary) stores key-value pairs; a **hash set** stores keys only. Both support, in *expected* `O(1)` time:

- insert / update
- membership test / lookup
- erase

They do **not** keep elements ordered and cannot answer "next larger key" (use a balanced tree, `std::map`/`TreeMap`, or sorting for that).

### How it works

1. A **hash function** `h(key)` maps the key to an integer; the table index is `h(key) mod m`.
2. Two keys can land in the same slot: a **collision**. Chaining (a small list per slot) or open addressing (probe to the next free slot) resolves it.
3. With a good hash and a table that grows when the **load factor** (entries / slots) passes a threshold, chains stay short, so the expected cost per operation is `O(1)`. A single operation costs `O(n)` in the worst case if every key lands in one slot.

## Pattern 2: two-sum and "have I seen the complement?"

**Task:** count pairs `i < j` with `a[i] + a[j] = k`. For a fixed `j`, the earlier partner must have value `k - a[j]`. Keep a map of how many times each value occurred so far, and **look up before inserting**:

<CodeRunner language="python" code={`def count_pairs(a, k):
    cnt = {}
    ans = 0
    for x in a:
        ans += cnt.get(k - x, 0)     # earlier partners
        cnt[x] = cnt.get(x, 0) + 1   # then insert x
    return ans

def brute(a, k):
    return sum(1 for i in range(len(a)) for j in range(i + 1, len(a)) if a[i] + a[j] == k)

import random
random.seed(1)
for _ in range(300):
    a = [random.randint(-4, 4) for _ in range(random.randint(1, 12))]
    k = random.randint(-6, 6)
    assert count_pairs(a, k) == brute(a, k), (a, k)
print(count_pairs([1, 5, 3, 3, 2], 6))   # 2
print("random tests agree")
`} />

For `[1, 5, 3, 3, 2]` and `k = 6` the pairs are `(1, 5)`, and the two `3`s are *one* pair `(3, 3)`: the answer is `2`. Looking up **before** inserting is what prevents pairing an element with itself and what counts `(3, 3)` exactly once.

## Pattern 3: prefix sums + map (subarray sums)

A subarray sum is a difference of two prefix sums, so "count subarrays with sum `k`" becomes a two-sum on prefix sums: for each prefix `P[j]`, count earlier prefixes equal to `P[j] - k`. Start the map with the empty prefix `{0: 1}`.

<CodeRunner language="python" code={`def count_subarrays(a, k):
    cnt = {0: 1}          # empty prefix
    s = ans = 0
    for x in a:
        s += x
        ans += cnt.get(s - k, 0)
        cnt[s] = cnt.get(s, 0) + 1
    return ans

print(count_subarrays([1, 2, 3, -3, 3], 3))   # [1,2], [3], [1,2,3,-3], [3,-3,3], [3] -> 5
print(count_subarrays([0, 0, 0], 0))          # 6 = 3*4/2
print(count_subarrays([1, -1, 1, -1], 0))     # 4
`} />

This works with **negative numbers and zeros**, where a two-pointer window fails. Variants: subarrays whose sum is divisible by `m` (key = prefix `mod m`), equal number of `0`s and `1`s (map `0 -> -1`, key = prefix), longest subarray with sum `k` (store the *first* index of each prefix instead of a count).

## The C++ trap: `unordered_map` can be made quadratic

Hash tables give `O(1)` *expected* time only if keys spread out. `std::unordered_map<int, ...>` uses a fixed, public hash (identity for integers) and a known set of bucket counts (prime sizes). On sites with open hacking (Codeforces), an adversary can submit inputs whose keys are all multiples of a bucket count, forcing every key into one bucket: `n` insertions cost `O(n^2)` and your solution times out.

Safe options, in order of preference:

1. **Avoid hashing:** sort + compress, or use `std::map` (`O(log n)`, no attack possible).
2. **Randomised hash:** supply your own hash functor with a random per-run offset.

```cpp
struct SafeHash {
    static uint64_t mix(uint64_t x) {            // splitmix64
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t R =
            chrono::steady_clock::now().time_since_epoch().count();
        return mix(x + R);
    }
};
unordered_map<long long, int, SafeHash> cnt;
// cnt.reserve(1 << 20); cnt.max_load_factor(0.25); also help constants
```

Other languages: Java's `HashMap` converts long chains to balanced trees (since Java 8) so adversarial collisions cost `O(log n)` per operation for comparable keys, but boxing makes it heavy. Python's `dict` uses open addressing with `hash(int) = int` for small ints; targeted attacks exist in principle, and the common defence is the same: avoid predictable keys (XOR keys with a random value) when hacks are a risk.

<Callout type="warning" title="Hash tables return nothing in order">
Iterating an `unordered_map` or a Python `set` gives an arbitrary order. If the output must be sorted, sort the keys first. Relying on iteration order is a classic reason for solutions that pass locally and fail on the judge.
</Callout>

## Choosing the structure

<TradeOffs caption="Pick by the queries you need, not by habit" rows={[
  { option: "Hash map / set", pros: "Expected O(1) insert, lookup, erase", cons: "No order, worst case O(n), attackable in C++", chooseWhen: "Counting, membership, seen-before, two-sum style matching" },
  { option: "Ordered map / set (tree)", pros: "O(log n) worst case, sorted iteration, lower/upper bound", cons: "Slower constants, more memory", chooseWhen: "Need predecessor/successor or sorted output, or want no attack surface" },
  { option: "Sorted array + binary search", pros: "Cache friendly, deterministic, tiny code", cons: "Static data only", chooseWhen: "Offline queries on a fixed collection" },
  { option: "Plain array indexed by value", pros: "Fastest, O(1) worst case", cons: "Only if values are small or compressed", chooseWhen: "Values up to about 10^6 to 10^7, or after coordinate compression" }
]} />

## Pitfalls

1. **Insert before lookup** in two-sum counting: pairs an element with itself.
2. **Missing the empty prefix** `{0: 1}`: subarrays starting at index 0 are lost.
3. **Overflow of counts.** Pair counts reach `n^2 / 2`; use 64-bit (`long long`, `long`) for the answer and for prefix sums.
4. **`cnt[x]` in C++ inserts** a zero entry on a mere read. Use `find` (or `count`) for lookups to avoid growing the map and invalidating iterators.
5. **Mutating a map while iterating** it.
6. **Floating point keys.** Never hash doubles; scale to integers or use an ordered structure with an epsilon-aware comparison.
7. **Mutable keys.** Python lists are unhashable (use tuples); Java arrays hash by identity (use `List` or `Arrays.toString`).
