## Intuition

A **functional graph** is a directed graph in which every vertex has **exactly one** outgoing edge: `next[v]`. A teleporter at every station, a pointer in every cell, the map `x to (a x + b) mod m` on residues, the step of a pseudorandom generator. All are functions from a finite set to itself.

Follow the pointers from any start and you must eventually repeat a vertex, because there are finitely many. The picture is the Greek letter rho: a **tail** of `mu` distinct vertices leading into a **cycle** of `lambda` vertices that you then circle forever. A whole functional graph is a set of cycles, each with trees of tails hanging into it.

The question "where am I after `k` steps?" for `k` as large as `10^18` has two good answers: use the **structure** (reduce `k` modulo the cycle length), or use **binary lifting** (jump by powers of two), which needs no structure at all.

## Definition

### Binary lifting

Let `up[j][v]` be the vertex reached from `v` after `2^j` steps. Then

```text
up[0][v]     = next[v]
up[j+1][v]   = up[j][ up[j][v] ]          (two jumps of 2^j make one of 2^(j+1))
```

For a query `(v, k)` write `k` in binary and, for each set bit `j`, do `v = up[j][v]`. The jumps all follow the same function, so their order is irrelevant. With `k < 2^60` (which covers `10^18`) the table has `60 n` entries, is built in `O(n log k)`, and each query costs `O(log k)`.

The same table solves **k-th ancestor** in a rooted tree (point the root at itself) and, with an extra array for sums, **weighted jumps**: `sum[j][v]` is the total weight along the `2^j` jumps.

### Tail and cycle

Walk from `v` recording the first time each vertex appears. The first repeat gives `mu` (the index of the repeated vertex) and `lambda` (walk length minus `mu`). Then for `k < mu + lambda` the answer is the `k`-th walked vertex, otherwise the `(mu + (k - mu) mod lambda)`-th. This is `O(mu + lambda)` per start, so it suits single queries, or all queries once you precompute tails and cycle positions for every vertex.

### Floyd's tortoise and hare

To find `mu` and `lambda` with **O(1) memory**: move a tortoise one step and a hare two steps per round until they meet (this proves a cycle). Then restart the tortoise at the start and move both one step at a time; they meet at the **cycle entry**, and the number of steps is `mu`. Finally walk the hare around the cycle once to measure `lambda`. This is the classic way to detect that a pseudorandom sequence has entered a loop, and the heart of Pollard's rho factorisation.

## Experiment

The program builds a random function on 20,000 stations, checks 2,000 queries with `k` up to `10^18` against the tail-and-cycle method, checks Floyd's tortoise and hare, and measures tail and cycle lengths.

<CodeRunner language="python" timeoutMs={30000} code={`import math

# ---------------------------------------------------------------- DEMO 3: functional graphs
def rho_dict(nxt, v):
    seen, order = {}, []
    cur = v
    while cur not in seen:
        seen[cur] = len(order)
        order.append(cur)
        cur = nxt[cur]
    mu = seen[cur]
    return mu, len(order) - mu


def rho_floyd(nxt, x0):
    """Floyd's tortoise and hare: tail length mu and cycle length lam using O(1) memory."""
    tort, hare = nxt[x0], nxt[nxt[x0]]
    steps = 1
    while tort != hare:
        tort, hare = nxt[tort], nxt[nxt[hare]]
        steps += 1
    mu, tort = 0, x0
    while tort != hare:
        tort, hare = nxt[tort], nxt[hare]
        mu += 1
    lam, hare = 1, nxt[tort]
    while tort != hare:
        hare = nxt[hare]
        lam += 1
    return mu, lam, steps


def lifting_table(nxt, n, log):
    up = [nxt[:]]
    for _ in range(1, log):
        prev = up[-1]
        up.append([prev[prev[v]] for v in range(n)])
    return up

    j = 0
    while k:
        if k & 1:
            v = up[j][v]
        k >>= 1
        j += 1
    return v

What it shows:

- Binary lifting and the **tail-and-cycle method** agree on all 2,000 queries, with `k` as large as `10^18`.
- The tortoise and hare finds the same `mu` and `lambda` as the dictionary method on 500 starts, using constant memory.
- On a random function of 20,000 stations the average **tail is 97**, the **cycle is 52** and the walk before a repeat is **149**. Random-mapping theory predicts about `sqrt(pi n / 8) = 89` for tail and cycle each and `sqrt(pi n / 2) = 177` for the walk: the same order, `sqrt(n)`, with sampling noise from 500 starts on one random function.
- The lifting table has **60 levels**; one query takes at most 60 jumps (here `10^18` has 24 set bits).

So walks in a random function are short, around `sqrt(n)`. Adversarial inputs (one big cycle through every vertex, or one long tail) are the ones that make naive simulation slow, which is why the problem tests include them.

## Pitfalls

1. **Number range of `k`.** `10^18` fits a signed 64-bit integer but not a JavaScript double. Use `BigInt` there, `long long` in C++ and `long` in Java.
2. **Too few levels.** `LOG = 30` handles only `k < 2^30`. For `10^18` you need 60.
3. **Indexing.** Mixing 0-indexed arrays with 1-indexed input is the classic off-by-one; convert once on input.
4. **Memory.** `60 * n` ints is 24 MB at `n = 10^5` as `int` in C++, but Python lists of ints are much heavier. Use arrays, or the tail-and-cycle method, when memory is tight.
5. **Reducing modulo the wrong length.** The cycle length applies only after the tail: use `mu + (k - mu) mod lambda`, not `k mod lambda`.
6. **Roots in a tree.** For k-th ancestor set `up[0][root] = root` (or a sentinel), otherwise jumps past the root fall off the table.
7. **Forgetting `k = 0`.** The loop over set bits handles it correctly (no jumps), but a hand-written special case often does not.
8. **Using the tortoise and hare for many queries.** It finds the structure from one start in `O(mu + lambda)`; it does not answer many arbitrary `k` queries quickly.
