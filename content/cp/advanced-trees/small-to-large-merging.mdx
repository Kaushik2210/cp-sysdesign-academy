## Intuition

You are asked something about **every subtree** of a rooted tree: how many distinct colours does it contain, which colour is the most frequent, what is the median value? The natural plan is bottom-up: each vertex keeps a container describing its subtree and **merges the containers of its children** into its own. The risk is the merge cost. On a path of `n` vertices the container grows to size `n` and, if every merge copies it, the total work is `1 + 2 + ... + n`, which is quadratic.

**Small-to-large merging** fixes this with one rule: when two containers meet, **pour the smaller into the larger** and keep the larger one as the result. Across the tree this takes `O(n log n)` insertion attempts, even when colours overlap.

Before choosing a technique, identify what each query selects.

| Query shape | Start with |
| --- | --- |
| A frequency table for every rooted subtree | Small-to-large merging, covered here |
| A mutable sum or maximum on arbitrary paths | [Heavy-light decomposition](/cp/trees/heavy-light-decomposition/) |
| A distinct count on arbitrary paths, with all requests known in advance | [Mo's algorithm on trees](/cp/advanced-trees/mo-on-trees/) |
| Distances among a small set of marked vertices | [Virtual trees](/cp/advanced-trees/virtual-trees/) |

## Definition

**The rule.** To merge containers `A` and `B`, iterate over the smaller one, insert each element into the larger, and keep the larger as the new container (swap references, never copy).

**Why `O(n log n)`.** Suppose the two groups being merged represent `a` and `b` original vertices. Their containers hold at most `a` and `b` entries, respectively, so scanning the smaller container costs at most `min(a, b)` iterations. Charge at most one iteration to each vertex of the group with fewer original vertices. Each charged vertex enters a group at least twice as large as before, even if many colours collide. A vertex is charged at most `floor(log2 n)` times. Hash sets give expected `O(n log n)` time, and ordered sets give `O(n log² n)` time.

**What "container" can be.**

| question per subtree | container |
| --- | --- |
| number of distinct colours | set of colours |
| most frequent colour | map colour to count, plus the current best (see pitfall 4) |
| `k`-th smallest or sorted values | ordered multiset |
| number of pairs with some property | map from value to count, updated while merging |

**Processing order.** Do it iteratively when the tree is deep. If labels are arranged so that `parent[v] < v`, run `v` from `n` down to `1`: all children of `v` have larger labels, so they were merged into `v` before `v` itself is read. Otherwise take the vertices in reverse of a DFS or BFS order.

**Relation to "DSU on tree" (sack).** The sack technique keeps **one** global map and re-uses it by processing the heavy child last without clearing. It reaches the same `O(n log n)` bound and uses less memory. Small-to-large with explicit containers is shorter to write and easier to adapt, so start there.

```python
sets = [None] + [{col[v]} for v in range(1, n + 1)]
ans = [0] * (n + 1)
for v in range(n, 0, -1):                 # children have larger labels than their parent
    ans[v] = len(sets[v])
    if v > 1:
        p = par[v]
        a, b = sets[v], sets[p]
        if len(a) > len(b):               # pour the smaller into the larger
            a, b = b, a
        b |= a
        sets[p] = b
        sets[v] = None
```

        if (sets[v].size() > sets[p].size()) swap(sets[v], sets[p]);   // O(1) swap of the two containers

## Experiment

The program first checks both merge strategies against an explicit scan of every subtree on 300 random small trees. Then it counts the **element insertions** performed while merging, with all colours distinct (the worst case for set sizes), comparing small-to-large with the naive rule "always insert the child's set into the parent's".

What it shows:

- Both strategies give the correct answers on all 300 random trees. The difference is only **cost**.
- On a **path** the naive rule is quadratic: **127,992,000** insertions for `n = 16,000` (8,000 per vertex, and it doubles with `n`), where small-to-large needs **15,999**, one per vertex, because each step pours a single element into the big set.
- On a **random tree** small-to-large needs 79,549 insertions at `n = 16,000` (0.36 per `n log2 n`); on a **complete binary tree** 102,930 (0.46 per `n log2 n`). Both stay below `n log2 n`, as the argument predicts.
- On a **star** both are linear. The naive rule is only bad when a big set is merged **into a small one**, which a path produces at every step.
- The naive rule can look fine on random or balanced trees (10 to 12 insertions per vertex here), which is why it passes small tests and fails on a path.

## Pitfalls

1. **Copying instead of swapping.** `b = a | b` creates a new set and costs the size of both. Merge in place and keep the larger object.
2. **Choosing which to keep by the tree rather than by size.** Keeping the parent's set regardless of size is exactly the naive rule.
3. **Recursion depth.** A path of `10^5` vertices overflows the default stack in Python and Java. Use the label order `parent < child`, or iterate over a reversed BFS order.
4. **Most frequent colour.** After merging counts you must update the current best carefully: counts only grow, so the best of the merged container is the best of the larger plus any colour whose count was raised by the merge. Do not recompute from scratch.
5. **Reading the answer too early or too late.** Record `ans[v]` after all children have been merged into `v` and **before** `v` is merged into its parent.
6. **Forgetting that the container is moved.** After pouring `v` into `p`, `sets[v]` is gone (set it to `None`); a later read of it is a bug.
7. **Hash flooding.** Adversarial inputs can break unordered containers in C++. For hacked-prone contests use a custom hash or an ordered set.
8. **Memory.** `n` one-element sets cost real memory in Python and Java. For `n` near `10^6` prefer the sack technique or an Euler tour with an offline distinct-count structure.
