## Intuition

Before writing a single line, a strong competitor reads the constraints and says: "n is 2 * 10^5, so the intended solution is about `n log n`." The input size is a *hint about the solution*, because problem setters choose limits so that the intended solution passes and the naive one fails.

This lesson turns that instinct into arithmetic.

## The budget

A typical judge executes about **10^8 simple operations per second** in a compiled language (C++, Java, Rust). "Simple" means an addition, comparison, array access, not a map lookup or a memory allocation. With a time limit of 1 to 2 seconds, plan for **at most about 10^8 to 3 * 10^8** simple operations.

```text
operations needed (as a function of n)   <=   budget (about 10^8 per second of time limit)
```

Python and JavaScript are slower: Python executes roughly `10^7` simple loop iterations per second, so either use a better algorithm, vectorised built-ins, or accept a smaller feasible `n`.

## The table to memorise

| Max `n` | Fits | Typical algorithm families |
| --- | --- | --- |
| `n <= 10` | `O(n!)`, `O(n^6)` | permutations, brute-force search |
| `n <= 20` to `25` | `O(2^n * n)` | subsets, bitmask DP |
| `n <= 40` | `O(2^(n/2) * n)` | meet in the middle |
| `n <= 100` | `O(n^4)` | Floyd-Warshall (`n^3`), small DP with 4 loops |
| `n <= 500` | `O(n^3)` | matrix DP, Floyd-Warshall |
| `n <= 5000` | `O(n^2)` | pairs, 2D DP, LIS `n^2` |
| `n <= 10^5` | `O(n sqrt n)`, `O(n log^2 n)` | Mo's algorithm, sqrt decomposition |
| `n <= 2 * 10^5` to `10^6` | `O(n log n)` | sorting, heaps, segment trees, binary search |
| `n <= 10^7` | `O(n)` | linear sieve, single scan, prefix sums |
| `n <= 10^9` | `O(sqrt n)`, `O(log n)` | trial division, number theory |
| `n <= 10^18` | `O(log n)`, `O(1)` | closed form, binary exponentiation, gcd |

These are guides, not laws. A `O(n^2)` algorithm with `n = 5000` is `2.5 * 10^7` steps: easy. `n = 10^5` with `n^2/2 = 5 * 10^9` is not.

## Worked examples

**Example 1.** `n = 2 * 10^5`, time limit 2 s, "count pairs `i < j` with `a_i + a_j = S`".

- `n^2 / 2 = 2 * 10^10`: about 200 seconds. Rejected.
- `n log n = 2 * 10^5 * 18 = 3.6 * 10^6`: trivially fast. Sort plus two pointers, or a hash map.

**Example 2.** `n = 20`, "can you split the numbers into two groups of equal sum?" `2^20 = 10^6` subsets: even `2^20 * 20 = 2 * 10^7` passes. A bitmask loop is intended; a greedy proof would be a trap.

**Example 3.** `n <= 10^12`, "is `n` prime?" A loop to `n` is `10^12`. A loop to `sqrt n = 10^6` is fast.

**Example 4.** `n <= 1500` and values small, "count zero-sum triples". Triple loop is `n^3 / 6 = 5.6 * 10^8`: borderline in C++, hopeless in Python. Fix one index and look up in a table: `n^2 / 2 = 10^6`. That is the problem below.

## Beyond the headline `n`

1. **Multiple test cases.** If the statement says "sum of `n` over all tests is at most `2 * 10^5`", the total work is bounded by the sum, so `O(n log n)` per test is fine. If instead there are `10^4` tests each with `n = 2 * 10^5` there is no such guarantee and you must read the limits carefully.
2. **Several parameters.** `n` items and `q` queries: naive `O(n * q)` is too slow at `2 * 10^5` each (`4 * 10^10`), the intended `O((n + q) log n)` is `7 * 10^6`.
3. **Hidden constants.** A hash map operation is ~20 to 50 simple operations, `std::sort` at `n = 10^6` takes ~80 ms, a recursive call costs more than a loop iteration. Memory access patterns matter: a `1000 x 1000` grid scanned row by row is much faster than column by column.
4. **Output size.** If the answer is a list of `n^2` items, you cannot be faster than `n^2`. The limits often reveal this.
5. **Answer range.** Values up to `10^18` suggest 64-bit integers and a counting formula; values up to `10^9+7` suggest modular counting (see [modular arithmetic](/cp/math-basics/modular-arithmetic/)).
6. **Language factor.** Use roughly `10^7` per second for pure Python loops. Prefer built-ins (`sorted`, `sum`, `bisect`, slicing on `bytearray`) which run at C speed.

## When the constraints do not match

If you can only find an `O(n^2)` solution for `n = 2 * 10^5`, the problem contains a structural property you are missing: sortedness, monotonicity, small answer, offline processing, a data structure, or math. Common mappings from slow to fast:

| Naive | Fast replacement | Typical enabler |
| --- | --- | --- |
| scan all pairs | sort + two pointers | order |
| scan for a value | hash set / map | membership |
| scan for max/min over range | sparse table, segment tree | range queries |
| try all answers | binary search on answer | monotone feasibility |
| recompute from scratch | prefix sums / incremental update | overlapping work |
| enumerate all subsets | meet in the middle, DP | small sums or structure |

## Pitfalls

1. **Ignoring the log factor** when `n = 10^6` and the limit is tight, or when the constant is large (segment tree with `n = 10^6` and `q = 10^6` is about `4 * 10^7` node visits times a constant).
2. **Trusting the table over reading the statement**: always check whether the limit is on `n`, on `sum of n`, or on a value.
3. **Overflow while estimating**: `n^2` for `n = 10^5` is `10^10`, which does not fit 32 bits. This applies to your *answer* too.
4. **Estimating with the wrong `n`.** For graphs use both `V` and `E`: BFS is `O(V + E)`.
5. **Optimising a pass that is not the bottleneck.** Estimate each phase and fix the largest one.
