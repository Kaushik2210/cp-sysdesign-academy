## Intuition

You cannot time an algorithm on every computer, and a stopwatch tells you nothing about the next input size. What you can do is ask: *how does the amount of work grow when the input grows?* Doubling `n` makes a linear algorithm twice as slow, a quadratic one four times as slow, and a logarithmic one only one step slower.

Big-O notation is a way to talk about that growth while ignoring constants and low-order terms: `3n^2 + 50n + 7` and `n^2` are "the same shape" for large `n`.

## Formal definitions

Let `f(n)` be the number of basic steps the algorithm takes on an input of size `n`, and `g(n)` a simple comparison function.

| Notation | Meaning | Formal statement |
| --- | --- | --- |
| `f = O(g)` | `f` grows **no faster** than `g` (upper bound) | exist `c > 0`, `n0` with `f(n) <= c * g(n)` for all `n >= n0` |
| `f = Omega(g)` | `f` grows **at least as fast** as `g` (lower bound) | exist `c > 0`, `n0` with `f(n) >= c * g(n)` for all `n >= n0` |
| `f = Theta(g)` | both: `f` has the **same growth** as `g` | `f = O(g)` and `f = Omega(g)` |

Example: `f(n) = 3n^2 + 50n + 7`. For `n >= 17` we have `50n + 7 <= 3n^2`, so `f(n) <= 6n^2`; choose `c = 6, n0 = 17`. Hence `f = O(n^2)`. Also `f(n) >= 3n^2`, so `f = Omega(n^2)`, thus `f = Theta(n^2)`. Note that `f = O(n^3)` is also true, merely a useless bound.

<Callout type="pitfall" title="O is not 'worst case'">
Big-O describes the growth of a function; "worst case" is which input you measure. You can say "the worst case of insertion sort is `Theta(n^2)`" and "the best case is `Theta(n)`". Saying "insertion sort is `O(n^2)`" is true for all its cases, but "insertion sort is `Theta(n^2)`" is false because the best case is linear.
</Callout>

## Common growth rates, slowest growing first

| Class | Name | `n = 10^6` takes about | Typical source |
| --- | --- | --- | --- |
| `O(1)` | constant | 1 | array index, hash lookup (expected) |
| `O(log n)` | logarithmic | 20 | binary search, halving loops |
| `O(sqrt n)` | square root | 1 000 | trial division |
| `O(n)` | linear | `10^6` | one scan |
| `O(n log n)` | linearithmic | `2 * 10^7` | sorting, divide and conquer |
| `O(n^2)` | quadratic | `10^12` | all pairs, nested loops |
| `O(n^3)` | cubic | `10^18` | triple loops, matrix multiply |
| `O(2^n)` | exponential | astronomically large | all subsets |
| `O(n!)` | factorial | astronomically large | all permutations |

## How to count operations

1. **Sequential blocks add**: `O(A) + O(B) = O(max(A, B))`.
2. **Nested loops multiply**, if the inner bound does not depend on the outer variable: `n` iterations of `m` is `n * m`.
3. **Dependent loops need a sum.** `for i in 0..n: for j in 0..i` runs `0 + 1 + ... + (n-1) = n(n-1)/2`, which is `Theta(n^2)`.
4. **Halving or doubling gives a logarithm.** `while i < n: i *= 2` runs `ceil(log2 n)` times.
5. **Harmonic loops give `n log n`.** `for i in 1..n: for j in i, 2i, 3i, ... <= n` does `n/i` steps for each `i`, in total `n * (1 + 1/2 + ... + 1/n) = n ln n + O(n)`.
6. **Drop constants and lower-order terms**, keep every variable that is independent: a grid scan is `O(h * w)`; `O(n + m)` is not `O(n)`.
7. **Function calls cost what they cost.** `len(list)` is `O(1)`, `list.pop(0)` is `O(n)`, `s += c` on an immutable string can be `O(n)`.

## Worked example: what does this cost?

```python
def solve(a):                 # a has n elements
    n = len(a)
    best = 0
    for i in range(n):        # n iterations
        s = 0
        for j in range(i, n): # n - i iterations
            s += a[j]
            best = max(best, s)
    a.sort()                  # n log n
    return best
```

The double loop does `n + (n-1) + ... + 1 = n(n+1)/2 = Theta(n^2)` steps, the sort `Theta(n log n)`. Total `Theta(n^2)`: the larger term dominates. The space is `O(1)` extra apart from whatever `sort` uses internally.

## Beyond a single `n`: what is the input size?

Sometimes `n` is a *value*, not a count of items. Trial division on a number `n` takes `O(sqrt n)` divisions, which is exponential in the number of bits of `n` (`b = log2 n` bits gives `2^(b/2)`). Euclid's gcd runs in `O(log n)`, i.e. linear in the bit length. When the statement says `n <= 10^12`, decide whether `n` is a count (you can only afford a few operations per unit) or a value (a loop to `sqrt n` or a logarithmic algorithm).

## Pitfalls

1. **Constants matter when `n` is moderate.** An `O(n log n)` algorithm with a huge constant can lose to a simple `O(n^2)` for `n = 50`. Big-O is about asymptotics; the constraint table in the [estimating lesson](/cp/complexity-analysis/estimating-from-constraints/) turns it into a budget.
2. **Hidden costs.** Slicing (`a[i:]`), string concatenation in a loop, `x in list`, and `list.insert(0, x)` each hide a linear factor.
3. **Confusing `O` and `Theta`.** If someone asks for the complexity of an algorithm they usually mean the tight bound.
4. **Forgetting a variable.** BFS on a graph is `O(V + E)`, not `O(V)`.
5. **Recursion hides loops.** Count the number of calls times the cost per call (see [recurrences](/cp/complexity-analysis/recurrences-and-master-theorem/)).
6. **Amortized is not worst case.** Some operations are occasionally expensive; see the [amortized lesson](/cp/complexity-analysis/amortized-analysis/).
