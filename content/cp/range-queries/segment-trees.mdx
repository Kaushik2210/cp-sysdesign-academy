## Intuition

A [prefix-sum](/cp/arrays-and-windows/prefix-sums/) array answers "sum of `a[l..r]`" in `O(1)`, but a single change `a[i] = v` ruins every prefix after `i`, so an update costs `O(n)`. Recomputing the sum for every query costs `O(n)` per query. When queries and updates are mixed and `n`, `q` are around `10^5`, both are too slow.

The compromise is to pre-compute **sums of blocks** with sizes that line up like a binary tree: blocks of 1, then 2, then 4, and so on. Any range is a union of only about `2 log n` such blocks, and changing one element affects only the `log n` blocks above it.

## Definition

A **segment tree** is a binary tree where each node stores the answer (here the sum) for a range of the array, and its two children split that range in half. Leaves are single elements.

- **Query** `[l, r]`: collect the stored values of `O(log n)` nodes whose ranges exactly cover `[l, r]`.
- **Update** `a[i] = v`: change the leaf, then recompute each ancestor from its two children.
- Build: `O(n)`. Query and update: `O(log n)`. Memory: `2n` with the layout below.

The merge operation only needs to be **associative** (sum, min, max, gcd, xor, matrix product). For a sum, the order of the two children does not matter, but for something like string concatenation it does.

## Code: the bottom-up layout

Store the leaves at positions `n .. 2n-1` and let node `i` have children `2i` and `2i+1`. No recursion, no `4n` array, and it works for any `n`, not only powers of two.

<Tab label="Python">

```python
n = len(a)
t = [0] * (2 * n)
for i in range(n):
    t[n + i] = a[i]
for i in range(n - 1, 0, -1):
    t[i] = t[2 * i] + t[2 * i + 1]

def update(i, v):                  # a[i] = v, 0-based
    i += n
    t[i] = v
    while i > 1:
        i >>= 1
        t[i] = t[2 * i] + t[2 * i + 1]

def query(l, r):                   # sum of a[l:r], half-open
    s = 0
    l += n
    r += n
    while l < r:
        if l & 1:
            s += t[l]
            l += 1
        if r & 1:
            r -= 1
            s += t[r]
        l >>= 1
        r >>= 1
    return s
```

```cpp
int n; vector<long long> t;        // size 2n
void build(const vector<long long>& a) {
    n = a.size(); t.assign(2 * n, 0);
    for (int i = 0; i < n; i++) t[n + i] = a[i];
    for (int i = n - 1; i >= 1; i--) t[i] = t[2 * i] + t[2 * i + 1];
}
void update(int i, long long v) {  // 0-based
    for (t[i += n] = v; i > 1; i >>= 1) t[i >> 1] = t[i] + t[i ^ 1];
}
long long query(int l, int r) {    // [l, r)
    long long s = 0;
    for (l += n, r += n; l < r; l >>= 1, r >>= 1) {
        if (l & 1) s += t[l++];
        if (r & 1) s += t[--r];
    }
    return s;
}
```

## Choosing the structure

| need | use |
| --- | --- |
| static array, range sum | prefix sums |
| point updates and range sum | segment tree (or a Fenwick tree) |
| range min/max/gcd with point updates | segment tree |
| range update (add to a whole range) and queries | segment tree with lazy propagation (a later topic) |

<Callout type="tip" title="Know the half-open convention">
The bottom-up query above takes `[l, r)`. Convert `1`-based inclusive `[x, y]` to `l = x - 1`, `r = y`. Mixing conventions is the most common source of off-by-one errors.
</Callout>

## Pitfalls

1. **Mixing inclusive and half-open ranges** in the same solution.
2. **Overflow.** A sum of `2·10^5` values up to `10^9` needs 64-bit integers.
3. **Non-commutative merges with the bottom-up loop.** It combines left and right pieces in the wrong order for operations like concatenation or matrix product. Keep left and right accumulators separately, or use the recursive version.
4. **Non-power-of-two `n` with a recursive tree and a too-small array.** Allocate `4n` for the recursive layout.
5. **Rebuilding the tree on each update.** An update touches only `log n` nodes.
6. **Using a segment tree where prefix sums suffice.** No updates means no need for it.
