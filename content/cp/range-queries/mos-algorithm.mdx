## Intuition

"How many **different** values are in `a[l..r]`?" is awkward. A prefix-sum array cannot answer it (distinct counts do not subtract), and a [sparse table](/cp/range-queries/sparse-table/) cannot merge overlapping ranges for it.

But there is something easy: if you already know the answer for a **window** `[L, R]`, you can update it in `O(1)` when the window grows or shrinks by **one element**. Keep a count per value and a running tally of how many values have a non-zero count.

So answer the queries by *sliding one window* from query to query. The danger is the order: jumping `[1, 5] → [90000, 90005] → [2, 6]` moves the window a long way each time. The trick of **Mo's algorithm** is to take advantage of the fact that the queries are **offline** (all known in advance), and to *reorder* them so the total window movement is small.

## The ordering

Cut the positions into blocks of size `B`. Sort the queries by

```text
(block of l,  then r)
```

Inside one block the right end `r` only moves **forward**, so across all the queries of a block it travels at most `n`. There are `n / B` blocks, so the right pointer moves about `n · n / B` in total. The left end `l` stays within a block, so it moves at most `B` per query: `q · B` in total.

```text
total movement  ≈  n² / B  +  q · B        minimised at  B ≈ n / sqrt(q)        giving  O((n + q) · sqrt(n))
```

A neat constant-factor trick: on **odd blocks** sort `r` in **descending** order. The right pointer then sweeps forward on one block and back on the next, instead of jumping back to the start each time.

## The window operations

You need two cheap operations for your problem:

```text
add(i):     cnt[a[i]] += 1; if it became 1: distinct += 1
remove(i):  cnt[a[i]] -= 1; if it became 0: distinct -= 1
```

To move the window `[L, R]` to the query `[l, r]`, **expand first, then shrink**, so the window never has negative length:

```text
while L > l:  L -= 1;  add(L)
while R < r:  R += 1;  add(R)
while L < l:  remove(L);  L += 1
while R > r:  remove(R);  R -= 1
```

Start with an empty window (`L = 0`, `R = -1`). Compress the values first (map each distinct value to `0, 1, 2, ...`) so `cnt` is a small array.

```python
def distinct_queries(a, queries):                 # queries: (l, r) 0-based inclusive
    n, q = len(a), len(queries)
    ids = {}
    arr = [ids.setdefault(x, len(ids)) for x in a]
    block = max(1, int(n / max(1, q ** 0.5)))
    order = sorted(range(q), key=lambda i: (queries[i][0] // block,
                                             queries[i][1] if (queries[i][0] // block) % 2 == 0 else -queries[i][1]))
    cnt = [0] * len(ids)
    distinct = 0
    L, R = 0, -1
    ans = [0] * q
    for i in order:
        l, r = queries[i]
        while L > l:
            L -= 1
            if cnt[arr[L]] == 0: distinct += 1
            cnt[arr[L]] += 1
        while R < r:
            R += 1
            if cnt[arr[R]] == 0: distinct += 1
            cnt[arr[R]] += 1
        while L < l:
            cnt[arr[L]] -= 1
            if cnt[arr[L]] == 0: distinct -= 1
            L += 1
        while R > r:
            cnt[arr[R]] -= 1
            if cnt[arr[R]] == 0: distinct -= 1
            R -= 1
        ans[i] = distinct
    return ans
```

```cpp
vector<int> distinctQueries(const vector<int>& arr, const vector<pair<int,int>>& qs, int distinctValues) {
    int n = arr.size(), q = qs.size();
    int block = max(1, (int)(n / max(1.0, sqrt((double)q))));
    vector<int> idx(q), cnt(distinctValues, 0), ans(q);
    iota(idx.begin(), idx.end(), 0);
    sort(idx.begin(), idx.end(), [&](int a, int b) {
        int ba = qs[a].first / block, bb = qs[b].first / block;
        if (ba != bb) return ba < bb;
        return (ba % 2 == 0) ? qs[a].second < qs[b].second : qs[a].second > qs[b].second;
    });
    int distinct = 0, L = 0, R = -1;
    for (int k : idx) {
        int l = qs[k].first, r = qs[k].second;
        while (L > l) { L--; if (cnt[arr[L]]++ == 0) distinct++; }
        while (R < r) { R++; if (cnt[arr[R]]++ == 0) distinct++; }
        while (L < l) { if (--cnt[arr[L]] == 0) distinct--; L++; }
        while (R > r) { if (--cnt[arr[R]] == 0) distinct--; R--; }
        ans[k] = distinct;
    }
    return ans;
}
```

## When can you use Mo's algorithm?

Mo's algorithm applies when all of these hold:

| requirement | why |
| --- | --- |
| the queries are known **offline** | you reorder them |
| the array does **not change** (the basic version) | the window only slides over a fixed array |
| you can **add** and **remove** one end element cheaply | each move changes the window by one element |
| the answer depends only on the **set/multiset in the window** | the order of processing does not matter |

Typical fits: distinct count, count of values that appear exactly `k` times, "power" of a range (sum of `cnt² · value`), number of inversions with a Fenwick tree inside (heavier), mode of a range.

Variants worth knowing:

- **Mo with updates**: add the time as a third sort key with block size about `n^(2/3)`, for `O(n^(5/3))`.
- **Mo on trees**: run it on an Euler tour for path queries.
- **Rollback Mo**: when you can *add* but not remove (for example "maximum in the window"), keep the left end fixed per block and roll back after each query.

For distinct counts specifically there is also an `O((n + q) log n)` offline solution (sort queries by `r`, keep a Fenwick tree marking the last occurrence of each value), but Mo is far simpler and generalises to many other statistics.

## Pitfalls

1. **Shrinking before expanding.** If you shrink first, the window can briefly have negative length and counts go negative. Always expand with `while L > l` and `while R < r` first.
2. **Bad block size.** Use about `n / sqrt(q)`, not a fixed `sqrt(n)`, when `q` and `n` differ a lot; and make sure it is at least 1.
3. **Slow `add` / `remove`.** The total number of moves is about `(n + q) · sqrt(n)`, so each must be `O(1)`. A tree-based structure inside multiplies the cost.
4. **Forgetting to compress values.** A `cnt` array indexed by values up to `10^9` does not fit; map values to small ids first.
5. **Losing the original order.** Sort a list of indices, then write `ans[i]` back to the query's original position.
6. **Comparator bugs.** Alternating the direction of `r` by block parity is an optimisation only; a comparator that is not a strict weak ordering can crash `sort` in C++.
