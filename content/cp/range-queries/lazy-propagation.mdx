## Intuition

A plain [segment tree](/cp/range-queries/segment-trees/) handles "change one element" and "answer a range". Now the events are different: **"add `d` to every element in `a[l..r]`"** mixed with range queries. Doing it element by element costs `O(n)` per update, and `n = q = 2·10^5` means `4·10^10` steps.

The observation behind **lazy propagation**: you rarely need the *individual* values. When an update covers a node's whole range, the node's answer changes in a way you can compute **without looking at its children**: adding `d` to every element adds `d` to the maximum, and adds `d · length` to the sum. So record the change on that one node and *postpone* telling the children. The postponed change is a **lazy tag**. It is paid for only if a later operation actually needs to look inside that node.

## Definition

Each node stores two things for its range:

- `val`: the answer for the range (max, sum, ...) **including** every update applied to this node or above it that has already been pushed here.
- `lz`: a tag, "add this amount to every element of the range, the children have not been told yet". Empty means `0`.

Three operations:

```text
apply(node, d):   val += effect(d, node)     # max: d      sum: d * length
                  lz  += d

push(node):       if lz != 0:
                      apply(left child,  lz)
                      apply(right child, lz)
                      lz = 0

update(node, [l, r], ql, qr, d):
    if [l, r] inside [ql, qr]:  apply(node, d); return      # stop: lazy
    push(node)                                              # children must be correct before we change them
    recurse into the children that overlap [ql, qr]
    val = combine(left.val, right.val)

query(node, ...): same shape; push(node) before descending; combine the answers
```

The rule that makes it correct: **always push before you descend**. Then any node you read has had every update above it delivered.

Both operations visit `O(log n)` nodes (at most two partially covered nodes per level), so the whole structure is `O((n + q) log n)`.

## Example, step by step

Array `[3, 1, 4, 1, 5]`, operation "add 10 to positions 2 to 4" (1-based).

1. Root covers `1..5`, only partly inside the update. Push (nothing to push), recurse.
2. Left child covers `1..3`: partly inside; recurse. Its child `1..2` is partly inside; its leaf `2` is fully inside, so `val` becomes `11` and the leaf gets a tag (harmless on a leaf).
3. Node `3..3` (leaf) is inside: `val = 14`.
4. Right child `4..5`: partly inside; leaf `4` becomes `11`.
5. Going back up, every touched node recomputes its maximum from its children.

Now the update "add 5 to the whole array": the root is fully covered, so only `root.val += 5; root.lz += 5` happens and the recursion stops immediately. The next query that goes below the root pushes the `5` down one level at a time, **only along the path it follows**. The rest of the tree never hears about it until it is needed.

```python
import sys
sys.setrecursionlimit(10000)

mx = [0] * (4 * n)
lz = [0] * (4 * n)

def build(o, l, r):
    if l == r:
        mx[o] = a[l]; return
    m = (l + r) // 2
    build(2*o, l, m); build(2*o+1, m+1, r)
    mx[o] = max(mx[2*o], mx[2*o+1])

def apply(o, d):
    mx[o] += d; lz[o] += d

def push(o):
    if lz[o]:
        apply(2*o, lz[o]); apply(2*o+1, lz[o]); lz[o] = 0

def update(o, l, r, ql, qr, d):
    if ql <= l and r <= qr:
        apply(o, d); return
    push(o)
    m = (l + r) // 2
    if ql <= m: update(2*o, l, m, ql, qr, d)
    if qr > m:  update(2*o+1, m+1, r, ql, qr, d)
    mx[o] = max(mx[2*o], mx[2*o+1])

def query(o, l, r, ql, qr):
    if ql <= l and r <= qr:
        return mx[o]
    push(o)
    m = (l + r) // 2
    best = None
    if ql <= m: best = query(2*o, l, m, ql, qr)
    if qr > m:
        v = query(2*o+1, m+1, r, ql, qr)
        best = v if best is None else max(best, v)
    return best
```

## Combining different tags

What you must define for a given problem:

| problem | node value | `apply(node, d)` | tag composition |
| --- | --- | --- | --- |
| range add, range max/min | max | `val += d` | `lz += d` |
| range add, range sum | sum | `val += d * len` | `lz += d` |
| range assign, range sum | sum | `val = d * len` | `lz = d` (a new assignment *replaces* any earlier tag) |
| range assign **and** range add, range sum | sum | needs two fields | order matters, see below |

A tag is a **function** applied to the elements. For correctness you need: composing two tags gives another tag of the same kind (so a node holds one pending tag, not a growing list), and the node's value can be updated from the tag in `O(1)`.

**Assign plus add together.** Store the pending tag as a pair `(mul, add)` meaning "x becomes `mul · x + add`". Composing a new `(m2, a2)` after `(m1, a1)` gives `(m2·m1, m2·a1 + a2)`. Assignment is `mul = 0`, `add = value`; addition is `mul = 1`, `add = d`. The order of composition is the classic place where this goes wrong.

## Two common alternatives

- **No-push (permanent tags).** For add + max you can leave a tag on the node forever and never push: define `mx[o] = max(mx[2o], mx[2o+1]) + add[o]`. A query adds the tags it passes on the way down. It is shorter, but it only works when the tag composes commutatively and the combine step can absorb it, so it does not extend to assignment.
- **Fenwick tree for add + sum.** Range add with *point* query needs just a Fenwick tree over the difference array. Range add with *range sum* needs two Fenwick trees. Use them when the operation set is that simple; reach for lazy propagation when you also need max, min, or assignment.

## Pitfalls

1. **Forgetting to push before descending**, in `update` *or* `query`. The children then hold stale values, and the bug appears only for particular operation orders.
2. **Pushing but not recomputing on the way back** (`mx[o] = max(children)`), so the parent keeps an old value.
3. **`apply` that ignores the length** for sums: `val += d`, instead of `val += d * len`.
4. **Overflow.** `10^9` plus `2·10^5` additions of `10^6` is `2·10^11`. Use 64-bit integers.
5. **Wrong tag composition** when mixing assign and add (assignment must clear the earlier add).
6. **Tag array too small.** Use `4n` entries for the recursive layout.
7. **Using it when you do not need it.** If every update is a single point, the plain segment tree is simpler and faster.
