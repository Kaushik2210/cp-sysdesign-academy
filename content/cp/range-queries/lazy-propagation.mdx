## Intuition

A plain [segment tree](/cp/range-queries/segment-trees/) updates **one** position in `O(log n)`. But if an event says "add 5 to every shelf from 3 to 90000", updating each position separately costs `O(n)`.

The trick is to be **lazy**. When an update covers a node's whole segment, do not touch the children. Fix the node's own answer immediately (a sum grows by `5 × length`) and leave a sticky note on the node: "my children still owe each of their elements 5". Only when a later operation has to look *inside* the node do we pass the note down. Each operation then visits only `O(log n)` nodes.

## Definition

Each node stores two things for its segment:

```text
sm[x]   the true sum of the segment, already including every tag at x or above that was applied
lz[x]   a pending "add this to each element" that the children have not received yet
```

Three small operations:

```text
apply(x, v):  sm[x] += v * length(x);  lz[x] += v        # the node's own state is fixed
push(x):      apply(left,  lz[x]); apply(right, lz[x]); lz[x] = 0
pull(x):      sm[x] = sm[left] + sm[right]
```

- **Range update** `[ql, qr]`: if the node's segment lies fully inside, `apply` and stop. Otherwise `push`, recurse into both children, then `pull`.
- **Range query** `[ql, qr]`: if fully inside, return `sm[x]`. Otherwise `push` first (the children must be up to date), then combine the children's answers.

Always push **before** descending, in updates *and* queries. That one rule is what makes the tags correct.

## Which operations can be lazy?

A lazy tag works when two things compose cleanly:

| update | query | tag | note |
| --- | --- | --- | --- |
| add `v` to a range | sum | `+v` | sum grows by `v · length` |
| add `v` to a range | minimum / maximum | `+v` | the min/max grows by `v`, no length factor |
| assign `v` to a range | sum | `= v` | needs a "has tag" flag, because `0` may be a legal value |
| add, then assign | sum | `(set?, add)` | order of composition matters: an assign overrides earlier adds |

For a range-add and range-sum **only**, a Fenwick tree with two arrays also works (and is shorter). Lazy propagation earns its keep when the update or query is something a Fenwick tree cannot express, such as range assign or range maximum with range add.

sm = [0] * (4 * n)
lz = [0] * (4 * n)

def apply(x, l, r, v):
    sm[x] += v * (r - l + 1)
    lz[x] += v

def push(x, l, r):
    if lz[x]:
        mid = (l + r) // 2
        apply(2 * x, l, mid, lz[x])
        apply(2 * x + 1, mid + 1, r, lz[x])
        lz[x] = 0

def update(x, l, r, ql, qr, v):
    if qr < l or r < ql: return
    if ql <= l and r <= qr:
        apply(x, l, r, v); return
    push(x, l, r)
    mid = (l + r) // 2
    update(2 * x, l, mid, ql, qr, v)
    update(2 * x + 1, mid + 1, r, ql, qr, v)
    sm[x] = sm[2 * x] + sm[2 * x + 1]

def query(x, l, r, ql, qr):
    if qr < l or r < ql: return 0
    if ql <= l and r <= qr: return sm[x]
    push(x, l, r)
    mid = (l + r) // 2
    return query(2 * x, l, mid, ql, qr) + query(2 * x + 1, mid + 1, r, ql, qr)

## Pitfalls

1. **Forgetting to push before descending.** Updates *and* queries must push, or you read children that have not yet received their tag.
2. **Forgetting `pull` after an update.** The node's sum must be recomputed from its children when you return.
3. **Tag value `0` as "no tag".** For range **assign**, `0` is a legitimate value: keep a separate boolean or use a sentinel such as `None`.
4. **Composing tags in the wrong order.** "Assign, then add" and "add, then assign" differ; define exactly how a new tag combines with a pending one.
5. **32-bit overflow.** A sum of `2·10^5` elements each up to `10^9` needs 64 bits, and `v * length` must be computed in 64 bits too.
6. **Array too small.** A recursive tree on `n` leaves needs up to `4n` nodes.
7. **Min/max with add.** The tag adds `v` to the stored extreme directly; do *not* multiply by the length.
