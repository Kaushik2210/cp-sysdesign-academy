## Intuition

You have a pile of tasks and one worker. Which order is best? You cannot try all `n!` orders, but you may be able to show a simple fact: **if two neighbours are in the "wrong" order, swapping them never hurts.** Then a schedule with any wrong neighbour pair can be fixed step by step, and the order with no wrong pair, a **sorted order**, is at least as good as every other. Sort once and you are done.

That proof pattern is the **exchange argument**, the most useful tool for proving a greedy correct.

## The recipe

1. Guess a rule that defines a "wrong pair" (a comparator `before(a, b)`).
2. Take any optimal solution that is **not** sorted by the rule.
3. Find two adjacent items `a, b` in the wrong order. Show that swapping them changes the cost only for those two items (everything else is unaffected) and does **not increase** the total.
4. Repeat. Each swap removes one inversion, so after finitely many swaps you reach the sorted order with cost no larger. So the sorted order is optimal.

Two details people forget: the swap must leave the **other** items untouched (the pair occupies the same block of time), and an unsorted permutation always contains an **adjacent** wrong pair (otherwise every neighbour pair is in order, so the whole thing is sorted, given the rule is a total preorder).

## Theorem 1: minimise the weighted sum of completion times

Jobs `i = 1..n` have processing time `t_i > 0` and weight `w_i > 0`. They run back to back with no gaps on one machine. If job `i` completes at `C_i`, minimise `sum w_i * C_i`.

**Claim.** Sort by `t_i / w_i` ascending (Smith's rule); equivalently put `i` before `j` when `t_i * w_j < t_j * w_i`.

**Proof.** Consider an optimal order that has an adjacent pair `i` immediately followed by `j` with `t_i / w_i > t_j / w_j`. Let `S` be the time at which `i` starts. Only these two completion times change under a swap, because together they occupy the same block `[S, S + t_i + t_j]`.

Cost of the pair as is: `w_i (S + t_i) + w_j (S + t_i + t_j)`.
Cost after swapping: `w_j (S + t_j) + w_i (S + t_j + t_i)`.

Subtract: `before - after = w_j t_i - w_i t_j`.

The assumption `t_i / w_i > t_j / w_j` means `t_i w_j > t_j w_i`, so `before - after > 0`. Swapping **strictly** reduces cost, contradicting optimality. Hence an optimal order has no adjacent pair with `t_i / w_i > t_j / w_j`, i.e. it is sorted by ratio. Orders that differ only in tie order cost exactly the same (swapping equal ratios changes cost by 0), so any sorted order is optimal. ∎

Sanity check with the brute force:

<CodeRunner language="python" code={`import random, itertools
from fractions import Fraction

random.seed(7)

def cost(order):
    t = c = 0
    for a, w in order:
        t += a
        c += w * t
    return c

ok = True
for _ in range(300):
    jobs = [(random.randint(1, 9), random.randint(1, 9)) for _ in range(random.randint(1, 6))]
    brute = min(cost(p) for p in itertools.permutations(jobs))
    greedy = cost(sorted(jobs, key=lambda j: Fraction(j[0], j[1])))
    ok = ok and brute == greedy
print("Smith's rule matches brute force:", ok)
`} />

Special cases are well known: all weights equal gives "shortest job first" (minimises the average completion time); all processing times equal gives "heaviest first".

## Theorem 2: minimise the maximum lateness

Jobs have processing time `t_i` and deadline `d_i`. Run them back to back from time 0. Lateness of job `i` is `C_i - d_i` (negative means early). Minimise the **maximum** lateness.

**Claim.** Earliest deadline first (EDF): sort by `d_i` ascending.

**Proof.** An **inversion** is a pair scheduled with `i` before `j` while `d_i > d_j`. Take an optimal schedule with the fewest inversions; suppose it has one. Then it has an adjacent inversion `i, j` (`i` immediately before `j`, `d_i > d_j`). Let the pair start at `S`. Before the swap, `j` completes at `S + t_i + t_j` with lateness `L_j = S + t_i + t_j - d_j`. After swapping:

- `j` completes at `S + t_j`, earlier than before, so its lateness got smaller.
- `i` completes at `S + t_i + t_j`, which is the old completion time of `j`. Its new lateness is `S + t_i + t_j - d_i`, which is less than `S + t_i + t_j - d_j = L_j` because `d_i > d_j`.

So both new latenesses are at most the old `L_j`, and no other job moves. The maximum lateness did not increase, and the inversion count dropped by one, contradicting the choice of a schedule with the fewest inversions. Hence an optimal schedule has no inversion: it is EDF. ∎

<CodeRunner language="python" code={`import random, itertools

random.seed(11)

def max_late(order):
    t = 0
    worst = -10**9
    for dur, dl in order:
        t += dur
        worst = max(worst, t - dl)
    return worst

ok = True
for _ in range(300):
    jobs = [(random.randint(1, 6), random.randint(1, 15)) for _ in range(random.randint(1, 6))]
    brute = min(max_late(p) for p in itertools.permutations(jobs))
    greedy = max_late(sorted(jobs, key=lambda j: j[1]))
    ok = ok and brute == greedy
print("EDF matches brute force:", ok)
`} />

Note the objective matters: EDF minimises the **maximum** lateness. It does not minimise the **number** of late jobs (that needs the Moore-Hodgson algorithm) nor the sum of lateness.

## Another style: "greedy stays ahead"

Instead of transforming an optimal solution into the greedy one, show that after each step greedy is **at least as good** as any other solution by some measure, then conclude at the end. For activity selection, the measure is "finish time of the `k`-th chosen activity": greedy's `k`-th finish is never later than that of any valid schedule, so greedy fits at least as many activities (proved in the interval lesson).

## Worked example: concatenating numbers

Given strings (numbers), arrange them to form the largest number. The comparator "`a` before `b` if `a + b > b + a` as strings" is a valid total preorder, and an adjacent-swap argument shows that an adjacent pair violating it can be swapped to give a number that is at least as large (the digits outside the pair do not change, and the pair block has the same length either way). So a plain sort with that comparator is correct.

<CodeRunner language="python" code={`from functools import cmp_to_key

nums = ["3", "30", "34", "5", "9"]
nums.sort(key=cmp_to_key(lambda a, b: -1 if a + b > b + a else (1 if a + b < b + a else 0)))
print("".join(nums))
`} />

<Callout type="note" title="A comparator must be a strict weak order">
Sorting with an inconsistent comparator is undefined behaviour in C++ (it can crash or loop) and raises an exception in Java. Exchange-argument comparators like `t_i * w_j < t_j * w_i` are fine because they compare a single real ratio `t / w`, which is a total preorder.
</Callout>

## Code: the scheduling greedy

```cpp
sort(jobs.begin(), jobs.end(), [](const auto& x, const auto& y) {
    return x.t * y.w < y.t * x.w;       // x.t / x.w < y.t / y.w, no floats

long long time = 0, cost = 0;
```

```python
from functools import cmp_to_key
jobs.sort(key=cmp_to_key(lambda x, y: x[0] * y[1] - y[0] * x[1]))

for t, w in jobs:
    time += t
    cost += w * time
```

## Pitfalls

<Callout type="pitfall" title="Exchange argument mistakes">
1. **Swapping non-adjacent items** without checking that the items in between are not affected.
2. **Forgetting that the rule must be transitive.** If your "better than" relation can cycle, no sorted order exists and the proof silently breaks.
3. **Optimising the wrong objective:** EDF is for maximum lateness, Smith's rule for weighted completion time, and the Moore-Hodgson algorithm for the number of late jobs. They are different problems with different rules.
4. **Overflow:** products `t * w` and the final cost can exceed 32 bits (and 53 bits in JavaScript). Use 64-bit integers or BigInt.
5. **Floating point ratios** `t / w` for sorting. Equal ratios may compare unequal; prefer integer cross-multiplication.
</Callout>
