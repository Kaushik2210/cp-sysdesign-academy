## Intuition

A **trie** (pronounced "try", from re*trie*val; also called a prefix tree) stores a set of strings so that strings with a **common prefix share the same path**. The root is the empty prefix; each edge is labelled with a letter; walking from the root along a string's letters reaches a node that stands for that prefix. A word is marked at the node where it ends.

That sharing is the whole point. A hash set answers "is this exact word present?"; a trie answers prefix questions with the same effort:

- how many words start with `"car"`? (count the words that pass through that node),
- what are the words with this prefix? (walk the subtree),
- what is the longest stored prefix of this string?

Every operation costs `O(length of the string)`, **independent of how many strings are stored**.

## Definition

Each node has up to `A` children, one per letter (`A = 26` for lowercase letters, `A = 2` for bits). Store the children either as an array of `A` indices (fast, memory `A` per node) or as a map (memory proportional to the real children, slower).

```text
insert(w):  node = root
            for each letter c of w:
                if node has no child c: create it
                node = child c;  passes[node] += 1
            ends[node] += 1
search(p):  walk the letters of p; fail if a child is missing
```

Memory is at most the **total length of all strings** plus one node. Strings with shared prefixes use less (see the experiment).

### Typical string problems

| question | what to store in the nodes |
| --- | --- |
| how many words have prefix `p` | `passes` counter |
| is `w` stored / how many copies | `ends` counter |
| autocomplete: the most frequent word with prefix `p` | the best word below each node |
| longest common prefix of a set of words | walk down while a node has exactly one child and is not a word end |
| does any word equal a prefix of this text position | walk the text from that position |

## Bits instead of letters: the maximum XOR trie

A number below `2^30` is a string of 30 **bits**. Insert each number's bits from the **most significant** to the least significant into a trie with 2 children per node. Now the question "which stored number gives the **largest `a xor x`**?" becomes a greedy walk:

- The highest bit of the xor dominates everything below it: a result with bit 29 set beats any result without it, whatever the lower bits are.
- So at each level, look at the bit of `x`. If the current node has a child with the **opposite** bit, go there (this bit of the xor becomes 1). Otherwise you must follow the same bit (the xor bit is 0).

After 30 steps you have the maximising partner, and `best` is the xor value. One query costs 30 steps whatever `n` is. The same trie answers:

| query | variation |
| --- | --- |
| maximum `a_i xor a_j` over all pairs | insert numbers one by one and query before inserting |
| **minimum** xor with `x` | prefer the **same** bit instead of the opposite |
| maximum xor of a **subarray** | prefix xors `p_0 .. p_n`; the subarray xor is `p_i xor p_j`, so it is a maximum pair xor over prefixes (CSES Maximum Xor Subarray) |
| count of numbers with `a xor x < k` | walk `x` and `k` together, adding the `passes` of subtrees that are entirely below `k` |
| xor queries with deletions | keep `passes` counters and delete by decrementing |

```python
B = 30
trie = [[-1, -1]]                     # trie[node][bit] = child index or -1
def insert(v):
    node = 0
    for b in range(B - 1, -1, -1):
        bit = (v >> b) & 1
        if trie[node][bit] == -1:
            trie.append([-1, -1])
            trie[node][bit] = len(trie) - 1
        node = trie[node][bit]

def max_xor(x):
    node, best = 0, 0
    for b in range(B - 1, -1, -1):
        bit = (x >> b) & 1
        if trie[node][bit ^ 1] != -1:         # the opposite bit makes this bit of the xor a 1
            best |= 1 << b
            node = trie[node][bit ^ 1]
        else:
            node = trie[node][bit]
    return best
```

What it shows:

- With **2,000 random 30-bit numbers and 2,000 queries**, the trie's answers equal the brute force's for every query. Each query takes **30 steps**, against 2,000 comparisons for the brute force; with `10^5` numbers the gap would be `30` against `100,000`.
- The trie has **40,336 nodes**, below the worst case of `30 * n + 1 = 60,001`: random numbers share their first few bits. Inserting 2,000 numbers **below 256** needs only **533 nodes**, because all those numbers share their 22 leading zero bits and the top of the trie is stored once.
- A small **word trie** of 9 words uses **15 nodes for 33 letters**, and the prefix counts come straight from the nodes: **4 words** start with `car`, **4** with `do`, and **0** with `cab` or `x`.

The counts are from one seeded run; the equality with brute force is the correctness evidence.

## Memory and implementation

- **Array of children** per node: fastest, `A` integers per node. For 26 letters and `10^6` total letters that is 26 million integers (about 100 MB in 32-bit): often too much; for bits it is tiny.
- **Map or sorted list of children**: less memory per node, slower constant factor.
- **Compressed tries** (radix trees) merge chains of single-child nodes into one edge; **suffix automata and Aho-Corasick** (next lessons) build on tries.
- Allocate the node arrays **once** at the maximum size (`n * B + 2` nodes) instead of growing per insertion; in garbage-collected languages avoid one object per node.
- For **deletions** keep a `passes` counter per node and just decrement; you do not have to free nodes.

## Pitfalls

1. **Inserting bits from the wrong end.** The greedy argument needs the **most significant bit first**.
2. **Wrong number of levels.** If values can reach `2^31 - 1` use 31 levels (or 32 for unsigned); otherwise high bits are ignored silently.
3. **Querying an empty trie.** The walk then has no child to follow; guarantee at least one inserted number, or handle it.
4. **Forgetting the sign.** Negative numbers have a different bit pattern; shift them (add an offset) or restrict to non-negative values.
5. **Memory blow-up** with 26-way array children on very large inputs.
6. **Confusing prefix with whole-word membership.** Searching `"car"` succeeds if `"card"` is stored; check `ends[node] > 0` for membership.
7. **Resetting between test cases** by reallocating huge arrays each time; reuse and clear only the nodes you used.
8. **Using a trie when sorting or hashing is enough.** For a single offline question about equal strings, a hash map is simpler.
