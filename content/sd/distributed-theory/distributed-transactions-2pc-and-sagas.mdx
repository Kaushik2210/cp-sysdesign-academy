## Intuition

Placing an order touches three services: reserve stock, charge the card, create the shipment. Each has its own database. You want all-or-nothing, but there is no single database to wrap in `BEGIN ... COMMIT`. Two families of answer exist: make the participants **agree atomically** (two-phase commit) or **undo** the earlier steps when a later one fails (saga).

## Two-phase commit (2PC)

A **coordinator** drives participants:

1. **Prepare**: ask each participant "can you commit?" Each makes the change durable but not visible, holds its locks and votes yes or no.
2. **Commit or abort**: if every vote is yes, tell everyone to commit; otherwise tell everyone to abort.

Once a participant votes yes it has promised to commit if told to and **cannot unilaterally abort**.

### The blocking problem

If the coordinator crashes after participants vote yes but before sending the decision, participants are **in doubt**: they hold locks and cannot decide alone, because the coordinator may already have told another participant to commit. They block until it recovers. Consequences:

- Locks held across network round trips cut throughput and raise latency.
- A single coordinator failure can stall many rows or tables.
- Participants must support the protocol (XA, or the database's native distributed transaction).

2PC is used inside some databases (Spanner runs 2PC across Paxos groups, whose replicated coordinators avoid permanent blocking) and for XA between a database and a broker. It is a poor fit across independently owned microservices over unreliable networks.

## Sagas

A **saga** is a sequence of local transactions. Each step commits on its own. If step k fails, the saga runs **compensating transactions** for steps k-1 down to 1, in reverse order.

- **Orchestration**: a central saga coordinator tells each service what to do and tracks state. Easier to reason about and monitor; the orchestrator is one more component to run.
- **Choreography**: each service reacts to events and emits new ones. No central point, but the flow is spread across services and is hard to trace and to change.

```python
def run_saga(steps, fail_at=None):
    """steps: list of (name, do, undo). fail_at: name of the step that fails."""
    log, done = [], []
    for name, do, undo in steps:
        if name == fail_at:
            log.append(f"FAIL {name}")
            for n, u in reversed(done):
                log.append(f"UNDO {n}")
            return log
        log.append(f"DO {name}")
        done.append((name, undo))
    log.append("COMMITTED")
    return log

steps = [("reserve_stock", 1, 1), ("charge_card", 1, 1), ("create_shipment", 1, 1)]
print(run_saga(steps))
print(run_saga(steps, fail_at="create_shipment"))
```

### What sagas give up

Sagas are **atomic in outcome (eventually) but not isolated**. Other requests can see the intermediate state (stock reserved, card not yet charged). Countermeasures:

- **Semantic locks**: mark records as `PENDING` so others know they are mid-saga.
- **Commutative updates** that do not care about order.
- **Reread values** before acting, and **versions** to detect change.
- Order the steps so the hard-to-undo one (sending an email, shipping) runs **last**.

Compensations must be **idempotent** and must be safe to run even if the forward step did not complete (the failure may have happened after the effect but before the ack). Some actions cannot be compensated (an email sent), so compensate semantically (send a correction) or avoid them until the end.

## Making steps reliable: outbox and idempotency

A service must update its database **and** publish an event atomically. Writing the DB row then calling the broker can crash between the two. The **transactional outbox** fixes it: write the business row and an `outbox` row in the same local transaction; a relay (polling or change-data-capture) publishes outbox rows to the broker and marks them sent. Delivery is at-least-once, so consumers deduplicate using an **idempotency key** (the saga id plus step).

## Worked example

Checkout saga: `reserve_stock` → `authorise_payment` → `create_shipment` → `capture_payment`.

- Authorising rather than charging first gives a cheap, reversible hold; capture comes last.
- If `create_shipment` fails: void the authorisation, release the stock. Both operations are idempotent and keyed by order id.
- The orchestrator persists its state after each step. After a crash it reloads state and resumes or compensates. Each service call carries the idempotency key `order-123:authorise`, so retries do not double-charge.
- Timeouts: if the payment service does not answer, the orchestrator retries with the same key; after the retry budget it compensates and marks the order failed, and a reconciliation job later checks for stuck payments.

## Pitfalls

- Using 2PC across public-network microservices and being surprised by lock waits.
- Compensations that are not idempotent, or that assume the forward step finished.
- Publishing events outside the database transaction (dual write).
- Doing the irreversible step early in the saga.
- No timeout or dead-letter path for a saga stuck mid-way.

## What would you choose and why?

A travel site books a flight, a hotel and a car from three independent suppliers whose APIs allow cancellation within 24 hours. Design the saga: what order do you run the steps, which are compensations, and what do you tell the user while it is in progress?
