## 1. Clarify requirements

**Functional**
- A merchant's checkout asks us to charge a customer's card or wallet for an amount.
- Support authorise then capture, refunds, and payouts to merchants.
- Report payment status; send webhooks to merchants.

**Non-functional**
- **Correctness above all**: never charge twice, never lose a charge, balances must always add up. Availability and latency matter, but a slow correct answer beats a fast wrong one.
- Fully auditable; money records are never updated in place.
- External PSPs (card networks, banks) are slow (hundreds of ms to seconds) and unreliable, with their own timeouts and duplicate semantics.
- Assume 1M payments per day, peak 10x average.

We integrate with a payment service provider (PSP) rather than talking to card networks ourselves, and we never store raw card numbers (tokens only, PCI DSS scope kept small).

## 2. Estimate

- 1M/day ≈ **12 payments/s**, peak about 120/s. This is a **low-throughput, high-correctness** system: you scale for safety, not QPS.
- Each payment creates about 5 ledger rows and a few events: ~5M rows/day, ~2 B rows over a year at 1 KB ≈ 2 TB/year. Easily a sharded relational database.

## 3. API and idempotency

```
POST /v1/payments
Idempotency-Key: 6f1c...      (required)
{ "amount": 4999, "currency": "USD", "paymentMethodToken": "...", "orderId": "..." }
-> 201 { id, status: "pending" | "succeeded" | "failed" }
```

Amounts are **integers in minor units** (cents), never floats. The `Idempotency-Key` makes retries safe: the first request stores `(key, request hash, response)` atomically with its effects; a retry with the same key returns the stored response; the same key with a different body is rejected with an error.

## 4. The ledger

Record every movement as **double-entry** rows: each transaction has debit and credit entries that sum to zero. Balances are derived from entries (and cached), entries are **append-only**, and corrections are new compensating entries, never edits.

```python
class Ledger:
    def __init__(self): self.entries, self.keys, self.bal = [], {}, {}
    def transfer(self, key, src, dst, amt):
        if key in self.keys: return self.keys[key]          # idempotent replay
        if self.bal.get(src, 0) < amt: return "insufficient"
        self.entries += [(src, -amt), (dst, amt)]            # double entry
        self.bal[src] = self.bal.get(src, 0) - amt
        self.bal[dst] = self.bal.get(dst, 0) + amt
        self.keys[key] = "ok"; return "ok"

L = Ledger(); L.bal["alice"] = 100
print(L.transfer("k1", "alice", "bob", 30), L.transfer("k1", "alice", "bob", 30), L.bal)
print(sum(a for _, a in L.entries))   # entries always sum to 0
```

In production, the key check, balance check and entry inserts happen in **one database transaction** (serializable, or a unique constraint on the idempotency key plus row locks on the accounts). That is what the toy shows in miniature.

## 5. Payment flow and state machine

States: `created → authorised → captured → (refunded)` with failure branches `declined`, `expired`, `failed`. Transitions are validated (no refund before capture) and every change is recorded as an event.

## 6. The hard problem: unknown outcomes

The call to the PSP times out. Did the charge happen? You cannot know. Rules:

1. **Never assume failure on a timeout** and never blindly retry with a new key.
2. Record the payment as `pending` / `unknown` and persist the PSP idempotency key before the call.
3. Retry with the **same** key (safe), or query the PSP by our reference.
4. A background job resolves stuck pending payments; the reconciliation job is the safety net.
5. Only mark `failed` when the PSP definitively says so.

This is the saga/outbox/idempotency toolkit of the previous modules applied where mistakes cost real money.

## 7. Deep dives

**Exactly-once effect.** Impossible to guarantee delivery exactly once; achieve it with at-least-once delivery plus idempotent consumers everywhere (API, PSP call, webhook, ledger posting).

**Concurrency on accounts.** Two payouts from the same balance must not overdraw: use row locks or optimistic versioning, and keep balance checks in the same transaction as the posting. Hot accounts (a big merchant) serialise; mitigate with sub-accounts or batching.

**Sharding.** Shard by merchant or account id so each transaction touches one shard; cross-shard transfers use a saga with a holding account.

**Refunds and chargebacks.** New ledger entries referencing the original; limits so total refunds never exceed the capture.

**Security and compliance.** Tokenise card data at the edge, encrypt at rest, restrict access, audit all reads of sensitive data, and keep a minimal PCI scope. Never log PANs or CVVs.

**Webhooks.** Sign payloads (HMAC), retry with exponential backoff for days, and let merchants fetch the current status because webhooks may be late or duplicated.

## 8. Bottlenecks and trade-offs

- Consistency vs availability: choose consistency for the ledger (CP), accept that during a database failover some requests fail and clients retry safely.
- Latency: the PSP dominates. Show "processing" states and push results by webhook; don't hold HTTP connections for slow flows.
- Multi-region: single-writer ledger region with synchronous standby; read replicas elsewhere for dashboards.
- Observability: payment success rate by PSP, unknown-outcome count and age, reconciliation mismatches, and ledger balance invariants checked continuously.

## Pitfalls

- Using floats for money.
- Updating balances in place without an append-only ledger.
- Retrying payments with a fresh idempotency key.
- Treating a timeout as a failure.
- Publishing events outside the transaction.
- No reconciliation.

## What would you choose and why?

You must support split payments (one customer payment paid out to three sellers, with a platform fee). Sketch the ledger accounts and entries, decide what happens if one payout fails, and say when funds become available to each seller.
