## 1. Clarify requirements

**Functional**
- As the user types a prefix, show the top 5 to 10 suggested completions.
- Suggestions are ranked by popularity (and optionally recency and personalisation).
- New trending queries should appear within minutes to hours; offensive or blocked terms must never appear.

**Non-functional**
- Very low latency: suggestions must arrive in under about 100 ms end to end, or the user has typed past them.
- High availability; slightly stale suggestions are acceptable (eventual consistency).
- Assume 10B searches/day and an average query length of 20 characters.

## 2. Estimate

- Each search types ~20 characters; with debouncing the client sends maybe 5 suggestion requests per search. 10B × 5 = 50B/day ≈ **580,000 requests/s**, peak well over 1M/s. This is a **read-heavy, latency-critical** workload.
- Distinct queries: assume 1B distinct strings ever seen, but a few tens of millions account for nearly all traffic (a long-tail distribution).
- Storage for the suggestion data: 100M distinct popular queries × ~30 bytes plus a score ≈ **3 to 5 GB**. It fits in memory on a single machine; the problem is request rate and freshness, not size.

## 3. API

```
GET /v1/suggest?q=app&limit=5&lang=en
-> { "q": "app", "suggestions": ["apple", "app store", "apple watch", ...] }
```

Cacheable: the response depends only on the prefix (plus coarse locale), so responses carry short `Cache-Control` headers and are served by the CDN or browser cache whenever possible.

## 4. Data structure: a trie with precomputed top-k

A trie stores strings by prefix: each node is a prefix. A naive approach walks the whole subtree under a prefix to find the best completions, which for the prefix `a` is huge. Instead, **store the top k suggestions at every node**, so a lookup is one walk of `len(prefix)` steps and returns the list directly.

```python
import heapq
class Node:
    __slots__ = ("kids", "top")
    def __init__(self): self.kids, self.top = {}, []   # top: list of (score, word)
class Trie:
    def __init__(self, k=3): self.root, self.k = Node(), k
    def add(self, word, score):
        n = self.root
        for ch in word:
            n = n.kids.setdefault(ch, Node())
            cand = [t for t in n.top if t[1] != word] + [(score, word)]
            n.top = heapq.nlargest(self.k, cand)       # keep only the best k
    def suggest(self, prefix):
        n = self.root
        for ch in prefix:
            if ch not in n.kids: return []
            n = n.kids[ch]
        return [w for s, w in sorted(n.top, reverse=True)]
t = Trie()
for w, s in [("apple", 50), ("app", 90), ("apply", 20), ("apt", 70), ("banana", 10)]:
    t.add(w, s)
print(t.suggest("ap"), t.suggest("app"), t.suggest("b"), t.suggest("z"))
# ['app', 'apt', 'apple'] ['app', 'apple', 'apply'] ['banana'] []
```

<Complexity time="O(L) per lookup, O(L·k) per insert" space="O(total characters × k) with top-k lists" note="L = prefix length; trading memory for lookup speed" />

Optimisations: compress single-child chains (radix tree), store word ids instead of strings in the top-k lists, cap depth (do not index beyond about 30 characters), and keep the whole structure in memory, built offline and loaded read-only.

**Serving.** Suggestion servers load an immutable snapshot at startup and swap atomically to a newer one (double-buffer). No locks on the read path. Replicate for throughput; shard only if the data outgrows memory.

**Sharding when needed.** Partition by the first one or two characters of the prefix, or by hash of a short prefix. Hot prefixes (`a`, `s`) are uneven, so balance by measured traffic, not by alphabet, and cache the shortest prefixes aggressively since they are the most requested and the least personalised.

## 6. Ranking, freshness, and safety

- **Score** = frequency over a time window with **exponential decay**, so last week's fad fades: `score = sum(count_in_bucket × decay^(age))`.
- **Trending**: a streaming job (windowed counts over minutes) flags queries whose recent rate far exceeds their baseline and merges them into the served list ahead of the next full rebuild.
- **Personalisation**: blend a user's recent searches or locale with the global list at request time; keep the global path cached and add a small personal layer.
- **Safety**: a block list and policy filters are applied at build time **and** at serve time (a fast set lookup) so emergency removals do not wait for a rebuild. Do not suggest queries containing private data (emails, ids): minimum-frequency thresholds from many distinct users guard against leaking one person's query.
- **Typos**: fuzzy matching via edit-distance bounded search or n-gram indexes; run it as a fallback only when exact prefixes return nothing, because it is far more expensive.

## 7. Bottlenecks and trade-offs

- **Freshness vs cost:** continuous trie updates complicate concurrency; periodic immutable snapshots plus a small trending overlay are simpler and fast.
- **Memory vs latency:** top-k at each node uses memory (k copies per path) but makes lookups constant-time per character.
- **Consistency:** different replicas may serve different snapshot versions for a few minutes; acceptable.
- **Availability:** if the service is down, the search box still works; suggestions degrade silently. Autocomplete must never block search.
- **Load:** debounce, cache, and cancel in-flight requests on the client, so the typical keystroke costs nothing.

## Pitfalls

- Walking a subtree per request instead of storing top-k.
- Updating the live trie in place under heavy read traffic.
- Ranking by all-time counts only (no recency).
- Not filtering abusive, private or blocked terms at serve time.
- Sending a request for every keystroke with no debounce or cancellation.
- Making search depend on autocomplete availability.
