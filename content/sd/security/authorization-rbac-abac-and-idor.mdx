## Intuition

**Authentication** answers *who are you?* **Authorization** answers *what are you allowed to do?* A system can get the first perfectly right and still leak everything if it forgets the second. The most common real-world breach pattern is not a clever exploit: it is a logged-in user changing an id in a URL and receiving **someone else's data**, because the server checked that the caller was authenticated but never checked that the order belonged to them.

Authorization is a **design** problem, not a feature you add at the end. Where is each decision made, on what information, and what happens when the rule is missing? The safe answer to the last question is **deny by default**.

## Models

- **ACL (access control list):** each object lists who may do what. Simple, but hard to audit at scale.
- **RBAC (role-based):** permissions attach to **roles** (`viewer`, `editor`, `admin`) and users get roles. Easy to understand and administer; becomes a mess when roles multiply ("regional-editor-for-finance-except-reports").
- **ABAC (attribute-based):** decisions are computed from **attributes** of the user, the resource, the action and the context (department, document sensitivity, time, location). Expressive, harder to reason about and test.
- **ReBAC (relationship-based):** decisions follow **relationships** in a graph: *alice is a member of team T; T is an editor of folder F; document D is in F; so alice can edit D.* This is how Google Docs-style sharing works (Google's Zanzibar, open-source systems such as SpiceDB and OpenFGA).
- **Policy as code:** rules are written in a dedicated language (Rego for Open Policy Agent, Cedar) evaluated by a policy engine, so that they are versioned, reviewed and tested.

Most systems combine them: roles for coarse permissions, attributes and relationships for the fine-grained ones, and **ownership checks** on every object.

## Where to enforce

- **Edge / gateway:** coarse checks (is the token valid, does it have the scope for this route, rate limits). Cheap and central, but it does not know your data.
- **Service layer:** the **real** decision, with the object in hand: "may *this user* read *this order*?"
- **Data layer:** defence in depth, such as **row-level security** in the database, tenant ids on every query, or per-tenant schemas, so that a forgotten check in code does not expose everything.

Rules that prevent most disasters:

1. **Deny by default.** A route or field with no rule is closed.
2. **Check on the server, on every request,** for every object, never in the UI only.
3. **Object-level authorization:** every endpoint that takes an id must verify the caller may access *that* object (BOLA/IDOR, number one on the OWASP API Security list).
4. **Least privilege:** tokens, service accounts and roles get only the scopes they need, for the shortest time.
5. **Do not trust client-supplied identity or role fields** (`userId`, `isAdmin` in a request body).
6. **Return the same response for "does not exist" and "not yours"** (usually 404) so ids cannot be probed.
7. **Beware the confused deputy:** a privileged service that acts on a user's request must check the user's rights, not its own.
8. **Log decisions** (who, what, allow or deny, why) for audit and detection.

## Code: the missing ownership check, and a policy decision

Part 1 builds 1,000 orders owned by 100 users and attacks the "get order" endpoint as user 7 by walking ids 1 to 1,000, with and without an ownership check; it also tries a million random 128-bit identifiers. Part 2 evaluates a small policy: role-based permissions combined with an attribute rule (confidential documents stay in their department) and an ownership rule for deletion.

### Measured results

Running this exact program with Python 3.13 produced:

| endpoint (attacker is user 7 and owns 13 orders) | other users' orders readable |
| --- | --- |
| no ownership check | **987** |
| ownership check | 0 |
| guessing random 128-bit ids, no check | 0 hits in 1,000,000 guesses |

| user (role, department) | read d1 (sales) | read d2 (hr, confidential) | write d1 | write d2 | delete d1 | delete d2 |
| --- | --- | --- | --- | --- | --- | --- |
| alice (editor, sales) | allow | **deny** (department rule) | allow | deny | deny (not the owner) | deny |
| carol (viewer, hr) | allow | allow | deny (role) | deny | deny | deny |
| root (admin, it) | allow | allow | allow | allow | allow | allow |

Without the check, one logged-in user read **987 of the other users' 1,000 orders** (everything except their own 13) just by counting. With a single ownership comparison, none. Random 128-bit identifiers made blind guessing hopeless (0 hits in a million tries), which is a useful extra layer, but any id that leaks (in a URL, a log, an email, a referrer) is still a key to the data, so unguessable ids are **not** an authorization mechanism. The policy table shows the layers composing: `carol` can read the confidential HR document because she is in HR, `alice` cannot even though her role may read documents, and only owners or admins may delete.

## Multi-tenancy

For SaaS, every request carries a **tenant** and every query must be constrained by it. Defences, from weakest to strongest: tenant id added by each developer to each query (easy to forget), a data-access layer that injects it automatically, **row-level security** enforced by the database, separate schemas or databases per tenant. Test it: a cross-tenant access attempt should be part of your automated test suite for every endpoint.

## Pitfalls

- Authenticating the request but not checking the object (BOLA / IDOR).
- Hiding buttons in the UI and calling that authorization.
- Trusting `role`, `isAdmin` or `userId` supplied by the client.
- Allow-lists that fail open on a missing rule or an exception.
- Checking the permission at the start of a long workflow, not when the action is performed (time-of-check to time-of-use).
- Broken function-level authorization: admin endpoints reachable by any logged-in user because only the menu was hidden.
- Mass assignment: letting a request body set fields (`role`, `owner`) that the user must not control.
- Permissions that never expire: users keep roles after changing teams.
