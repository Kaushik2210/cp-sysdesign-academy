## Intuition

Data is at risk in three states: **in transit** (crossing a network), **at rest** (on disks and backups) and **in use** (in memory). Cryptography protects the first two cheaply; the hard part is **key management**: whoever holds the key holds the data, so the real security question is "where do keys live, who can use them, and how do we rotate or revoke them".

## Cryptography in four sentences

- **Hashing** (SHA-256): one-way fingerprint; for integrity and (with salts and slow functions) passwords. Not encryption.
- **Symmetric encryption** (AES-GCM, ChaCha20-Poly1305): one shared key encrypts and decrypts; fast; use **authenticated** modes (AEAD) so tampering is detected.
- **Asymmetric encryption / signatures** (RSA, ECDSA, Ed25519, X25519): a public/private key pair; slower; used to exchange keys and to sign.
- **Rule one:** never invent your own algorithms or protocols; use vetted libraries (libsodium, your language's standard crypto, cloud KMS) with safe defaults.

## Encryption in transit: TLS

**TLS** gives confidentiality, integrity and server authentication on a connection (HTTPS is HTTP over TLS).

TLS 1.3 handshake, simplified: the client says hello with supported ciphers and a key share; the server replies with its key share and its **certificate**; both derive session keys using an ephemeral Diffie-Hellman exchange (so past traffic stays secret even if the server key later leaks: **forward secrecy**); the client **verifies the certificate chain** up to a trusted root CA and checks the hostname. Application data then flows encrypted with a fast symmetric cipher. TLS 1.3 needs one round trip (and zero for resumed sessions).

- **Certificates** bind a public key to a name, signed by a certificate authority. Automate issuance and renewal (ACME / Let's Encrypt, cloud certificate managers); expired certificates are a classic outage cause.
- **Terminate TLS** at the load balancer or edge for simplicity, but **re-encrypt to backends** (or use a mesh) so internal traffic is not plaintext. Zero trust assumes the internal network is hostile.
- **mTLS (mutual TLS):** the client also presents a certificate, so both sides authenticate. Standard for service-to-service traffic, usually provided by a service mesh with short-lived certificates rotated automatically.
- **HSTS** tells browsers to always use HTTPS; modern config only (TLS 1.2+, disable old ciphers).
- TLS protects the channel, not the endpoints: a compromised server still sees plaintext.

## Encryption at rest and envelope encryption

Encrypt disks, databases, object stores and backups. Cloud providers offer this by default, which protects against stolen disks and some insider risk, but not against an attacker who gets valid application credentials (the storage layer decrypts for them). Use **application-level (field) encryption** for the most sensitive fields (card numbers, national ids) so even a database administrator or a SQL injection cannot read them.

### Envelope encryption

Encrypting everything directly with one master key from a KMS would send all data to the KMS and make rotation painful. Instead:

1. A **KMS/HSM** holds a **key-encryption key (KEK)** that never leaves it.
2. For each object (or each record, file or tenant) generate a random **data-encryption key (DEK)**; encrypt the data locally with the DEK.
3. Ask the KMS to encrypt the DEK with the KEK; store the **wrapped DEK** next to the ciphertext.
4. To read: send the wrapped DEK to the KMS to unwrap (access-controlled and logged), then decrypt locally.

Benefits: only small keys cross the network, rotation of the KEK re-wraps DEKs without re-encrypting data, per-tenant DEKs allow **crypto-shredding** (delete the key to make a tenant's data unrecoverable), and every key use is auditable.

## Secrets management

Secrets: database passwords, API keys, signing keys, certificates.

- **Never** commit them to git, bake them into images, or put them in plain environment files on shared machines. Scan repositories and CI logs for leaked secrets, and rotate immediately if one leaks.
- Use a **secrets manager** (Vault, AWS Secrets Manager, GCP Secret Manager, Kubernetes secrets backed by KMS encryption) with fine-grained access and audit logs.
- Prefer **identity over secrets**: a workload authenticates with its platform identity (IAM role, workload identity) and fetches short-lived credentials, so there is no long-lived key to steal.
- Prefer **short-lived, dynamically issued** credentials (database users created per service with a TTL) and **rotation** on a schedule and on suspicion of compromise. Design for rotation: support two valid keys at once during the changeover.
- Separate secrets per environment and per service; least privilege on who can read them.
- Do not log secrets; redact tokens, passwords and personal data.

## Key and certificate lifecycle

Generate → store (HSM/KMS) → distribute → use → **rotate** → revoke → destroy. Plan rotation before launch: tokens signed with a key need a `kid` (key id) in the header so verifiers can hold several public keys during overlap (publish them via JWKS). Keep a documented, tested procedure for emergency revocation.

## Data protection beyond encryption

- **Classify data** (public, internal, confidential, regulated) and handle each class accordingly.
- **Minimise:** do not collect or keep what you do not need; set retention limits; delete on request (GDPR/CCPA).
- **Tokenisation:** replace a card number with a random token from a vault so most systems never touch real card data (keeps PCI scope small).
- **Masking and redaction** in logs, analytics and lower environments; never copy production data into development.
- **Backups** are copies of your data: encrypt them, restrict access and test restores.
- **Integrity:** sign artifacts and releases, verify checksums, and protect the supply chain.

## Worked example

A health-records platform stores documents in object storage. Each tenant has a DEK wrapped by a KMS key dedicated to that tenant; documents are AES-GCM encrypted by the app before upload. Offboarding a customer deletes the tenant key, making the data unrecoverable (crypto-shredding), which is documented in the privacy policy. Services get database credentials from Vault with a one-hour TTL via workload identity; certificates are issued by an internal CA through ACME and rotate every 24 hours; edge TLS uses managed certificates with HSTS. Access to unwrap keys is limited to the document service and alerts fire on unusual unwrap rates.

## Pitfalls

- "Encrypted at rest" treated as complete protection when the app can read everything anyway.
- Hard-coded keys, shared keys across environments, secrets in git history.
- No rotation plan, so a leaked key stays valid for years.
- Disabling certificate validation "to make it work".
- Plain HTTP between internal services.
- Home-grown crypto, ECB mode, reusing nonces with AES-GCM, using hashes as encryption.
- Unmonitored KMS access.

## What would you choose and why?

A startup stores customers' government ids. They propose encrypting the whole database disk and calling it done. Which additional controls (field encryption, tokenisation, access paths, logging, retention) do you add, in what order, and what would an attacker with application-level SQL injection still be able to read afterwards?
