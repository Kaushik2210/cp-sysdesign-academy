## Intuition

HTTP forgets you between requests. After you sign in, the server needs a way to recognise your next request without asking for the password again. The answer is always some **credential that the client presents on every request**: a **session identifier** in a cookie, or a **token** in an `Authorization` header. Whoever holds it **is** you, as far as the server can tell. So the design questions are about this thing:

- What is it, and what does the server have to remember to check it?
- How long does it live, and how do we **take it back** if it is stolen?
- Where does the client keep it, and what protects it there?

## Two designs

**Server-side sessions (opaque identifiers).** On login the server creates a random, unguessable id, stores `session_id -> user, expiry, attributes` in a store (memory, Redis, a database) and sends the id in a cookie. Each request is a lookup. Revocation is trivial: delete the record. The cost is a lookup per request and a shared store when you run many servers (the stateless-services lesson covers this).

**Self-contained tokens (such as JWT).** The server issues a signed statement: *"user alice, role user, expires at 12:05"*. Any service that knows the verification key can check the signature and trust the contents **without a lookup**. That is convenient for microservices and third parties. The cost: you cannot easily **revoke** a token before it expires, and everything in it is visible to the client (signed, not encrypted, unless you use JWE).

A **JWT** has three base64url parts, `header.payload.signature`. The header names the algorithm (`HS256` for a shared-secret HMAC, `RS256` or `ES256` for a public-key signature), the payload carries *claims* (`sub`, `exp`, `aud`, `iss`, roles), and the signature covers the first two parts.

## OAuth 2.0 and OpenID Connect in one paragraph

**OAuth 2.0** lets an application act on a user's behalf without holding their password: the user signs in at the *authorization server*, which issues an **access token** (short-lived, sent to APIs) and optionally a **refresh token** (long-lived, used only against the authorization server to get new access tokens). For browser and mobile apps use the **authorization code flow with PKCE**. **OpenID Connect (OIDC)** adds an **ID token** (a JWT that says who the user is) on top, and is what "Sign in with Google" uses. The pattern **short-lived access token + revocable refresh token** is the standard compromise between the two designs above.

## Cookies versus headers

| where the credential lives | protects against | exposed to |
| --- | --- | --- |
| Cookie with `HttpOnly; Secure; SameSite=Lax` | script access (XSS cannot read it), network sniffing, most cross-site requests | **CSRF** if not for SameSite or anti-CSRF tokens |
| `Authorization: Bearer` header, token in memory | CSRF (the browser does not add it automatically) | XSS can use or steal it; harder to keep across reloads |
| Token in `localStorage` | nothing in particular | any script on the page (XSS) can read it |

A common safe default for a web app: an opaque session id (or a short-lived token) in an `HttpOnly`, `Secure`, `SameSite` cookie, plus CSRF defences. For mobile and service-to-service calls, bearer tokens with short lifetimes.

## Code: forging, flawed verifiers and revocation

The program signs a token with HMAC-SHA256 and then attacks it five ways against two verifiers. The **flawed** verifier believes the algorithm named in the *untrusted* token header (a real class of bugs: the `alg: none` attack). The **strict** verifier fixes the algorithm on the server, always checks the signature and enforces expiry. The second part simulates a stolen token that is revoked 10 minutes after the theft, for three token lifetimes.

        good = b64(hmac.new(SECRET, f"{header}.{body}".encode(), hashlib.sha256).digest())

### Measured results

Running this exact program with Python 3.13 produced:

| attack | flawed verifier | strict verifier |
| --- | --- | --- |
| valid token | accepted (user) | accepted (user) |
| role changed to admin, old signature | rejected | rejected |
| `alg: none`, no signature | **ACCEPTED as admin** | rejected |
| expired token | rejected | rejected |
| signature stripped | rejected | rejected |

| token lifetime | average minutes the thief can still use it after revocation (no blocklist) | with a blocklist check |
| --- | --- | --- |
| 5 minutes | 0.0 | 0.0 |
| 60 minutes | 20.8 | 0.0 |
| 24 hours (1,440 minutes) | 712.2 | 0.0 |

The signature protects the contents: changing the role invalidates it in both verifiers. But the flawed verifier let an attacker **skip the signature altogether** simply by declaring `alg: none`, a complete authentication bypass in one field, because the verifier trusted the attacker-controlled header. The fix is a rule, not a trick: **the server decides the algorithm and the key**, never the token. The second table shows the cost of self-contained tokens: with a 24-hour lifetime a stolen token stays usable for about 12 hours *after* you revoke it (the closed form is `(T - 10)^2 / (2T)` minutes for lifetime `T`), whereas a 5-minute lifetime leaves no window at all for a 10-minute response time. Hence **short-lived access tokens**, refresh tokens that the server *can* revoke, and a blocklist (or token version per user) checked on sensitive operations. The model assumes the theft happens at a uniformly random time in the token's life.

## Rules for JWTs in practice

- Fix the allowed algorithms on the server; reject `none` and unexpected algorithms (and never let a public key be treated as an HMAC secret, the other classic confusion).
- Validate `exp`, `nbf`, `iss` and **`aud`** (the token must be meant for *this* service), allowing small clock skew.
- Keep access tokens short (minutes), and keep secrets out of the payload: it is readable by anyone holding the token.
- Prefer asymmetric signatures (`RS256`, `ES256`) when many services verify tokens: they hold only the public key; publish it at a JWKS endpoint and rotate keys with `kid`.
- Do not use JWTs as a general-purpose session store; if you need instant revocation or lots of mutable state, use server-side sessions.
- Store refresh tokens securely, rotate them on use, and detect reuse (a reused refresh token means theft).

## Pitfalls

- Trusting any field of the token header, especially `alg`.
- Long-lived JWTs with no revocation story.
- Putting personal data or secrets in the payload.
- Not checking `aud` and `iss`, so a token issued for one service works on another.
- Putting tokens in URLs (they end up in logs and referrer headers).
- Storing tokens in `localStorage` in an application that may suffer XSS.
- Comparing signatures with `==` instead of a constant-time comparison.
- Using the same signing key for years; no rotation plan.
