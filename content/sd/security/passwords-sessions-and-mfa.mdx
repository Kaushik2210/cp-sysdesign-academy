## Intuition

**Authentication** answers "who is this?". Almost every system answers it with a secret the user knows, and almost every system will, sooner or later, have its user database copied by someone who should not have it. So the design question is not "how do we keep the database safe?" but "**what does an attacker get when it leaks?**".

Three ideas carry this lesson:

1. **Never store the password.** Store something from which the password cannot be recovered, and which is expensive to guess against.
2. **After login, hand out a short-lived proof** (a session) so the user is not asked for the password on every click, and make that proof hard to steal or forge.
3. **A password alone is weak.** A second factor means a stolen or guessed password is not enough.

## Storing passwords

Assume the table of `(user, password_hash)` is stolen. The attacker will now try millions of likely passwords offline, with no rate limit, on their own hardware. Our only defence is to make **each guess expensive**.

| mistake | what goes wrong |
| --- | --- |
| store the password | one leak exposes every account, and every other site where users reused it |
| plain `SHA-256(password)` | hash functions are built to be fast: a single GPU tries billions per second |
| the same hash for the same password | two users with the same password are visible, and one precomputed table cracks all of them |

The fix has two parts.

- A **salt**: a random value, unique per user, stored next to the hash (it is not secret). Equal passwords now produce different hashes, and the attacker must attack each user separately; precomputed tables (rainbow tables) are useless.
- A **deliberately slow, tunable function**: **Argon2id**, **scrypt**, **bcrypt** or **PBKDF2**. Argon2id and scrypt also need a lot of memory, which blunts GPUs and custom chips.

At the time of writing, the OWASP cheat sheet suggests, as minimums: Argon2id with 19 MiB of memory, 2 iterations and parallelism 1; or scrypt with N = 2^17, r = 8, p = 1; or bcrypt with a work factor of at least 10; or PBKDF2-HMAC-SHA256 with at least 600,000 iterations. Treat those numbers as a snapshot and check the current sheet.

Run this to see the effect. The first block compares a plain hash with a salted slow one, and measures how many guesses per second each allows.

<CodeRunner language="python" timeoutMs={30000} code={`import hashlib, hmac, os, time

def fast_hash(pw):
    return hashlib.sha256(pw.encode()).hexdigest()

def slow_hash(pw, salt, iterations):
    return hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, iterations).hex()

print("same password, plain SHA-256, two users:")
print(" alice:", fast_hash("hunter2")[:16], " bob:", fast_hash("hunter2")[:16])
salt_a, salt_b = os.urandom(16), os.urandom(16)
print("same password, salted PBKDF2, two users:")
print(" alice:", slow_hash("hunter2", salt_a, 1000)[:16], " bob:", slow_hash("hunter2", salt_b, 1000)[:16])

def guesses_per_second(fn, seconds):
    n, end = 0, time.perf_counter() + seconds
    while time.perf_counter() < end:
        fn(n)
        n += 1
    return n / seconds

fast = guesses_per_second(lambda i: fast_hash(f"password{i}"), 0.4)
salt = os.urandom(16)
rows = [("SHA-256 (no salt, 1 round)", fast)]
for iters in (10_000, 100_000):
    rate = guesses_per_second(lambda i: slow_hash(f"password{i}", salt, iters), 0.6)
    rows.append((f"PBKDF2-SHA256, {iters:,} iterations", rate))
for name, rate in rows:
    print(f"{name:38s} {rate:>12,.0f} guesses/s   ({fast / rate:>8,.0f}x slower)")
`} />

On one laptop run the plain hash allowed about 1.2 million guesses per second in pure Python, 10,000 PBKDF2 iterations about 250 per second (roughly 5,000 times slower) and 100,000 iterations about 28 per second (over 40,000 times slower). Your numbers will differ with the machine, and real attackers use GPUs that are far faster, which is why the **ratio** and the memory-hardness matter, not the absolute figures.

Operational rules that go with this:

- **Store the algorithm and its parameters inside the hash string** (`$argon2id$v=19$m=19456,t=2,p=1$...`), so you can raise the cost later and **upgrade a user's hash at their next successful login**.
- **Compare in constant time** (`hmac.compare_digest`, `MessageDigest.isEqual`), so response timing does not leak how many leading characters matched.
- **Budget for the cost.** If one login costs 100 ms of CPU, then a flood of login attempts is a denial-of-service attack on your servers. Rate limit the endpoint (see [rate limiting algorithms](/sd/scalability/rate-limiting-algorithms/)).
- An optional **pepper**, a secret key kept outside the database (in a KMS or HSM) and mixed into the hash, protects against a database-only leak.

## After login: sessions

The password is checked once. Then the server issues a **session**, and the browser sends it back automatically with every request.

<Diagram kind="mermaid" code={`sequenceDiagram

**Cookie attributes that do real work**

| attribute | effect |
| --- | --- |
| `HttpOnly` | JavaScript cannot read the cookie, so a cross-site scripting (XSS) bug cannot simply copy it |
| `Secure` | sent only over HTTPS, never in clear text |
| `SameSite=Lax` (or `Strict`) | the browser does not attach the cookie to most cross-site requests, which blocks the common forms of cross-site request forgery (CSRF) |
| short `Max-Age` / absolute lifetime | a stolen session stops working on its own |
| `__Host-` name prefix | the cookie must be `Secure`, have `Path=/` and no `Domain`, so a sibling subdomain cannot overwrite it |

**Session rules**

- The id must be **random and long** (at least 128 bits from a cryptographic generator), never derived from the user or a counter.
- **Issue a new id at login** (and when privileges change). Otherwise an attacker who planted a known id before login (**session fixation**) is logged in as the victim.
- Enforce both an **idle timeout** and an **absolute lifetime**. On **logout, delete the server-side record**.
- Sensitive actions (change email, password, payment details) can ask for the password again.

### Where the session lives

| approach | how it works | strength | weakness |
| --- | --- | --- | --- |
| server-side session | cookie holds a random id; data lives in a shared store | instant revocation; small cookie | a store lookup on every request; the store must be highly available |
| sticky sessions | the load balancer pins a user to one server that holds the session in memory | no external store | breaks on server restarts or scale-in; uneven load |
| signed stateless cookie or token | the cookie carries the data plus a signature | no lookup; scales trivially | cannot be revoked before expiry without a denylist; size limits |

A **shared store** such as Redis (see [Redis, Memcached and CDN caching](/sd/caching/redis-memcached-and-cdn-caching/)) is the usual choice because it combines revocation with a stateless app tier. The stateless option is worth understanding precisely; here is the idea in code, using an HMAC signature so the client cannot change what the cookie says.

<CodeRunner language="python" code={`import hashlib, hmac, base64, json

SECRET = b"server-side secret, never sent to the client"

def b64(b):
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

def unb64(s):
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

def make_cookie(data):
    payload = b64(json.dumps(data, sort_keys=True).encode())
    tag = b64(hmac.new(SECRET, payload.encode(), hashlib.sha256).digest())
    return payload + "." + tag

def read_cookie(cookie):
    payload, _, tag = cookie.partition(".")
    expected = b64(hmac.new(SECRET, payload.encode(), hashlib.sha256).digest())
    if not hmac.compare_digest(tag, expected):
        return None
    return json.loads(unb64(payload))

cookie = make_cookie({"user": "alice", "role": "member", "exp": 1900000000})
print("valid cookie reads as :", read_cookie(cookie))

forged_payload = b64(json.dumps({"user": "alice", "role": "admin", "exp": 1900000000}, sort_keys=True).encode())
forged = forged_payload + "." + cookie.partition(".")[2]
print("role changed, old tag :", read_cookie(forged))
print("tag from the wrong key:", read_cookie(cookie.partition(".")[0] + "." + b64(hmac.new(b"guess", b"x", hashlib.sha256).digest())))
`} />

The signature gives **integrity** (nobody can change the role without the key) but not **secrecy** (the payload is only base64: anyone can read it), and no way to revoke a cookie before it expires. Keep secrets out of such cookies, keep lifetimes short, and rotate the key.

## Multi-factor login and TOTP

A stolen or guessed password should not be enough. A **second factor** adds something the user has. The common authenticator-app code is **TOTP** (RFC 6238):

1. At enrolment the server and the app share a random **secret key** (usually through a QR code).
2. Both compute `HMAC(secret, floor(time / 30 seconds))` and **truncate** it to 6 digits.
3. The server accepts the current code, often also one window before and after, to allow for clock drift.

The code below implements it and checks the result against the test vectors published in the RFC itself.

<CodeRunner language="python" code={`import hmac, hashlib, struct

def hotp(key, counter, digits=6):
    mac = hmac.new(key, struct.pack(">Q", counter), hashlib.sha1).digest()
    offset = mac[-1] & 0x0F
    code = (struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF) % (10 ** digits)
    return str(code).zfill(digits)

def totp(key, t, step=30, digits=6):
    return hotp(key, int(t // step), digits)

key = b"12345678901234567890"          # the RFC's SHA-1 test key
vectors = {59: "94287082", 1111111109: "07081804", 1111111111: "14050471",
           1234567890: "89005924", 2000000000: "69279037", 20000000000: "65353130"}
for t, want in vectors.items():
    got = totp(key, t, digits=8)
    print(t, got, "ok" if got == want else "MISMATCH, expected " + want)

print("6-digit code at t=59:", totp(key, 59))
print("same 30 s window    :", totp(key, 61) == totp(key, 89))
print("next window differs :", totp(key, 89) != totp(key, 90))
`} />

All six RFC vectors match. What TOTP does **not** do:

- It does not stop **phishing**: a user can type the code into a fake site, which relays it immediately. **WebAuthn / passkeys** bind the login to the real site's origin and are phishing-resistant, which is why they are the preferred second factor today.
- The server must store the shared secret (so protect and ideally encrypt it), unlike a password hash.
- Limit attempts on the code field, offer **one-time recovery codes**, and design the lost-device flow carefully: it is often the weakest link.

## Attacks on the login endpoint

- **Credential stuffing:** attackers replay username/password pairs leaked from other sites. Defences: breached-password checks, MFA, rate limits per account and per IP, bot detection.
- **Brute force:** throttle with growing delays. **Hard lockouts let an attacker lock any user out on purpose**, so prefer progressive delays, CAPTCHA or risk-based challenges.
- **Account enumeration:** return the same message ("wrong username or password") and similar timing whether the user exists or not; the same applies to password-reset flows.
- **Password policy:** length matters more than composition rules. Allow long passphrases and password managers, and check against lists of known breached passwords.

## Pitfalls

- Storing passwords with a fast hash, without a salt, or "encrypting" them reversibly.
- Writing your own crypto instead of a vetted library; comparing hashes with `==`.
- Cookies without `HttpOnly`, `Secure` or `SameSite`, or with long or never-expiring lifetimes.
- Not rotating the session id at login (session fixation).
- A guessable session id (sequential, time-based, or derived from the user).
- Unlimited login attempts, or hard lockouts that become a denial-of-service tool.
- Different error messages for "no such user" and "wrong password".
- Logging passwords, tokens or full cookies.
