## Intuition

An API is a contract: *what can I ask for, in what shape, and what comes back*. The three styles you will meet most often answer that differently. **REST** models your domain as resources with URLs and uses HTTP verbs. **GraphQL** exposes a typed schema and lets the client ask for exactly the fields it needs. **gRPC** exposes remote procedures with a strict binary schema, optimised for service-to-service calls. None is "best"; each moves cost to a different place.

## One feature, three styles

Feature: show an order with its customer name and the titles of its items.

### REST

```http
GET /orders/4412
```

```json
{
  "id": 4412,
  "status": "shipped",
  "customerId": 77,
  "items": [{ "productId": 9, "qty": 2 }]
}
```

To render the page the client may also call `GET /customers/77` and `GET /products/9`, so three round trips. A server may offer `?expand=customer,items.product` to reduce this, but each such option is something the API author must design and maintain.

Strengths: cacheable by URL with standard HTTP caching, simple tooling, easy to explore. Weakness: **over-fetching** (fields you do not need) and **under-fetching** (needing more calls).

### GraphQL

```graphql
query {
  order(id: 4412) {
    status
    customer { name }
    items { qty product { title } }
  }
}
```

```json
{
  "data": {
    "order": {
      "status": "shipped",
      "customer": { "name": "Asha" },
      "items": [{ "qty": 2, "product": { "title": "Desk lamp" } }]
    }
  }
}
```

One round trip, only the requested fields. Typically all queries go to a single `POST /graphql`, so URL-based HTTP caching does not apply directly; caching moves to the client library or to persisted queries. A server resolving nested fields naively makes one database call per item (the **N+1 problem**), usually fixed with batching (for example a DataLoader pattern). Because clients can write arbitrary queries, servers need depth limits, cost analysis and timeouts to avoid expensive queries.

### gRPC

```protobuf
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrders (WatchRequest) returns (stream OrderEvent);
}

message GetOrderRequest { int64 id = 1; }
message Order {
  int64 id = 1;
  string status = 2;
  int64 customer_id = 3;
}
```

The schema compiles to client and server stubs in many languages. Messages are Protocol Buffers, a compact binary format, sent over HTTP/2. gRPC supports four call shapes: unary, server streaming, client streaming and bidirectional streaming. Browsers cannot call gRPC directly without a proxy layer (gRPC-Web), so it is mostly used between services.

## Evolving an API without breaking clients

- **REST/GraphQL (JSON)**: add fields freely; clients must ignore unknown fields. Never change meaning or remove fields without versioning or deprecation.
- **GraphQL**: mark fields `@deprecated` and track usage before removal; often no version number is used.
- **gRPC/protobuf**: never reuse or renumber a field tag; add new fields with new numbers; reserve removed ones. Old clients ignore unknown fields.

## Pitfalls

- Choosing GraphQL to avoid designing an API. The schema still needs careful design, and the server needs performance guardrails.
- Exposing gRPC directly to browsers without an adapter.
- Calling "REST" any JSON-over-HTTP API. Real REST uses resources, standard verbs and caching semantics, not verbs in URLs like `/doGetOrder`.
- Letting an internal service graph grow into long synchronous chains; every extra hop multiplies latency and failure probability.
