## Intuition

Two ideas finish this module. First, the fastest request is the one that never reaches your servers: a **CDN** keeps copies of content close to users. Second, an API that works in a demo can still hurt in production unless it handles large lists, retries, change over time and abusive clients. The second half of this lesson collects the practices that make an API survivable.

## How a CDN works

A Content Delivery Network is a fleet of **edge servers** in many locations. A user's request is routed (by DNS or anycast) to a nearby edge. If the edge has a fresh copy it answers directly (**cache hit**); otherwise it fetches from your **origin**, stores the result and answers (**cache miss**).

### Cache keys, headers and invalidation

The **cache key** decides when two requests share one cached object. By default it is roughly the host plus path plus query string. Common mistakes: including a random tracking parameter (every request becomes a unique key, hit ratio collapses) or ignoring a header the response depends on (users see each other's variants). `Vary: Accept-Encoding` tells caches that gzip and brotli responses differ.

Key headers on responses:

```http
Cache-Control: public, max-age=31536000, immutable
Cache-Control: private, no-store
Cache-Control: public, max-age=60, stale-while-revalidate=30
ETag: "a91f"
```

- `public` allows shared caches such as a CDN; `private` limits caching to the user's browser.
- `max-age` is freshness lifetime in seconds. `no-store` forbids storing at all (sensitive data).
- `ETag` plus `If-None-Match` lets a cache revalidate cheaply: the origin answers `304 Not Modified` with no body.

**Invalidation strategies**, in order of preference:

1. **Versioned filenames** (`app.4f9c2.js`) with a very long `max-age`: a new deploy uses a new URL, no purge needed.
2. **Short TTL** plus revalidation for content that changes.
3. **Explicit purge** by URL or tag for urgent fixes; fast on most CDNs but not instantaneous worldwide.

<Callout type="warning" title="Never cache personalised responses publicly">
A response containing user-specific data must be `private` or `no-store`, or be keyed by the user. A shared cache that serves one user's page to another is a classic security incident.
</Callout>

Worked number: a site gets 1,000 requests per second for static assets with a 95% edge hit ratio. The origin sees about 50 requests per second instead of 1,000, a 20 times reduction. Raising the hit ratio to 99% brings it to about 10 per second, which is why cache key hygiene is worth the effort.

## API design best practices

### Pagination

Never return an unbounded list. Two common approaches:

```http
GET /v1/orders?limit=50&offset=100
GET /v1/orders?limit=50&cursor=eyJpZCI6IDQ0MTJ9
```

- **Offset pagination** is simple and allows jumping to page N, but the database must skip all earlier rows (slow for deep pages) and results shift if rows are inserted during paging.
- **Cursor (keyset) pagination** uses the last seen sort key (for example `WHERE id < :last ORDER BY id DESC LIMIT 50`). It is stable and fast at any depth, but cannot jump to an arbitrary page. Return an opaque `nextCursor` in the response so you can change its internals.

### Idempotency keys

Networks lose responses. If a client retries `POST /payments` after a timeout, the charge may be created twice. The client sends a unique `Idempotency-Key` header; the server stores the key with the result of the first execution and returns the saved result for any repeat with the same key, instead of running it again. Practical details: keys live for a bounded time (for example 24 hours), the key is stored atomically with the operation, and a repeat with the same key but a different body is rejected with an error.

### Versioning

Plan for change from day one. Common options are a path prefix (`/v1/`), a header or media type, or evolving a single version additively. Additive changes (new optional fields, new endpoints) are safe; removing, renaming or changing the meaning of fields is breaking and needs a new version plus a deprecation period announced in advance (a `Deprecation` or `Sunset` header can signal this). Tell clients to ignore unknown fields.

### Rate limiting and its headers

Rate limits protect shared capacity and limit abuse. When a client exceeds the limit, return `429 Too Many Requests` with a `Retry-After` header (seconds or an HTTP date) so well-behaved clients know when to come back. Many APIs also expose the remaining budget, with `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` as a widespread convention, and an IETF draft proposing standard `RateLimit-*` fields; check which one your target ecosystem uses.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
Content-Type: application/json

{"error": {"code": "rate_limited", "message": "Try again in 30 seconds"}}
```

Algorithms you will see later in depth: fixed window, sliding window and token bucket (allows bursts up to a bucket size while enforcing an average rate).

### Errors and other basics

- Use correct status codes and a consistent error body with a machine-readable `code`.
- Authenticate every request; authorise per resource. Validate and bound all inputs (page size, body size).
- Set timeouts and document them. Prefer `202 Accepted` with a status URL for long operations.
- Log a request id and return it in a header so support can trace a failure.

## Failure modes

- **Cache stampede**: a popular object expires and thousands of requests hit the origin at once. Mitigate with request coalescing, `stale-while-revalidate` and staggered TTLs.
- **Stale after deploy**: a new HTML page referencing assets that edges have not yet fetched, or old HTML referencing removed files. Keep old asset versions available for a while.
- **Idempotency store outage**: decide whether to fail closed (reject writes) or open (risk duplicates); for payments, fail closed.
- **Retry storms**: clients retrying 429 or 503 without backoff multiply load. Use exponential backoff with jitter and honour `Retry-After`.

## Pitfalls

- Using offset pagination on large, changing tables and wondering why deep pages are slow or repeat items.
- Adding the idempotency check in the application but not making the key and the operation atomic.
- Caching API responses at the CDN without accounting for authorization headers or cookies.
- Breaking a field name "because it was ugly" with no versioning plan.
- Returning rate-limit state only through error text instead of headers clients can parse.

## What would you choose and why?

Your product catalog API serves 2 million products. A mobile app wants "page 3,000 of the list" while a feed screen wants "keep scrolling". Which pagination style do you offer for each, what does the response carry, and how would you cache the first page at a CDN?
