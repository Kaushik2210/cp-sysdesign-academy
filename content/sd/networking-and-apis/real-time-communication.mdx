## Intuition

HTTP is "client asks, server answers". But chat messages, live scores and progress bars need the server to tell the client something *when it happens*. There are four common techniques, ranging from "ask repeatedly" to "keep a two-way pipe open". Each trades simplicity against efficiency and server resources.

## The four techniques

### Short polling

The client asks every N seconds: "anything new?" The server answers immediately, usually with nothing.

- Simple, works everywhere, plays well with caches and load balancers.
- Wasteful: with 100,000 clients polling every 5 seconds, the server handles 20,000 requests per second, mostly empty. Worst-case delay for an event is nearly the whole interval.

### Long polling

The client asks and the server **holds the request open** until it has data or a timeout (often 20 to 60 seconds), then answers; the client immediately asks again.

- Near-real-time delivery over plain HTTP, no special protocol.
- Each waiting client still holds a connection and the server must manage many idle requests. Between response and the next request there is a small gap where events must be buffered or replayed by an id.

### Server-sent events (SSE)

One long-lived HTTP response with `Content-Type: text/event-stream`. The server writes events as text lines; the browser's `EventSource` parses them and **reconnects automatically**, sending `Last-Event-ID` so the server can resume.

```text
id: 105
event: price
data: {"symbol":"ABC","price":101.4}

```

- One direction only: server to client. Client-to-server messages use ordinary requests.
- Works over normal HTTP (including HTTP/2 multiplexing), so proxies and auth work as usual. Text only. On HTTP/1.1, browsers limit connections per domain, which can matter.

### WebSockets

A request with `Upgrade: websocket` switches the connection (status `101 Switching Protocols`) into a full-duplex message channel over the same TCP connection.

- Two-way, low overhead per message after the handshake, binary or text.
- Stateful: each connection is pinned to one server, so you need a way to route messages to the right server (a pub/sub backplane), plus heartbeats, reconnect logic and backpressure handling. Some proxies and corporate networks need configuration for long-lived connections.

## Scaling stateful connections

Each open connection costs memory (commonly some KB to tens of KB, depending on buffers and the stack), and one process can hold many thousands to hundreds of thousands with careful tuning. A million concurrent users therefore needs a fleet of connection servers. The routing problem: user A is connected to server 3, user B to server 17; a message from A to B must reach server 17.

## Failure modes

- **Reconnect storm**: when a gateway restarts, tens of thousands of clients reconnect at the same instant. Use exponential backoff with jitter on the client.
- **Missed messages**: connections drop silently. Give each message a monotonically increasing id and let the client ask for everything after the last id it saw.
- **Half-open connections**: a client vanishes without closing. Use heartbeats (ping/pong) and idle timeouts.
- **Slow consumers**: a client that cannot keep up makes server buffers grow. Bound the buffer and drop or disconnect.

## Pitfalls

- Reaching for WebSockets by default when SSE or polling would do. Statefulness is a real operational cost.
- Forgetting authentication on the upgrade request and re-validation for long sessions.
- Treating the live connection as the source of truth. It is a delivery optimisation; the durable record belongs in a store.
- Deploying with a load balancer idle timeout shorter than your heartbeat interval.

## What would you choose and why?

A food-delivery app shows the courier's position updating every few seconds to the customer. The customer never sends data on this screen. Pick between short polling, SSE and WebSockets and explain what you would pay for the choice and what would make you change your mind.
