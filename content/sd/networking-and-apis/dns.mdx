## Intuition

Computers reach each other by IP address, people remember names. DNS (the Domain Name System) is the distributed, hierarchical, heavily cached database that maps names such as `www.example.com` to addresses. It sits in front of nearly every connection, so its speed, caching and failure behaviour are part of every system's latency and availability story. It is also a design tool: because the answer can differ per user, DNS can steer traffic between regions and data centres.

## The hierarchy

A name is read right to left: `www` . `example` . `com` . (the root).

- **Root servers** know which servers handle each top-level domain.
- **TLD servers** (for `com`, `org`, `in`) know which name servers are responsible for each registered domain.
- **Authoritative name servers** hold the actual records for a domain and give the final answer.
- **Recursive resolvers** (run by your ISP, company or a public provider) do the lookup work on behalf of clients and cache results.
- The **stub resolver** in your operating system just asks the recursive resolver.

A cold lookup can involve several round trips; a cached one answers in about a millisecond from a nearby resolver. In practice most lookups are cache hits because resolvers cache not only final answers but also the locations of TLD and authoritative servers.

## Common record types

| Type | Meaning | Example |
| --- | --- | --- |
| A | Name to IPv4 address | `www` to `203.0.113.10` |
| AAAA | Name to IPv6 address | `www` to `2001:db8::10` |
| CNAME | Alias to another name | `www` to `lb.example.net` |
| NS | Which servers are authoritative | `example.com` to `ns1.dnsprovider.net` |
| MX | Mail servers | `example.com` to `mail.example.com` |
| TXT | Free text (verification, SPF) | `"v=spf1 ..."` |

A name that has a CNAME cannot hold other record types at the same name, which is why the bare "apex" domain (`example.com`) cannot be a CNAME in standard DNS; many providers offer an ALIAS or flattening feature as a workaround.

## TTL and caching

Every record carries a **TTL** (time to live, in seconds). Resolvers, operating systems and browsers may cache the answer for that long.

- **Long TTL** (hours): fewer queries, faster lookups, lower load on authoritative servers, but changes propagate slowly.
- **Short TTL** (30 to 300 seconds): changes and failovers take effect quickly, but more queries and more latency on cache misses.

<Callout type="warning" title="Changing DNS is not instant">
If a record has a one-day TTL and you change it, some clients keep the old address for up to a day. Before a planned migration, lower the TTL well in advance (at least the old TTL ahead of time), switch, then raise it again. Some resolvers also ignore low TTLs or clamp them, so treat TTL as a request, not a guarantee.
</Callout>

Negative answers (name does not exist) are cached too, for a period set by the zone.

## DNS as a traffic tool

- **Round-robin**: return several A records; clients pick among them. Simple, but unaware of server health or load.
- **GeoDNS / latency-based routing**: the authoritative server returns different answers depending on where the query comes from (usually inferred from the resolver's address, or from EDNS Client Subnet when supported), sending users to the nearest region.
- **Weighted routing**: send 5% of traffic to a new deployment for a gradual rollout.
- **Health-checked failover**: remove an unhealthy endpoint from answers; limited by TTL and client caching.
- **Anycast**: many servers advertise the same IP and the network routes each client to a nearby one; commonly used by root servers, public resolvers and CDNs.

## Pitfalls

- Treating DNS failover as instant. Clients, resolvers and libraries (for example runtimes that cache a lookup for the life of a process) can keep stale addresses.
- Putting everything on one DNS provider. DNS is a single point of failure for the whole domain.
- Forgetting that the lookup is part of latency on the first request to a new hostname; many separate hostnames (sharded domains) can add lookups.
- Using DNS for load balancing when you need real load or health awareness; use a load balancer behind it.
- Pointing the apex domain at a CNAME where the provider does not support flattening.
