## Intuition

Almost every system you will design is a conversation between a **client** that asks and a **server** that answers. The client opens a connection, sends a request, and waits. The server may be a single process or a fleet behind a load balancer, but the client sees one address and one contract. HTTP is that contract for the web: a text-oriented request/response protocol that runs on top of a reliable byte stream (TCP, or QUIC for HTTP/3).

Understanding what one request costs, and what can go wrong between the two ends, is the foundation for everything else in this module.

## The client-server model

- The client **initiates**; the server **responds**. A server cannot normally push to a client that has not asked (that is why real-time techniques exist; see the later lesson).
- Servers should be **stateless between requests** where possible: each request carries what the server needs (credentials, parameters). State lives in a database or shared store.
- Servers are shared by many clients, so they need limits (timeouts, rate limits, body-size caps) to protect themselves.

A single page load is not one request. It may be one HTML document, then tens of requests for scripts, styles, images and API calls. Each one pays connection, security and server costs, which is why connection reuse and caching matter so much.

## Anatomy of an HTTP exchange

```http
GET /v1/orders/4412 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <token>
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=30
ETag: "a91f"

{"id": 4412, "status": "shipped"}
```

A request has a **method**, a **target**, **headers** and an optional **body**. A response has a **status code**, headers and an optional body.

### Methods and their guarantees

| Method | Typical use | Safe (no side effects) | Idempotent (repeat has same effect) |
| --- | --- | --- | --- |
| GET | Read a resource | Yes | Yes |
| HEAD | Read headers only | Yes | Yes |
| PUT | Replace a resource at a known URL | No | Yes |
| DELETE | Remove a resource | No | Yes |
| POST | Create or trigger an action | No | No |
| PATCH | Partial update | No | Not guaranteed |

*Idempotent* matters because networks fail: if a response is lost, a client does not know whether the request ran. Retrying a PUT or DELETE is safe; retrying a POST may create a second order, which is why APIs add idempotency keys (covered in the last lesson).

### Status code families

| Range | Meaning | Examples |
| --- | --- | --- |
| 2xx | Success | 200 OK, 201 Created, 202 Accepted, 204 No Content |
| 3xx | Redirect or cache validation | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | Client error: do not retry unchanged | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests |
| 5xx | Server error: may be retried | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

<Callout type="tip">
Retry guidance: retry 5xx and network timeouts (with backoff and jitter) only for idempotent requests or when an idempotency key is used. Do not retry most 4xx; the request itself is wrong. 429 is the exception: wait as told by `Retry-After`.
</Callout>

## HTTPS and the TLS handshake (high level)

HTTP itself is plain text. **HTTPS** is HTTP inside a **TLS** session, which gives three properties: *confidentiality* (encrypted), *integrity* (tampering detected) and *authentication* (the server proves its identity with a certificate signed by a trusted authority).

At a high level the handshake does this:

1. **ClientHello**: client lists supported TLS versions and cipher suites and sends key-exchange material.
2. **ServerHello and certificate**: the server picks parameters and sends its certificate chain, proving it owns the domain.
3. **Key agreement**: both sides derive shared session keys using an ephemeral key exchange (so past sessions stay safe even if a long-term key leaks later, called forward secrecy).
4. **Finished**: both confirm, then application data (the HTTP request) flows encrypted using fast symmetric cryptography.

TLS 1.3 completes this in one round trip after the TCP connection is established, and can resume earlier sessions with fewer round trips. Cost summary for a brand-new HTTPS connection over TCP: DNS lookup, one round trip for TCP, one for TLS 1.3, then the request itself. On a 100 ms round-trip path, that is about 200 ms of setup before the first byte of the request is even sent, which is why **connection reuse (keep-alive)** and edge servers near the user matter.

## HTTP/1.1 vs HTTP/2 vs HTTP/3

<TradeOffs caption="Protocol versions" rows={[
  { option: "HTTP/1.1", pros: "Simple text protocol, universally supported, easy to debug", cons: "One request at a time per connection; browsers open several connections; verbose repeated headers", chooseWhen: "Legacy clients, simple internal tools" },
  { option: "HTTP/2", pros: "Binary framing, many multiplexed streams on one connection, header compression (HPACK)", cons: "Runs on TCP, so one lost packet stalls all streams (TCP head-of-line blocking)", chooseWhen: "Default for modern sites and APIs; gRPC uses it" },
  { option: "HTTP/3", pros: "Runs on QUIC over UDP: per-stream loss recovery, faster setup (TLS built in), survives network changes via connection IDs", cons: "UDP can be blocked or throttled by some networks; newer tooling; more CPU in user space", chooseWhen: "Mobile and lossy networks, latency-sensitive global users; fall back to HTTP/2 when blocked" }
]} />

All three keep the same semantics (methods, status codes, headers); only the wire format and transport change. That is why your API design does not depend on the version.

## Pitfalls

- Using `GET` for actions with side effects. Caches, prefetchers and crawlers assume GET is safe.
- Returning `200` with an error message in the body. Clients, caches and monitoring rely on status codes.
- Confusing `401` (not authenticated) with `403` (authenticated but not allowed).
- Forgetting timeouts. A client or server without a timeout can hang forever and exhaust resources.
- Assuming HTTPS means the data is safe at rest or that the server is trustworthy; it protects the wire only.

## What would you choose and why?

A mobile app in a region with lossy cellular networks makes many small API calls on app start. Would you stay on HTTP/1.1 with several connections, move to HTTP/2, or enable HTTP/3 with fallback? State which cost you are reducing and what you lose.
