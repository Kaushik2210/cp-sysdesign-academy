## The problem

Design a **web search engine**: it **crawls** billions of pages, builds an **index**, and answers a typed query with the ten most **relevant** results in a fraction of a second, while staying **fresh** (news appears within minutes) and resisting people who manipulate the rankings.

Earlier lessons built the parts: the [web crawler](/sd/case-studies-core-services/design-a-web-crawler/) fetches pages, [inverted indexes](/sd/search-systems/inverted-indexes-and-text-analysis/) map words to documents, [BM25](/sd/search-systems/ranking-tf-idf-and-bm25/) scores text relevance, and [scatter-gather](/sd/search-systems/scatter-gather-search-and-tail-latency/) fans a query over shards. This case study connects them and adds what is specific to the **whole web**: using the **link graph** as a quality signal (PageRank), **adversarial spam**, and **tiered indexes** that make the enormous index affordable.

## Requirements

**Functional**
- Crawl and index web pages continuously.
- Return ranked results for a text query, with titles and snippets.
- Handle typos, synonyms and different languages.
- Support freshness: new and changed pages become searchable quickly.

**Non-functional**
- Median latency under 200 ms; high availability.
- **Relevance** is the product: results should be useful, trustworthy and hard to game.
- Scale to tens of billions of pages and hundreds of thousands of queries per second.

## Estimation

| quantity | assumption | result |
| --- | --- | --- |
| Indexed pages | 50 billion | |
| Index size | about 10 KB of postings per page (assumption, after compression) | about 500 TB |
| Queries | 8.6 billion per day | about 100,000 per second on average, 300,000 at peak |
| Result cache | about 40% of queries repeat and are served from a cache | about 180,000 per second reach the index at peak |
| Shards | document-partitioned, about 500 GB per shard | about 1,000 shards, and **every uncached query visits every shard** |

The last row is the central difficulty: with a **document-partitioned** index each shard holds a slice of all documents, so each query must ask **all** shards. Throughput then means **many replicas of every shard**, which is expensive. The remedies are **caching** (above), **tiered indexes**, and **early termination** (stop scanning a postings list once the best results can no longer change).

## Indexing pipeline

1. **Parse** the HTML: extract text, title, headings, anchors and outgoing links; detect the language.
2. **Deduplicate**: the web is full of copies. Exact duplicates are caught by hashing the content; **near duplicates** (same article with a different sidebar) by a similarity fingerprint such as SimHash. Keep one canonical page and credit it with the links of the copies.
3. **Build the inverted index**: for every term, a sorted **postings list** of documents (with positions and fields). Built as a **batch job** (MapReduce style) over the whole corpus, plus an **incremental** path for fresh pages.
4. **Shard by document**, so a shard owns an independent slice and can rank locally; replicate each shard for availability and throughput.
5. **Tier** the index. Put the **best pages** (high quality, frequently clicked, high link score) in a small, fast **tier 1**; the vast **long tail** goes in a cheaper **tier 2** consulted only when tier 1 gives too few good results. Most queries are answered from tier 1, so the expensive hardware serves a small fraction of the corpus.
6. **Freshness**: a separate small **real-time index** for newly crawled pages and news, merged with the main results at query time, and rebuilt into the main index periodically.

## The link graph and PageRank

Text matching alone is easy to manipulate: stuff a page with the right words. Links are a harder-to-fake signal of **quality**: a page that many good pages link to is probably good. **PageRank** formalises this with a **random surfer**: with probability d (the *damping factor*, typically 0.85) the surfer follows a random outgoing link, otherwise jumps to a random page. The page's rank is the long-run fraction of time the surfer spends there, computed by **power iteration**: start with equal ranks and repeatedly redistribute each page's rank among the pages it links to, until the values stop changing. Rank flows from page to page, and pages with no links send theirs to the random jump.

At web scale the iteration is a **distributed batch job** over the link graph (each iteration is one pass over all links), run periodically.

### The experiment

The program below builds a synthetic web of 2,000 pages (10,245 links) where popular pages attract more links, runs PageRank, and then attacks it with a **link farm**: 200 worthless pages that all link to one target page and to each other. It compares plain PageRank with a **trust-biased** variant in which the random jump goes **only to 10 trusted seed pages** (the idea behind TrustRank).

def make_web(n, seed):
    """A synthetic web: every page links to 3 to 8 pages, favouring pages that already have many links in."""
    rnd = random.Random(seed)
    out = {p: [] for p in range(n)}
    pool = list(range(10))                      # a few early, well known pages
    for p in range(n):
        for _ in range(rnd.randint(3, 8)):
            q = rnd.choice(pool)
            if q != p and q not in out[p]:
                out[p].append(q)
                pool.append(q)                  # being linked to makes a page more likely to be linked again
        pool.append(p)
    return out


def pagerank(out, damping=0.85, tol=1e-10, teleport=None):
    """Power iteration. A random surfer follows a link with probability 'damping', otherwise jumps to a page
    chosen by 'teleport' (uniform by default). Pages with no links send their rank to the teleport distribution."""
    n = len(out)
    tele = teleport or {p: 1.0 / n for p in out}
    rank = dict(tele)
    for it in range(1, 1000):
        new = {p: (1 - damping) * tele[p] for p in out}
        dangling = sum(rank[p] for p in out if not out[p])
        for p, links in out.items():
            if links:
                share = damping * rank[p] / len(links)
                for q in links:
                    new[q] += share
        for p in out:
            new[p] += damping * dangling * tele[p]
        diff = sum(abs(new[p] - rank[p]) for p in out)
        rank = new
        if diff < tol:
            return rank, it
    return rank, 1000


def position(rank, page):
    order = sorted(rank, key=lambda p: -rank[p])
    return order.index(page) + 1

## What the output shows

- **Convergence**: PageRank converges in **31 iterations** at damping 0.85, and the ranks add up to 1. A lower damping factor converges faster (**18 iterations at 0.5**) and a higher one slower (**40 at 0.99**), because rank has to travel further along link chains. Real systems stop after a few dozen iterations.
- **Top pages**: the five most linked-to pages hold between about 8.5% and 13.6% of all rank each, together roughly 60%: link-based importance is extremely **concentrated** in a few pages, as on the real web.
- **The link farm works against plain PageRank**: even though **no real page links to the farm**, the target page jumps from position **1553 to 12** and the farm holds **6.0%** of all rank. Why? Every page, including the 200 farm pages, receives a share of the **uniform random jump**, and the farm's internal links **trap** that rank and funnel it to the target.
- **Trust-biased rank removes it, when the farm is isolated**: with jumps only to 10 trusted seeds, the unlinked farm holds **0.0%** and the target falls back to position **1501**.
- **But a few real links bring it back**: when just **5 real pages link into the farm** (think hacked sites or comment spam), plain PageRank puts the target at position **11** with **0.941%** of all rank (it had 0.008%). Trust-biased rank is better but not enough: the target is at **12** and the farm still holds **8.0%** of rank, because once rank gets in, the farm's loops **keep it**.

So a single signal can always be attacked. Production systems add: ignoring links from known-bad or low-trust sources (**spam mass** estimation compares ordinary and trust-biased ranks), **nofollow** annotations on user-generated links, detecting **dense closed link clusters**, limiting the influence of any one site, and many independent signals so that gaming one barely helps.

The graph is synthetic and the numbers come from one seed; they show the mechanism, not the behaviour of the real web.

## Ranking

A query is answered in stages, each cheaper and more precise than the last:

1. **Query understanding**: tokenise, fix spelling, expand synonyms, detect intent and language.
2. **Retrieval** from the inverted index in each shard: documents containing the terms, scored by a fast function ([BM25](/sd/search-systems/ranking-tf-idf-and-bm25/)) plus the **static** document score (link-based rank, quality).
3. **Local top K** per shard (for example 1,000), merged centrally ([scatter-gather](/sd/search-systems/scatter-gather-search-and-tail-latency/)).
4. **Re-ranking** of the top few hundred with a **learned model** over hundreds of signals: text match in title and anchors, link score, page quality, freshness, click behaviour, location and language, page speed, and **semantic similarity** from embeddings ([vector search](/sd/search-systems/vector-search-and-ann/)).
5. **Snippets and presentation**: pick the passage matching the query; assemble the result page.

The learned ranker is trained on **human relevance ratings** and **click data**, evaluated with metrics such as **NDCG** and with online **A/B tests**.

## Serving at low latency

- **Cache** whole result pages for frequent queries; a skewed query distribution makes caching very effective.
- **Tier 1 first**: answer from the small tier; consult tier 2 only if needed.
- **Early termination**: postings are sorted by static score, so a shard can stop once the remaining documents cannot enter the top K.
- **Tail latency**: the query waits for the slowest shard, so use **timeouts, hedged requests** (a second request to another replica after a short wait) and return **partial results** rather than waiting ([tail latency](/sd/search-systems/scatter-gather-search-and-tail-latency/)).

## Pitfalls

- Ranking on **text match alone** (trivially stuffed with keywords).
- Trusting **one link-based signal**: a link farm lifted a worthless page from position 1553 to 12 in the demo.
- **Visiting every shard** for every query with no cache, tiers or early termination.
- Waiting for the **slowest shard** with no timeout or hedging.
- No **near-duplicate** detection: results full of copies and split link credit.
- Treating the index as **static**: new pages and breaking news arrive late.
- Evaluating changes by intuition instead of **human ratings and A/B tests**.
- Letting **personalisation** or location dominate without guardrails.
- Ignoring **crawl politeness** and robots rules ([web crawler lesson](/sd/case-studies-core-services/design-a-web-crawler/)).
- Not measuring **tail latency** (p99), only the average.
