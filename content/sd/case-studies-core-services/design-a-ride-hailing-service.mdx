## The problem

Design a **ride-hailing service** like Uber, Lyft or Ola. A rider opens the app and requests a ride from their location. The system finds **available drivers nearby**, offers the trip to a suitable one, and then tracks the **driver on a map** until the rider is dropped off, with an **estimated arrival time (ETA)** and a price.

This is the standard system-design question about **location**: a million moving points that update every few seconds, and a query "who is closest to this spot right now?" that must answer in a fraction of a second. The interesting parts are the **geospatial index**, the **matching without double-booking a driver**, **routing and ETA**, and the **sheer rate of location updates**.

## 1. Requirements

**Functional**

- A rider requests a ride (pickup, destination) and sees **nearby cars and an ETA and price estimate**.
- The system **matches** the rider with a nearby driver; the driver can **accept or reject**.
- **Live tracking** of the driver's location for the rider during pickup and trip.
- Trip lifecycle: requested, matched, driver arriving, in progress, completed, cancelled; then **payment** ([payment system](/sd/case-studies-core-services/design-a-payment-system/)) and ratings.

**Non-functional**

- **Fast matching** (a few seconds at most from request to driver offer).
- **A driver must never be assigned two trips at once**, even under concurrent requests (strong consistency for the assignment).
- **Location data can be slightly stale** (a second or two) for the map display (eventual consistency is fine).
- High availability in each city; **graceful degradation** (an inaccurate ETA is better than no ride).
- Handle **hot spots**: airports, stadium exits, New Year's Eve.

Two consequences: keep the **current position of every driver in memory** (a latest-value store) instead of writing every update to a database, and send only a **sampled history** to long-term storage for analytics and machine learning.

## 3. Representing "nearby": spatial indexes

You cannot search a million points by scanning them all for every request. The standard trick is to divide the map into **cells** and index drivers **by cell**. A query looks at the rider's cell and its neighbours.

**Geohash** is a popular scheme: it recursively halves the world by longitude and latitude, interleaves the bits, and writes them in base 32. **Longer strings mean smaller cells, and points in the same cell share a prefix**, so a prefix lookup in a sorted store finds everything in a cell. **S2** (square cells on a sphere) and **H3** (hexagonal cells) are alternatives; hexagons have the useful property that all neighbours are the same distance away.

<CodeRunner language="python" code={`import math, os

BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"

def geohash_encode(lat, lon, precision):
    lat_lo, lat_hi, lon_lo, lon_hi = -90.0, 90.0, -180.0, 180.0
    bits, bit, ch, out, even = [16, 8, 4, 2, 1], 0, 0, "", True
    while len(out) < precision:
        if even:
            mid = (lon_lo + lon_hi) / 2
            if lon >= mid:
                ch |= bits[bit]; lon_lo = mid
            else:
                lon_hi = mid
        else:
            mid = (lat_lo + lat_hi) / 2
            if lat >= mid:
                ch |= bits[bit]; lat_lo = mid
            else:
                lat_hi = mid
        even = not even
        if bit < 4:
            bit += 1
        else:
            out += BASE32[ch]; bit, ch = 0, 0
    return out

def cell_size_km(precision, lat=0.0):
    lon_bits, lat_bits = (5 * precision + 1) // 2, (5 * precision) // 2
    return 360 / 2 ** lon_bits * 111.32 * math.cos(math.radians(lat)), 180 / 2 ** lat_bits * 111.32

print("geohash precision and cell size (at the equator):")
for p in (4, 5, 6, 7, 8):
    w, h = cell_size_km(p)
    print(f"  {p} characters: about {w:7.2f} km x {h:7.2f} km")

def km(lat1, lon1, lat2, lon2):
    r = 6371.0
    p1, p2 = math.radians(lat1), math.radians(lat2)
    a = math.sin((p2 - p1) / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(math.radians(lon2 - lon1) / 2) ** 2
    return 2 * r * math.asin(math.sqrt(a))

a, b = (51.5072, -0.0001), (51.5072, 0.0001)                  # two points about 14 m apart, straddling the prime meridian
ga, gb = geohash_encode(*a, 7), geohash_encode(*b, 7)
print(f"\\ntwo points {km(*a, *b) * 1000:.0f} m apart: geohash {ga} and {gb}, shared prefix length {len(os.path.commonprefix([ga, gb]))}")
`} />

The table shows the trade-off: **6 characters is about 1.2 km by 0.6 km**, and **7 characters about 150 m**. Choose a cell size close to your **typical search radius**.

The last line shows the **boundary problem** every cell index has: two points only **14 metres apart** that sit on opposite sides of the prime meridian end up in cells with **no common prefix at all**. A query that looks only at the rider's own cell would miss a driver 14 m away. So **a search must always include the neighbouring cells** (the 8 around the rider's cell, or a ring of cells covering the radius), and then filter by true distance.

**Density varies**: a city centre may hold thousands of drivers in a cell while a suburb holds one. Fixed-size cells then give hot cells and empty ones. Remedies: choose a finer level in dense areas (an adaptive **quadtree**, or hierarchical cells in S2/H3), and shard the index by region so one hot cell does not overload one machine.

## 4. Finding the nearest drivers

The program below indexes 40,000 simulated drivers in a city in a **grid of cells about 1.1 km wide**, and finds the 5 nearest to a rider by searching **rings** of cells outward until the k-th best candidate is closer than anything that could still be hiding in an unsearched cell. It checks that the answer equals a brute-force scan of all drivers.

<CodeRunner language="python" timeoutMs={60000} code={`import math, random

def km(lat1, lon1, lat2, lon2):
    r = 6371.0
    p1, p2 = math.radians(lat1), math.radians(lat2)
    a = math.sin((p2 - p1) / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(math.radians(lon2 - lon1) / 2) ** 2
    return 2 * r * math.asin(math.sqrt(a))

random.seed(3)
LAT0, LON0, SPAN = 40.70, -74.02, 0.25                        # a city about 28 km x 21 km
drivers = [(LAT0 + random.random() * SPAN, LON0 + random.random() * SPAN * 1.3) for _ in range(40_000)]
CELL = 0.01                                                   # about 1.1 km

def cell(lat, lon):
    return int((lat - LAT0) / CELL), int((lon - LON0) / CELL)

grid = {}
for i, (la, lo) in enumerate(drivers):
    grid.setdefault(cell(la, lo), []).append(i)

def nearest_brute(lat, lon, k):
    return sorted(range(len(drivers)), key=lambda i: km(lat, lon, *drivers[i]))[:k]

def nearest_grid(lat, lon, k):
    cx, cy = cell(lat, lon)
    checked, found, ring = 0, [], 0
    while True:
        for dx in range(-ring, ring + 1):
            for dy in range(-ring, ring + 1):
                if max(abs(dx), abs(dy)) != ring:
                    continue                                   # only the new outer ring of cells
                for i in grid.get((cx + dx, cy + dy), []):
                    checked += 1
                    found.append((km(lat, lon, *drivers[i]), i))
        found.sort()
        # anything in an unsearched cell is at least this far away (a conservative bound, since cells are narrower in longitude)
        safe_km = ring * CELL * 111.32 * 0.7
        if len(found) >= k and found[k - 1][0] <= safe_km:
            return [i for _, i in found[:k]], checked
        ring += 1

queries = [(LAT0 + random.random() * SPAN, LON0 + random.random() * SPAN * 1.3) for _ in range(10)]
same, checked_total = 0, 0
for lat, lon in queries:
    fast, c = nearest_grid(lat, lon, 5)
    same += nearest_brute(lat, lon, 5) == fast
    checked_total += c
print(f"find the 5 nearest of {len(drivers):,} drivers, {len(queries)} queries:")
print(f"  scan everyone: {len(drivers):,} distance computations per query")
print(f"  grid index   : {checked_total / len(queries):,.0f} distance computations per query on average; same answer as the scan in {same} of {len(queries)} queries")
`} />

The grid index examined **a few hundred drivers per query instead of all 40,000**, and returned the **same top 5 as the full scan in every query**, which is the correctness check that matters. At 1 million drivers the saving is larger still, and a production store (Redis geo commands, an in-memory R-tree or a purpose-built service) does this lookup in well under a millisecond.

## 5. High-level design

- **Location gateway**: long-lived connections (or batched HTTP/UDP) from drivers; updates go to the **live index** and to a **stream** for history.
- **Live location index**: an in-memory structure keyed by cell, **sharded by geography** (city or cell-prefix ranges) so one region's load and failures stay local. Each driver entry has a **timestamp and a TTL**: a driver who stops reporting disappears from results after a few seconds.
- **Matching service**: finds candidates, ranks them, and runs the offer protocol.
- **ETA and routing service**: computes road-network travel times.
- **Driver and trip state store**: the strongly consistent record of each driver's status and each trip's state, in a replicated database (see [replication](/sd/databases-2/replication/)).
- **Pricing and surge**: per-region supply and demand to set prices and attract drivers.
- **Notifications** to driver apps use [push infrastructure](/sd/case-studies-core-services/design-a-notification-system/); trips settle through the [payment system](/sd/case-studies-core-services/design-a-payment-system/).

## 6. Matching without double booking

When a rider requests a ride, the matching service:

1. **Finds candidates**: available drivers within a radius (the cell search above), usually the nearest few dozen.
2. **Ranks them** by **road ETA to the pickup** (not straight-line distance: a driver across a river may be far by road), plus rating, vehicle type, and the probability that they will accept.
3. **Offers the trip** to the best driver for a short window (around 10 to 15 seconds). If they reject or time out, offer to the next. Many systems instead **batch** requests over a short interval (for example 2 seconds) and solve an **assignment problem** over all riders and drivers together, which can improve overall wait times (see [bitmask DP and assignment](/cp/dynamic-programming/bitmask-dp/) for the problem; real systems use polynomial algorithms such as the Hungarian method).

The hard guarantee is **one driver, one trip**. Two matching workers serving two riders could pick the same driver at the same moment. The fix is an **atomic claim** on the driver's state, using a conditional update, never "read, check, write":

```sql
UPDATE drivers
SET status = 'offered', offer_trip = :trip, offer_expires_at = now() + interval '15 seconds'
WHERE id = :driver AND status = 'available';          -- succeeds for exactly one worker
```

If zero rows change, someone else claimed that driver and the worker moves to the next candidate. The offer carries an **expiry (a lease)**, so a driver who never answers returns to `available` automatically (a background sweep or an in-memory TTL). The same pattern appears in the [payment system](/sd/case-studies-core-services/design-a-payment-system/) lesson's overdraft check. The driver state machine is `available` → `offered` → `assigned` → `on_trip` → `available`, with transitions guarded by conditions and idempotent operations, because phones disconnect and retry.

## 7. ETA and routing

An ETA needs the **road network**, not a straight line. Model roads as a **graph** (intersections are nodes, road segments are edges with travel time as the weight) and run a shortest-path search. Travel times change with **traffic**, so the weights are updated from live driver speeds and historical patterns. The program below runs Dijkstra's algorithm ([shortest paths](/cp/graphs/dijkstra-shortest-paths/)) on a 30 by 30 block city, first in free-flowing traffic and then with a congested band across the middle.

<CodeRunner language="python" code={`import heapq

N = 30
def shortest(weights, src, dst):
    dist = {src: 0.0}
    pq = [(0.0, src)]
    while pq:
        d, u = heapq.heappop(pq)
        if u == dst:
            return d
        if d > dist.get(u, 1e18):
            continue
        x, y = u
        for v in ((x + 1, y), (x - 1, y), (x, y + 1), (x, y - 1)):
            if 0 <= v[0] < N and 0 <= v[1] < N:
                nd = d + weights[(u, v)]
                if nd < dist.get(v, 1e18):
                    dist[v] = nd
                    heapq.heappush(pq, (nd, v))

free_flow = {}
for x in range(N):
    for y in range(N):
        for v in ((x + 1, y), (x - 1, y), (x, y + 1), (x, y - 1)):
            if 0 <= v[0] < N and 0 <= v[1] < N:
                free_flow[((x, y), v)] = 30.0               # 30 seconds per block
congested = dict(free_flow)
for (u, v) in free_flow:                                       # a congested band of streets through the middle of the city
    if 12 <= u[1] <= 17 and 12 <= v[1] <= 17:
        congested[(u, v)] = 120.0

corner = (0, 0), (N - 1, N - 1)
print(f"corner to opposite corner of a {N}x{N} grid:")
print(f"  free flow                      : {shortest(free_flow, *corner) / 60:5.1f} min")
print(f"  congested band, best route     : {shortest(congested, *corner) / 60:5.1f} min (the route avoids most of the band)")
straight = sum(congested[((i, 14), (i + 1, 14))] for i in range(N - 1))
print(f"  driving straight along the band: {straight / 60:5.1f} min (29 blocks at 4x the normal time)")
`} />

Free-flow time for the 58 blocks is 29 minutes. With congestion the **best route takes 36.5 minutes** because it detours around the slow band, whereas driving straight along it would take **58 minutes**. Real systems add:

- **Faster algorithms for continent-sized graphs**: plain Dijkstra on millions of nodes is too slow for each request. **Contraction hierarchies** and similar methods preprocess the graph so that a query visits only a few hundred nodes, in milliseconds.
- **Traffic**: live speeds from driver GPS probes, historical speed profiles by time of day, and machine-learned corrections, because the **ETA** is the sum of segment times plus turn and signal delays and pickup time.
- **Map matching**: GPS positions are noisy and must be snapped to the correct road.
- **Caching** ETAs for popular origin/destination cells for short periods, and computing ETAs for many drivers in one batch for ranking.

## 8. The location pipeline

At 250,000 updates a second, the rules are:

- Keep only the **latest position per driver** in memory; each update overwrites the entry (a write to the cell index). This is a **latest-value store**, not a log.
- **Batch and compress** updates from the app, and **adapt the frequency**: moving drivers every 3 to 5 seconds, idle or parked drivers less often; save battery and bandwidth.
- Send updates **asynchronously to a stream** ([stream processing](/sd/queues-and-streaming/stream-processing-basics/)) and store a **sampled or compacted history** for analytics, demand forecasting and audits; do not insert 2 TB a day into the operational database.
- When a driver crosses from one cell to another, the update **moves them between cells** atomically; if the cell lives on another shard, hand off the record.
- Drivers' devices lose connectivity: use **timestamps and TTLs** so stale drivers stop receiving offers, and make location updates idempotent and order-tolerant (ignore an update older than the one stored).

## 9. Tracking, pricing and reliability

- **Live tracking for the rider** subscribes to the assigned driver's location (over a WebSocket or server-sent events), smoothed and throttled to about once a second ([chat system](/sd/case-studies-core-services/design-a-chat-system/) shows the connection tier).
- **Surge pricing** compares supply (available drivers) and demand (open requests) per cell over a short window and raises prices smoothly; avoid oscillation by smoothing and by pricing at the level of **regions** rather than single cells.
- **Partition by city**: each city or region can run its own cluster of the location index and matching, so an outage or hot spot in one city does not affect others. Global services (accounts, payments) sit above them.
- **Hot spots** (airport queues, event ends): pre-scale, use virtual queues for airport pickup, and make matching tolerate surges by queueing and shedding load gracefully.
- **Failure handling**: if the live index is lost, **rebuild it from fresh updates** within seconds (drivers keep reporting); if the matching service is down, retry with backoff; if a driver's app disconnects mid-trip, the trip continues from stored state and reconnects.
- **Safety and trust**: trip sharing, SOS, anonymised phone numbers, identity verification, and fraud detection (GPS spoofing) belong in the design discussion.

## Pitfalls

- Searching only the rider's own cell, which misses drivers just across a boundary.
- Scanning all drivers per request instead of using a spatial index.
- Writing every location update to the main database.
- Read-check-write assignment of drivers, which double-books them under concurrency.
- Offers without expiry, so drivers who do not answer stay locked.
- Ranking by straight-line distance.
- A single global location index, so one region's load or failure affects everyone.
- Stale drivers (no TTL) receiving offers they never see.
- Surge prices that flip rapidly between cells.
- Treating latitude and longitude as equal-sized units (a degree of longitude is shorter away from the equator).
