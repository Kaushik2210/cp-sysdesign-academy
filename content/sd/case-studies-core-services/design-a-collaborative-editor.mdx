## The problem

Design a **collaborative document editor** like Google Docs: several people open the same document, **type at the same time**, see each other's changes and cursors within a fraction of a second, and everybody ends up with **exactly the same document**, even though edits were made concurrently, possibly offline, with no central referee deciding who "really" went first.

Why this is hard: two people edit the same sentence at once, each on their own screen, and the network delivers their edits in different orders to different people. If edits are described as "insert X at position 7", then after another edit lands the position 7 means something different. Naive handling gives **documents that silently disagree**, the worst outcome for an editor.

## Requirements

**Functional**
- Many users edit one document at once; changes appear for others in real time.
- **Convergence**: all users end up with the same text.
- **Intention preservation**: a user's edit should mean what they meant, even after other edits arrive.
- Show other users' **cursors and selections (presence)**.
- **Version history**, undo, and **offline editing** that merges when you reconnect.
- Permissions: view, comment, edit.

**Non-functional**
- Local typing feels instant (**no waiting for the server**).
- Remote edits arrive in **well under 200 milliseconds**.
- Documents are durable; a server crash loses no acknowledged edit.

## Estimation

| quantity | assumption | result |
| --- | --- | --- |
| Concurrent editing users | 5 million | |
| Operations per active user | about 1 per second (batched keystrokes) | about 5 million operations per second overall |
| Users per document | 2 or 3 typically, up to about 100 | per-document load is small |
| Operation size | about 50 bytes | about 250 MB per second of operation traffic |

The workload is **huge in total but tiny per document**: documents are independent, so the system **shards by document id** and every document's traffic is handled by one server (or a small group), never by a global component. The design problem is therefore **correctness of merging**, not raw throughput.

## Architecture

- Each client keeps a **full local copy** and applies its own edits **immediately** (optimistic, local-first). It sends **operations** to the server over a **WebSocket** ([real-time communication](/sd/networking-and-apis/real-time-communication/)).
- A **gateway routes by document id** (consistent hashing or a registry) so all collaborators of one document connect to the **same document server**. That server holds the live session in memory.
- The server **appends operations to a durable log** before acknowledging, **broadcasts** them to the other clients, and periodically writes a **snapshot** so loading a document does not mean replaying its whole history.
- **Presence** (cursors, selections, who is online) is **ephemeral**: kept in memory, sent over the same connection, never written to the log.
- On server failure, another server loads the **latest snapshot plus the log tail** and clients reconnect and **resend** operations the server has not acknowledged (operations carry unique ids, so resending is idempotent).

## Two ways to merge concurrent edits

### Operational transformation (OT)

Operations are positional ("insert 'x' at 7"). When two concurrent operations meet, each is **transformed** against the other so it still does the intended thing (if someone inserted a character before position 7, mine becomes position 8). Google Docs uses OT with a **central server that assigns one total order**, which keeps the transformation rules manageable. Pros: compact operations, small documents. Cons: the transformation functions are **notoriously hard to get right** (several published algorithms were later found to be incorrect), and it **needs the central ordering**.

### Conflict-free replicated data types (CRDT)

Give **every character a unique, permanent id**. An insert says "put this character **after the character with id X**", not "at position 7". A delete marks a character with that id as removed (a **tombstone**). Because operations name characters rather than positions, they **commute**: replicas can apply them **in any order** and reach the same result, **with no central server and no transformation**. This is what makes peer-to-peer and offline editing natural.

The ordering rule for two inserts after the same character: place the one with the larger id first (id = a logical clock plus the site id, see [logical clocks](/sd/distributed-theory/clocks-and-ordering/)). Every replica applies the same rule, so they pick the same order. This is the idea of the **RGA** algorithm.

## The simulation

The program is a small RGA-style CRDT. First a hand-made case: **two people type at the same spot at the same time**. Then **300 random sessions**: three editors start from the same text, make **four rounds of concurrent edits** (inserts and deletes, edits made without seeing the others'), and each replica receives the other editors' operations in a **random interleaving** (each editor's own operations stay in order, like separate network connections). For comparison the same sessions are run with **plain index-based operations** applied as they arrive, with no transformation.

class Replica:
    """A sequence CRDT in the style of RGA: every character has a unique id, inserts name the character
    they go after, deletes leave a tombstone. Operations commute, so replicas converge in any delivery order
    (as long as an insert is applied after the character it refers to)."""
    def __init__(self, site):
        self.site, self.clock = site, 0
        self.seq = []                # list of [id, char, deleted]
        self.known = set()           # ids already applied
        self.pending = []            # operations waiting for their reference character

    # ---- local edits generate operations ----
    def _visible(self):
        return [i for i, e in enumerate(self.seq) if not e[2]]

    def local_insert(self, index, ch):
        vis = self._visible()
        after = self.seq[vis[index - 1]][0] if index > 0 else None
        self.clock += 1
        op = ("ins", (self.clock, self.site), after, ch)
        self.apply(op)
        return op

    def local_delete(self, index):
        target = self.seq[self._visible()[index]][0]
        op = ("del", target)
        self.apply(op)
        return op

    # ---- applying operations (local or remote) ----
    def apply(self, op):
        self.pending.append(op)
        progress = True
        while progress:
            progress = False
            for p in list(self.pending):
                if self._ready(p):
                    self._do(p)
                    self.pending.remove(p)
                    progress = True

    def _ready(self, op):
        if op[0] == "ins":
            return op[1] not in self.known and (op[2] is None or op[2] in self.known)
        return op[1] in self.known

    def _do(self, op):
        if op[0] == "ins":
            _, nid, after, ch = op
            self.clock = max(self.clock, nid[0])
            pos = 0 if after is None else next(i for i, e in enumerate(self.seq) if e[0] == after) + 1
            while pos < len(self.seq) and self.seq[pos][0] > nid:       # skip concurrent siblings with a larger id
                pos += 1
            self.seq.insert(pos, [nid, ch, False])
            self.known.add(nid)
        else:
            for e in self.seq:
                if e[0] == op[1]:
                    e[2] = True

    def text(self):
        return "".join(e[1] for e in self.seq if not e[2])


def naive_apply(text, op):
    """Index based operations applied as they arrive, with no transformation."""
    kind, i, ch = op
    if kind == "ins":
        return text[:min(i, len(text))] + ch + text[min(i, len(text)):]
    return text[:i] + text[i + 1:] if i < len(text) else text

    """Other sites' operations in a random interleaving that keeps each site's own order (like separate network streams)."""
    queues = [list(b) for t, b in enumerate(batches) if t != me]
    out = []
    while any(queues):
        q = rnd.choice([q for q in queues if q])
        out.append(q.pop(0))
    return out

## What the output shows

- **The hand-made conflict**: both start with "cat". A types "s" at the end while B types "!" at the end, at the same moment. Each person applies the other's edit and **both see "cat!s"**. Both inserts named the same character ("t") as their predecessor; the tie is broken the same way everywhere by comparing ids, so the order agrees.
- **300 random sessions**: the CRDT replicas were **identical at the end in all 300**, and the **index-based replicas in none (0 of 300)**: positional operations applied without transformation diverge as soon as edits are concurrent. (A real OT system would transform them and converge; this is the baseline that shows why one of the two techniques is needed.)
- **The price of a CRDT**: on average each replica stored **about 26.5 characters but only 18.6 were visible**, so **about 7.9 were tombstones**: deleted characters are kept so later operations that refer to them still make sense. Tombstones **grow the data** over time; real systems **garbage collect** them once every replica is known to have seen the delete, and compress runs of characters typed together.

The sessions are small, synthetic and use a fixed seed; the tombstone share depends on how much is deleted. The convergence result is not luck: it follows from the operations being commutative, and the 300 runs are a check of the implementation.

## Presence, undo and history

- **Cursors and selections** attach to **character ids**, not positions, so a remote cursor stays in the right place as text changes around it.
- **Undo** must undo **your own** last operation, not the last operation overall: store inverse operations per user and transform or rebase them over later edits.
- **Version history** comes from the log plus snapshots: replay to any point, or diff two snapshots. Attribution (who typed what) comes from the operation's site id.
- **Rich text** (bold, lists, comments) needs a richer model: formatting is attached to ranges of character ids, and conflicts between formats (one person bolds, another deletes) need their own rules. Tree-shaped documents use CRDT or OT variants for trees.

## Offline editing

A CRDT client keeps editing offline and, on reconnecting, **sends the operations it accumulated and receives the others'**; commutativity does the merging. With OT, the client must transform its local operations over everything it missed, which is more complex and grows with the length of the outage. Offline merges can produce **surprising text** (two people rewrote the same sentence), so show **change attribution** and a **history** that makes it easy to repair.

## Pitfalls

- **Positional operations without transformation**: documents silently diverge (0 of 300 sessions converged in the demo).
- Making users **wait for the server** before showing their own keystrokes.
- Shipping a **hand-written OT** without a model checker or heavy randomised testing.
- **Unbounded tombstones** with no garbage collection.
- Using the **wall clock** to order edits: clocks differ; use logical clocks plus a site id.
- Writing **presence** to the durable log.
- **Losing acknowledged edits** because the log is written after the broadcast, not before.
- No **idempotent resend**: a reconnect duplicates operations.
- **Undo** that reverts other people's edits.
- Forgetting **permissions** checks on every operation, not only on opening the document.
