## The problem

Design an **email service** like Gmail or Outlook.com: users **receive** mail from anywhere on the internet, **send** mail to anywhere, keep a **mailbox** with folders or labels, **search** it, see messages grouped into **conversations**, and are protected from **spam and phishing**.

Email is a good case study because it is a **federated, decades-old protocol** (SMTP): you cannot change how other servers behave, they may be down for hours, nothing in the protocol proves who sent a message, and a large share of all traffic is hostile. The design is about **reliable delivery through unreliable parties**, **authenticating** senders after the fact, and **storing and searching a huge per-user archive**.

## Requirements

**Functional**
- Receive mail for the service's domains; send mail to other domains.
- Mailbox per user: inbox, labels or folders, read state, attachments.
- Conversation threading, search, drafts, and notifications of new mail.
- Spam and phishing filtering; bounce messages when delivery fails.

**Non-functional**
- **Never lose accepted mail**: once we answer "250 OK" to a sender, the message must be durably stored.
- **Reliable outbound delivery** despite temporarily failing destinations.
- Fast mailbox access and search (hundreds of milliseconds).
- Resist abuse: spam, forged senders, a compromised account used to spam.

### Receiving

- **MX records in DNS** tell the world which hosts accept mail for our domains ([DNS](/sd/networking-and-apis/dns/)). Many stateless SMTP gateways sit behind them, scaled horizontally.
- During the **SMTP conversation** the gateway can **reject cheaply**: unknown recipient, blocklisted sending IP, failed authentication policy, obvious spam. Rejecting *before* accepting the message means the sender is told, and we store nothing.
- **Accept only after durable write**: the gateway answers "250 OK" only once the message is on a replicated queue or store. Before that, a crash simply makes the sender retry (SMTP is built around retries).
- Delivery workers then **write the body to a blob store**, **metadata to the user's mailbox shard**, update the **search index**, and notify clients.

### Mailbox storage

- **Metadata** (sender, subject, labels, read flag, thread id, date, pointer to the body) lives in a **store sharded by user id**, in a wide-column or relational database, so a user's mailbox listing is a **range scan on one shard**.
- **Bodies and attachments** live in a **blob store**, keyed by content hash, so an attachment sent to 1,000 recipients is stored **once** (deduplication) ([blob stores](/sd/storage/blob-stores/)).
- **Labels, not folders**: a message has a set of labels; "move to folder" just changes labels, and a message can be in several places.
- **Search**: a **per-user inverted index** ([inverted indexes](/sd/search-systems/inverted-indexes-and-text-analysis/)) built by the indexer from each delivered message. Per-user indexes keep queries fast (they scan only your mail) and make privacy and deletion simple.

### Sending

Outbound mail goes into a **durable queue** and an **outbound sender** pool delivers it by SMTP to the recipient's MX host. Destinations are often unreachable or slow, so the sender uses **retries with backoff** and finally a **bounce** (a non-delivery message) to the sender. Outbound senders also **sign** messages (DKIM) and respect **per-destination rate limits** so large providers do not throttle us.

## The simulation

The program models four mechanisms with the Python standard library only:

1. **Delivery retries**: 10,000 messages per row, comparing **3 quick retries (give up after 15 minutes)** with **exponential backoff (5, 10, 20 ... 640 minutes, about 21 hours in all)**, first when the destination is **independently** up or down at each attempt, and then when **outages last a while** (30% of sends meet an outage averaging 3 hours).
2. **Message signing** in the spirit of DKIM, showing that editing the body or a signed header in transit breaks verification. (Real DKIM uses **public-key signatures** published in DNS so anyone can verify; this toy uses a shared-secret HMAC to stay in the standard library, which only the signer and verifier could share.)
3. **Threading** by following reply links between messages.
4. A **naive Bayes spam filter** trained on ten hand-written messages.

def deliver_all(n_messages, p_up, schedule, seed):
    """Each message is retried on the given schedule (minutes after the previous try) until the receiving
    server is reachable. The destination is up with probability p_up at each attempt, independently."""
    rnd = random.Random(seed)
    delivered, delays, attempts = 0, [], []
    for _ in range(n_messages):
        t, tries = 0, 0
        for wait in [0] + list(schedule):
            t += wait
            tries += 1
            if rnd.random() < p_up:
                delivered += 1
                delays.append(t)
                attempts.append(tries)
                break
    return delivered, delays, attempts


def deliver_outages(n_messages, schedule, seed, p_down=0.3, mean_outage=180):
    """Outages last for a while: with probability p_down the destination is down when we send, for an
    exponentially distributed number of minutes. Every attempt before the outage ends fails."""
    rnd = random.Random(seed)
    delivered, delays = 0, []
    for _ in range(n_messages):
        outage = rnd.expovariate(1 / mean_outage) if rnd.random() < p_down else 0
        t = 0
        for wait in [0] + list(schedule):
            t += wait
            if t >= outage:
                delivered += 1
                delays.append(t)
                break
    return delivered, delays

def canonical(headers, body, signed=("from", "to", "subject")):

def sign(domain, headers, body):
    return hmac.new(KEYS[domain], canonical(headers, body).encode(), hashlib.sha256).hexdigest()

def verify(domain, headers, body, sig):
    return hmac.compare_digest(sign(domain, headers, body), sig)


# ---------------------------------------------------------------- 3. threading by Message-ID / References
def thread(messages):
    """Group messages into conversations by following In-Reply-To links (union-find over message ids)."""
    parent = {m["id"]: m["id"] for m in messages}
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x
    for m in messages:
        if m.get("in_reply_to") in parent:
            parent[find(m["id"])] = find(m["in_reply_to"])
    groups = defaultdict(list)
    for m in messages:
        groups[find(m["id"])].append(m["id"])
    return sorted(groups.values())

    def train(self, text, label):

        for w in set(words(text)):

    def spam_probability(self, text):

        log = {}

## What the output shows

**Retries, independent failures.** When the destination is up half the time at each attempt, 3 quick retries deliver **93.6%** and backoff **99.8%** (4 attempts give 1 minus 0.5^4 = 93.75% in theory, 9 attempts give 99.8%). When it is up 20% of the time, quick retries deliver **59.6%** against **87.0%** for backoff, with a median delay of **15 minutes** instead of 5.

**Retries, realistic outages.** Real outages are **correlated**: a server that is down now is probably down in five minutes too. With 30% of sends meeting an outage of about 3 hours, quick retries deliver only **72.5%** (they give up before the outage ends) while exponential backoff delivers **100.0%**. The independent model **understates** how much backoff matters, because retrying again immediately is wasted when the cause lasts hours. This is why real mail servers keep retrying for **days** (commonly 4 to 5) before sending a bounce. The trade-off is that spread-out retries make a successful message take longer, and the queue holds more messages.

**Signing.** The untouched message **verifies**; changing "100" to "900" in the body, or the subject from "Invoice 42" to "Invoice 43", makes verification **fail**: a signature lets the receiver detect tampering after the fact. It does not stop someone from sending as their **own** domain; that is what SPF and DMARC policies are for (below).

**Threading.** Following reply links groups six messages into conversations [a, b, c], [d, e] and [f]: f replies to a message we never received, so it starts its own conversation. Real systems also fall back on subject lines and references headers when links are missing.

**Spam filter.** After training on ten messages, "free prize click now" scores **0.993** spam probability, "report for the friday meeting" **0.007**, and "free lunch at the meeting" **0.172**: it contains the spammy word "free" but mostly meeting words, so it stays on the ham side. This is a **toy** with ten training messages; production filters use millions of messages and many signals, and adversaries adapt.

The retry percentages come from 10,000 simulated messages per row with fixed seeds; they match the theory in the independent case and show the mechanism for the outage case, but the outage length and share are assumptions.

## Authenticating senders: SPF, DKIM, DMARC

SMTP lets anyone write any "From" address, so receivers check:

- **SPF**: the domain publishes in DNS which IP addresses may send for it. The receiver checks the connecting IP.
- **DKIM**: the sender signs selected headers and the body with a private key; the public key is in DNS. Receivers verify the signature (tampering fails, as in the demo).
- **DMARC**: the domain says what to do if SPF and DKIM do not **align** with the visible From domain (none, quarantine, reject) and where to send reports.

Together they make **forging a domain that publishes a strict DMARC policy** hard; they do not prove a message is *good*, since spammers can authenticate their own domains. Reputation, content analysis and user feedback remain essential.

## Spam and abuse

Layered defences, cheapest first:

1. **Connection level**: IP and domain **reputation**, blocklists, rate limits per sender, greylisting.
2. **Authentication**: SPF, DKIM and DMARC results as features.
3. **Content**: a classifier (naive Bayes as above, then gradient boosted trees or neural models) over words, URLs, header patterns, attachments; **link and attachment scanning**.
4. **Behaviour and feedback**: "report spam" clicks from many users feed back into reputation within minutes.
5. **Outbound controls**: rate limits per account, detection of sudden volume changes, and quarantine of **compromised accounts**, to protect our own **sending reputation** (if we send spam, other providers block us).

False positives (good mail in spam) are costlier than false negatives, so thresholds err towards delivering and filing in a spam folder rather than rejecting.

## Pitfalls

- Answering "250 OK" **before** the message is durably stored.
- **Short retry windows**: mail lost during an outage that lasts hours.
- Treating SMTP failures as independent when outages are **correlated**.
- **Bouncing spam** to forged sender addresses (backscatter) instead of rejecting during the conversation.
- Storing each attachment **once per recipient**.
- A single global search index, so every query scans everyone's mail.
- **Trusting the From header** without SPF, DKIM and DMARC checks.
- Ignoring our **outbound reputation**: one compromised account can get the whole service blocklisted.
- Scoring spam with a model trained once: spammers adapt, so the filter needs continual retraining and feedback.
- Deleting a message without removing it from the **index, blob references and backups** according to the retention policy.
