## Intuition

You want **exactly one** worker to run a nightly job, **one** server to be the leader of a shard, **one** process to hold the right to update a file. On a single machine you use a mutex. Across machines you need a **distributed lock**, and the first obstacle is that the holder can **fail while holding it**. If the lock never expires, a crashed holder blocks everyone for ever.

The standard answer is a **lease**: a lock with an expiry time. The holder must renew it before it runs out, and if it stops (crash, partition) the lock service will hand the lock to someone else after the lease expires. That solves the dead-holder problem but creates a subtle new one: a holder can be **paused** (garbage collection, a VM stall, a slow disk, a laptop going to sleep) for longer than the lease, **not know that its lease expired**, and then carry on and act as if it still holds the lock. Now two processes both believe they are the exclusive holder.

## Definition

- **Lease:** a time-limited grant of a right (a lock, leadership of a shard, a cache entry's validity) from a lock service. Correctness cannot depend on the holder noticing the expiry in time.
- **Lock service:** a small strongly consistent store (ZooKeeper, etcd, Consul, Chubby) built on consensus. It decides who holds each lock, and it can expire leases using its own clock.
- **Fencing token:** a number that **increases every time the lock is granted**. The lock service gives the holder its token; the holder includes it in every request to the protected resource; the **resource itself** remembers the highest token it has seen and **rejects any request with a lower one**.

```text
client A acquires lock           -> token 33
client A pauses (longer than the lease)
lock service expires A's lease; client B acquires lock -> token 34
client B writes to storage with token 34   -> accepted, storage remembers 34
client A wakes up and writes with token 33 -> REJECTED (33 < 34)
```

The key point: you **cannot** make a lock safe from the client side alone, because the client cannot know in time that it lost the lock. Safety comes from a check at the **resource**. Without fencing, a lease gives you *efficiency* (usually only one worker does the job) but not *correctness* (never two).

## Building coordination on a consensus store

Systems like ZooKeeper and etcd offer primitives that make these patterns easy:

- **Ephemeral nodes / leases tied to sessions:** a key that disappears when the client's session times out.
- **Sequential nodes / revisions:** a monotonically increasing number per creation. Use it as the fencing token, since the store's commit order is a total order.
- **Watches:** be notified when a key changes, instead of polling.
- **Recipes:** leader election (the lowest sequential node is leader and each candidate watches its predecessor), group membership, barriers and distributed queues.

Keep the lock service for **coordination**, not for data; its throughput is limited (every write is a majority commit).

## Code: pausing past the lease

Client A takes a lock with a 10 second lease (token 1) and then pauses for a random, exponentially distributed time before writing. If the pause exceeds the lease, the lock service gives the lock to client B (token 2), which writes. A then wakes up and writes. The storage either accepts every write (no fencing) or compares the token with the highest it has seen (fencing).

<CodeRunner language="python" timeoutMs={30000} code={`import random

random.seed(9)
LEASE = 10.0

class Storage:
    def __init__(self, fencing):
        self.fencing, self.max_token, self.value, self.log = fencing, 0, None, []

    def write(self, token, value):
        if self.fencing and token < self.max_token:
            return False
        self.max_token = max(self.max_token, token)
        self.value = value
        self.log.append((token, value))
        return True

def trial(pause_mean, fencing):
    store = Storage(fencing)
    pause = random.expovariate(1 / pause_mean)
    a_token = 1
    expired = pause > LEASE
    if expired:
        store.write(2, "B")
    accepted = store.write(a_token, "A")
    stale_write_landed = expired and accepted
    return expired, stale_write_landed

print("lease 10 s; client A pauses for an exponentially distributed time before its write; 200000 trials per row")
print(" mean pause   lease expired during pause   stale write overwrites B")
print("                                           no fencing   with fencing tokens")
for pause_mean in (1, 3, 5):
    exp = no_f = with_f = 0
    for _ in range(200000):
        e, landed = trial(pause_mean, False)
        exp += e
        no_f += landed
    random.seed(9 + pause_mean)
    for _ in range(200000):
        e, landed = trial(pause_mean, True)
        with_f += landed
    print(f" {pause_mean:4d} s     {100 * exp / 200000:12.3f}%                    {100 * no_f / 200000:8.3f}%      {100 * with_f / 200000:8.3f}%")
`} />

### Measured results

Running this exact program with Python 3.13 produced:

| mean pause | lease expired during the pause | stale write overwrites B, no fencing | stale write overwrites B, with fencing |
| --- | --- | --- | --- |
| 1 s | 0.005% | 0.005% | 0.000% |
| 3 s | 3.602% | 3.602% | 0.000% |
| 5 s | 13.616% | 13.616% | 0.000% |

Every lease expiry during a pause became a **lost update** without fencing, and none did with it. Longer average pauses make the problem frequent: with a mean pause of 5 seconds (not unusual for a loaded JVM or a swapping machine) more than 1 in 8 operations would have corrupted data. Even 0.005% is not negligible at a million operations a day (about 50 corrupted updates). The pause distribution here is a simple assumption; real pauses are heavy tailed and correlated (a stop-the-world GC hits many processes at once).

<Callout type="warning" title="Do not use clocks to decide you still hold the lock">
Code such as `if (now < lease_expiry) write()` does not help: the pause can start **after** the check and before the write, and clocks on different machines disagree. Only the protected resource can reliably reject a stale holder, which is why the token travels with every request.
</Callout>

## Pitfalls

- Treating a lease as a guarantee of exclusion. It guarantees only that the *service* will not grant the lock to two clients at once; the first client may not have noticed it lost it.
- Using a cache such as a single Redis instance as a correctness lock: a failover can grant the same lock twice, and there is no fencing token.
- Renewing the lease from a background thread that can be paused together with the worker.
- Computing the token on the client (timestamps) instead of getting a monotonically increasing number from the consensus store.
- Holding locks across slow operations such as remote calls; split the work or use optimistic concurrency.
- Forgetting to make the resource check the token (the most common mistake), so the token is generated but never enforced.

## What would you choose and why?

Ten workers share a queue of invoices to email, and each invoice must be sent at most once. A worker takes a lock on an invoice, sends the email and marks it sent. A worker can pause for 20 seconds. Would you use a lease, fencing, an idempotency key at the mail provider, or all three? Where does the fencing check live when the email provider is an external service that does not know about your tokens?
