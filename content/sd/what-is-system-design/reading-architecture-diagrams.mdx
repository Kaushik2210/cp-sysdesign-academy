## Intuition

Almost every web system is assembled from the same handful of parts. Once you know what each part is *for*, an architecture diagram stops being a wall of rectangles and becomes a story: a request enters on the left, hits some components, and either returns an answer or leaves a side effect on the right. This lesson gives you that vocabulary and a method for reading any diagram.

## How to read a diagram

Ask four questions of every diagram, in order:

1. **Where does a request enter?** Find the client and the first server it touches.
2. **What is on the hot path?** Follow the arrows for the most common request. Anything on it adds latency.
3. **What is synchronous and what is asynchronous?** A solid call waits for an answer; a queue means "do it later".
4. **Where does state live?** State (data that must survive) is the hard part. Stateless boxes are easy to replicate; stateful ones need care.

Arrows should mean one thing. In this course an arrow points from caller to callee, and its label names the operation or protocol. If an arrow has no label, it is a hint the author has not decided what it means.

## The building blocks

| Block | What it does | Typical problem it solves |
| --- | --- | --- |
| Client | Browser, mobile app or another service that starts requests | Presents the product; cannot be trusted |
| DNS | Turns a name like `example.com` into an IP address | Finding the server |
| CDN | Caches static content at edge locations near users | Latency and origin load for images, scripts, video |
| Load balancer | Spreads requests across servers and drops unhealthy ones | Scaling out, removing a single server as a failure point |
| Application server | Runs business logic; ideally stateless | Handling requests; scales horizontally |
| Cache | In-memory store for hot data (for example Redis or Memcached) | Slow or expensive reads |
| Database | Durable, queryable storage of the source of truth | Persistence, consistency, queries |
| Message queue | Buffers work between producer and consumer | Bursts, slow downstream systems, decoupling |
| Object storage | Cheap, durable storage for large blobs (images, backups) | Files too big for a database |

<Callout type="note" title="Stateless is a superpower">
If an app server keeps no per-user data in its own memory or disk, any server can handle any request. That is what lets a load balancer add and remove servers freely. Put session data in a shared store or in a signed token instead.
</Callout>

## Reading numbers off the diagram

Order-of-magnitude costs help you judge a diagram quickly. These are approximations that vary with hardware and distance:

- Memory read: around 100 nanoseconds.
- Cache hit over the network in the same data centre: well under 1 to a few milliseconds including the network hop.
- Database query served from disk or its buffer cache: from a few milliseconds up to hundreds under load.
- Round trip within one data centre: around 0.5 ms; across continents: roughly 100 to 200 ms.

If a request path makes ten sequential database calls, you can read "tens of milliseconds at least" straight from the picture.

## Pitfalls

- Drawing every possible component. Each box needs a stated reason to exist; if you cannot say what breaks without it, remove it.
- Mixing levels of detail: "Redis" next to "backend" next to "the internet" in one picture.
- Ignoring the data stores. Diagrams that show ten services and one unnamed "DB" hide the hardest decisions.
- Treating arrows as free. Each network hop adds latency and a new way to fail.

## What would you choose and why?

Your product page is slow only for users far from your data centre, and the slow part is downloading images and scripts. Which block do you add first: a cache, a CDN, or more app servers? Explain what evidence in a diagram or a trace would confirm your choice.
