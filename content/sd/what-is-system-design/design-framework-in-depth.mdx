## Intuition

The framework from the previous lesson is a checklist. This lesson walks it end to end on one problem so you can see how each step *constrains* the next: requirements decide the estimates, estimates decide the data store, and the store and the traffic shape decide where the bottlenecks are. We will design a **notification service** that other teams in a company call to send push, email and SMS messages to users.

## Step 1: Clarify

Good clarifying questions turn a vague prompt into a testable spec. Ask, then write the answers down.

| Question | Assumed answer |
| --- | --- |
| Who calls the service? | Internal product services via an API, not end users directly |
| Which channels? | Push, email, SMS |
| Delivery guarantee? | At least once; duplicates are tolerable but should be rare |
| Latency? | Transactional messages (one-time codes) within seconds; marketing within minutes |
| Scale? | 10 million users, about 5 notifications per user per day on average |
| User preferences? | Users can opt out per channel; opt-outs must be honoured |
| Out of scope | Building the email or SMS carrier, a rich-text template editor |

<Callout type="note" title="Scope is a feature">
Writing the out-of-scope list is not wasted time. It protects the design from growing without bound and gives you something to point at when a new requirement appears.
</Callout>

## Step 2: Estimate

Back-of-envelope numbers only need to be right within a factor of two or three.

- Volume: 10M users times 5 per day is 50M notifications per day.
- Average rate: 50M divided by 86,400 seconds is about 580 per second.
- Peak: traffic is bursty (a sale starts, a match ends). Assume a peak of 10 times the average, so roughly 6,000 per second.
- Storage: a record of about 500 bytes (ids, channel, status, timestamps, a payload reference) gives about 25 GB per day. Keeping 30 days for debugging and audit is about 750 GB.
- Fan-out: a single "flash sale" request may target 5M users. That one API call becomes 5M delivery tasks, which at 6,000 per second takes about 14 minutes to drain. This is the number that drives the design.

<Callout type="tip">
Always estimate the *worst realistic burst*, not only the average. Averages hide the moment the system falls over.
</Callout>

## Step 3: API

Keep the contract small and explicit. Callers supply an idempotency key so retries do not send duplicates.

```http
POST /v1/notifications
Idempotency-Key: 7c1d-order-4412-shipped
Content-Type: application/json

{
  "userId": "u_981",
  "channel": "push",
  "template": "order_shipped",
  "params": { "orderId": "4412" },
  "priority": "high"
}
```

The response is `202 Accepted` with `{ "id": "n_5521", "status": "queued" }`. Returning `202` rather than `200` is deliberate: the service has *accepted* the work, not completed it. A `GET /v1/notifications/n_5521` returns the status (`queued`, `sent`, `failed`). A bulk endpoint accepts an audience description instead of a single user.

## Step 4: Data model

Access patterns decide the store:

- Look up one notification by id (status checks): key-value access.
- List recent notifications for a user (inbox, debugging): partition by `userId`, sort by time.
- Preferences: read on every send, tiny, rarely written: a relational table plus a cache.

A wide-column or key-value store partitioned by `userId` handles the first two at 6,000 writes per second comfortably; preferences stay in a relational database. Using two stores is fine when access patterns genuinely differ, but each extra store is another thing to operate.

## Step 5: High-level design

The central idea is to **decouple accepting a request from delivering it** with a queue. The API validates and stores the request, then returns quickly. Workers pull tasks and call external providers (a push gateway, an email provider, an SMS provider). Separate queues per channel and priority stop a slow SMS provider from delaying one-time codes.

## Step 6: Deep dive on the hardest part

Pick the part where the design can go wrong. Here it is *reliable delivery without duplicates*. The queue gives at-least-once delivery: if a worker crashes before acknowledging, the task is redelivered. To make duplicates harmless, the worker records a per-notification attempt key (for example notification id plus channel) before sending and passes it to providers that support idempotency. Exactly-once delivery across a network to a third party is not achievable in general; the practical target is *at-least-once plus idempotent handling*.

Retries use exponential backoff with jitter (wait about 1s, 2s, 4s and so on, each randomised) so a recovering provider is not hit by a synchronised retry wave. After a fixed number of attempts the task moves to a **dead-letter queue** for inspection.

## Pitfalls

- Skipping estimation and then discovering the fan-out problem in the final minutes.
- Treating the queue as a magic fix. A queue moves the problem to "how big can the backlog get and how fast can we drain it".
- Promising exactly-once delivery. Say at-least-once with idempotent consumers.
- Forgetting user preferences and rate limits, which are real product requirements.

## What would you choose and why?

Product asks that one-time login codes must arrive within 5 seconds even during a marketing blast. Do you add more workers to the shared queue, split queues by priority, or move codes to a separate service entirely? Write your answer, then name the failure mode of your choice.
