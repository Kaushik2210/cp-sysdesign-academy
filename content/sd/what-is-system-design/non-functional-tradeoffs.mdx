## Intuition

You cannot maximise everything. Making reads faster usually costs memory or freshness; making a system more available usually costs money and consistency; raising throughput often raises the latency of an individual request. Design is choosing which quality to protect and which to spend. This lesson puts numbers on those choices so they stop being slogans.

## Latency vs throughput

**Latency** is how long one request takes. **Throughput** is how many requests finish per unit time. They are related but not the same: a highway can move many cars per hour (throughput) while each trip is still long (latency).

**Little's Law** ties them together: the average number of requests in flight equals throughput times average latency.

- 1,000 requests per second with 200 ms latency means about 1,000 times 0.2 = 200 requests in flight at once.
- If a downstream slowdown pushes latency to 2 s at the same arrival rate, in-flight requests grow to about 2,000. Thread pools and connection pools run out, which is how a slow dependency becomes an outage.

**Batching** shows the trade directly. Writing 1 record per disk flush wastes work; writing 100 records per flush raises throughput a lot, but each record now waits up to the batch window before it is acknowledged. You buy throughput with latency.

**Percentiles matter.** Averages hide the slow tail. If a page needs 10 backend calls in parallel and each has a 1% chance of being slow, the page is slow about 1 minus 0.99 to the tenth, roughly 10%, of the time. So track p50, p95 and p99, not just the mean.

## Availability vs cost

Availability is the fraction of time the system is up. Each extra nine is dramatically stricter:

| Availability | Downtime per year (approx.) | Downtime per month (approx.) |
| --- | --- | --- |
| 99% | 3.65 days | 7.3 hours |
| 99.9% | 8.76 hours | 43.8 minutes |
| 99.99% | 52.6 minutes | 4.4 minutes |
| 99.999% | 5.26 minutes | 26 seconds |

Components in **series** (all must work) multiply: two 99.9% components in a chain give 0.999 times 0.999, about 99.8%. Components in **parallel** (any one suffices, with perfect failover) fail only when all fail: two independent 99.9% replicas give 1 minus 0.001 squared, which is 99.9999%. Real failover is imperfect and failures are often correlated (same bug, same region, same bad config), so treat the parallel figure as an upper bound.

Redundancy costs money: a second region roughly doubles infrastructure for that tier and adds data-replication complexity. The right target depends on the cost of downtime. A internal reporting tool does not need five nines.

## Availability vs consistency

When a network partition separates replicas, a system must choose: refuse some requests (stay consistent) or answer with possibly stale data (stay available). This is the practical content of the CAP theorem. It applies *during a partition*; when the network is healthy, the real everyday trade-off is between latency and consistency, because waiting for more replicas to confirm a write takes longer.

- **Strong consistency**: after a write completes, every read sees it. Examples where it matters: account balances, inventory for the last item, unique usernames.
- **Eventual consistency**: replicas converge if writes stop. Acceptable for like counts, view counts, a news feed slightly behind.

A quorum illustration: with N = 3 replicas, requiring W = 2 acknowledgements for writes and R = 2 for reads gives W + R = 4, which is more than N, so every read overlaps at least one replica with the latest write. Choosing W = 1 makes writes faster and more available but allows stale reads.

## Cost

Cost is a first-class requirement. Questions to ask: what dominates the bill (compute, storage, network egress, per-request fees)? Is the load steady (reserved capacity is cheaper) or spiky (elastic capacity is cheaper)? Simple examples with approximations:

- Keeping 1 TB in RAM costs far more than 1 TB on SSD, which costs far more than 1 TB in cold object storage. A cache is expensive per byte, so cache only the hot subset.
- Cross-region and internet egress is often priced per gigabyte and can dominate a media-heavy product; a CDN can lower it.
- Engineer time is also cost: a simpler design you can operate beats a clever one you cannot.

## Pitfalls

- Quoting "five nines" without computing the downtime budget or asking what the business actually needs.
- Multiplying availabilities as if failures were independent when they share a region, a deploy or a dependency.
- Reporting average latency only. Tail latency is what users and upstream timeouts feel.
- Saying "we need strong consistency" for everything. Decide per data type: balances yes, view counters no.
- Forgetting that CAP is about behaviour during partitions, not a menu of two permanent choices.

## What would you choose and why?

A shopping site shows "3 left in stock". For checkout you can read the count from a replica that is at most a few seconds stale, or from the primary on every read. Which do you use for the product page, and which for the final purchase step? Defend each choice using latency, consistency and cost.
