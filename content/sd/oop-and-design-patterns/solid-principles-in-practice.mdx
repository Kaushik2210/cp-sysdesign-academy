## Intuition

Code that works today is easy. Code that you can **change next month without breaking something unrelated** is hard. Most real programs live for years and change constantly: a new payment method, a new report format, a new notification channel. **Low-level design** is the craft of arranging classes and functions so that such changes are **small and local**.

The **SOLID** principles are five widely taught guidelines for doing that in object-oriented code:

| letter | principle | one-line meaning |
| --- | --- | --- |
| **S** | Single Responsibility | a class should have **one reason to change** |
| **O** | Open/Closed | add new behaviour by **adding code**, not by editing working code |
| **L** | Liskov Substitution | a subtype must be usable **anywhere its base type is**, without surprises |
| **I** | Interface Segregation | many **small, focused interfaces** beat one fat one |
| **D** | Dependency Inversion | depend on **abstractions**, not on concrete details |

They are **heuristics, not laws**. Each one trades a little extra structure for easier change, and the trade is only worth it where change is actually likely. This lesson shows each principle as a **smell, a refactoring and a payoff**, in code you can run.

## S: Single Responsibility Principle

**A class should have one reason to change.** "Reason to change" means a **kind of stakeholder or concern**: the people who decide business rules, the people who decide how output looks, the people who decide where data is stored.

**The smell:** a class that does several unrelated jobs, so a change to one job risks the others and every test needs everything.

<CodeRunner language="python" code={`# BEFORE: one class computes, formats and saves. Three reasons to change.
class ReportBefore:
    def __init__(self, sales):
        self.sales = sales
    def total(self):
        return sum(self.sales)
    def to_text(self):
        return f"Total sales: {self.total():.2f}"
    def save(self, path):
        with open(path, "w") as f:
            f.write(self.to_text())

# AFTER: each class has one reason to change.
class SalesReport:                              # the business rule: what is in the report
    def __init__(self, sales):
        self.sales = sales
    def total(self):
        return sum(self.sales)

class TextFormatter:                            # how it looks
    def format(self, report):
        return f"Total sales: {report.total():.2f}"

class HtmlFormatter:                            # a new format changes only this file
    def format(self, report):
        return f"<p>Total sales: <b>{report.total():.2f}</b></p>"

class InMemoryStorage:                          # where it goes (a real one would write a file or a database row)
    def __init__(self):
        self.saved = {}
    def save(self, name, content):
        self.saved[name] = content

report = SalesReport([120.5, 80.25, 99.25])
storage = InMemoryStorage()
for formatter in (TextFormatter(), HtmlFormatter()):
    storage.save(type(formatter).__name__, formatter.format(report))
for name, content in storage.saved.items():
    print(f"{name:14s} {content}")
print("The total is computed once; adding PDF output or database storage touches neither the rule nor the other formats.")
`} />

**Payoff:** adding an HTML format changed **no existing class**, and the business rule (`total`) can be tested without touching a file system. **Caution:** do not split a class until there is a real second reason to change. A class with a few related methods is fine; "one method per class" is the over-engineered extreme.

## O: Open/Closed Principle

**Software entities should be open for extension but closed for modification.** Adding a new case should mean **adding a new class or function**, not editing a long chain of `if/elif` in tested code (where each edit risks breaking an old case).

**The smell:** a function that switches on a type name or a flag, and gets another branch every few weeks.

<CodeRunner language="python" code={`# BEFORE: every new customer type means editing this function (and re-testing all branches).
def discount_before(kind, amount):
    if kind == "regular":
        return amount
    elif kind == "member":
        return amount * 0.9
    elif kind == "vip":
        return amount * 0.8
    raise ValueError(kind)

# AFTER: each rule is an object with the same interface; new rules are new classes.
from abc import ABC, abstractmethod

class Discount(ABC):
    @abstractmethod
    def apply(self, amount: float) -> float: ...

class NoDiscount(Discount):
    def apply(self, amount): return amount

class Percent(Discount):
    def __init__(self, percent): self.factor = 1 - percent / 100
    def apply(self, amount): return amount * self.factor

class Student(Discount):                        # added later: no existing code was edited
    def apply(self, amount): return max(0.0, amount - 5.0)

def checkout(amount, discount: Discount):
    return round(discount.apply(amount), 2)

print("regular  :", checkout(100, NoDiscount()))
print("member   :", checkout(100, Percent(10)))
print("vip      :", checkout(100, Percent(20)))
print("student  :", checkout(100, Student()), " <- a new rule, added without touching checkout() or the others")
print("same results as the old function:", all(abs(checkout(100, d) - discount_before(k, 100)) < 1e-9 for k, d in (("regular", NoDiscount()), ("member", Percent(10)), ("vip", Percent(20)))))
`} />

**Payoff:** `checkout` is **closed** (it never changes) while behaviour is **open** to extension. This is the **Strategy pattern**, covered with the other design patterns later in this module. **Caution:** do not build an extension point for variation that may never come. A two-case `if` is fine until a third case appears (a good rule of thumb: **refactor on the third occurrence**).

## L: Liskov Substitution Principle

**If `S` is a subtype of `T`, code that works with a `T` must keep working when given an `S`.** Subclasses must honour the **behavioural contract** of the parent (what it promises, what it accepts), not only its method signatures.

**The smell:** a subclass that throws on a method the parent supports, ignores a guarantee, or needs `isinstance` checks around it. The classic example: a `Square` that inherits from `Rectangle`.

<CodeRunner language="python" code={`# BEFORE: Square "is a" Rectangle in geometry, but not in behaviour.
class Rectangle:
    def __init__(self, w, h):
        self.w, self.h = w, h
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h
    def area(self): return self.w * self.h

class Square(Rectangle):
    def set_width(self, w): self.w = self.h = w          # keeps it square...
    def set_height(self, h): self.w = self.h = h          # ...but breaks what Rectangle promised

def stretch(rect):
    """Written against Rectangle's contract: setting the width must not change the height."""
    rect.set_width(5)
    rect.set_height(4)
    return rect.area()                                    # a Rectangle promises 5 * 4 = 20

print("Rectangle:", stretch(Rectangle(1, 1)))
print("Square   :", stretch(Square(1, 1)), " <- surprise: the contract was broken (expected 20)")

# AFTER: model what the types promise. Both are Shapes with an area; neither pretends to be the other.
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Rect(Shape):
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h

class Sq(Shape):
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2

def total_area(shapes):
    return sum(s.area() for s in shapes)

print("any Shape works:", total_area([Rect(5, 4), Sq(3)]))
`} />

**Payoff:** code written against the base type keeps working with every subtype. Warning signs of an LSP violation: overriding a method to do **nothing** or **raise `NotImplementedError`**, **strengthening preconditions** (accepting less than the parent) or **weakening postconditions** (promising less). The usual cure is **composition** or a **different hierarchy** that reflects behaviour, not real-world taxonomy.

## I: Interface Segregation Principle

**Clients should not be forced to depend on methods they do not use.** Prefer several small interfaces over one large one.

**The smell:** implementers that must stub out methods (`raise NotImplementedError`, or silently do nothing) because the interface demands more than they offer.

<CodeRunner language="python" code={`from typing import Protocol

# BEFORE: one fat interface. A basic printer is forced to claim it can scan and fax.
class MultiFunctionDevice(Protocol):
    def print_doc(self, doc: str) -> str: ...
    def scan(self) -> str: ...
    def fax(self, doc: str) -> str: ...

class BasicPrinterBefore:
    def print_doc(self, doc): return f"printed {doc}"
    def scan(self): raise NotImplementedError("this printer cannot scan")      # a lie in the type
    def fax(self, doc): raise NotImplementedError("this printer cannot fax")

# AFTER: small roles. Each class implements only what it truly does.
class Printer(Protocol):
    def print_doc(self, doc: str) -> str: ...

class Scanner(Protocol):
    def scan(self) -> str: ...

class BasicPrinter:
    def print_doc(self, doc): return f"printed {doc}"

class OfficeMachine:
    def print_doc(self, doc): return f"printed {doc}"
    def scan(self): return "scanned page"

def print_report(printer: Printer, text):       # depends only on what it needs
    return printer.print_doc(text)

def archive_paper(scanner: Scanner):
    return scanner.scan()

print(print_report(BasicPrinter(), "Q3 report"))
print(print_report(OfficeMachine(), "Q3 report"))
print(archive_paper(OfficeMachine()))
print("A type checker such as mypy rejects archive_paper(BasicPrinter()): the mistake shows up in the design, before the code runs.")
`} />

**Payoff:** functions ask for the **narrowest role** they need (a type checker enforces it), implementers stay honest, and tests need smaller fakes. Python's `Protocol` (structural typing) makes this lightweight: anything with the right methods qualifies, with no inheritance required. In languages with explicit interfaces, the same idea splits `IWorker` into `IRunnable` and `IFeedable`.

## D: Dependency Inversion Principle

**High-level policy should not depend on low-level details; both should depend on abstractions.** Concretely: a class that **creates** its collaborators (`self.mailer = SmtpMailer()`) is welded to them. Instead, it should **receive** something that satisfies an interface (**dependency injection**).

**The smell:** business logic that instantiates a database client, an HTTP client or a clock inside itself, so you cannot test it without the real thing.

<CodeRunner language="python" code={`from typing import Protocol

# BEFORE: the service builds its own mailer, so every test would really send email.
class SmtpMailer:
    def send(self, to, body):
        raise RuntimeError("would contact a real mail server")

class SignupBefore:
    def __init__(self):
        self.mailer = SmtpMailer()                  # a hard-wired low-level detail
    def register(self, email):
        self.mailer.send(email, "Welcome!")

try:
    SignupBefore().register("ada@example.com")
except RuntimeError as e:
    print("before: cannot test without side effects ->", e)

# AFTER: depend on an abstraction and receive it from outside.
class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...

class SignupService:
    def __init__(self, mailer: Mailer):
        self.mailer = mailer
    def register(self, email):
        if "@" not in email:
            raise ValueError("invalid email")
        self.mailer.send(email, "Welcome!")
        return "registered"

class FakeMailer:                                   # a test double: records instead of sending
    def __init__(self): self.outbox = []
    def send(self, to, body): self.outbox.append((to, body))

fake = FakeMailer()
print("after:", SignupService(fake).register("ada@example.com"), fake.outbox)
print("after: invalid input never reaches the mailer:", end=" ")
try:
    SignupService(fake).register("nope")
except ValueError:
    print(len(fake.outbox) == 1)
`} />

**Payoff:** `SignupService` knows nothing about SMTP, queues or vendors. In production you pass an SMTP or queue-backed mailer; in tests, a fake; later, a different provider, with **no change to the service**. The **composition root** (usually `main`) is the one place that decides which concrete classes to wire together. Note the arrow of **source-code dependency** now points from details toward the abstraction, which is the "inversion".

## Putting it together: composition over inheritance

All five principles point toward the same habit: **assemble behaviour from small objects (composition) rather than extending deep class hierarchies (inheritance).** Inheritance couples a subclass to its parent's internals and invites LSP violations; composition lets you swap pieces at runtime. A useful default: **prefer an interface plus composition; use inheritance only for a true "is-a" relationship with a stable contract.**

## How the principles relate to system design

The same ideas appear at larger scale: a **microservice** with one clear responsibility (S), extended by new services rather than edits to a core (O), exposing a narrow API (I) and depending on contracts, not another service's internals (D). ## Pitfalls

- Applying every principle everywhere: dozens of one-method classes, interfaces with a single implementation and no second one in sight.
- Splitting responsibilities by technical layer only when the real axes of change are business concepts.
- An `if isinstance(...)` ladder around a polymorphic call (a sign of an LSP or OCP problem).
- Subclasses that override a method to raise or do nothing.
- Fat interfaces that grow every time a new implementer needs one more method.
- Hard-wired `new` of databases, clocks, random numbers or network clients inside business logic.
- Mocking everything: tests that verify call sequences instead of behaviour.
- Reading the principles as rules rather than as tools for reducing the cost of change.
