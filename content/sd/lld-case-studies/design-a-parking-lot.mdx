## The problem

Low-level design (LLD) interviews, and real design work, ask a different question from system design: not "how do we scale this across machines?" but **"what are the classes, what does each one own, and how do they collaborate?"** The **parking lot** is the standard first exercise because everyone understands the domain and it exercises every skill: clarifying requirements, finding entities, choosing interfaces, applying a couple of patterns, handling concurrency and leaving room for change.

A good process, which this lesson follows:

1. **Clarify requirements** and decide the scope out loud.
2. **Find the entities** (the nouns) and their **relationships**.
3. **Identify behaviours** (the verbs) and decide **which class owns each one**.
4. **Apply patterns only where variation is real** (strategies for allocation and pricing).
5. **Write the code** with clear invariants and **test it**.
6. **Discuss concurrency, failure and extensions.**

## 1. Requirements

Ask first. For this design assume:

- A lot has **several floors**, each with **spots of different sizes** (small, medium, large).
- Vehicles are **motorcycles, cars and trucks**. A motorcycle fits any spot, a car fits medium or large, a truck needs a large spot.
- On **entry** the lot **assigns a spot** and gives the driver a **ticket**. On **exit** the driver presents the ticket and **pays** according to the time parked and vehicle type.
- The lot can be **full** (for that vehicle type). The same vehicle cannot be parked twice.
- **Multiple entrances** act at the same time, so two cars must never be given the same spot.
- Pricing and the choice of spot must be **easy to change** (peak rates, "park near the exit" versus "keep large spots free").

**Out of scope** for now: reservations, payment processing, EV charging, persistence, display boards. We will say how each would fit in at the end.

## 2. Entities and relationships

Read the requirements and underline the nouns:

| noun | role in the design |
| --- | --- |
| **Vehicle** | a plate number and a type; an immutable value |
| **Spot** | belongs to a floor, has a size, may hold a vehicle |
| **Ticket** | a record that a vehicle is in a spot since a time; immutable |
| **ParkingLot** | owns all spots and tickets; the only place that changes them |
| **Allocation strategy** | decides which free spot a vehicle gets |
| **Pricing strategy** | turns parked time and vehicle type into a fee |

Two design decisions shape everything:

- **One class owns the invariants.** `ParkingLot` is the only code that marks a spot occupied or free, and does so inside one critical section. Nothing else mutates spots.
- **Variation lives in strategies.** Allocation and pricing are the parts that business will keep changing, so each gets an interface (the [Strategy pattern](/sd/oop-and-design-patterns/behavioral-patterns/)). Everything else is plain data.

## 3. The code

The model below is complete and runnable. Notes on the choices:

- **Value objects** (`Vehicle`, `Ticket`) are frozen dataclasses: they cannot change, so they are safe to share and to use as dictionary keys.
- The **fit rules** live in **one table** (`FITS`), not scattered as `if` statements.
- **Time is passed in** (`now`) instead of read from a clock inside the class. This makes the code **deterministic and testable**: tests choose the times.
- `park` does **check-and-claim inside one lock**, the same discipline as the atomic conditional update in the [ticket booking case study](/sd/case-studies-data-and-transactions/design-a-ticket-booking-system/).
- The lot keeps a **plate index** to reject the same vehicle parking twice.

<CodeRunner language="python" timeoutMs={30000} code={`import math, threading
from abc import ABC, abstractmethod
from dataclasses import dataclass
from enum import Enum, IntEnum


class VehicleType(Enum):
    MOTORCYCLE = "motorcycle"
    CAR = "car"
    TRUCK = "truck"


class SpotSize(IntEnum):
    SMALL = 1
    MEDIUM = 2
    LARGE = 3


# which spot sizes can hold which vehicle (a design decision kept in one table)
FITS = {
    VehicleType.MOTORCYCLE: {SpotSize.SMALL, SpotSize.MEDIUM, SpotSize.LARGE},
    VehicleType.CAR: {SpotSize.MEDIUM, SpotSize.LARGE},
    VehicleType.TRUCK: {SpotSize.LARGE},
}


@dataclass(frozen=True)
class Vehicle:
    plate: str
    kind: VehicleType


@dataclass
class Spot:
    spot_id: str
    floor: int
    size: SpotSize
    vehicle: Vehicle | None = None

    def is_free(self):
        return self.vehicle is None


@dataclass(frozen=True)
class Ticket:
    ticket_id: int
    vehicle: Vehicle
    spot_id: str
    entered_at: float


class LotFull(Exception):
    pass


class AlreadyParked(Exception):
    pass


class UnknownTicket(Exception):
    pass


class AllocationStrategy(ABC):
    @abstractmethod
    def choose(self, free_spots, vehicle):
        """Return one spot from free_spots that fits the vehicle, or None."""


class NearestFirst(AllocationStrategy):
    """Lowest floor, then lowest spot id. It ignores size, so it may waste large spots."""
    def choose(self, free_spots, vehicle):
        fitting = [s for s in free_spots if s.size in FITS[vehicle.kind]]
        return min(fitting, key=lambda s: (s.floor, s.spot_id), default=None)


class SmallestFit(AllocationStrategy):
    """Use the smallest spot that fits, keeping large spots free for the vehicles that need them."""
    def choose(self, free_spots, vehicle):
        fitting = [s for s in free_spots if s.size in FITS[vehicle.kind]]
        return min(fitting, key=lambda s: (s.size, s.floor, s.spot_id), default=None)


class PricingStrategy(ABC):
    @abstractmethod
    def fee(self, vehicle, parked_seconds): ...


class HourlyPricing(PricingStrategy):
    RATES = {VehicleType.MOTORCYCLE: 1.0, VehicleType.CAR: 2.0, VehicleType.TRUCK: 5.0}   # per started hour
    def __init__(self, minimum_hours=1):
        self.minimum_hours = minimum_hours
    def fee(self, vehicle, parked_seconds):
        hours = max(self.minimum_hours, math.ceil(parked_seconds / 3600))
        return hours * self.RATES[vehicle.kind]


class ParkingLot:
    def __init__(self, spots, allocation=None, pricing=None):
        self._spots = {s.spot_id: s for s in spots}
        self._allocation = allocation or NearestFirst()
        self._pricing = pricing or HourlyPricing()
        self._tickets = {}                       # ticket id -> Ticket, only for vehicles currently inside
        self._by_plate = {}                      # plate -> ticket id, to forbid parking the same car twice
        self._next_id = 1
        self._lock = threading.Lock()            # one lock guards the whole check-and-claim step

    def park(self, vehicle, now):
        with self._lock:
            if vehicle.plate in self._by_plate:
                raise AlreadyParked(vehicle.plate)
            free = [s for s in self._spots.values() if s.is_free()]
            spot = self._allocation.choose(free, vehicle)
            if spot is None:
                raise LotFull(f"no spot for a {vehicle.kind.value}")
            spot.vehicle = vehicle                # claimed inside the lock: no other caller can take it
            ticket = Ticket(self._next_id, vehicle, spot.spot_id, now)
            self._next_id += 1
            self._tickets[ticket.ticket_id] = ticket
            self._by_plate[vehicle.plate] = ticket.ticket_id
            return ticket

    def unpark(self, ticket_id, now):
        with self._lock:
            ticket = self._tickets.pop(ticket_id, None)
            if ticket is None:
                raise UnknownTicket(ticket_id)
            self._spots[ticket.spot_id].vehicle = None
            del self._by_plate[ticket.vehicle.plate]
            return self._pricing.fee(ticket.vehicle, now - ticket.entered_at)

    def free_count(self):
        with self._lock:
            return sum(1 for s in self._spots.values() if s.is_free())


def build_lot(allocation=None, pricing=None):
    """Two floors, each with 2 small, 2 medium and 1 large spot."""
    spots = []
    for floor in (1, 2):
        spots += [Spot(f"F{floor}-S{i}", floor, SpotSize.SMALL) for i in (1, 2)]
        spots += [Spot(f"F{floor}-M{i}", floor, SpotSize.MEDIUM) for i in (1, 2)]
        spots.append(Spot(f"F{floor}-L1", floor, SpotSize.LARGE))
    return ParkingLot(spots, allocation, pricing)


# ---------------- tests: each one states a rule of the design ----------------
HOUR = 3600
bike, car, truck = Vehicle("BIKE-1", VehicleType.MOTORCYCLE), Vehicle("CAR-1", VehicleType.CAR), Vehicle("TRK-1", VehicleType.TRUCK)

lot = build_lot(SmallestFit())
t1, t2, t3 = lot.park(bike, 0), lot.park(car, 0), lot.park(truck, 0)
print("SmallestFit placements (bike, car, truck):", t1.spot_id, t2.spot_id, t3.spot_id)
assert (t1.spot_id, t2.spot_id, t3.spot_id) == ("F1-S1", "F1-M1", "F1-L1")

wasteful = build_lot(NearestFirst()).park(bike, 0)
print("NearestFirst puts the motorcycle in:", wasteful.spot_id, "<- a large spot wasted on a motorcycle")
assert wasteful.spot_id == "F1-L1"

fees = (lot.unpark(t1.ticket_id, 90 * 60), lot.unpark(t2.ticket_id, 3 * HOUR + 1), lot.unpark(t3.ticket_id, 10))
print("fees (bike 90 min, car 3 h + 1 s, truck 10 s):", fees)
assert fees == (2.0, 8.0, 5.0)

lot.park(car, 0)
try:
    lot.park(car, 0)
    raise AssertionError("the same car must not park twice")
except AlreadyParked as e:
    print("double parking rejected:", e)

trucks = build_lot()
trucks.park(Vehicle("T1", VehicleType.TRUCK), 0)
trucks.park(Vehicle("T2", VehicleType.TRUCK), 0)
try:
    trucks.park(Vehicle("T3", VehicleType.TRUCK), 0)
    raise AssertionError("only two large spots exist")
except LotFull as e:
    print("third truck rejected:", e, "| spots still free for other vehicles:", trucks.free_count())
assert trucks.free_count() == 8

try:
    lot.unpark(999, 0)
    raise AssertionError("an unknown ticket must be rejected")
except UnknownTicket:
    print("unknown ticket rejected")
print("all checks passed")

The output shows each rule at work. **`SmallestFit` places the bike, car and truck in a small, medium and large spot**; **`NearestFirst`, which ignores size, parks a motorcycle in the large spot**, wasting capacity a truck may need: a concrete reason strategies exist. Fees come out as expected (90 minutes rounds up to 2 hours; 3 hours and 1 second rounds up to 4; a 10-second stay pays the 1-hour minimum). The same car cannot park twice, a third truck is refused when both large spots are taken (while 8 other spots remain free for other vehicles), and an unknown ticket is rejected.

## 4. Concurrency

Two entrances can call `park` at the same instant. Without a lock, both could see the same spot as free and both claim it (the check-then-act race). The lock turns **check and claim into one atomic step**. A quick stress test using threads (run it locally with CPython, because the browser runner cannot start threads) shows the guarantee:

```python
lot = build_lot()
results = []
def worker(i):
    try:
        results.append(lot.park(Vehicle(f"C{i}", VehicleType.CAR), 0).spot_id)
    except LotFull:
        results.append(None)

threads = [threading.Thread(target=worker, args=(i,)) for i in range(200)]
[t.start() for t in threads]
[t.join() for t in threads]
placed = [r for r in results if r]
print(len(placed), len(set(placed)))      # 6 6
```

On a run of this test, **200 cars competed for the 6 car-sized spots (4 medium plus 2 large); exactly 6 were parked in 6 different spots** and the other 194 were refused. Design notes:

- **One coarse lock** is simple and correct. A single lot handles a few operations per second, so lock contention is irrelevant. Only when profiling shows contention would you split the lock (per floor, or per size class) or maintain **indexed free lists** so `park` does not scan every spot.
- **Never hand out references to mutable state** from inside the lock: `free_count` returns a number, not the spots.
- With **several processes or machines** (distributed lots, a database), the in-memory lock is not enough; use a database transaction with an **atomic conditional update** on the spot row ([ticket booking](/sd/case-studies-data-and-transactions/design-a-ticket-booking-system/)).

## 5. Extending the design

A good design makes the common changes **small**. How would each extension fit?

| requirement | change |
| --- | --- |
| **Peak and weekend pricing** | a new `PricingStrategy` (or a decorator around `HourlyPricing`); `ParkingLot` unchanged |
| **Prefer spots near the exit, or EV spots** | a new `AllocationStrategy` that filters on spot attributes |
| **A new vehicle type (bus, bicycle)** | add to `VehicleType` and to the `FITS` table; no other code branches on type |
| **Reservations** | a `Reservation` entity and a spot state `RESERVED`; `park` honours the reservation holder; a hold with expiry ([seat holds](/sd/case-studies-data-and-transactions/design-a-ticket-booking-system/)) |
| **Pay at an exit machine, card or cash** | a `PaymentGateway` interface and adapter ([adapter pattern](/sd/oop-and-design-patterns/creational-and-structural-patterns/)); `unpark` returns a fee, the payment step is separate |
| **Display boards showing free counts** | an observer: the lot publishes "spot freed or taken" events ([observer pattern](/sd/oop-and-design-patterns/behavioral-patterns/)) |
| **Multiple lots under one operator** | a `ParkingService` that holds lots by id and routes to them |
| **Persistence and audits** | a `Repository` interface (injected) for tickets; spots can be rebuilt from open tickets after a restart |
| **Lost ticket** | look up the open ticket by plate through the plate index and charge a fixed penalty |

Notice how the extensions land in **new classes** behind existing interfaces, the [Open/Closed Principle](/sd/oop-and-design-patterns/solid-principles-in-practice/) in practice.

## 6. Checklist for any LLD answer

1. Did I **state requirements and scope** before drawing classes?
2. Is each class's **responsibility** nameable in one sentence?
3. Is there **one owner** for each invariant (here, spot occupancy)?
4. Are the **parts that vary** behind interfaces, and the rest plain and simple?
5. Can I **test** it with fixed inputs (no hidden clocks, randomness or globals)?
6. Did I discuss **concurrency, failure and extension** concretely?

## Pitfalls

- Starting with classes before clarifying requirements and scope.
- Scattering "if vehicle is a truck" checks everywhere instead of one fit table.
- Letting several classes change spot state, so no one owns the invariant.
- Mutable value objects shared across the system.
- Reading the clock, random numbers or global state inside the model, making tests flaky.
- Check-then-act on shared state without a lock or an atomic operation.
- Inheritance hierarchies for vehicles (`Car(Vehicle)`, `Truck(Vehicle)`) with no behavioural difference, instead of an enum and a table.
- Over-engineering: a factory, a builder and an event bus for a requirement that needed none.
- Forgetting the failure cases: a full lot, an unknown or reused ticket, a double entry.

## What would you choose and why?

The operator wants **dynamic pricing** (rates rise when the lot is more than 80% full), **EV charging spots** that only charging-capable vehicles may use and that bill for electricity separately, and a **second entrance system run by another vendor** that talks to you over HTTP. Which classes or interfaces do you add or change, which stay untouched, and where does the dynamic price get its occupancy number without making `HourlyPricing` depend on `ParkingLot`?
