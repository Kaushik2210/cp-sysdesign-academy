## The problem

Design a **distributed message queue** (a broker) like Kafka, Pulsar or SQS. **Producers** publish messages to named **topics**; **consumers** read them, possibly many independent applications reading the same stream. The system must be **durable** (an acknowledged message survives a machine failure), **scalable** (millions of messages per second), **ordered where it matters**, and clear about its **delivery guarantees**.

Why build one? Queues **decouple** producers from consumers, **absorb bursts**, and let many consumers process the same data independently (the [why queues](/sd/queues-and-streaming/why-queues/) lesson). This case study is about the broker's insides: how a log, partitions, offsets, consumer groups and replication fit together.

## Requirements

**Functional**
- Producers **publish** messages to a topic, with an optional **key**.
- Consumers **subscribe** and read in order; many **consumer groups** can read the same topic independently; consumers in one group **share the work**.
- Messages are retained for a configurable period (for example 7 days) so consumers can **replay**.

**Non-functional**
- **Throughput**: about 1 million messages per second, 1 KB each (1 GB/s in).
- **Durability**: an acknowledged message is not lost if a broker dies.
- **Availability**: producers and consumers continue through a single broker failure.
- **Ordering**: messages with the **same key** are read in the order they were published.
- **Latency**: single-digit milliseconds end to end under normal load.

**Delivery guarantee we will offer:** **at-least-once** by default, with ways to reach effectively-once (explained below).

## Back-of-the-envelope

| quantity | calculation | result |
| --- | --- | --- |
| Ingest | 1,000,000 msg/s x 1 KB | 1 GB/s |
| Retention (7 days) | 1 GB/s x 604,800 s | about 605 TB |
| With 3 replicas | 605 TB x 3 | about 1.8 PB |
| Partitions for throughput | 1 GB/s / about 10 MB/s per partition | about 100, so provision about 200 with headroom |

(Assume about 10 MB/s per partition as a safe write rate; real systems differ, so measure.) The storage figure dominates, which is why retention, compression and tiered storage matter. Reads are mostly **sequential**, which disks and the operating system's page cache handle very well; that is the main reason log-structured brokers are fast.

## The core abstraction: the partitioned log

A **partition** is an **append-only log**: messages get consecutive **offsets** (0, 1, 2, ...) and are never modified. A **topic** is split into **partitions** that live on different brokers.

- **Why a log?** Appending and reading sequentially is the fastest thing disks do. A reader only needs to remember **one number**, its offset. Replaying is just "read from offset 0 again".
- **Why partitions?** One log on one machine is a throughput ceiling. Partitions **spread load** and let consumers **work in parallel**.
- **Ordering**: only **within a partition**. Across partitions there is no global order (it would need a single point of coordination). Producers choose the partition with `hash(key) mod partitions`, so **all messages of one key land in one partition** and stay ordered.

## Consumer groups and offsets

- A **consumer group** is a set of consumers that **share** a topic: each partition is assigned to **exactly one** consumer in the group, so a message is processed by one consumer of the group. Different groups are independent and each sees every message.
- The group's progress is stored as a **committed offset** per partition ("next message to read"). Committing after processing gives **at-least-once**; committing before processing gives **at-most-once** (a crash loses messages).
- When consumers **join or leave**, partitions are **rebalanced** across the remaining members.
- **Parallelism limit**: a group can usefully have at most as many consumers as partitions. More consumers than partitions sit idle.

## Replication and durability

Each partition has a **leader** and several **followers** on other brokers. Producers write to the leader; followers copy the log. A write is **acknowledged** when enough replicas have it (the **in-sync replicas**, ISR). If the leader dies, a follower with the full log is **elected** as the new leader (coordinated through a consensus system, see [Raft](/sd/consensus-and-coordination/raft-log-replication-and-safety/)).

| producer setting | meaning | risk |
| --- | --- | --- |
| acks = 0 | do not wait | messages can be lost silently |
| acks = 1 | leader has it | lost if the leader dies before followers copy |
| acks = all | every in-sync replica has it | slowest, survives a broker failure |

Pair `acks = all` with a **minimum in-sync replicas** setting (for example 2 of 3) so a write is refused rather than accepted with a single copy. This is the standard durability versus availability dial.

## The simulation

The program is a small single-process model of the design: a `Partition` log, a `Broker` that routes by a stable hash of the key, consumer groups with committed offsets and a **rebalance**, and a driver that can **skip a commit** to simulate a consumer crash after processing. It then demonstrates four properties: **per-key ordering**, **at-least-once duplicates**, an **idempotent consumer** that removes them, and **rebalancing**. (It models the logic, not networking, disks or replication.)

<CodeRunner language="python" timeoutMs={30000} code={`import random
import zlib
from collections import defaultdict


class Partition:
    """An append-only log. A message's offset is its index; messages are never modified."""
    def __init__(self):
        self.log = []

    def append(self, key, value):
        self.log.append((key, value))
        return len(self.log) - 1

    def read(self, offset, max_n):
        return [(offset + i, k, v) for i, (k, v) in enumerate(self.log[offset:offset + max_n])]


class Broker:
    def __init__(self, n_partitions):
        self.partitions = [Partition() for _ in range(n_partitions)]
        self.committed = defaultdict(int)       # (group, partition) -> next offset to read
        self.members = defaultdict(list)        # group -> sorted consumer ids
        self.assignment = {}                    # (group, partition) -> consumer id

    def produce(self, key, value):
        p = zlib.crc32(key.encode()) % len(self.partitions)     # same key -> same partition
        return p, self.partitions[p].append(key, value)

    # consumer groups: each partition is owned by exactly one consumer of the group
    def join(self, group, cid):
        self.members[group] = sorted(self.members[group] + [cid])
        self._rebalance(group)

    def leave(self, group, cid):
        self.members[group].remove(cid)
        self._rebalance(group)

    def _rebalance(self, group):
        ids = self.members[group]
        for p in range(len(self.partitions)):
            self.assignment[(group, p)] = ids[p % len(ids)] if ids else None

    def owned(self, group, cid):
        return [p for p in range(len(self.partitions)) if self.assignment.get((group, p)) == cid]

    def poll(self, group, cid, max_n=4):
        out = []
        for p in self.owned(group, cid):
            for off, k, v in self.partitions[p].read(self.committed[(group, p)], max_n):
                out.append((p, off, k, v))
        return out

    def commit(self, group, p, next_offset):
        self.committed[(group, p)] = next_offset


def drain(broker, group, consumers, handler, crash_every=None):
    """Run consumers until the log is consumed. Optionally a consumer crashes before committing."""
    polls = 0
    while True:
        progressed = False
        for cid in list(consumers):
            batch = broker.poll(group, cid)
            if not batch:
                continue
            progressed = True
            polls += 1
            for p, off, k, v in batch:
                handler(cid, p, off, k, v)
            if crash_every and polls % crash_every == 0:
                continue                         # crash after processing, before commit: batch will be redelivered
            for p in {p for p, *_ in batch}:
                last = max(off for pp, off, *_ in batch if pp == p)
                broker.commit(group, p, last + 1)
        if not progressed:
            return


if True:
    rnd = random.Random(3)
    users = [f"user{i}" for i in range(6)]
    b = Broker(4)
    sent = {u: [] for u in users}
    for n in range(60):
        u = rnd.choice(users)
        b.produce(u, (u, len(sent[u])))

    applied, done = [], set()

## What the output shows

- **Partition load is uneven**: 60 messages over 4 partitions landed as **10, 24, 12 and 14**. Two of the six keys (user1 and user3) hash to partition 1, so it carries 24 messages. This is **key skew**: ordering by key means a hot key cannot be spread over partitions. Fixes are a better key, adding a random suffix for keys that need no ordering, or more partitions.
- **Per-key order is preserved**: with two consumers in one group, each key's messages were consumed in exactly the order they were sent (`True`). Consumer 1 owns partitions 0 and 2, consumer 2 owns 1 and 3.
- **At-least-once means duplicates**: when a batch is processed but the commit is skipped (a crash before the commit), the same messages are delivered again. **84 deliveries for 60 distinct messages: 24 duplicates.** Nothing was lost, which is the point of committing after processing.
- **An idempotent consumer fixes the duplicates**: remembering `(partition, offset)` of processed messages, the same run **applied exactly 60 distinct messages**. The processing is *effectively once* even though delivery is at-least-once.
- **Rebalance**: with three consumers the partitions split as [0, 3], [1] and [2]; when consumer 2 leaves, its partition goes to the others ([0, 2] and [1, 3]).

The duplicate count depends on the simulated crash pattern (every third poll skips its commit), so treat 24 as an illustration of the mechanism, not a rate.

## Delivery semantics, summarised

| guarantee | how | cost |
| --- | --- | --- |
| **At-most-once** | commit the offset first, then process | a crash loses messages |
| **At-least-once** | process, then commit | duplicates after a crash or rebalance, so consumers must be idempotent |
| **Effectively-once** | at-least-once plus idempotent handling (dedupe by id or offset, or an upsert) | design effort in the consumer |
| **Transactional exactly-once** | atomic write of output and offset commit, with producer ids for deduplication | complexity and lower throughput; only within the system that supports it |

See [delivery semantics and idempotency](/sd/queues-and-streaming/delivery-semantics-and-idempotency/) for the full discussion.

## Other design questions

- **Retention and compaction**: delete by age or size, or **compact** by key (keep only the latest message per key) for changelog topics.
- **Poison messages and retries**: a message that always fails would block its partition. Use a bounded retry count, a **retry topic** with delay and a **dead-letter topic** ([backpressure, retries and DLQ](/sd/queues-and-streaming/backpressure-retries-and-dlq/)).
- **Backpressure**: consumers **pull** at their own pace, so a slow consumer falls behind (**lag**) instead of being overwhelmed. Monitor lag per group and partition as the key health metric.
- **Queue-style systems (SQS, RabbitMQ)** differ: messages are **deleted** after acknowledgement and a **visibility timeout** hides a message while one consumer works on it; there is no replay and ordering is weaker. They suit task distribution; logs suit streams and replay.
- **Partition count is hard to change**: increasing it changes `hash(key) mod n` and breaks per-key ordering for existing keys. Over-provision partitions at the start.
- **Large messages**: store the payload in an object store and send a reference.

## Pitfalls

- Assuming **global ordering**: it exists only within a partition.
- A **hot key** that overloads one partition.
- Committing offsets **before** processing and losing messages on a crash.
- Non-idempotent consumers behind an at-least-once broker.
- Changing the partition count and silently **breaking per-key order**.
- More consumers than partitions, so some are idle.
- Long processing that exceeds the **session or poll timeout**, triggering rebalances that cause duplicates and more rebalances.
- No **dead-letter** path, so one poison message blocks a partition forever.
- Monitoring broker health but not **consumer lag**.
- Treating the broker as a database: using it as the system of record without understanding retention.

## What would you choose and why?

An e-commerce company wants (1) order events that three teams consume independently, never lost and ordered per order; (2) an image resize job queue where each job should run once on any free worker; and (3) a firehose of page-view events for analytics where losing 0.1% is fine.
