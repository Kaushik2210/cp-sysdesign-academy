## The problem

Design the **data pipeline** of a company: data from many **sources** (application databases, event streams, log files, third-party exports) must be **collected, cleaned, joined and aggregated**, and delivered to **analysts, dashboards and machine learning models** as trustworthy tables that are fresh enough to be useful.

Everything that makes a service hard (scale, failure, change) applies, plus a problem unique to data: **a wrong number looks exactly like a right number**. A pipeline can run to completion, with all green status lights, and deliver revenue figures that are doubled, truncated or stale. The design is about **correctness you can verify**, **re-runnable steps** that make recovery boring, and **noticing problems before the CEO does**.

## Requirements

**Functional**
- **Ingest** from databases (including change streams), event logs, files and APIs.
- **Transform**: clean, deduplicate, join, aggregate.
- **Load** curated tables into a warehouse or lake for SQL, dashboards and ML features.
- **Schedule and orchestrate** dependencies between jobs.
- **Backfill**: recompute history after a bug fix or a logic change.

**Non-functional**
- **Freshness** targets (for example "yesterday's numbers by 06:00" for batch, "within 5 minutes" for streaming).
- **Correctness and repeatability**: re-running a job gives the same result, never duplicates.
- **Scale**: terabytes per day, petabytes of history, at reasonable cost.
- **Observability**: know when data is late, missing or wrong.
- **Governance**: lineage (where did this number come from), access control, retention and deletion.

## Estimation

| quantity | assumption | result |
| --- | --- | --- |
| Raw events | 50 billion per day, about 100 bytes | about 5 TB per day, 1.8 PB per year |
| Columnar compressed storage | about 5 times smaller than raw rows | about 360 TB per year |
| Batch window | process yesterday's 5 TB in a few hours | a cluster scanning on the order of 1 GB per second in aggregate |
| Daily curated tables | thousands of tables, mostly small | the big ones are event-level facts |

The raw data is **huge and mostly read in bulk**, so **cheap object storage with columnar files** (Parquet or ORC) plus a **distributed compute engine** (Spark, Flink, or a cloud warehouse) is the standard answer, not a transactional database.

### The layers (sometimes called bronze, silver and gold)

- **Raw (bronze)**: data exactly as it arrived, **never modified**, partitioned by arrival date. It is the **source of truth for reprocessing**: if a transformation is wrong, fix it and rebuild from here. Keep it as long as legal and cost limits allow.
- **Clean (silver)**: **deduplicated, typed, validated** records, with bad rows quarantined and counted. Partitioned by **event date** (when the thing happened), not arrival date.
- **Curated (gold)**: **business-level tables**: daily revenue by country, user activity, model features. Modelled for the questions people ask (often as fact and dimension tables).

### ETL versus ELT

**ETL** transforms data **before** loading it into the warehouse; **ELT** loads raw data first and transforms it **inside** the warehouse or lake engine with SQL. ELT dominates today: storage and compute are cheap and elastic, raw data is kept for reprocessing, and analysts can own transformations in SQL. ETL remains useful for filtering, masking sensitive fields or reducing volume **before** data leaves a secure zone.

## The three ideas that make pipelines reliable

### 1. Idempotent, partition-scoped writes

A job that can safely be **run twice** with the same result makes failures cheap: retry until it works. The standard technique is to **write each output partition atomically, replacing whatever was there** (overwrite-partition), keyed by a logical date, instead of **appending**. Modern table formats (Iceberg, Delta, Hudi) provide atomic partition overwrite and **snapshots** so readers never see a half-written partition.

### 2. Immutable inputs and backfills

Because raw data is never changed, any derived table can be **recomputed** by running the same code over a date range. Backfills are a first-class operation: the orchestrator accepts "run this DAG for these dates", and overwrite semantics make them safe.

### 3. Checks as part of the pipeline

Treat data like code: **tests on every run**. Row counts, null rates, uniqueness of keys, accepted value ranges, referential integrity, freshness, and reconciliation against the source ("the warehouse revenue matches the payments system within 0.1%"). A failed check **stops downstream tasks** and alerts the owner, instead of publishing wrong numbers.

## The simulation

The program builds 30 days of order events (day 21 simulates an **upstream outage**: only 40% of the events arrive, and half of those have lost their country), a tiny warehouse that can write a daily table by **appending** or by **overwriting the partition**, and runs four experiments:

1. **A retry**: the job for day 5 runs twice (the first attempt timed out after writing but before reporting success), in each write mode.
2. **A backfill**: ten days are reloaded with a corrected cleaning step, in each write mode.
3. **A task graph**: ingest, then clean, then three parallel tasks (revenue, users, fraud), then a report. One task fails once; the retry skips finished tasks.
4. **Data quality checks** over the 30 days: row count outliers by median and spread, and the share of rows missing their country.

class Warehouse:
    def __init__(self):
        self.tables = defaultdict(lambda: defaultdict(list))     # table -> partition (day) -> rows

    def append(self, table, day, rows):
        self.tables[table][day].extend(rows)                     # not safe to retry: running twice stores everything twice

    def overwrite_partition(self, table, day, rows):
        self.tables[table][day] = list(rows)                     # replaces the whole partition: running twice gives the same result

    def revenue(self, table):
        return {d: round(sum(r["amount"] for r in rows), 2) for d, rows in sorted(self.tables[table].items())}

    """Clean step: drop rows with no country, as a downstream consumer of the raw data might."""
    return [r for r in rows if r["country"] is not None]

def run_dag(tasks, deps, fail_once=None, done=None):
    """Run tasks in dependency order. A failed task blocks everything downstream. 'done' is the set of tasks already
    completed by an earlier attempt, which are skipped on a retry (each task is idempotent)."""
    done = set(done or ())
    executed, failed, blocked = [], None, []
    order, seen = [], set()
    def visit(t):
        if t in seen:
            return
        seen.add(t)
        for d in deps.get(t, []):
            visit(d)
        order.append(t)

        visit(t)

## What the output shows

- **Retry with append** left **day 5's revenue wrong by exactly the whole day's revenue (+107,604.15)**: the job's rows were stored twice. **Overwriting the partition** left **every day correct** (difference 0.00). Both runs executed the same code the same number of times; the **write mode** decided whether retrying was safe.
- **Backfill with append** left the table with **19,876 rows when the correct answer is 9,938**: the old rows and the corrected rows were both kept (exactly double). **Overwrite** produced **9,938**, the right number. Without idempotent writes, a backfill needs a manual delete step first, and that step is where mistakes happen.
- **Task graph**: the first attempt ran ingest, clean, revenue, users and fraud, and **failed at users**; the **report was blocked** (its dependency never finished). The **retry ran only users and report: 2 tasks instead of the 6 a full rerun needs**, because the other tasks had completed and their outputs are idempotent. Failing downstream tasks **should not** run on partial data.
- **Quality checks**: the daily row count had a **median of 1,002** with a typical spread (median absolute deviation) of **54**. The check, "more than 5 robust standard deviations from the median", flagged **only day 21** among the 30 days (no false alarms on the other 29), and the **missing country** check (more than 5% of rows) flagged **only day 21** as well. Either check alone would have caught the outage; a pipeline without them would have published a revenue figure about 60% too low for that day.

The data are synthetic, the outage is one chosen day, and the thresholds are illustrative: real checks need tuning per table, seasonal baselines (weekends are lower), and a triage process.

## Late data, event time and partitioning

- **Partition by event time** (when it happened) in the clean and curated zones, but ingest by **arrival time** in the raw zone. Late events then land in an **old event-date partition**, and the pipeline must **recompute** that partition (idempotent overwrite makes this simple).
- Decide a **lateness window** (for example "events can arrive up to 3 days late") and **re-run recent partitions daily** within that window. After it, late events go to a correction process. This is the batch cousin of the watermark in the [ad click aggregation lesson](/sd/case-studies-data-and-transactions/design-an-ad-click-aggregation-system/).
- **Deduplicate** on a unique event id in the clean step (at-least-once ingestion repeats events).

## Batch, streaming and both

- **Batch** (hourly or daily) is simpler to reason about, cheaper, and easy to re-run.
- **Streaming** ([stream processing basics](/sd/queues-and-streaming/stream-processing-basics/)) gives minutes or seconds of freshness for the metrics that need it.
- Many companies run **both** for the same data: a streaming path for fresh approximate numbers and a batch path for the exact final ones (the lambda pattern), or one streaming engine that can also replay history (kappa). Choose per table by **freshness actually needed**, not by fashion.

## Schema evolution and contracts

Sources change: columns are added, renamed, retyped. Pipelines break when they discover this at 3 a.m.
- **Additive changes** (new optional column) are safe if readers ignore unknown fields. **Renames, type changes and removals are breaking.**
- Use a **schema registry** or data contracts between producers and the pipeline, with compatibility checks in the producers' CI ([evolving APIs and events](/sd/microservice-patterns/evolving-apis-and-events/)).
- Table formats such as Iceberg support **schema evolution** (add, rename, reorder columns) without rewriting data.
- **Detect drift** automatically: compare the incoming schema with the expected one and quarantine or alert.

## Operating the pipeline

- **Orchestration**: a DAG of tasks with dependencies, schedules, retries with backoff, timeouts, backfill commands and clear ownership (Airflow, Dagster, Prefect, or a cloud equivalent).
- **Lineage and catalogue**: for every table, where it comes from and who uses it, so "what breaks if I change this column?" is answerable.
- **Freshness monitoring**: alert when a table is not updated on time (the age of the newest partition), not only when a job fails (a job that never started never fails).
- **Cost control**: partition pruning, columnar formats, compaction of **small files** (thousands of tiny files slow every query), and lifecycle rules that move old data to cheaper storage.
- **Privacy and deletion**: personal data must be deletable on request even from immutable raw zones: tokenise or encrypt per user and delete keys, or rewrite affected partitions.

## Pitfalls

- **Appending in jobs that can be retried**, creating duplicates.
- **Mutating raw data**, losing the ability to reprocess.
- **Partitioning by arrival time** and then computing daily metrics by that partition, so late events land in the wrong day.
- **No checks**: green pipelines publishing wrong numbers.
- **Treating "no data arrived" as "no problem"**: alert on missing partitions and stale tables.
- **Breaking schema changes** discovered in production.
- **Small-file explosion** from tiny frequent writes.
- **Unowned tables** with no documented owner or consumer.
- **Rerunning everything** for a single failure instead of the failed task and its dependents.
- **Backfills that overwrite production tables without a snapshot** to roll back to.
- Ignoring **time zones** in daily partitions.
