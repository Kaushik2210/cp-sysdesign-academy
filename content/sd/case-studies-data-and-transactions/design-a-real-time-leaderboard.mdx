## The problem

Design a **real-time leaderboard** for a game or app with a hundred million players: show the **top 100**, show **any player's rank**, show the **players just above and below me**, and update everything within a second or two of a score change. Variants: daily, weekly and all-time boards, boards among **friends**, and boards per country.

It sounds like "sort the players by score", and the trap is that **sorting is too slow and a database query is too slow**: "what is my rank?" means counting everyone with a higher score, and a million players changing scores every minute make any scan-based approach collapse. The design question is choosing a **data structure that answers rank, top-K and neighbours in logarithmic time**, and deciding when one machine is enough.

## Requirements

**Functional**
- Update a player's score (set, or add points).
- **Top K** players (for example 100) with their scores.
- **Rank of a player** (1 is best); players with equal scores share a rank or are ordered by a tie-break rule.
- **Players around me**: the 5 above and 5 below.
- Several boards: all-time, daily, weekly, by country, among friends.

**Non-functional**
- Updates visible in **under 2 seconds**; reads in **milliseconds**.
- Handle bursts (a tournament ends and everybody's scores change).
- Durable: a cache failure must not lose scores.

## Estimation

| quantity | assumption | result |
| --- | --- | --- |
| Players | 100 million | |
| Entry size | 8 bytes id + 8 bytes score, about 100 bytes with in-memory structure overhead | about 1.6 GB raw, about 10 GB in a typical in-memory sorted set |
| Score updates | 50,000 per second at peak | one in-memory node handles on the order of 100,000 operations per second |
| Reads | 200,000 per second at peak (top lists are cached) | read replicas |

The key observation: **a whole leaderboard of 100 million players fits in the memory of one ordinary server** (about 10 GB). The first design is therefore **one in-memory sorted structure** with replicas, not a sharded database. Sharding is for **more boards, more players or more traffic than one node can handle**.

## The data structure is the design

What operations must be fast? **Update a score**, **rank of a player**, **top K**, **range around a rank**. Three approaches, compared in the simulation below:

| structure | rank query | score update | notes |
| --- | --- | --- | --- |
| **Scan everyone** (hash map of scores) | O(n): count players with a higher score | O(1) | what a naive SQL "count where score greater than mine" does |
| **Sorted array** | O(log n) by binary search | **O(n)**: inserting shifts the tail | fine for a read-only board |
| **Balanced tree or skip list with order statistics** | O(log n) | O(log n) | the general answer; **Redis sorted sets** use a **skip list plus a hash map** |
| **Fenwick tree over score buckets** | O(log S) | O(log S) | when scores are **bounded integers** (S distinct values); cost independent of the number of players |

A **Fenwick tree** (binary indexed tree) stores, for each score, how many players have it, so that "how many players have a score above mine" is a **prefix sum** computed by walking about log2(S) tree nodes. A score update is two such walks (remove at the old score, add at the new). The number of players does not appear in the cost at all. It needs **bounded integer scores**; for floating point or huge ranges, use a skip list or tree, or bucket the scores.

## The simulation

The program implements the three approaches (the scan, a sorted list, and a Fenwick tree) behind the same interface and does three things:
1. **Cross-checks them**: 2,000 players, 5,000 random score changes, comparing rank and top-5 answers across all three every ten changes.
2. **Counts the work**: 20,000 players with scores up to one million; then 1,000 rank queries and 1,000 score updates on each structure. "Steps" are comparisons, shifted list elements and tree nodes touched.
3. **Merges a sharded top 10**: players are hashed over 8 shards, each shard keeps its own best 10, and the merged answer is compared with the global one.

    """A dictionary of scores. Rank = count how many players have a higher score: a scan of everyone."""

        self.score[user] = s
        self.steps += 1

        self.steps += len(self.score)

        self.steps += len(self.score)

class FenwickBoard:
    """Scores are integers in [0, max_score]. A Fenwick tree counts players per score, so the number of players
    above a score is a prefix sum: O(log max_score) for rank and for each update, whatever the number of players."""
    def __init__(self, max_score):
        self.size = max_score + 2
        self.tree = [0] * (self.size + 1)
        self.score, self.by_score = {}, {}
        self.steps = 0
    def _add(self, s, d):
        i = self.size - 1 - s + 1                              # flip so a prefix sum counts the HIGHER scores
        while i <= self.size:
            self.tree[i] += d
            self.steps += 1
            i += i & -i
    def _prefix(self, s):                                      # players with score strictly above s
        i, total = self.size - 1 - s, 0
        while i > 0:
            total += self.tree[i]
            self.steps += 1
            i -= i & -i
        return total
    def set(self, user, s):
        if user in self.score:
            old = self.score[user]
            self._add(old, -1)
            self.by_score[old].discard(user)
        self.score[user] = s
        self._add(s, +1)
        self.by_score.setdefault(s, set()).add(user)
    def rank(self, user):
        return 1 + self._prefix(self.score[user])

        out = []
        for s in sorted(self.by_score, reverse=True):
            self.steps += 1
            for u in sorted(self.by_score[s]):
                out.append(u)
                if len(out) == k:
                    return out
        return out

## What the output shows

- **All three agree** on 500 rank and top-5 checks: the fast structures compute the same answers as the obviously correct scan.
- **Work per operation** with 20,000 players:

| structure | steps per rank query | steps per score update |
| --- | --- | --- |
| scan everyone | 20,000 | 1 (but every rank query needs the full scan) |
| sorted list | 15.0 | **20,360.2** |
| Fenwick tree | **9.9** | **20.0** |

- The **sorted list** answers rank queries cheaply (a binary search, 15 steps) but every **update shifts, on average, about as many elements as there are players** (20,360 steps), so it cannot absorb 50,000 updates per second at scale. (A list shift is a fast memory move, so it is much cheaper in time than 20,000 comparisons, but it still grows linearly with the number of players.)
- The **Fenwick tree** needs about **10 steps per rank query and 20 per update** and **would not change if there were 200 million players**; its cost depends on the **number of distinct score values** (one million here, so about 20 levels), not on the number of players.
- **Sharded top 10**: each of 8 shards returned its best 10, and **merging those 80 candidates gave exactly the global top 10** (`True`), instead of examining all 20,000 players. This works because **the global top K is always contained in the union of the shards' top Ks**.

The steps are counted operations, not measured times, and the data are random; real timings depend on memory layout and implementation.

## Production design with Redis

A **Redis sorted set** (a skip list plus a hash table) provides exactly these operations in O(log n):
- `ZADD board score player` to set a score, and `ZINCRBY` to add points.
- `ZREVRANGE board 0 99 WITHSCORES` for the top 100.
- `ZREVRANK board player` for a player's rank.
- Players around me: take the rank, then `ZREVRANGE` over rank minus 5 to rank plus 5.

Design details:
- **Ties**: a sorted set orders equal scores by member name, which is arbitrary. To rank ties fairly (the player who reached the score first ranks higher), **encode the tie-break into the score**, for example score times 2^20 plus (a maximum timestamp minus the time reached), as one number.
- **Several boards**: separate keys per period (`board:daily:2026-11-23`, `board:weekly:47`); old keys expire or are deleted. A new period starts empty; **all-time** is a separate key updated alongside.
- **Friends board**: fetch the player's friends' scores (`ZSCORE` per friend, or a pipeline) and sort a few hundred values in the application; do not build a sorted set per user.
- **Country boards**: one sorted set per country (and a global one), updated together.
- **Durability**: the sorted set is a **rebuildable index**. Scores live in the durable log and the database; after a failure, rebuild the board from the database (a few minutes for 100 million rows) or restore a snapshot and replay the log tail. Make the writer **idempotent** so replay does not double count points ([delivery semantics](/sd/queues-and-streaming/delivery-semantics-and-idempotency/)).
- **Cache the top 100** for a second or two: it is the hottest read, and every client in the world asks for the same list.

## When one node is not enough

If a single sorted set cannot hold or serve the board, shard it. Two options:

| sharding | rank query | top K | updates |
| --- | --- | --- | --- |
| **By player (hash)** | needs a count from every shard: sum of the number of players above the score in each shard (scatter-gather) | merge each shard's top K (as in the simulation) | one shard per update, spread evenly |
| **By score range** | exact: the shard owning the score range, plus the **total counts** of the shards above it | read the top shard (and the next if needed) | a player may move between shards when their score crosses a range; hot top shard if scores bunch up |

For a **very large** board, an **approximate rank** is often acceptable: keep a **histogram of players per score bucket** (cheap and shardable) and report "you are in the top 3%" or a rank estimate for everyone outside the top few thousand, with **exact** ranks only for the top. Players do not care whether they are 4,201,337th or 4,201,402nd.

## Pitfalls

- **Ranking by scanning** or sorting on every request.
- Using a **sorted array with in-place inserts** under heavy updates.
- Treating the in-memory structure as the **only copy** of the scores.
- **Non-idempotent updates** ("add 10 points") replayed after a failure, double counting.
- **Ties** broken arbitrarily, so players swap places between refreshes.
- Building a **sorted set per user** for friends boards.
- Forgetting to **expire old period boards**, filling memory.
- Computing **exact global rank** for 50 million players when an approximation would do.
- Hot **top shard** when sharding by score range and scores bunch together.
- **Clock skew** in the tie-break timestamps from different servers: use a server-assigned sequence.
