## The problem

Design a service (or library) that generates **unique identifiers** for rows, messages, orders and tweets, across **many machines**, at **very high rate**, without a coordination step on every request.

On one database an auto-incrementing column is perfect. Once data is **sharded** over many databases, or many services create records concurrently, every one of them needs ids that are **unique everywhere**, ideally **roughly sorted by creation time** (so recent items cluster together and "latest first" is cheap), and **small** (so indexes stay compact).

## Requirements

**Functional**
- Every id is **unique** across the whole system.
- Ids are **numeric** and fit in **64 bits**.
- Ids are **roughly ordered by time** (sortable by creation).

**Non-functional**
- **High throughput**: 10,000 ids per second per machine, and much more in total.
- **Low latency**: generating an id is a local computation, not a network call.
- **Highly available**: no single point of failure.
- Safe under **clock problems** (skew, steps backwards).

## The candidate designs

| design | how | strengths | weaknesses |
| --- | --- | --- | --- |
| **Database auto-increment** | one counter in a database | tiny, perfectly ordered | single point of failure and bottleneck; does not span shards |
| **Auto-increment per shard with a stride** | shard k hands out k, k+N, k+2N, ... | no coordination | adding shards breaks the stride; ordering across shards is lost |
| **Ticket server** (Flickr) | a dedicated database hands out id ranges | simple; uses a database | needs redundancy (two servers with odd and even ids); every id or range is a network call |
| **UUID version 4** (random, 128 bits) | 122 random bits, no coordination | trivial, no infrastructure, effectively collision-free | **128 bits** (twice the space); **random** keys scatter across an index |
| **UUID version 7 or ULID** (timestamp plus random, 128 bits) | time-ordered prefix, random suffix | sortable and coordination-free | still 128 bits |
| **Snowflake** (64 bits) | timestamp, worker id and sequence packed in one integer | **64 bits, time-ordered, no per-id coordination** | needs unique worker ids and trustworthy clocks |

The rest of this lesson builds **Snowflake**, the design that meets all the requirements.

## The Snowflake layout

A 64-bit integer (the top bit unused so the value is positive in signed 64-bit systems) is divided into fields:

| field | bits | meaning | capacity |
| --- | --- | --- | --- |
| timestamp | 41 | milliseconds since a custom epoch | 2^41 ms is about **69.7 years** |
| worker id | 10 | which generator produced it | **1,024** workers |
| sequence | 12 | counter within the same millisecond on one worker | **4,096** ids per millisecond per worker |

Consequences:
- **Capacity**: one worker issues up to 4,096 ids per millisecond, about **4.1 million per second**; 1,024 workers together about **4.2 billion per second**. Far more than required.
- **Uniqueness without coordination**: two workers differ in the worker bits; one worker never repeats a (timestamp, sequence) pair, as long as its clock never goes backwards and the sequence is handled correctly.
- **Time ordering**: the timestamp occupies the **high bits**, so ids sort by time first. Ids made in the same millisecond on different workers sort by worker id (no meaningful order), and clock disagreement between machines can reorder ids by a few milliseconds: ids are **k-sortable** (roughly sorted), not strictly ordered.
- A **custom epoch** (a recent starting date) rather than 1970 stretches the 69.7 years into the future.

### The generator

1. Read the clock in milliseconds.
2. If the time equals the last time used, **increment the sequence**. If the sequence overflows (4,096 ids already issued this millisecond), **wait for the next millisecond**.
3. If the time moved forward, **reset the sequence to 0**.
4. If the time is **before** the last time used (the clock stepped backwards), **do not issue ids**: wait until it catches up, or fail the request.
5. Pack the three fields into one integer and return it.

### Assigning worker ids

Ten bits means at most 1,024 concurrent workers, and **two live workers with the same id would generate duplicates**. Common approaches: a **coordination service** (ZooKeeper, etcd) hands each process a **leased** worker id when it starts and reclaims it if the process dies; a **static assignment** per host or pod in configuration; or a database table that allocates ids. The lease must make sure an id is never held by two processes at once, even after a network partition.

## The simulation

The program implements the generator with a **clock that the test controls** (so every run is deterministic) and runs four experiments:

1. **Ten workers whose clocks disagree** by a few milliseconds, **100,000 ids** requested over about 2,500 ms of simulated time: are they unique, do they decode back into their fields, and how well would they work as database index keys compared with random ids?
2. **Sequence overflow**: one worker asked for 10,000 ids when the clock barely moves.
3. **The clock stepping back** by one millisecond, with and without the guard.
4. **Random ids**: how likely are collisions for 32, 48, 64 and 122 random bits?

class Snowflake:
    """64-bit ids: 41 bits of milliseconds since the epoch | 10 bits worker id | 12 bits sequence within the millisecond."""
    def __init__(self, worker, clock, guard=True):
        self.worker, self.clock, self.guard = worker, clock, guard
        self.last_ms, self.seq = -1, 0
        self.waits = 0

    def next_id(self):
        ms = self.clock() - EPOCH
        if self.guard and ms < self.last_ms:                    # the clock went backwards: never go back in time
            while ms < self.last_ms:
                ms = self.clock() - EPOCH
                self.waits += 1
        if ms == self.last_ms:
            self.seq = (self.seq + 1) & MAX_SEQ
            if self.seq == 0:                                   # 4096 ids already issued in this millisecond: wait for the next
                while ms <= self.last_ms:
                    ms = self.clock() - EPOCH
                    self.waits += 1
        else:
            self.seq = 0
        self.last_ms = ms
        return (ms << (WORKER_BITS + SEQ_BITS)) | (self.worker << SEQ_BITS) | self.seq


def decode(i):
    return (i >> (WORKER_BITS + SEQ_BITS)) + EPOCH, (i >> SEQ_BITS) & ((1 << WORKER_BITS) - 1), i & MAX_SEQ

## What the output shows

- **100,000 ids from 10 workers with skews of up to 3 ms: all 100,000 unique**, all within 63 bits. Decoding one id returns its timestamp, worker (4) and sequence (2): the fields really are in the number.
- **Index friendliness.** Database indexes (B-trees) are fastest when new keys go to the **newest end** of the index, because that page stays in memory and pages fill up in order. In the experiment, **81.9% of Snowflake inserts landed among the newest 1% of keys**, against **1.1% for random 63-bit ids** (about what chance predicts) and 100% for a single auto-increment counter. The missing 18% are ids from workers whose clocks are a few milliseconds behind: **k-sortable** means *close to* time order. Random ids touch **random pages**, causing cache misses and page splits, which is the main practical reason to prefer time-ordered ids for primary keys.
- **Sequence overflow.** Asked for 10,000 ids while the clock moved only every 5,000 reads, the worker produced them over **3 milliseconds, never more than 4,096 in one**, all distinct; it spent **1,807 clock reads waiting** for the next millisecond when the sequence ran out. The wait is the cost of the guarantee.
- **The clock stepping back by 1 ms.** **Without the guard**, 7 requests produced **only 4 distinct ids**: when the clock went back and returned, the generator reissued (timestamp, sequence) pairs it had already used, so **3 duplicates**. **With the guard**, all 7 ids are distinct and strictly increasing. This is the most important correctness rule of the design: **never move backwards in time**.
- **Random ids and the birthday problem.** With **32 random bits**, 100,000 ids are expected to produce about **1.16 collisions** (we saw 2). With **48 bits**, 5 million ids have about a **4.4%** chance of at least one collision. With **64 bits**, 5 million ids: about **7 in 10 million**. With **122 bits** (a version 4 UUID), even **a trillion ids give about 9 in 10^14**. So random ids are safe only when there are **enough bits**; the collision probability grows with the **square** of the number of ids issued.

The skews, rates and seeds are fixed in the program, so these numbers reproduce exactly; the 81.9% figure depends on the chosen skew and request rate.

## Clock problems in practice

Everything depends on the **clock never going backwards on one worker**:
- **NTP corrections** can step the clock back by milliseconds (or more). The guard in the generator waits for time to catch up; if the step is large (seconds), refuse to issue ids and alert.
- Use a **monotonic clock** for measuring elapsed time within a process, combined with the wall clock at startup, so the generator itself is immune to wall-clock steps. Persist the **last used timestamp** so that a **restart** after a backwards step cannot reuse the past.
- **Leap seconds and virtual machine pauses** cause surprises; test them.
- **Skew between machines** is harmless for uniqueness (worker ids differ) and only affects **ordering** by a few milliseconds.

## Other design points

- **Where does it run?** Best as a **library inside each service instance** (no network call) with a leased worker id. Alternatively a small **ID service** that clients call, which adds a network hop but centralises worker-id management.
- **Wasted capacity versus bit allocation**: if you have fewer workers but need more throughput, shift bits from the worker field to the sequence (for example 8 worker bits and 14 sequence bits). The layout is a design choice; the constraint is that the **total is 63 bits**.
- **JavaScript clients**: numbers above 2^53 lose precision in JavaScript. Send 64-bit ids to browsers **as strings**.
- **Security**: sequential ids leak **volume and timing** (a competitor can count your orders per day) and make **guessing neighbouring ids** possible. Never use ids as secrets or as the only access check; if exposure matters, expose a separate random public id.
- **Extracting the time**: because the timestamp is embedded, "created after time T" becomes a **range query on the primary key**, with no separate timestamp index.
- **Sharding by id**: the high bits are time, so partitioning by id range puts all new writes on one shard (a hot shard); hash the id (or the worker and sequence bits) when sharding by id ([sharding](/sd/databases-2/sharding-and-partitioning/)).

## Pitfalls

- **Two processes with the same worker id** (after a bad configuration or a lease race): silent duplicates.
- **Not guarding against clocks stepping backwards**, or forgetting to persist the last timestamp across restarts.
- **Sequence overflow** not handled: ids wrap and repeat within a millisecond.
- Using **random ids with too few bits** and trusting luck.
- Assuming ids are **strictly** time-ordered across machines.
- Sending 64-bit ids to **JavaScript as numbers**.
- Treating sequential ids as **secure** or unguessable.
- Sharding by **raw id range** and sending all new writes to one shard.
- A **central id service** with no redundancy.
- Choosing 128-bit ids by default and paying for the doubled index size without needing to.
