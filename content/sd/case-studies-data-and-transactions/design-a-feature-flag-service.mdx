## The problem

Design a **feature flag service**: engineers wrap new behaviour in a flag, deploy the code switched **off**, then turn it **on** for 1% of users, then 10%, then everyone, and can flip it **off in seconds** if something breaks. The same machinery runs **A/B experiments**: users are split into groups that see different variants and the groups' behaviour is compared.

Flags decouple **deploying** code from **releasing** it ([safe deployments and feature flags](/sd/observability/safe-deployments-canaries-and-feature-flags/)). The design challenge is that every request in every service asks "is this flag on for this user?" **dozens of times**, so the evaluation must be **extremely fast and available**, while the rules behind it change at any moment and must reach every server **quickly**, and it must **not be able to take the product down** if the flag system itself fails.

## Requirements

**Functional**
- Define flags with variants (on/off, or several values) and **targeting rules**: specific users, user attributes (country, plan), **percentage rollouts**.
- Update a flag instantly (including a **kill switch**) and see an **audit log**.
- Evaluate a flag for a user in application code, in web and mobile clients and in backend services.
- Run **experiments**: assign users to variants consistently, record exposures, report results.

**Non-functional**
- **Evaluation latency** measured in microseconds, with no network call on the hot path.
- **Availability**: if the flag service is down, applications keep working with the last known rules or safe defaults.
- **Fast propagation**: a change reaches clients in seconds.
- **Consistency for a user**: the same user keeps getting the same variant (sticky), and ramping up never switches anyone off.

## Estimation

| quantity | assumption | result |
| --- | --- | --- |
| Services and instances | 1,000 services, 20,000 instances | |
| Flag evaluations | 100,000 per second per instance | 2 billion per second overall |
| Flags | 5,000 flags, about 2 KB of rules each | about 10 MB of rules in total |
| Rule changes | 100 per day | tiny write load |

**Two billion evaluations per second cannot be network calls**: that is the central observation. The rule set is **small (10 MB)** and changes **rarely**, so the right design **ships the rules to the clients and evaluates locally**. The service becomes a **distribution system for a small, slowly changing document**, not a high-traffic query service.

## Architecture

- The **control plane** validates a change (does the rule parse, does it reference real attributes?), stores it as a **new version**, records **who changed what and why**, and publishes a new **snapshot**.
- A **snapshot** (all flags of one environment) is a static file on a CDN or object store: cheap, cached, extremely available ([CDN and API design](/sd/networking-and-apis/cdn-and-api-design/)).
- The **server SDK** downloads the snapshot at startup, keeps it **in memory**, and refreshes it by **polling** (every 10 to 60 seconds) and/or a **streaming connection** that announces a new version so it downloads immediately.
- **Browsers and mobile apps** do not receive the full rule set (it may contain internal targeting): a server or edge relay **evaluates for that user** and returns only the resulting flag values.
- Applications call `variation(flag, user, default)`: evaluation is a function over the in-memory rules. **Exposure events** ("user U was shown variant B of experiment X") are **batched** and sent asynchronously.
- If the snapshot cannot be fetched at startup, the SDK uses a **bootstrap copy** baked into the image or a **cached file**, and the **default value** in the code as a last resort.

## Deterministic percentage rollouts

A rollout to "10% of users" must pick **the same 10% every time**, without storing a per-user decision. The standard trick is **hashing**: compute a **bucket** number from the **flag's key (a salt) and the user id**, for example `hash(salt + ":" + user_id) mod 10,000`, and enable the flag when the bucket is below `percent x 100`.

- **Stable**: the same user and flag always give the same bucket, so a user does not flicker between variants on each request and **no state needs storing**.
- **Monotonic ramps**: a user enabled at 10% has a bucket below 1,000, which is also below 2,500 and 5,000, so **raising the percentage only adds users**, never removes anyone.
- **Independent flags**: the salt differs per flag, so being in flag A's 50% says nothing about flag B's 50%. (Reusing a salt makes the two flags move together and **contaminates experiments**.)
- **Fair spread**: a good hash function (SHA-256, MurmurHash) maps ids uniformly over the buckets.
- **Which identifier?** The **bucketing key** matters: a logged-in user id keeps a person's experience consistent across devices; a device or session id works for anonymous visitors but changes when cookies are cleared. Pick it per flag, and **never change it mid-experiment**.

### Targeting rules

Rules are evaluated **in a fixed order**, first match wins: **blocked users** (explicitly off), **allowed users** (explicitly on, for testers), **attribute rules** (for example country is Germany, plan is enterprise), then the **percentage rollout**, then the **default**. A clear order makes behaviour predictable and debuggable; the dashboard should show **which rule matched**.

## The simulation

The program implements the bucketing and the rule evaluation, on a population of 30,000 simulated users (a fifth with country DE), and measures: **rollout accuracy** at 1%, 10% and 50%; **uniformity** of the bucket spread over **100 different flags** with a chi-square test; whether **ramping** switches anyone off; the **correlation of two flags** with different and with shared salts; **rule precedence**; and how long it takes clients to notice a change under **polling** (60, 30 and 10 seconds) and **streaming**.

import random


def bucket(user, salt):
    """A stable number in [0, 10000) for this user and flag. The same inputs always give the same bucket."""
    h = hashlib.sha256(f"{salt}:{user}".encode()).hexdigest()
    return int(h[:8], 16) % 10000


def evaluate(flag, user):
    """Rules are checked in order: explicit block, explicit allow, attribute rules, then the percentage rollout."""
    if user["id"] in flag.get("block", ()):
        return False
    if user["id"] in flag.get("allow", ()):
        return True
    for attr, values in flag.get("rules", []):
        if user.get(attr) in values:
            return True
    return bucket(user["id"], flag["salt"]) < flag.get("percent", 0) * 100


if True:
    users = [{"id": f"u{i}", "country": "DE" if i % 5 == 0 else "US"} for i in range(30000)]

    # 1. does a 10% rollout reach about 10%, and are buckets spread evenly?
    for pct in (1, 10, 50):
        flag = {"salt": "new-checkout", "percent": pct}
        on = sum(evaluate(flag, u) for u in users)
        print(f"rollout at {pct:2d}%: {on:6,} of {len(users):,} users enabled ({on / len(users) * 100:.2f}%)")
    # is the bucket spread even? chi-square over ten equal slices of the bucket range, for 100 different flags on 5,000 users each
    sample = users[:5000]
    expected = len(sample) / 10
    stats = []
    for k in range(100):
        counts = [0] * 10
        for u in sample:
            counts[bucket(u["id"], f"flag-{k}") // 1000] += 1
        stats.append(sum((c - expected) ** 2 / expected for c in counts))
    print(f"chi-square of the bucket spread for 100 flags: average {sum(stats) / len(stats):.1f} (a fair spread averages 9), "
          f"{sum(x > 16.9 for x in stats)} of 100 above the 95% limit of 16.9 (about 5 are expected by chance)")

    # 2. ramping up never switches anyone off
    steps = [1, 5, 10, 25, 50, 100]
    enabled_prev, flips_off = set(), 0
    for pct in steps:
        flag = {"salt": "new-checkout", "percent": pct}
        now = {u["id"] for u in users if evaluate(flag, u)}
        flips_off += len(enabled_prev - now)
        enabled_prev = now
    print(f"ramp {steps}: users who lost the feature at any step: {flips_off}")

    # 3. two flags at 50%: independent salts versus the same salt (a common mistake)
    a, b_ok, b_bad = {"salt": "flag-a", "percent": 50}, {"salt": "flag-b", "percent": 50}, {"salt": "flag-a", "percent": 50}

    both_bad = sum(evaluate(a, u) and evaluate(b_bad, u) for u in users)
    print(f"two 50% flags with different salts: {both_ok / len(users) * 100:.1f}% of users get both (independent would be 25%)")
    print(f"two 50% flags that share a salt:    {both_bad / len(users) * 100:.1f}% of users get both (they move together, which ruins experiments)")

    # 4. rule precedence
    flag = {"salt": "beta", "percent": 0, "allow": {"u7"}, "block": {"u5"}, "rules": [("country", {"DE"})]}

    # 5. how stale can a client be? 10,000 clients poll every P seconds at random phases; the flag changes at t=0
    rnd = random.Random(2)

## What the output shows

- **Rollout accuracy**: a 1% rollout enabled **1.06%** of the 30,000 users (318), 10% enabled **9.74%**, 50% enabled **49.49%**. Hash-based rollouts are exact only on average: with a small population the actual share wobbles around the target (the expected random spread at 10% of 30,000 users is about plus or minus 0.17 percentage points, so 9.74% is about 1.5 standard deviations low). For an experiment, **measure the real split**, do not assume it.
- **Uniformity**: over **100 different flags**, each tested on 5,000 users, the chi-square statistic averaged **8.7** (a fair spread averages 9) and **4 of 100** exceeded the 95% limit of 16.9 (about 5 are expected by chance): the hash spreads users evenly.
- **Ramping is safe**: going 1, 5, 10, 25, 50, 100 percent, **0 users lost the feature at any step**.
- **Independence matters**: two 50% flags with **different salts** gave **25.0%** of users both (independent would be 25%); with the **same salt** it was **49.7%**: the flags move together, so an experiment on one is confounded by the other.
- **Rule precedence**: with user u5 blocked, u7 allowed, and country DE targeted at 0% rollout, the first ten users show **u0 on (country DE), u7 on (allow list), u5 off (blocked), everyone else off**.
- **Propagation**: polling every **60 seconds**: half of the clients see a change within **29.8 s**, 99% within **59.4 s**, the last after **60 s**; every **30 s**: **15.0 s**, 29.7 s, 30 s; every **10 s**: **5.0 s**, 9.9 s, 10 s. **Streaming** (assuming 50 to 400 ms delivery delay): half within **0.22 s**, 99% within **0.40 s**. A kill switch wants **streaming**, or at least short polling, plus polling as the safety net if the stream breaks.

The population, seeds and delays are fixed in the program, so these numbers reproduce exactly; the propagation delays for streaming are an assumption, not a measurement.

## Experiments

An A/B test is a flag whose rollout splits users into **variants** (for example 50% control, 50% treatment) plus **measurement**:
- **Exposure logging**: record the moment a user is actually **shown** the variant (not merely assigned), with the flag version, so analysis compares the users who saw each variant.
- **Sticky assignment** by the hashing above, with a **fixed salt** for the lifetime of the experiment.
- **Sample ratio mismatch (SRM)**: if the intended 50/50 split shows up as 51/49 in the data by more than chance allows (tested with a chi-square test on the counts), something is wrong (a bug, bot traffic, a client that fails to load the variant) and **the results must not be trusted**. Check it before reading any result.
- **Metrics and statistics** (significance, confidence intervals, avoiding peeking) are a separate subject; the platform must at least guarantee **clean assignment and exposure data**.
- **Mutual exclusion** between experiments that would interfere: put them in a **layer** and assign each user to at most one experiment in the layer using a hash with the layer's salt.

## Failure modes and safety

- **Fail safe**: the default passed to `variation(flag, user, default)` is the behaviour **if anything goes wrong** (usually the old behaviour, off). A flag system outage must never turn features on or break pages.
- **Guard the guard**: a malformed rule update must not crash every client. The control plane **validates** before publishing; SDKs **ignore** a snapshot they cannot parse and keep the last good one.
- **Version everything**: each snapshot has a version; clients log which version they use, so "why did user X see this?" is answerable. Roll back by publishing the previous version.
- **Permissions and review**: changing a production flag is a production change: roles, approvals for critical flags, an audit trail.
- **Flag debt**: stale flags are dead branches and a source of bugs. Give each flag an **owner, a type and an expiry**; release flags are removed after full rollout; permanent flags (kill switches, entitlements) are marked as such. Test **both** sides of a flag while it exists.
- **Dependencies between flags** (flag B only meaningful if flag A is on) are a source of confusing states; validate them in the control plane.
- **Privacy**: SDKs for browsers must not receive other users' data or the full targeting rules; evaluate server-side or send only the result.

## Pitfalls

- **Network calls on every flag check**: the flag service becomes a single point of failure and a latency tax.
- **Reusing one salt** (or hashing only the user id) so flags and experiments correlate.
- **Changing the bucketing key** or the salt mid-rollout, which reshuffles users and breaks stickiness.
- **Trusting the intended split** without checking the observed one (sample ratio mismatch).
- **Sending full targeting rules to browsers**.
- **No safe default**, or a default that turns the new code on.
- **Unvalidated rule changes** that crash clients.
- **No expiry or owner**: hundreds of dead flags and untested code paths.
- **Evaluating flags deep inside hot loops** with expensive context building.
- **Using flags as a configuration database** for large or frequently changing values.
- **Confusing assignment with exposure** in experiment analysis.
