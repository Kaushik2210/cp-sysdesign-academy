## The problem

When you type `how to` into a search box, a list drops down: `how to tie a tie`, `how to screenshot on mac`, ... That is **search autocomplete** (also called typeahead or search suggestions). Design the system that produces those suggestions: for each prefix the user has typed, return the **best few completions** in **well under 100 milliseconds**, ranked by how likely people are to want them, and keep them fresh as the world changes.

It looks like a trivial lookup, but it combines three hard things: a **data structure** chosen for extremely fast prefix queries, a **huge and bursty request rate** (one request per keystroke), and a **continuous data pipeline** that turns search logs into suggestions without ever serving something offensive or stale.

## 1. Requirements

**Functional**

- Given a **prefix**, return the top **5 to 10** suggested queries.
- Suggestions are ranked by **popularity**, with **freshness** (trending queries rise quickly).
- Optional extensions: **personalisation**, **spelling tolerance**, location awareness, several languages.
- **Safety**: never suggest blocked, offensive or legally restricted queries.

**Non-functional**

- **Very low latency**: results must arrive faster than the user types the next character (aim for under 50 to 100 ms end to end).
- **High availability**: the search box must work even if suggestions fail (degrade to plain search).
- **Scalable**: hundreds of millions of searches a day.
- **Eventually consistent** is fine: a new trending query may take minutes to appear; it does not need to be instant.

## 2. Estimation

Assume 500 million searches a day with an average of 12 characters each. If the client sent a request per keystroke, how much traffic would that be, and how much do simple client-side optimisations save?

The naive client would send **about 69,000 requests a second on average and over 200,000 at peak**. Debouncing (waiting for a short pause in typing), skipping the first character and caching in the browser cut that by roughly two thirds. (The reduction factors are assumptions; measure your own.) This is a **read-heavy, latency-critical, small-response** workload: each answer is a handful of short strings. The **corpus** is also small: even a billion logged searches contain perhaps 100 million distinct popular queries averaging 20 bytes, which is about 2 GB of text, **small enough to hold in memory** on each serving node.

## 3. The data structure: a trie with the answers precomputed

A **trie** (prefix tree) stores strings character by character, so all queries that share a prefix share a path. To answer "what are the best completions of `tor`?" you walk three edges to the node for `tor` and then need the best queries **below** it.

Finding them by traversing the whole subtree on every request would be slow for short prefixes (the subtree of `a` is huge). The trick: **precompute at every node the top-k completions** of its subtree and store them in the node. A lookup becomes **O(length of the prefix)**, independent of how many queries exist.

The program builds such a trie from 30,000 synthetic queries with Zipf-like popularity (the k-th most popular query is searched about 1,000,000 / k times), stores the top 5 at every node, and checks the answers against a brute-force scan of all queries.

<CodeRunner language="python" timeoutMs={60000} code={`import heapq, random, time

random.seed(7)
syllables = ["pa", "ri", "to", "ma", "ne", "ko", "li", "sa", "du", "ve", "no", "ba", "ze", "fi", "gu", "he"]
def make_query():
    words = ["".join(random.choice(syllables) for _ in range(random.randint(1, 3))) for _ in range(random.randint(1, 3))]
    return " ".join(words)
queries = {}
for rank in range(1, 30001):
    q = make_query()
    queries[q] = queries.get(q, 0) + int(1_000_000 / rank)          # Zipf-like popularity
print(f"{len(queries):,} distinct queries")

K = 5
class Node:
    __slots__ = ("kids", "top")
    def __init__(self):
        self.kids, self.top = {}, []

root, nodes = Node(), 1
for q, count in queries.items():
    node = root
    for ch in q:
        if ch not in node.kids:
            node.kids[ch] = Node()
            nodes += 1
        node = node.kids[ch]
        node.top.append((count, q))
def trim(node):
    node.top = heapq.nlargest(K, node.top)                           # keep only the K best completions at every node
    for kid in node.kids.values():
        trim(kid)
trim(root)

def suggest(prefix):
    node, steps = root, 0
    for ch in prefix:
        node = node.kids.get(ch)
        steps += 1
        if node is None:
            return [], steps
    return [q for _, q in node.top], steps

def suggest_scan(prefix):
    return [q for _, q in heapq.nlargest(K, ((c, q) for q, c in queries.items() if q.startswith(prefix)))]

tests = ["pa", "tori", "ma ne", "ko l", "zzz", "b", "ve no ba"]
print(f"trie nodes: {nodes:,}; top-{K} lists agree with a full scan on {len(tests)} prefixes: {all(suggest(p)[0] == suggest_scan(p) for p in tests)}")
for p in ("pa", "tori"):
    s, steps = suggest(p)
    print(f"  '{p}' -> {s[:3]} ...  looked at {steps} nodes instead of scanning {len(queries):,} queries")

t0 = time.perf_counter()
for _ in range(2000):
    suggest("tori")
trie_time = time.perf_counter() - t0
t0 = time.perf_counter()
for _ in range(20):
    suggest_scan("tori")
scan_time = (time.perf_counter() - t0) / 20 * 2000
print(f"  2,000 lookups: the trie is roughly {scan_time / trie_time:,.0f}x faster than scanning (timings depend on the machine)")
`} />

The trie's answers matched the brute force on every test prefix. A lookup of `tori` touched **4 nodes** instead of scanning **21,307 queries**, and on a typical run the trie is **more than a thousand times faster** than the scan (the exact ratio depends on the machine). The price is **memory**: every node stores up to `k` completions, so the structure is larger than a plain trie. That is the standard trade: **spend memory at build time to make every lookup constant work**.

Alternatives and refinements:

- **Sorted array plus binary search**: keep all queries sorted; a prefix is a contiguous **range**, found by two binary searches. The top-k in a range comes from a range-maximum structure such as a [sparse table](/cp/range-queries/sparse-table/) over the counts. Compact and cache-friendly, slower to update.
- **Compressed tries / finite state transducers** (what Lucene and Elasticsearch's completion suggester use) shrink memory dramatically by sharing both prefixes and suffixes.
- **Store query ids in nodes, not strings**, and keep the strings in one table, so top-k lists are small integers.
- **Limit depth**: suggestions rarely need more than the first 30 to 50 characters of a query.

## 4. Ranking: popularity, freshness and personalisation

The simplest rank is **total search count**, but it favours the all-time giants. A query that suddenly spikes (breaking news, a sports result, a product launch) should rise quickly and fade as interest ends. A standard approach: score each query with **exponentially decayed counts**, where each past search counts for less the older it is, with a **half-life** of a few hours to a few days.

<CodeRunner language="python" code={`HALF_LIFE_H = 6

def decayed(hourly_counts):                                         # hourly_counts[0] is the most recent hour
    return sum(c * 0.5 ** (age / HALF_LIFE_H) for age, c in enumerate(hourly_counts))

evergreen = [1000] * 72                                             # a steady query: 1,000 searches an hour for 3 days
breaking = [4000, 3500, 3000, 2000, 1000, 400] + [0] * 66           # an event that erupted over the last six hours
print(f"all-time count over 72 h: evergreen {sum(evergreen):,}, breaking news {sum(breaking):,}")
print(f"  -> ranking by all-time count keeps the evergreen query on top")
print(f"decayed score (half-life {HALF_LIFE_H} h): evergreen {decayed(evergreen):,.0f}, breaking news {decayed(breaking):,.0f}")
print(f"  -> the decayed ranking puts breaking news first, as users expect")
`} />

By raw count the evergreen query leads (72,000 against 13,900), yet its **decayed score is 9,164 and the breaking query's is 11,768**, so the breaking query rises to the top. In production, blend several signals: **long-term popularity**, **recent trend**, the **click-through rate** of the suggestion itself (do people pick it when shown?), and optional **personal** and **location** signals (your recent searches, your city). Personalised results are computed by **merging** a small per-user or per-segment list into the global top-k at request time, never by building a trie per user.

## 5. The data pipeline

Suggestions are only as good as the data behind them.

1. **Collect**: every search (with timestamp, language, region, and whether the user clicked a suggestion) is written to a log stream ([stream processing](/sd/queues-and-streaming/stream-processing-basics/)). Log only what you need and respect privacy rules.
2. **Clean and filter**: normalise text (case, Unicode, whitespace), drop queries that are too rare (to avoid exposing individuals' unique searches), remove spam, bot traffic and **blocked or sensitive content** using blocklists and classifiers, and apply legal removals.
3. **Aggregate**: count queries in time windows (say hourly), and maintain decayed scores. A batch job (MapReduce or Spark) handles the long history; a streaming job maintains the **fresh** window.
4. **Build**: create the serving structure (the trie or compressed index) with top-k lists. Keep each build as a **versioned snapshot**.
5. **Publish**: ship the snapshot to all serving nodes and **swap it in atomically**; keep the previous version for instant rollback.

Two cadences work together. A **daily or hourly full rebuild** gives complete, stable suggestions. A small **trending overlay** (updated every few minutes from the streaming job) holds the currently spiking queries; the serving layer merges the overlay's top entries into the trie results at request time. Rebuilding the whole trie every few minutes would be wasteful, and updating it in place on every search would require locks and constant top-k recomputation along the whole path.

## 6. The serving architecture

<Diagram kind="mermaid" code={`flowchart LR

- **Suggestion service**: stateless, holds the current snapshot in memory, answers in a millisecond or two. Replicate it widely; it needs no database on the request path.
- **Sharding** is needed only when the structure outgrows one machine's memory, or to spread load. Shard by the **first one or two characters** of the prefix, but beware **skew**: some starting letters carry far more traffic than others, so split by measured load (hash of the prefix, or learned ranges), and keep every shard replicated.
- **Caching in layers**: the **browser** (recent prefixes), the **CDN** (very popular short prefixes cached for tens of seconds to minutes; the shortest prefixes are the same for everyone), and a **local cache** in the service. Short prefixes dominate traffic and have enormous cache hit rates; deep, unusual prefixes are rare and cheap to compute.
- **Graceful degradation**: if the suggestion service is slow or down, the client shows no suggestions and plain search still works. Use short timeouts and never block the typing experience.
- **Safety filter at serve time** as well as build time, so an urgent takedown (a harmful suggestion) can be applied immediately through a small deny list without waiting for a rebuild.

## 7. Details that matter

- **Typos and fuzzy matching**: suggest `restaurant` for `restuarant`. Exact-prefix tries do not do this. Options include a spell-correction layer using **edit distance** ([edit distance and LCS](/cp/dynamic-programming/edit-distance-and-lcs/)) against a dictionary of popular queries, character n-gram indexes, or learned models. Apply it only when the exact prefix yields few results, because it costs far more.
- **Multiple languages and scripts**: normalise Unicode, segment words appropriately (some languages have no spaces), and keep language-specific tries chosen by the user's language and region. Right-to-left and mixed-script input need testing.
- **Tokenisation and word-start matching**: users type `new york` or `york new`; supporting matches that begin at any word start is an extension, with its own index.
- **Quality and evaluation**: measure **click-through rate on suggestions**, **keystrokes saved**, **latency percentiles**, **coverage** (how often there is any suggestion), and run **A/B tests** on ranking changes.
- **Ethics and policy**: autocomplete can surface harmful, defamatory or private information. Maintain **policies, review and removal processes**, avoid suggesting personal data from rare queries (minimum counts, k-anonymity style thresholds), and be careful with personalised suggestions.
- **Cold start for new content**: a brand-new query has no history; the trending overlay and click feedback are what let it appear.

## Pitfalls

- Traversing the subtree under a prefix on each request instead of storing top-k per node.
- Updating the trie in place on every search, with locks and constant top-k recomputation.
- Ranking only by all-time popularity, so fresh events never appear.
- Sending a request per keystroke with no debounce or cache.
- Sharding by first letter without accounting for skew.
- No offensive-content filtering, or a filter that needs a full rebuild to take effect.
- Exposing rare personal queries as suggestions.
- Blocking the search box on suggestion latency instead of timing out quickly.
- Swapping snapshots non-atomically, so users see a mixture of old and new results.
- Measuring only latency, not whether suggestions actually help (clicks, keystrokes saved).
