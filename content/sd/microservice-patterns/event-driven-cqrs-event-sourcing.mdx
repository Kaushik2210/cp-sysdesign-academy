## Intuition

In a request/response design, service A **tells** service B what to do ("reserve stock"). In an **event-driven** design, A **announces what happened** ("OrderPlaced") and any interested service reacts. A does not know or wait for them. This decouples services in time (consumers can be down and catch up) and in knowledge (new consumers need no change to A), at the price of eventual consistency and harder end-to-end reasoning.

## Commands, events, queries

- **Command**: a request to do something; may be rejected. `PlaceOrder`.
- **Event**: a fact that already happened, immutable, named in the past tense. `OrderPlaced`.
- **Query**: a read that changes nothing.

Name events for **business facts**, not table changes. `OrderShipped` is useful to everyone; `OrderTableRowUpdated` leaks your schema.

## Event notification vs event-carried state

- **Notification**: the event says "order 7 changed". Consumers call back for details. Small events, but coupling and load return to the producer.
- **Event-carried state transfer**: the event contains the data consumers need. Consumers keep local copies, so they run even when the producer is down, but must tolerate duplicates, ordering issues and schema evolution.

Use a schema registry and **backward-compatible changes** (add optional fields, never repurpose them) so old consumers keep working.

## Reliable publishing: the outbox again

The producer must save its state and publish its event atomically. Write the event to an `outbox` table in the same database transaction as the state change; a relay or change-data-capture publishes it to the broker. Consumers handle **at-least-once** delivery with idempotent processing (dedupe by event id). Order is guaranteed only within a partition, so partition by the entity id (all events for one order go to the same partition).

## CQRS: separate the write model and the read model

**Command Query Responsibility Segregation** uses different models for changing and for reading data. Writes validate business rules against a consistent, normalised model. Reads are served from one or more **denormalised read models** (projections) shaped exactly for the screens or APIs that need them: a search index, a Redis hash per user, a wide-column table per query.

The write side publishes events; **projectors** consume them and update read models.

When to use: very different read and write shapes or loads (read-heavy dashboards, search), multiple views of the same data, or complex domains. When not to: simple CRUD. CQRS adds moving parts and eventual consistency to every feature that touches it.

## Event sourcing

Instead of storing the **current state**, store the **sequence of events** that produced it. State is derived by replaying events. A bank account is the classic example: store `Deposited(50)`, `Withdrew(20)`, not just `balance = 30`.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Event:
    kind: str
    amount: int

def apply(balance, e):
    if e.kind == "deposited": return balance + e.amount
    if e.kind == "withdrew": return balance - e.amount
    raise ValueError(e.kind)

def replay(events, upto=None):
    bal = 0
    for e in events[:upto]:
        bal = apply(bal, e)
    return bal

class Account:
    def __init__(self): self.events = []
    def deposit(self, n):
        self.events.append(Event("deposited", n))
    def withdraw(self, n):
        if replay(self.events) < n:                      # command validated against current state
            raise ValueError("insufficient funds")
        self.events.append(Event("withdrew", n))

a = Account()
a.deposit(50); a.withdraw(20)
print(replay(a.events), replay(a.events, upto=1))        # 30 50  (state now, and state at an earlier point)
try: a.withdraw(100)
except ValueError as e: print(e)                         # insufficient funds
```

Benefits: a perfect **audit log**, **time travel** (state at any past moment), the ability to build new read models by replaying history, and natural fit with event-driven systems.

Costs and rules:

- Events are **immutable**; fix mistakes with compensating events, not edits.
- Replay gets slow for long histories: take periodic **snapshots** and replay only the tail.
- **Schema evolution** is hard because old events live forever; use versioned events and upcasters that translate old shapes when reading.
- Queries over current state need projections (hence the pairing with CQRS).
- Concurrency: use **optimistic concurrency** (append only if the stream version equals what you read), retrying on conflict.
- Privacy and deletion rights (GDPR) conflict with immutability; keep personal data outside events or encrypt it with a per-person key you can destroy ("crypto-shredding").

<Callout type="warning" title="Do not adopt it casually">
Event sourcing is a big commitment. Many teams that want an audit trail are better served by an ordinary database plus an append-only audit table, or change-data-capture. Reserve true event sourcing for domains where history is the product: ledgers, orders with complex lifecycles, collaborative systems.
</Callout>

## Orchestration vs choreography (recap)

Choreography (services react to each other's events) avoids a central brain but hides the overall flow. Orchestration (a coordinator emits commands, as in the saga lesson) is easier to follow and monitor. In practice: choreography for loosely coupled side effects (send email, update search), orchestration for business transactions that must be tracked to completion.

## Worked example

A marketplace publishes `OrderPlaced`. Inventory reserves stock; Payments authorises; Notifications emails; Analytics counts; Search updates a "popular items" index. Adding a Fraud service later means subscribing to the stream, with no change to Orders. The order page, however, reads from a projection that may lag by a second. To avoid showing a confusing blank page right after checkout, the command response returns the new order id and the page polls or subscribes until the projection catches up.

## Pitfalls

- Treating events as RPCs in disguise (events that demand a specific reaction).
- Missing idempotency, ordering assumptions across partitions, and unversioned schemas.
- Putting giant payloads or secrets in events.
- Unmonitored consumer lag, so read models silently go stale.
- Event sourcing used where simple CRUD would do.
- No way to rebuild projections (so a bug becomes permanent).

## What would you choose and why?

Support wants "what did this customer's cart look like last Tuesday?", the finance team wants an immutable ledger, and the product team wants fast search over orders. Which parts need event sourcing, which need only CQRS projections, and which can stay as ordinary tables?
