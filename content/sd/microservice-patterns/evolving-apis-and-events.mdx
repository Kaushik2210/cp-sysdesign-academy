## Intuition

In a system of independent services you can never deploy every producer and consumer at the same instant. During a rollout, old and new versions run side by side; data written yesterday is read tomorrow; a mobile app released last year still calls your API. So every interface (REST payloads, gRPC messages, queue events, database rows) must tolerate **two versions at once**.

Two directions matter:

- **Backward compatible:** a **new** reader can read data written by an **old** writer. (Needed when you deploy consumers first or replay old events.)
- **Forward compatible:** an **old** reader can read data written by a **new** writer. (Needed when you deploy producers first, or old clients keep running.)

A change that is both is **fully compatible** and can be deployed in any order. A change that is neither is **breaking**, and needs a new version or a multi-step migration.

## The rules of thumb

Model a record as fields with a type, a *required* flag and an optional default. A reader accepts a record if each field it requires is present (or has a default) with the right type, and it ignores unknown fields. Then:

- **Backward:** every field the new reader requires must be present in every old record. So a field added as required needs a **default** in the new schema; an optional field made required breaks old data.
- **Forward:** every field the old reader requires must still be present in new records. So you cannot remove a required field, and new records must keep sending what old readers need.
- **Types** may only widen on the reading side (an `int` can be read as a `float`, not the other way).
- **Renaming** a field is a removal plus an addition, and is therefore breaking unless you keep both for a while (or use aliases, as Avro does).

### Measured results

Running this exact program with Python 3.13 produced:

| change | backward (new reads old) | forward (old reads new) | verdict |
| --- | --- | --- | --- |
| add optional field | yes | yes | safe both ways |
| add required field, no default | **no** | yes | forward only |
| add required field with default | yes | yes | safe both ways |
| remove optional field | yes | yes | safe both ways |
| remove required field | yes | **no** | backward only |
| rename a field | **no** | **no** | breaking |
| widen `score` int to float | yes | **no** | backward only |
| narrow `id` int to str | **no** | **no** | breaking |
| make an optional field required | **no** | yes | forward only |

The rules of thumb agreed with real parsing in all 9 cases. A note on how that number was reached: the first draft of the rules in this lesson predicted that making an optional field required was safe in both directions, and the check disagreed (8 of 9). The reason is that old records may legitimately omit an optional field, so a reader that now requires it fails on them. The rule above includes that clause because the test found it. That is the case for **testing compatibility mechanically** instead of reasoning about it.

The safe habit is visible in the table: **adding an optional field, or a required field with a default, is the only change that is safe in both directions.** Everything else needs a plan.

## How to change a field safely: expand and contract

For a rename or a type change, use several deployable steps, never one:

1. **Expand:** add the new field alongside the old, optional. Writers send **both**.
2. **Migrate:** deploy readers that prefer the new field and fall back to the old one. Backfill stored data.
3. **Contract:** once no reader depends on the old field (check with metrics, or after all old clients are retired), stop writing it, then remove it in a later release.

For HTTP APIs, additive changes go in place; breaking changes get a **new version** (`/v2/orders`, a header, or a new gRPC package) and a published deprecation timeline.

## Tools

- **Schema formats with rules built in:** Protocol Buffers (never reuse a field number; new fields optional with defaults), Avro (writer and reader schemas resolved by name with defaults and aliases), JSON Schema with `additionalProperties` policy.
- **Schema registry** (Confluent and others): producers register schemas; the registry **rejects** changes that violate the topic's compatibility mode (backward, forward, full, or transitive variants).
- **Consumer-driven contracts** (Pact): each consumer records the fields it actually uses; the provider's CI verifies it still honours every consumer's contract before release. This finds breaking changes without a shared integration environment.
- **Tolerant reader:** consumers ignore unknown fields and unknown enum values (map them to a safe default) instead of failing.
- **Upcasters** for event-sourced data: translate old event versions to the current shape at read time.

## Pitfalls

- Renaming a field "because it is cleaner", which breaks every consumer at once.
- Adding a required field with no default.
- Reusing a field number or a name with a new meaning.
- Strict readers that fail on unknown fields or enum values, so any addition becomes a breaking change.
- Treating events as internal and changing them freely, although other teams replay them for years.
- Removing a field before checking that nothing reads it (use usage metrics, not guesses).
- Deploying a producer change before consumers, when the change is only backward compatible.
