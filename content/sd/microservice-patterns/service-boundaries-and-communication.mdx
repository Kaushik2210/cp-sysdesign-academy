## Intuition

A **microservice architecture** splits one application into many small services, each owning a piece of the business and deployable on its own, usually by its own team. The promise is organisational: teams ship independently, scale independently and choose their own tools. The price is technical: every call that used to be a function call is now a network call that can be slow, fail, return a stale answer or arrive twice. You exchange the complexity of a large codebase for the complexity of a distributed system.

That trade is excellent when you have many teams and a large, fast-changing product, and poor when you have a small team and a modest product. The most common failure is not too few services but the wrong boundaries: services that must be changed together, call each other constantly and share a database form a **distributed monolith**, which has all the costs of microservices and none of the benefits.

## Draw boundaries around business capabilities

The goal is that most changes touch **one** service. Boundaries drawn around technical layers (a "database service", a "validation service") force every feature to cross all of them. Boundaries drawn around **business capabilities** (orders, payments, inventory, shipping, catalogue) keep a feature's logic and data together.

**Bounded contexts.** From domain-driven design: each part of the business has its own model and vocabulary. "Customer" means one thing to billing (a payer with invoices), another to support (a person with tickets) and another to marketing (a segment). Each context owns its own model; services map onto contexts, and translate at the edges instead of sharing one giant "Customer" table.

**Data ownership.** Each service owns its data and is the **only** one that reads or writes it. Others get at it through the service's API or through events it publishes. A shared database is the strongest coupling there is: a schema change breaks every reader, and you cannot scale, secure or migrate one service independently.

**Signs the boundary is wrong**

- Two services are always deployed together, or one cannot work when the other is down.
- A single feature needs coordinated changes in three or more services.
- Services call each other in long synchronous chains, or in circles.
- A "shared library" contains business rules that every service imports.
- You need a distributed transaction for an everyday operation.

**Start with a modular monolith.** Build one deployable application with clean internal module boundaries and enforced dependencies, and extract a module into a service only when a real need appears (independent scaling, a different team, different release cadence, fault isolation). Getting a boundary wrong inside a monolith costs a refactor; getting it wrong across a network costs a migration.

## How services talk

| Style | How | Good for | Cost |
| --- | --- | --- | --- |
| **Synchronous request/response** (REST, gRPC) | Caller waits for the answer | Queries, user-facing reads, commands needing an immediate result | Caller depends on the callee being up and fast; failures and latency propagate |
| **Asynchronous messaging** (queue, command) | Caller sends a message and moves on | Work that can finish later, load levelling, decoupling in time | No immediate result; delivery semantics and idempotency matter |
| **Event publishing** (pub/sub, log) | A service announces "something happened"; any number of consumers react | Many consumers, loose coupling, building read models | Consumers can lag; the event contract becomes a public API; harder to trace |

A good rule: use **synchronous calls for queries** the user is waiting on, and **events for facts** other services react to. Avoid using synchronous calls for operations that merely "tell" another service something; that couples availability for no reason.

### API composition and backends for frontends

A screen often needs data from many services. Instead of the browser calling ten services, a **composition layer** calls them in parallel and merges the results. An **API gateway** does this generically (plus authentication, rate limiting and routing); a **backend for frontend (BFF)** is a composition service tailored to one client (mobile, web) so each gets exactly the shape it needs.

### Service discovery

Instances come and go with deploys and autoscaling, so callers cannot hard-code addresses. **Service discovery** maps a service name to the currently healthy instances:

- **Client-side discovery:** the caller asks a registry (Consul, etcd, Eureka) and load-balances itself.
- **Server-side discovery:** the caller talks to a stable name (DNS, a load balancer, Kubernetes Service) that forwards to healthy instances.
- **Service mesh:** a sidecar proxy next to each service handles discovery, retries, timeouts, mutual TLS and metrics uniformly, so application code does not have to.

Health checks decide who is in the pool; see the failure-detection lesson for why a ping alone is a weak signal.

### Contracts and versioning

When services deploy independently, the interface between them is a **contract**. Keep changes **backward compatible**: add optional fields rather than renaming or removing, tolerate unknown fields ("be liberal in what you accept"), and version when you must break. **Consumer-driven contract tests** let each consumer publish the requests and responses it relies on, so a provider's pipeline fails before it breaks a consumer.

## The arithmetic of chained calls

Every synchronous dependency multiplies risk. Two effects deserve numbers.

**Availability in series.** A request that needs `n` services in sequence is only up if all are up: availability is the product. **Tail latency under fan-out.** If a request calls `n` services in parallel and waits for all of them, it is slow whenever any one call is slow, so rare per-call slowness becomes common per-request slowness.

<CodeRunner language="python" code={`import random

# Part 1: availability of a chain of synchronous calls (each service independently up with probability a)
print("a request that must pass through n services in series, each 99.9% available")
print("   n   chain availability   downtime per 30-day month")
for n in (1, 3, 5, 10, 20):
    chain = 0.999 ** n
    print(f"  {n:>2}   {100 * chain:>17.3f}%   {30 * 24 * 60 * (1 - chain):>9.1f} min")

# Part 2: tail latency amplification when one request fans out to n services in parallel and waits for all
rng = random.Random(42)
print()
print("one request fans out to n services in parallel and waits for the slowest; each call is slow (above the 99th percentile) 1% of the time")
print("   n   requests that hit a slow call (simulated)   exact 1 - 0.99^n")
trials = 100000
for n in (1, 5, 10, 25, 50, 100):
    slow = sum(1 for _ in range(trials) if any(rng.random() < 0.01 for _ in range(n)))
    print(f"  {n:>3}   {100 * slow / trials:>38.1f}%   {100 * (1 - 0.99 ** n):>14.1f}%")
`} />

A local run printed: for services that are each 99.9% available, a chain of 5 is only **99.501%** available (about 216 minutes of downtime in a 30-day month) and a chain of 20 is **98.019%** (about 856 minutes, over 14 hours). For fan-out where each call is slow 1% of the time, a request that waits on 10 services hits a slow call **9.5%** of the time (exact 9.6%), on 50 services **39.4%**, and on 100 services **63.2%**. Each individual service looks healthy; the composed request does not. This is why chatty call graphs, deep chains and wide fan-outs are architecture problems, not tuning problems, and why you set per-call timeouts, hedge or cut slow calls, and keep the critical path short.

## Failure modes

- **Cascading failure:** a slow dependency ties up callers' threads, which makes them slow, which spreads upstream.
- **Retry storm:** every layer retries, multiplying load on a struggling service.
- **Version skew:** a consumer deployed before a provider supports a new field (or after it removed an old one).
- **Chatty coupling:** one user action triggers dozens of calls and a hundred milliseconds of network time.
- **Lost event contract:** a producer changes an event's meaning and silently breaks consumers.
- **Registry outage or stale entries:** callers send traffic to dead instances.

## Pitfalls

- Splitting by technical layer instead of by business capability.
- Sharing a database or a "common" library full of business logic.
- Making everything synchronous, so the system is only as available as its worst dependency.
- Decomposing too early, before the domain is understood.
- Forgetting the operational cost: each service needs deploy pipelines, monitoring, alerts, on-call ownership and security.
- Treating the number of services as a measure of maturity.
