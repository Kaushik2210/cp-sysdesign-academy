## Intuition

Every design choice gives something up. A cache speeds reads and adds stale data. Sharding scales writes and complicates queries. Interviewers rarely care which option you pick; they care that you **know what you are paying**. A choice stated without its cost sounds like a guess. A choice stated with its cost sounds like engineering.

## A five-part sentence

Use the same structure every time, so it becomes automatic:

1. **Decision:** what you choose.
2. **Alternative:** what you considered instead.
3. **Criterion:** the requirement that decides between them.
4. **Cost:** what you are giving up.
5. **Trigger:** what would make you change your mind.

> "I will use a relational database for orders, not a document store, because we need multi-row transactions for payments (criterion). The cost is harder horizontal scaling, which I would address with read replicas first and sharding by customer id only if writes outgrow one primary (trigger)."

That is 45 seconds and answers the question the interviewer was about to ask.

## Anchor trade-offs to numbers and requirements

Vague trade-offs sound like memorised lists. Tie them to your own estimates:

- "At 400 reads per second the database is not the bottleneck, so I would not add a cache for throughput. I would add one only to cut p99 read latency."
- "A 10 ms cross-region round trip is fine for the feed but not for the checkout flow, so the feed can read from a nearby replica while checkout stays on the primary."

<Callout type="pitfall" title="Trade-offs without a criterion">
"Redis is fast but costs more" is true of almost everything and decides nothing. Always name the requirement that tips the scale: latency target, consistency need, budget, team skill.
</Callout>

## Practise out loud

Pick a decision and answer in the five-part form, speaking, timed to under a minute. Try these:

- Queue between the API and a slow downstream service, or call it synchronously?
- Store shopping carts in a database or in a cache with a persistence layer?
- Generate IDs with a database sequence, UUIDs or a time-ordered ID service?

If you cannot name a cost for your choice, you have not understood the choice yet.

## Pitfalls

- **Presenting one option.** If you never mention an alternative, the interviewer will, and you will be reacting.
- **Defending instead of listening.** If the interviewer pushes back, treat it as new information. "Good point, that changes the trade-off, so I would..." is a strong answer.
- **Hedging everything.** "It depends" is only useful followed by "on X, and in this case X is Y, so I choose Z."

## What would you choose and why?

A chat product can deliver messages through long-lived WebSocket connections or through push notifications plus polling. Name the criterion you would use to choose, the cost of your pick and what would make you switch.
