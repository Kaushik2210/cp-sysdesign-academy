## Intuition

A system is scalable if adding resources lets it handle proportionally more load while keeping latency acceptable. There are two ways to add resources:

- **Vertical scaling (scale up)**: a bigger machine. Simple, no code change, but bounded by the largest machine, gets steeply more expensive, and leaves one failure domain.
- **Horizontal scaling (scale out)**: more machines behind a load balancer. Nearly unbounded and fault tolerant, but requires that work can be split and that machines do not depend on local state.

Most real systems do both: scale a database vertically first because it is simplest, and scale the stateless tier horizontally from the start.

## Stateless services

A service is **stateless** when any instance can handle any request, because everything it needs arrives with the request or lives in a shared external store. Then instances are interchangeable: add one, kill one, replace one, and no user notices.

What counts as state to move out of the process:

- **Sessions**: login state, shopping carts.
- **Uploaded files** in a local disk: move to a blob store.
- **In-memory caches that must be coherent**: move to a shared cache, or accept per-instance caches as an optimisation only.
- **Background timers or leader roles**: use a coordination service or database lock.

### Session handling options

| Approach | How | Pros | Cons |
| --- | --- | --- | --- |
| Sticky sessions | Load balancer pins a user to an instance (cookie or IP hash) | No code change | Uneven load, session lost when instance dies, hinders autoscaling in |
| Central session store | Session id in a cookie, data in Redis or a database | Any instance serves anyone, survives instance loss | Extra network hop, the store must be highly available |
| Signed token (for example JWT) | Client holds the state, server verifies signature | No server-side lookup, scales trivially | Cannot easily revoke before expiry, token size, sensitive data must not be put in it |

## Why scaling is not linear: Amdahl and USL intuition

**Amdahl's law**: if a fraction `p` of the work can be parallelised and `1-p` is serial, the speedup with `N` workers is at most `1 / ((1-p) + p/N)`.

With `p = 0.95` (5% serial):

| N | Speedup |
| --- | --- |
| 2 | 1.9 |
| 8 | 5.9 |
| 32 | 12.6 |
| 100 | 16.8 |
| 1000 | 19.6 |

The ceiling is `1/(1-p) = 20` no matter how many machines you add. The serial part might be a global lock, a single database primary, or one coordinator.

**Universal Scalability Law (USL)** adds a second penalty: coordination cost between workers, growing roughly with `N^2`. Capacity is `C(N) = N / (1 + a(N-1) + b N(N-1))`, with `a` the contention (serial) coefficient and `b` the coherency (crosstalk) coefficient. With `a = 0.05, b = 0.001`:

| N | Relative capacity |
| --- | --- |
| 1 | 1.0 |
| 8 | 5.7 |
| 16 | 8.0 |
| 32 | 9.0 |
| 64 | 7.8 |

Throughput peaks near `N = sqrt((1-a)/b)`, about 31 here, and then *falls*: more machines made it worse. The practical lesson is not to trust the formulas' parameters but to **measure scaling**, find which of contention (queues, locks, single primary) or coherency (all-to-all chatter, cache invalidation storms) dominates, and fix that.

<Callout type="note">
These are models, not laws of physics for your system. Fit a and b from load tests at several sizes before using them for planning.
</Callout>

## Autoscaling: signals and cooldowns

Autoscaling adds or removes instances automatically. Choices:

- **Signal**: CPU utilisation is common but poor for IO-bound services. Better signals map to user pain or saturation: requests in flight per instance, queue depth or message age for workers, p95 latency (with care), and for GPU or memory-bound services the relevant resource.
- **Target tracking**: keep a metric near a target (say 60% CPU). Simple and stable.
- **Scheduled scaling**: scale up before known peaks (a 9 am login surge, a sale) because instances take time to start.
- **Cooldown / stabilisation window**: wait after a scaling action before another, and use asymmetric rules (scale out fast, scale in slowly) to avoid **flapping** where capacity oscillates.
- **Warm-up**: new instances need time to boot and warm caches; do not count them as full capacity immediately.
- **Bounds**: minimum for availability, maximum for cost and for protecting downstream systems.

## Pitfalls

- **Scaling the stateless tier and melting the database.** Doubling app servers doubles connections and queries to the shared store. Use connection pooling and caching and size downstream capacity first.
- **Scaling on CPU for an IO-bound service**, so it never scales while requests queue.
- **Scale-in kills in-flight work.** Drain connections and finish jobs before termination.
- **No maximum.** A retry storm or attack can scale your bill without bound.
- **Cold start surprises.** Autoscaling takes minutes; keep headroom for spikes shorter than that.
