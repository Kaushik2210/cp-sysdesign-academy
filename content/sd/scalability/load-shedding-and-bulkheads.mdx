## Intuition

When demand exceeds capacity, something has to give. Without a plan, *everything* gives: queues grow, latency climbs, timeouts trigger retries, retries add load, and the system collapses and serves nobody. This is **congestion collapse**, and a service that is merely overloaded can look dead for far longer than the spike that started it.

The strategy is to choose in advance what to sacrifice:

1. **Shed load**: refuse some requests quickly so the rest are served well.
2. **Degrade gracefully**: serve a cheaper, lesser answer instead of failing.
3. **Isolate**: make sure one failing or greedy part cannot drain resources the others need (bulkheads).

## Why queues alone make it worse

A server doing work at rate `mu` with arrivals above `mu` builds a queue that grows without bound. Latency is queue length divided by `mu`. Past the client timeout, the server is working on requests whose callers already gave up, so *useful throughput falls toward zero* (goodput collapse). Bounded queues, deadlines and early rejection fix this.

## Load shedding techniques

- **Concurrency limit**: allow at most `C` requests in flight (Little's law: `C = throughput x latency`). Reject extras immediately with 503 or 429. Adaptive versions raise and lower `C` based on observed latency.
- **Bounded queue with drop policy**: small queue; drop the *oldest* (LIFO under overload) because the oldest request's client has probably timed out.
- **Priority-based shedding**: drop low-value traffic first (analytics, prefetch, background sync), keep checkout and login.
- **Deadline propagation**: pass the remaining time budget downstream; drop work whose deadline has passed.
- **Cheap rejection**: the reject path must cost far less than the work, or shedding itself overloads you.

<Callout type="tip">
Shedding by priority needs the priority to be known *early* (a header or the route), because the point is to decide before spending resources.
</Callout>

## Graceful degradation

Return something useful with fewer resources:

- Serve cached or stale data when the database is slow ("stale-while-revalidate").
- Drop non-essential features: personalised recommendations replaced by a generic popular list, search with fewer filters, no real-time counts.
- Reduce quality: lower image resolution, skip enrichment calls.
- Read-only mode when the write path is unhealthy.

Feature flags and kill switches let operators trigger these modes. Degrade paths must be *tested regularly*; an untested fallback often fails when first needed.

## Bulkheads

Named after ship compartments: a leak floods one compartment, not the hull. In software:

- **Separate thread pools or connection pools per dependency** so a slow payment provider cannot consume all threads the product catalogue needs.
- **Separate fleets per tenant tier or per endpoint class**, so a flood of bulk-export requests cannot starve interactive ones.
- **Cell-based architecture**: users are partitioned into independent cells, each a full copy of the stack; a failure affects one cell only.

Combine with **timeouts** (every remote call bounded), **retries with exponential backoff and jitter and a retry budget** (so retries are at most a small percentage of traffic), and **circuit breakers** (stop calling a failing dependency for a cooling-off period, then probe).

## Worked example: a product page under a dependency slowdown

A product page calls inventory, pricing, reviews and recommendations. Normal latency is 80 ms total; thread pool of 200 threads shared by all calls. Recommendations start taking 10 s per call.

- *Without bulkheads*: at 500 requests per second, each waiting thread is held 10 s, so about 5,000 concurrent calls are needed; all 200 threads are stuck within half a second and the whole page, including inventory, times out.
- *With a separate 20-thread pool and 300 ms timeout for recommendations*: at most 20 calls wait, the rest fail instantly and fall back to a cached "popular items" list. Inventory and pricing keep their own pools and the page still renders in about 400 ms.

This is Little's law at work: in-flight requests equal arrival rate times latency, so latency growth silently multiplies resource use.

## Pitfalls

- **Retries without budgets**, tripling load on a failing service.
- **Timeouts longer than the caller's own timeout**, so work continues for nobody.
- **Shedding on CPU only** when the real limit is a downstream pool; measure the actual bottleneck.
- **Health checks that fail under load**, causing the load balancer to remove healthy-but-busy instances and push even more load onto the rest.
- **Fallbacks that call the same failing dependency.**

## What would you choose and why?

A ticketing site gets ten times normal traffic when sales open. Rank these by value: browsing event pages, searching, seat selection, payment, order history, recommendations. Which would you shed first, which would you degrade to a cached version, and which must be protected by their own bulkhead?
