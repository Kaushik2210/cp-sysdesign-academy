## Why evaluation is the central skill

A traditional program is **deterministic**: given the same input it gives the same output, so a unit test either passes or fails. A system built on a language model is **probabilistic**, its outputs are **free text** that can be right in many ways and wrong in subtle ways, and **a change that improves one kind of question quietly breaks another**. There is no compiler error for "the assistant became slightly less helpful on refund questions."

So in AI products, **evaluation (evals) plays the role that tests, monitoring and code review play elsewhere**. Teams that ship good AI features are usually the ones with the **best measurement**, not the best prompts. This lesson covers the machinery: **building test sets**, **reading results honestly** (statistics), **using models as graders** without being fooled by their biases, **monitoring in production**, and **watching cost**.

## The layers of evaluation

| layer | what it answers | cost and speed |
| --- | --- | --- |
| **Programmatic checks** | Is the output valid JSON? Does the code compile and pass tests? Does the answer contain the required citation? | cheap, instant, exact |
| **Reference-based scoring** | Does the answer match a known correct answer (exact match, extracted fields, retrieved passage ids)? | cheap, needs labels |
| **Model-graded evaluation (LLM as judge)** | Is this answer helpful, faithful to the sources, polite? Which of two answers is better? | moderate, scales, **biased** |
| **Human review** | Is it actually good? Calibrates everything above. | slow and expensive, the gold standard |
| **Online experiments** | Do real users succeed more? Do they come back? | slow, needs traffic, measures what matters |
| **Production monitoring** | Is quality holding up **today**, on real traffic? | continuous |

Use the cheap layers **often** (every code change) and the expensive layers **sparingly** (before releases, and on samples). Each layer **calibrates** the one above it: model graders are checked against human labels; offline scores are checked against online results.

## Building the evaluation set

- **Start from real traffic** (with privacy handling): sample actual questions, and include the **hard and weird ones**, not only typical ones.
- **Add every production failure**: each bug report becomes a test case, so the same failure cannot return unnoticed (a regression suite).
- **Cover the dimensions** that matter: topics, languages, lengths, adversarial inputs, questions that **should be refused**, questions the system **cannot answer** (it should say so).
- **Define "correct" before measuring**: a written rubric or a programmatic check. Disagreement among human labelers is information: measure it and fix the rubric.
- **Keep a held-out set** that is **never used to tune prompts**, to detect over-fitting to the evaluation set. Treat leaks (test questions appearing in training or in few-shot examples) as contamination.
- **Version it** like code, with a changelog; a score only means something relative to a specific set.

## Reading results honestly: noise

Every score is an **estimate** from a **sample** of questions. With 100 test questions and a true accuracy of 80%, the 95% confidence interval is about **plus or minus 7.8 percentage points** (1.96 x the square root of 0.8 x 0.2 / 100): a measured 74% and a measured 86% are statistically indistinguishable. To measure accuracy to within plus or minus 3 points needs roughly **680 questions**. Improvements are usually **small** (a few points), so evaluation sets must be **large enough** or the comparison is a coin flip.

### The simulation

The program has four parts (standard library only, fixed seeds):

1. **Can an evaluation notice a 3-point improvement?** Two systems, B better than A by exactly 3 points on average (B fixes 15% of A's errors). Each question has its own difficulty, so both systems fail the same hard questions. For test sets of 300, 1,000 and 3,000 questions, 120 repeated experiments each, count how often a 5% test declares B better: scoring the systems on **different random questions** versus on the **same questions** (a **paired** comparison, which uses only the questions where they differ).
2. **A model judge with a position bias.** A judge picks the better of two answers but favours whichever is shown **first** by 10 points. Compare judging each pair in one order with judging in **both orders** and averaging.
3. **Watching production quality.** Each day a sample of answers is graded; an alarm fires when the accuracy looks lower than the 90% baseline. Exact probabilities (computed from the binomial distribution) of a **false alarm** and of **catching a drop** to 85% or 80%, for daily samples of 50 to 1,000.
4. **The cost tail**: per-request cost with a heavy tail (log-normal), at two levels of spread.

import random


def boosted(s):
    """System B fixes 15% of the cases that system A would get wrong, which is 3 points better on average (0.15 x 0.2)."""
    return s + 0.15 * (1 - s)


def experiment(n_items, paired, rnd):
    """Score system A and system B on test questions. Each question has its own difficulty, so both systems tend
    to fail the same hard questions. Returns the z statistic for 'B is better than A'."""
    a_right = b_right = a_only = b_only = 0
    for _ in range(n_items):
        s = rnd.betavariate(1.6, 0.4)                       # chance that A answers this question correctly (mean 0.8)
        a = rnd.random() < s
        if paired:
            b = rnd.random() < boosted(s)                   # B answers the very same question
        else:
            b = rnd.random() < boosted(rnd.betavariate(1.6, 0.4))     # B is scored on its own, different questions
        a_right += a
        b_right += b
        a_only += a and not b
        b_only += b and not a
    if paired:
        d = a_only + b_only
        return (b_only - a_only) / math.sqrt(d) if d else 0.0       # only questions where they differ carry information
    pa, pb = a_right / n_items, b_right / n_items
    se = math.sqrt(pa * (1 - pa) / n_items + pb * (1 - pb) / n_items)
    return (pb - pa) / se if se else 0.0


def detection_power(n, p0, p1, z_crit):
    """Exact chance that a one-sided test on n sampled answers flags a drop, when the true accuracy is p1."""
    sd0 = math.sqrt(p0 * (1 - p0) / n)
    total = 0.0
    for k in range(n + 1):
        z = (k / n - p0) / sd0
        if z < -z_crit:
            total += math.comb(n, k) * p1 ** k * (1 - p1) ** (n - k)
    return total


def judge_pairs(n, p_a_better, position_bias, rnd, swap):
    """A judge model compares two answers. It favours whichever answer is shown FIRST by 'position_bias'."""
    a_wins = 0.0
    for _ in range(n):
        a_truly_better = rnd.random() < p_a_better
        # order 1: A first
        p_first_wins = min(1.0, max(0.0, (1.0 if a_truly_better else 0.0) * 0.8 + 0.1 + position_bias))
        w1 = rnd.random() < p_first_wins                     # True means A (shown first) was chosen
        if not swap:
            a_wins += w1
        else:
            p_first_wins2 = min(1.0, max(0.0, (0.0 if a_truly_better else 1.0) * 0.8 + 0.1 + position_bias))
            w2 = rnd.random() < p_first_wins2                # now B is shown first; True means B was chosen
            a_wins += (w1 + (1 - w2)) / 2                    # average the two verdicts for A
    return a_wins / n


if True:

    rnd = random.Random(1)
    print("system B is truly 3 points better than system A. How often does the evaluation notice (z above 1.96)?")
    for n in (300, 1000, 3000):
        res = {}
        for paired in (False, True):
            hits = sum(experiment(n, paired, rnd) > 1.96 for _ in range(120))
            res[paired] = hits / 120
        print(f"  {n:5d} test questions: scoring the two systems on different random questions {res[False] * 100:5.1f}% | on the SAME questions (paired) {res[True] * 100:5.1f}%")

## What the output shows

**1. Small improvements need big test sets** (how often a 3-point real improvement is detected):

| test questions | different questions for A and B | the same questions (paired) |
| --- | --- | --- |
| 300 | 16.7% | 19.2% |
| 1,000 | 45.8% | 58.3% |
| 3,000 | 84.2% | 94.2% |

- With **300 questions the evaluation misses a real 3-point improvement about 5 times out of 6**: "no significant difference" often means "not enough data". With **1,000** it is a coin flip. Only at **3,000** does it become reliable.
- **Comparing on the same questions helps** (58.3% against 45.8% at 1,000, and 94.2% against 84.2% at 3,000), because the shared difficulty of questions cancels out and only the cases where the systems differ carry the signal. **Always compare systems on the same set**, and use a paired test.
- The converse risk: with many variants and many metrics, **some will look significantly better by chance** (about 1 in 20 at a 5% level). Pre-decide the primary metric, and confirm surprising wins on fresh data.

**2. Judge bias.** The judge favours the first-shown answer by 10 points, and this is **not harmless**:
- When the two answers are **equally good**, showing A first makes A "win" **60.0%** of the time. Judging both orders and averaging gives **50.0%**.
- When A is **truly better in 55%** of pairs, a single-order judge reports **64.0%** (an overstatement of 9 points, larger than the real effect you wanted to measure), while the two-order average reports **54.1%**, close to the truth.
- Other known judge biases: **verbosity** (longer answers preferred), **self-preference** (a model favours its own style), and sensitivity to formatting. Mitigations: **randomise or swap order**; **score against a rubric and a reference answer** instead of open comparison; use a **different model family** for judging; and **calibrate the judge against human labels** on a sample (measure its agreement, and stop trusting it where it disagrees).

**3. Production monitoring.** With a baseline accuracy of 90% and a target false alarm level of 1% per day:

| graded answers per day | false alarms | drop to 85% caught | drop to 80% caught |
| --- | --- | --- | --- |
| 50 | 2.5% of days | 20.9% of days | 55.6% |
| 100 | 2.1% | 32.8% | 80.8% |
| 300 | 1.1% | 65.1% | 99.6% |
| 1,000 | 1.0% | 99.4% | 100.0% |

- **Sample size sets how fast you notice.** A 5-point quality drop is caught on only one day in five with 50 graded answers per day, and **on two days out of three** with 300. A silent regression can run for **days** under a small sample.
- **Small samples also misbehave**: the alarm meant to fire 1% of days fires on **2.5%** of days at 50 samples (the normal approximation is poor for small counts). Use exact binomial or sequential tests for small samples, and expect noisy alerts.
- So decide **what size of drop matters**, then **budget the grading** (human or model) to detect it within an acceptable time, and **stratify** (by topic, language, customer) so a collapse in one segment is not averaged away.

**4. Cost has a tail.** With a moderate spread, the **mean request costs 1.64 times the median** and the **most expensive 1% of requests cause 9% of the total cost** (the top 10% cause 39%). With a heavier tail (as with long agent runs or very long documents) the mean is **3.06 times the median**, the 99th percentile is **32 times the median**, and **the top 1% of requests cause 21% of the cost** (the top 10% cause 59%). Budgeting from the **median** request badly underestimates the bill, and a **handful of requests or users** can dominate it: **alert on cost percentiles and per-user and per-feature totals**, not on the average.

The simulated systems, judge and costs are idealised and the probabilities are assumptions: they demonstrate **why** evaluation statistics matter, not the numbers you will see for your product.

## Putting evaluation into the engineering process

- **A regression gate in continuous integration**: every change to a prompt, model version, retriever or tool runs the programmatic evals (fast) and, before release, the larger model-graded set. **Block** changes that cross agreed thresholds on any critical segment, and show **confidence intervals**, not single numbers.
- **Release carefully**: **shadow** new versions on live traffic and compare outputs offline; **canary** to a small share of users; use **A/B tests** for user-facing quality; keep the **old version** available for instant rollback ([safe deployments and flags](/sd/observability/safe-deployments-canaries-and-feature-flags/)). **Model providers update their models**: pin versions, and re-run your evals when a version changes or is retired.
- **Close the loop**: sample production traffic for grading, review the failures weekly, **turn failures into test cases**, fix the root cause (retrieval, tool, prompt, data) and confirm the fix in the suite.
- **Guardrail metrics next to the target metric**: improving "helpfulness" while **refusal rate, latency, cost per request or safety violations** worsen is not an improvement.
- **Track input drift**: new topics, languages, longer prompts or new document types can degrade quality without any change on your side. Monitor the **distribution of inputs** (topic mix, length, language) and the **share of low-confidence or abstained answers**.
- **Online signals**: thumbs, edits, regeneration, copy, abandonment and escalation rates are **noisy and biased** (only some users give feedback), but they are measured on real work; use them to find where to look, and to validate offline metrics.
- **Privacy**: evaluation data contains real user text. Apply the same retention, access and anonymisation rules as production data.

## Pitfalls

- **Judging quality by looking at a few examples** ("vibes") and shipping.
- **Comparing two versions on different test questions**, or on a set too small to show a few-point difference.
- **Treating "not significant" as "no difference"**.
- **Testing many variants and reporting the best**, without a held-out confirmation.
- **Using a model judge without checking it against humans**, or with a fixed answer order.
- **Tuning prompts on the evaluation set** until it saturates, then trusting its score.
- **Averaging over topics** so a collapse in one segment is invisible.
- **No regression suite** from past failures.
- **Ignoring cost and latency** in evaluation, then discovering the bill.
- **Budgeting from the average request** when the tail dominates.
- **Letting a provider's silent model update** change behaviour without re-running evals.
- **Collecting user feedback without privacy controls**.
