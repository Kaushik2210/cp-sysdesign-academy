## Why this matters

Large language models (LLMs) are becoming a standard component of products: assistants, search, code tools, support bots. For a system designer, an LLM is a **new kind of backend**: it is **slow** (seconds, not milliseconds), **expensive** (a request can cost thousands of times more than a database query), **memory hungry**, and its work is **sequential** in a way that defeats the usual "just add more parallel workers" reflex. Designing around those properties is the skill; the model itself can be treated as a service with unusual performance rules.

This lesson explains the **three ideas that decide cost and latency**: how a model generates text, why **memory** (the key-value cache) limits how many conversations fit on one accelerator, and why **how requests are batched** can change throughput by a factor of three. All numbers come from simulations whose assumptions are stated; they are **illustrations of mechanisms**, not benchmarks of any product.

## How a model produces text (intuition)

An LLM generates an answer **one token at a time** (a token is a piece of a word, roughly three quarters of an English word). Each new token depends on **all the tokens before it**. A request has two phases:

1. **Prefill**: the model reads the **whole prompt** at once and builds an internal summary of it. All prompt tokens can be processed **in parallel**, so this phase keeps the accelerator busy (it is **compute-bound**). Its duration grows with the prompt length. It determines the **time to first token (TTFT)**: how long the user stares at a blank screen.
2. **Decode**: the model produces the answer **one token per step**, each step reading all of the model's weights from memory again. A step does little arithmetic per byte moved, so decoding is **memory-bandwidth-bound**: the step takes about the same time whether it generates one token for one user or one token each for sixteen users. This is the key fact behind batching.

Users care about: **TTFT** (responsiveness), **inter-token latency** (smoothness of the streaming text), **total latency**, and the provider cares about **tokens per second per accelerator** (cost).

## The key-value cache

To produce each new token the model needs the "keys and values" computed for **every earlier token** in every layer. Recomputing them on every step would be far too slow, so they are **kept in memory** (the **KV cache**) and extended by one entry per step. The cache grows with the conversation and **lives in accelerator memory next to the model weights**.

Memory per token = 2 (keys and values) x layers x key-value heads x head dimension x bytes per number. For an example model shape (32 layers, head dimension 128, 16-bit numbers):

- with **32 key-value heads** (classic multi-head attention): 512 KiB per token, so **2 GiB for one 4,096-token conversation**;
- with **8 key-value heads** (grouped-query attention, a design chosen largely to shrink the cache): **128 KiB per token, 512 MiB per conversation**.

If 40 GiB remain after the weights, that is **20 concurrent conversations** in the first case and **80** in the second. **The cache, not arithmetic, usually limits concurrency**, and concurrency is what makes batching, hence cost per token, work.

### Not wasting the cache

A simple server **reserves the maximum length** (4,096 tokens) for every conversation up front, because it does not know how long the answer will be. Most conversations are far shorter, so most of the reservation is **empty**. **Paged** cache management (the idea behind PagedAttention) allocates the cache in **small blocks as the conversation grows**, like virtual memory, so little is wasted and conversations that share a prefix (the same system prompt) can **share blocks**.

## Batching: the biggest lever

Because a decode step costs about the same for one sequence or for many, the way to get throughput is to **decode many conversations in the same step**.

- **Static batching**: collect up to B requests, run them together **until the longest answer finishes**, then start the next batch. Short answers sit finished but **occupy their slot** (padding), and **new requests wait** for the whole batch to drain. With answer lengths that vary from a few tokens to hundreds, much of the batch is idle most of the time.
- **Continuous (iteration-level) batching**: **after every decoding step**, finished conversations **leave** and waiting requests **join** the running batch. Slots are never wasted on finished answers, and a new request waits at most for one step, not for a whole batch.

### The simulation

The program models one accelerator with **assumed constants**: a decode step takes 25 ms for a batch of one and 0.6 ms more for each extra sequence (memory-bound, nearly flat), prefill takes 0.15 ms per prompt token. Requests arrive as a random (Poisson) stream with prompts of 100 to 1,500 tokens and answers with a **heavy tail** (median about 100 tokens, some close to 1,000), at most 16 conversations per batch. It prints the **cache arithmetic**, compares **static and continuous batching at four loads**, and converts the saturated throughput into **cost per million tokens** using an assumed accelerator price of 2.00 per hour.

import random

# ---- a simple model of one accelerator serving one model (all constants are assumptions, chosen to be plausible, not measured)
BASE_STEP_MS = 25.0          # time for one decoding step with a batch of one (memory bound: dominated by reading the weights)
PER_SEQ_MS = 0.6             # extra time per additional sequence in the batch
PREFILL_MS_PER_TOKEN = 0.15  # time to process one prompt token


def step_ms(batch):
    return BASE_STEP_MS + PER_SEQ_MS * (batch - 1)


def make_requests(n, rate_per_s, seed):
    """Poisson arrivals; prompts of 100 to 1,500 tokens; answers with a heavy tail (many short, a few very long)."""
    rnd = random.Random(seed)
    t, out = 0.0, []
    for i in range(n):
        t += rnd.expovariate(rate_per_s) * 1000.0
        prompt = rnd.randint(100, 1500)
        answer = max(5, min(1000, int(rnd.lognormvariate(4.6, 0.9))))      # median about 100 tokens, long tail
        out.append({"id": i, "arrival": t, "prompt": prompt, "answer": answer})
    return out


def summarize(done, horizon_ms):
    lat = sorted(r["finish"] - r["arrival"] for r in done)
    ttft = sorted(r["first"] - r["arrival"] for r in done)
    tokens = sum(r["answer"] for r in done)
    return {
        "tokens_per_s": tokens / (horizon_ms / 1000.0),
        "mean_s": sum(lat) / len(lat) / 1000.0,
        "p95_s": lat[int(0.95 * len(lat)) - 1] / 1000.0,
        "ttft_p95_s": ttft[int(0.95 * len(ttft)) - 1] / 1000.0,
    }


def static_batching(reqs, max_batch):
    """Form a batch from the waiting requests, run it until the LONGEST answer finishes, then form the next batch."""
    now, i, done = 0.0, 0, []
    while i < len(reqs):
        now = max(now, reqs[i]["arrival"])
        batch = []
        while i < len(reqs) and len(batch) < max_batch and reqs[i]["arrival"] <= now:
            batch.append(reqs[i])
            i += 1
        now += sum(r["prompt"] for r in batch) * PREFILL_MS_PER_TOKEN
        steps = max(r["answer"] for r in batch)
        for s in range(1, steps + 1):
            now += step_ms(len(batch))                         # finished sequences still occupy their slot (padding)
            for r in batch:
                if s == 1:
                    r["first"] = now
                if s == r["answer"]:
                    r["finish"] = now                          # the answer exists, but the batch is not released yet
        done.extend(batch)                                     # (a client gets its answer at its own finish time, which favours static batching)
    return done, now


def continuous_batching(reqs, max_batch):
    """Iteration-level scheduling: after every decoding step, finished sequences leave and waiting ones join."""
    now, i, active, done = 0.0, 0, [], []
    while i < len(reqs) or active:
        if not active:
            now = max(now, reqs[i]["arrival"])
        while i < len(reqs) and len(active) < max_batch and reqs[i]["arrival"] <= now:
            r = reqs[i]
            i += 1
            now += r["prompt"] * PREFILL_MS_PER_TOKEN          # prefill the newcomer
            r["left"] = r["answer"]
            active.append(r)
        now += step_ms(len(active))
        for r in list(active):
            if "first" not in r:
                r["first"] = now
            r["left"] -= 1
            if r["left"] == 0:
                r["finish"] = now
                active.remove(r)
                done.append(r)
    return done, now


def kv_cache_bytes_per_token(layers, kv_heads, head_dim, bytes_per_value=2):
    return 2 * layers * kv_heads * head_dim * bytes_per_value      # keys and values, for every layer


if True:

    for name, kv_heads in (("full multi-head attention (32 kv heads)", 32), ("grouped-query attention (8 kv heads)", 8)):

        per_seq = per_tok * 4096
        budget = 40 * 1024 ** 3                                     # 40 GiB left for the cache after the weights
        print(f"{name}: {per_tok / 1024:.0f} KiB per token, {per_seq / 1024 ** 2:.0f} MiB for a 4,096-token conversation, {budget // per_seq} conversations fit in 40 GiB")
    lens = [r["prompt"] + r["answer"] for r in make_requests(5000, 1.0, 1)]
    avg = sum(lens) / len(lens)
    print(f"average conversation is {avg:.0f} tokens: reserving the 4,096-token maximum for each wastes {100 * (1 - avg / 4096):.0f}% of the cache; "
          f"paged allocation in small blocks lets about {4096 / avg:.1f}x more conversations fit")

    # 2. static versus continuous batching at several loads
    capacity = {}
    for rate in (0.5, 1.0, 2.0, 10.0):
        print(f"arrivals {rate:g} requests per second, 600 requests, maximum batch of 16" + (" (more than either can serve: this shows capacity)" if rate >= 10 else "") + ":")
        for name, fn in (("static batching", static_batching), ("continuous batching", continuous_batching)):
            reqs = make_requests(600, rate, 7)
            done, end = fn(reqs, 16)
            s = summarize(done, end)
            if rate >= 10:

## What the output shows

**Cache arithmetic.** The classic 32-head shape needs 512 KiB per token (2,048 MiB for 4,096 tokens, **20 conversations in 40 GiB**); grouped-query attention needs 128 KiB per token (512 MiB, **80 conversations**): a 4 times difference in how many users one accelerator can hold. The simulated conversations average **953 tokens**, so reserving 4,096 tokens each **wastes 77%** of the cache; paged allocation lets about **4.3 times more** conversations fit.

**Batching.** With a maximum batch of 16:

| arrivals per second | static: mean and p95 latency, p95 time to first token | continuous: mean and p95 latency, p95 time to first token |
| --- | --- | --- |
| 0.5 | 11.6 s, 28.2 s, 21.9 s | **4.2 s, 12.1 s, 0.3 s** |
| 1 | 89.9 s, 183.3 s, 179.2 s | **4.8 s, 13.6 s, 0.4 s** |
| 2 | 219.1 s, 444.6 s, 441.7 s | **6.5 s, 18.2 s, 2.4 s** |
| 10 (more than either can serve) | 336.8 s, 666.5 s, 663.6 s | 101.0 s, 189.5 s, 184.7 s |

- At **0.5 requests per second** both servers keep up (about 71 to 72 tokens per second, equal to the offered load), but static batching makes the slowest 5% of users wait **about 70 times longer** for the first token (21.9 s against 0.3 s at the 95th percentile): a request that arrives just after a batch starts waits for the whole batch to finish.
- At **1 request per second** static batching is **already saturated** (about 111 tokens per second against its capacity of about 115): a queue builds and the **mean latency reaches 90 seconds**. Continuous batching handles the same load with a mean of **4.8 seconds**.
- At **2 requests per second** continuous batching still keeps up (277 tokens per second, mean 6.5 s); static batching is far past its capacity and latencies grow without bound as the 600-request test ends (219 s mean).
- At **10 requests per second** (more than either can serve) the throughput is each system's **capacity**: static about **115 tokens per second**, continuous about **328**, roughly **2.9 times more** from scheduling alone, on the same hardware and the same model.

**Cost.** At an assumed price of 2.00 per accelerator hour, capacity of 115 tokens per second is 0.41 million tokens per hour, or **4.84 per million tokens**; 328 tokens per second is 1.18 million per hour, or **1.70 per million tokens**. **Scheduling decided a factor of about 2.8 in cost.**

Honest limits of the model: the step-time constants, the heavy-tailed answer lengths and the price are **assumptions**; real systems also **chunk long prefills** so a long prompt does not stall other users, run on **multiple accelerators**, and are limited by the cache as well as by the batch cap. The static baseline is also generously treated (each client receives its answer at its own finish time). Treat the **ratios and the shape** (flat step time, wasted slots, queues that explode past capacity) as the lesson, not the exact figures.

## Capacity planning for LLM traffic

1. **Measure demand in tokens, not requests.** Average prompt tokens and answer tokens per request, times requests per second, gives input and output **tokens per second**. Input and output are priced and limited differently (prefill is cheaper per token than decode).
2. **Find the capacity per accelerator** for your model with a **load test** on your own prompt length distribution (the saturated throughput figure above).
3. **Required accelerators = peak tokens per second / capacity per accelerator**, plus headroom (30 to 50%) for variance and failures. **Latency targets** (p95 TTFT) usually bind before raw throughput: run below saturation, because queueing delay explodes past it (the 1 request per second row).
4. **Cost per request** = (accelerator price per hour / tokens per hour) x tokens per request. Put it on a dashboard: with LLMs, **one bad prompt change can double the bill**.

## Other levers that change the economics

- **Prefix caching**: many requests start with the **same long system prompt or document**. Process that prefix **once** and reuse its cache, cutting prefill work and TTFT.
- **Smaller or quantised models**: storing weights in fewer bits makes decoding faster (less to read) and frees cache memory. Quality must be **evaluated**, not assumed.
- **Model routing and cascades**: send easy requests to a small, cheap model and only hard ones to a large model; fall back to the large model when the small one is unsure.
- **Speculative decoding**: a small model drafts several tokens and the large model verifies them in one step, producing more than one token per expensive step at unchanged quality.
- **Response caching**: identical (or, with care, semantically similar) questions can reuse earlier answers; the hit rate depends heavily on the product.
- **Limit output length**: output tokens are the expensive ones; set maximum lengths and instruct concise answers.
- **Streaming**: send tokens as generated; perceived latency is TTFT plus reading speed, not total time.

## Reliability and operations

- **Admission control and backpressure**: when the queue is long, **reject early** (or shed lowest-priority work) rather than let every request time out ([load shedding and bulkheads](/sd/scalability/load-shedding-and-bulkheads/), [backpressure](/sd/queues-and-streaming/backpressure-retries-and-dlq/)). The table above shows how past capacity every request suffers.
- **Rate limit by tokens**, per tenant, not only by request count: one request can be 10 tokens or 100,000.
- **Priorities**: interactive requests ahead of batch jobs, with a share of capacity reserved for each.
- **Timeouts and retries**: retries of a long generation **repeat the cost**; retry only on clear failures, with budgets ([retry amplification](/sd/microservice-patterns/retry-amplification-and-circuit-breakers/)).
- **Slow cold starts**: loading a large model onto an accelerator takes minutes, so autoscaling reacts slowly: scale on the **queue depth and token rate**, keep warm spare capacity, and pre-load models.
- **Fallbacks**: a second region, a second model, or a degraded mode ("answers may be shorter") when capacity is lost.
- **Observability**: TTFT and inter-token latency percentiles, tokens per second, queue depth, cache hit rate and memory use, cost per request, error and refusal rate, and **quality metrics** from continuous evaluation.

## Pitfalls

- Sizing capacity by **requests per second** instead of **tokens per second**.
- Using **static batching** (or one request at a time) for interactive traffic.
- **Reserving worst-case cache** for every conversation.
- Running **at saturation** and discovering that latency has no ceiling.
- **Retrying** long generations blindly, doubling cost during an incident.
- **No admission control**: an overloaded queue makes every request fail.
- Ignoring **cold start times** when autoscaling.
- Treating **input and output tokens as equal** in cost and limits.
- Measuring only **average latency**; watch p95 TTFT.
- Changing prompts or models **without cost and quality tracking**.
- Benchmarking with **unrealistic prompt lengths** (all short, or all identical).
