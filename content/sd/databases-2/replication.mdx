## Intuition

One database machine has three limits: it can die, it can only serve so many reads, and it may sit far from some of your users. **Replication** keeps copies of the same data on several machines to address all three. Copies give you durability (a disk dies, the data survives), availability (another copy takes over) and read capacity (spread reads across copies).

The price is that copies can disagree for a while. Almost every design decision in this lesson is a decision about how much disagreement you tolerate and who is allowed to accept writes.

## Three replication topologies

| Topology | Who accepts writes | Typical systems |
| --- | --- | --- |
| Leader-follower (primary-replica) | Exactly one leader; followers apply its change log | PostgreSQL, MySQL, MongoDB replica sets |
| Multi-leader | Several leaders, usually one per region; they replicate to each other | Multi-region MySQL setups, CouchDB-style sync, collaborative editors |
| Leaderless | Any replica; clients write to and read from several replicas and use quorums | Dynamo, Cassandra, Riak |

### Leader-follower

All writes go to the leader, which appends them to a replication log (WAL, binlog, oplog). Followers replay that log in order. Because there is a single writer, there are no write conflicts and ordering is trivial. This is the default choice and the one to reach for first.

### Multi-leader

Each region has its own leader, so a user writes to a nearby node and the write is fast even if other regions are unreachable. The cost is **write conflicts**: two leaders can accept different updates to the same row concurrently. You then need a resolution policy (last-write-wins by timestamp, which can silently drop a write; merge functions; CRDTs; or surfacing conflicts to the application). Conflict handling is hard enough that many teams avoid multi-leader unless they truly need multi-region writes or offline operation.

### Leaderless and quorums

With `n` replicas per key, a write is sent to all and counts as successful after `w` acknowledgements; a read asks `r` replicas and takes the freshest answer. If `w + r > n`, the read set and write set must overlap in at least one replica, so a read normally sees the latest successful write. A common setting is `n = 3, w = 2, r = 2`. Caveats worth knowing: sloppy quorums, concurrent writes and clock-based conflict resolution can still return stale or lost data, so "quorum" is not the same as linearizable.

## Synchronous vs asynchronous replication

- **Synchronous**: the leader waits for the follower to confirm before acknowledging the client. No acknowledged write can be lost if the leader dies, but every write is as slow as the slowest synchronous follower, and one stuck follower can block writes.
- **Asynchronous**: the leader acknowledges immediately and ships changes in the background. Writes are fast and survive follower outages, but an acknowledged write may exist only on the leader. If the leader crashes before shipping it, that write is lost on failover.
- **Semi-synchronous**: one follower is synchronous and the rest asynchronous, so at least two nodes hold every acknowledged write while one slow node cannot stall everything.

<Callout type="note" title="Durability vs latency">
Choosing synchronous vs asynchronous is choosing between "no acknowledged write is ever lost" and "writes stay fast and available when a replica is slow". There is no free option.
</Callout>

## Replication lag and the anomalies it causes

With asynchronous replication, a follower is always some amount behind the leader: the **replication lag**. Under normal load it is often milliseconds, but it can stretch to seconds or minutes under heavy writes, network trouble or a long-running query on the replica. If reads go to followers, users can observe three classic anomalies.

1. **Read-your-writes violation**: you post a comment, the page reloads from a lagging follower, and your comment is missing.
2. **Monotonic-read violation**: you read from a fresh follower, then from a staler one, and see data move backwards in time.
3. **Consistent-prefix violation**: you see an answer before the question it responds to, because causally related writes landed on different partitions and replicated at different speeds.

### Worked example: read-your-writes

Suppose the leader is at log position 1000 and follower B is at 940. Alice updates her profile; the write lands at position 1001. If her next page load goes to B, B has not applied 1001, so she sees the old profile and thinks the save failed.

Common fixes, from simplest to most precise:

- Route a user's reads to the leader for a short window (say a few seconds, longer than typical lag) after they write.
- Always read the user's own data from the leader, and other people's data from followers.
- Track the log position of the user's last write (a token in the session or cookie) and only read from a replica that has applied at least that position.
- If users act from multiple devices, the token or routing rule must be shared across them.

## Pitfalls

- Treating a replica as a free backup: replication copies mistakes too. A bad `DELETE` replicates instantly. You still need point-in-time backups.
- Sending latency-sensitive "read after write" traffic to replicas without any consistency strategy.
- Using wall-clock last-write-wins across leaders: clock skew can make an older write win.
- Assuming `w + r > n` means linearizable. It does not by itself.

## What would you choose and why?

A product-comments service has one region, 95% reads, and users expect their own new comment to show immediately. Others seeing it a second late is fine. Which topology and which read-routing policy do you choose, and what happens if the leader dies between a write acknowledgement and replication?
