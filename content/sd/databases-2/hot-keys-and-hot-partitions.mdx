## Intuition

Sharding spreads *keys* evenly, but traffic is rarely spread evenly across keys. Real access patterns are heavily skewed: a celebrity profile, a viral post, a flash-sale product, today's date as a key. Whichever shard holds that key takes disproportionate load while the others idle. Adding shards does not help, because the hot key still lives on exactly one of them.

Two related terms:

- **Hot key**: a single key receiving a very large share of requests.
- **Hot partition**: a shard whose load greatly exceeds the others, from one hot key, many warm keys that happen to co-locate, or a skewed key design (all new writes to the newest range).

## Spotting them

Look for imbalance, not averages: per-shard QPS, CPU, p99 latency, throttling counts and storage size. A cluster whose average CPU is 20% can still have one node at 100%. Many stores expose top-key or hot-range diagnostics; otherwise sample request keys at the proxy and count.

## Mitigations

### Read-heavy hot keys

- **Cache in front**: a hot key served from an in-memory cache absorbs nearly all reads. Add request coalescing so a cache miss triggers one backend fetch rather than thousands.
- **Local (in-process) cache** with a short TTL, so even the cache tier is not hit for the hottest keys.
- **Replicate the hot key**: store copies under `key#0 .. key#k-1` (or more replicas of that partition) and have readers pick one at random.
- **CDN or edge caching** for public, cacheable objects.

### Write-heavy hot keys

Caches do not help writes. Options:

- **Key splitting (write sharding)**: append a random or round-robin suffix, so counter `likes:post42` becomes `likes:post42#0..#15`. Writes spread across 16 shards; reads sum the 16 values. This trades read cost and extra complexity for write throughput.
- **Batching and aggregation**: buffer increments in memory or a queue and flush periodic aggregate updates, accepting a short delay.
- **Move to a better data structure**: an approximate counter or a CRDT counter when exact instant totals are not needed.

### Skewed key design

- Avoid monotonically increasing keys on range-partitioned stores. Prefix with a hash or bucket (`hash(id) % 16 + timestamp`) so writes fan out across ranges, then query the buckets in parallel.
- **Split the hot partition**: stores with dynamic splitting divide a hot range into two; some can isolate a single hot key into its own partition.
- **Move hot tenants** in a directory-based scheme to dedicated shards.
- **Admission control and rate limiting** for abusive or buggy clients that create the skew.

## Worked example: a like counter

A viral post receives 30,000 like events per second. Assume one shard sustains about 5,000 writes per second on a single counter row (illustrative). Splitting into 16 sub-counters gives each about `30000 / 16 = 1875` writes per second, comfortably under the limit even if it is not perfectly even. Reading the total means 16 reads, or a cached sum refreshed once per second. Everyone viewing sees the count up to a second stale, which is acceptable for likes but not for bank balances.

## Pitfalls

- Assuming consistent hashing or more shards fixes a hot key.
- Splitting keys for every counter by default; apply it only to measured hot keys.
- Caching without stampede protection so that expiry of the hot key melts the origin.
- Ignoring "hot by time": the key everyone hits at midnight or on a sale start.

## What would you choose and why?

A ticketing site sells a stadium concert: 500,000 users hit one `event:123` inventory row in the first minute. Reads can be cached, but each purchase must decrement inventory exactly. What would you do, and where can you accept approximation and where not? Consider queueing purchases, splitting inventory into per-section sub-counters, and a waiting room.
