## Intuition

A **forward proxy** sits in front of *clients* and speaks for them to the internet (corporate web filters). A **reverse proxy** sits in front of *servers* and speaks for them to the world: clients believe they talk to one site, the proxy forwards to whichever backend is appropriate. A load balancer is a reverse proxy whose main job is spreading load; many reverse proxies (NGINX, HAProxy, Envoy) do both.

An **API gateway** is a reverse proxy specialised for APIs: a single front door that applies cross-cutting policy (authentication, rate limits, routing, observability) so every microservice does not re-implement it.

## What a reverse proxy does

- **Routing**: by host, path, header or method. `/users/*` goes to the user service, `/orders/*` to the order service.
- **TLS termination**: the proxy holds certificates, performs the handshake and talks plain HTTP (or re-encrypted mTLS) to backends. Central certificate management and one place to tune ciphers, at the cost of a trust boundary inside your network if you leave the hop unencrypted.
- **Connection management**: client connections are long-lived and numerous; the proxy keeps a small pool of keep-alive connections to backends, shielding them from slow clients (it buffers the request, then sends it quickly).
- **Caching and compression**: serve cached responses, gzip or brotli content.
- **Request shaping**: size limits, timeouts, header normalisation (set `X-Forwarded-For`, strip untrusted headers), protocol translation (HTTP/2 or HTTP/3 to clients, HTTP/1.1 to old backends).
- **Resilience**: retries on idempotent requests, circuit breaking, outlier ejection.

## What an API gateway adds

- **Authentication and authorisation offload**: validate API keys, OAuth access tokens or JWT signatures once at the edge, then pass a verified identity (a header or an internal token) to services. Services must still authorise *what* the caller may do and must not trust identity headers that could arrive from outside the gateway.
- **Rate limiting and quotas**: per key, user, IP or route. Common algorithms are token bucket (allows bursts up to bucket size, refills at a steady rate) and sliding window. Respond `429 Too Many Requests` with a `Retry-After` header. Counters often live in a shared store such as Redis so that all gateway nodes enforce one limit; a local-only limit is cheaper but multiplies by the node count.
- **Request/response transformation**: version routing, header injection, schema validation.
- **Aggregation and the BFF pattern**: a **Backend for Frontend** is a gateway tailored to one client type (mobile, web, partner) that fans out to several services and returns exactly the payload that client needs, which reduces round trips on slow mobile networks and lets each client team evolve its API independently.
- **Observability**: uniform access logs, metrics, trace IDs injected at the edge.

### Token bucket in a few lines

<CodeRunner language="python" code={`import time

class TokenBucket:
    def __init__(self, rate_per_sec, burst):
        self.rate, self.burst = rate_per_sec, burst
        self.tokens, self.last = burst, 0.0

    def allow(self, now):
        # refill based on elapsed time, capped at burst
        self.tokens = min(self.burst, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

tb = TokenBucket(rate_per_sec=5, burst=10)
# 30 requests arriving over 1 second (one every 1/30 s): burst of 10 passes, then ~5/s
allowed = sum(tb.allow(i / 30) for i in range(30))
print("allowed", allowed, "of 30")
`} />

With a bucket of 10 and a refill of 5 per second, a burst of 30 requests in one second admits 10 immediately plus the roughly 5 refilled over that second, so about 14 or 15 pass.

## Failure modes

- **Gateway as single point of failure**: run it as a replicated stateless tier behind the LB, deploy across zones, and keep its config reloadable without downtime.
- **Rate-limit store outage**: decide explicitly. Fail open protects availability but removes abuse protection; fail closed protects backends but rejects legitimate users. Many teams fall back to coarse local limits.
- **Auth dependency latency**: a token introspection call per request adds to every request. Prefer locally verifiable tokens (signed JWTs with short lifetimes) or cache introspection results briefly.
- **Header spoofing**: if services trust an identity header, ensure only the gateway can reach them and that the gateway strips client-supplied copies.

## Pitfalls

- Letting the gateway accumulate business logic until it is an unmaintainable monolith.
- Terminating TLS at the edge and leaving the internal hop unauthenticated in a shared network.
- Rate limiting only by IP, which punishes users behind NAT and is trivial to evade with many IPs.
- Applying a generous timeout at the gateway and shorter ones downstream, so work continues after the client has gone.
- Forgetting that a gateway adds latency (typically on the order of a millisecond or a few) to every call.
