## Intuition

One server has a ceiling: CPU, memory, network, file descriptors. Past it you either buy a bigger machine (vertical scaling, which has a hard limit and a single failure domain) or run many identical machines and put something in front that decides *which machine handles each request*. That something is a **load balancer (LB)**.

A load balancer gives you three things at once:

1. **Capacity**: N servers handle roughly N times the traffic of one, as long as the work is spread sensibly.
2. **Availability**: if one server dies, the LB stops sending it traffic and users barely notice.
3. **Operational freedom**: you can deploy, drain and replace servers behind a single stable address.

The catch is that the LB itself becomes a component that must not fail and must not become the bottleneck. This lesson covers how LBs work, the L4 versus L7 distinction, health checks, sticky sessions and how to make the LB itself highly available.

## Formal picture

A load balancer exposes a **virtual address** (a VIP or a DNS name) and forwards each connection or request to one member of a **pool** (also called backend set or target group). It makes the choice with a **balancing algorithm** (next lesson) restricted to the **healthy** members.

For stateless app servers the model is simple: any server can serve any request, so the LB is free to choose by load alone. If servers hold per-user state in memory, the LB must route the same user to the same server, which is the sticky-session problem below, and the better fix is usually to move that state out of the servers.

## L4 versus L7

The layers refer to the OSI model: layer 4 is transport (TCP/UDP), layer 7 is application (HTTP, gRPC).

| | L4 load balancer | L7 load balancer |
| --- | --- | --- |
| Sees | IP addresses, ports, TCP/UDP flags | Full HTTP request: path, host, headers, cookies, method |
| Decision basis | 5-tuple (src/dst IP and port, protocol) | Anything in the request |
| Connection handling | Forwards packets or splices one TCP connection to one backend; often does not parse the payload | Terminates the client connection, parses the request, opens or reuses a separate backend connection |
| Cost | Very cheap per packet, very high throughput | More CPU and memory (parsing, TLS, buffering) |
| Typical features | Fast TCP/UDP balancing, absorbing floods at line rate | Path/host routing, header rewrite, TLS termination, retries, compression, WAF, per-request balancing |

Two consequences matter in design discussions:

- With an L4 LB and HTTP/1.1 keep-alive or HTTP/2, one client connection stays on one backend for its whole life. A few long-lived, chatty connections can pin a lot of work on one server, so balance is *per connection*, not per request.
- An L7 LB can balance each request independently and can route `/api` and `/static` to different pools. That flexibility is why most web architectures put an L7 LB at the edge, sometimes with an L4 tier in front of it for raw scale.

<Callout type="note" title="Naming">
Cloud products blur the lines. For example AWS Network Load Balancer is an L4 product and Application Load Balancer is L7. Check each vendor's documentation rather than inferring behavior from the marketing name.
</Callout>

## Health checks

An LB is only as good as its knowledge of which backends are alive. Two complementary mechanisms:

- **Active checks**: the LB periodically probes each backend (a TCP connect, or an HTTP `GET /healthz` expecting a 2xx). It marks a backend down after K consecutive failures and up again after M consecutive successes. Typical numbers are an interval of a few seconds and thresholds of 2 to 3, so detection takes on the order of 5 to 10 seconds.
- **Passive checks** (outlier detection): the LB watches real traffic and ejects a backend that returns errors or times out, with no extra probe traffic and often faster detection.

Design points:

- **Shallow vs deep health endpoints.** A shallow check (process is up) is cheap but misses a server that is up yet cannot reach its database. A deep check (it queries the DB) catches that, but if the shared database blips, *every* backend fails the check at once and the LB removes the entire pool, turning a partial outage into a full one. A common compromise is a check that verifies local readiness and treats downstream dependencies as degraded rather than fatal.
- **Readiness vs liveness.** Liveness answers "restart me?", readiness answers "send me traffic?". A starting server should be live but not ready until caches are warm.
- **Connection draining.** When removing a backend for a deploy, stop sending *new* requests but let in-flight ones finish (with a timeout), otherwise every deploy produces errors.
- **Retry budgets.** If the LB retries failed requests on another backend, cap the retries (for example only idempotent requests, and a small percentage of total traffic), or a slow backend turns into a retry storm that overloads the rest.

## Sticky sessions (session affinity)

Sticky sessions pin a client to one backend, usually by an LB-issued cookie (L7) or by hashing the client IP (L4 or L7).

When people reach for them: legacy apps that keep login state or shopping carts in server memory; WebSocket or long-poll connections that are naturally tied to one server; local caches that are much more effective when the same user returns to the same node.

Costs:

- **Uneven load**: a few heavy users can overload one server while others idle.
- **Failure hurts users**: when the pinned server dies, the session state is gone and those users are logged out or lose carts.
- **Harder deploys and scaling**: draining pinned sessions takes long; new servers receive no existing users.
- **IP hashing breaks behind NAT**: thousands of users behind one corporate or carrier NAT share one source IP and all land on one backend.

The robust alternative is **stateless app servers with state in a shared store** (a cache such as Redis, a database, or a signed token the client carries, like a JWT or an encrypted cookie). Then affinity becomes an optimization rather than a correctness requirement.

## High availability of the load balancer itself

An LB in front of ten redundant servers is a single point of failure unless it is redundant too. Common patterns:

- **Active-passive pair with a floating IP.** Two LBs share a virtual IP using a protocol such as VRRP (implemented by keepalived). The standby takes over the IP when the primary stops sending heartbeats. Failover is typically seconds. The standby sits idle (wasted capacity), and a partition between the pair can cause both to claim the IP ("split brain").
- **Active-active with DNS.** DNS returns several LB addresses. Clients spread across them; if one fails, health-checked DNS stops returning it. DNS caching means clients may keep using a dead address for up to the record's TTL plus resolver behavior.
- **Active-active with ECMP.** Routers spread flows across many identical LB nodes using equal-cost multipath, so capacity scales horizontally. Large providers run L4 LBs this way, often with consistent hashing so that adding or removing a node disturbs few flows.
- **Managed cloud LBs.** The provider runs the redundancy across zones, and you get one DNS name. You trade control for operational simplicity.

Also remember **cross-zone placement**: LB nodes and backends should span at least two failure domains (zones or racks).

## Worked example

Peak 20,000 requests per second; each backend sustains about 1,500 requests per second at a healthy CPU of 60 to 70 percent. You need at least 20,000 / 1,500, about 14 backends. To survive the loss of one zone out of three, the remaining two zones must carry peak: 14 / (2/3) = 21 backends, 7 per zone. A single software L7 LB node typically handles tens of thousands of requests per second (an approximation that depends heavily on TLS and request size), so one node is rarely the bottleneck, but you still run at least two for availability.

## Failure modes

- **LB overload**: a traffic spike or slow backends fill connection tables; use autoscaling or multiple nodes and set connection and queue limits.
- **Pool-wide health failure**: a deep check on a shared dependency removes every backend. Many LBs offer a "panic mode" or minimum healthy percentage that keeps routing to all backends when too few look healthy.
- **Thundering reconnect**: after an LB restart, millions of clients reconnect at once. Use jittered client backoff.
- **Slow backend**: not dead, just slow, so health checks pass while latency climbs. Use latency-aware algorithms, timeouts and outlier ejection.

## Pitfalls

- Treating the LB as a magic fix while the database stays a single machine; the bottleneck just moves.
- Forgetting the LB's own redundancy.
- Health endpoints that always return 200, or that check too much.
- Using IP hash behind NAT or a proxy, or trusting `X-Forwarded-For` blindly (clients can forge it unless the edge overwrites it).
- No connection draining on deploys.

## What would you choose and why?

You run an API with 30 stateless pods behind an L7 LB in one region. A recent outage happened when the shared database restarted: every pod failed its deep `/healthz` check and the LB returned 503 for all traffic even though cached reads could still have been served. How would you redesign the health check and LB settings, and what would you give up?
