## Intuition

One region, however redundant, has two limits: **physics** (a user in Mumbai talking to a server in Virginia pays roughly 200 ms round trips; light in fibre covers about 200 km per millisecond, so distance alone sets a floor) and **blast radius** (a regional outage, a bad deploy or a fibre cut takes everyone down). Running in several regions fixes both, but then something must decide *which region* each user reaches and *move traffic away* when a region fails. That is **global server load balancing (GSLB)**.

## Mechanisms for steering users to a region

### DNS-based steering

The authoritative DNS answers a lookup for `api.example.com` with the address of a chosen region. Policies commonly offered by managed DNS:

- **Geolocation**: answer by the resolver's (or client subnet's) location.
- **Latency-based**: answer with the region that has lowest measured latency from the resolver's network.
- **Weighted**: send X percent to each region (canary, gradual migrations).
- **Failover**: primary address while health checks pass, else secondary.

Strengths: works with any client, cheap, simple. Weaknesses: the DNS answer is **cached** by resolvers and clients for the TTL (and some ignore low TTLs), so failover takes at least on the order of the TTL, often longer in the tail. DNS sees the *resolver*, not the user, so a user on a public resolver may be steered poorly unless EDNS Client Subnet is used. Granularity is per lookup, not per request.

### Anycast

The same IP prefix is announced via BGP from many locations. Internet routing delivers each packet to the *topologically nearest* announcer. Properties:

- Automatic nearest-site selection, fast failover: if a site stops announcing (withdraws the route), traffic converges to the next nearest in seconds to minutes depending on BGP convergence.
- Natural DDoS dilution, since attack traffic spreads over many sites.
- Caveat: routing changes mid-connection can send later packets of a TCP flow to a different site, so anycast fits UDP services (DNS), short-lived HTTP, or designs where the edge terminates the connection and each site is self-sufficient. "Nearest" in BGP terms is not always lowest latency.

CDNs and public DNS providers commonly use anycast for their edge. A typical large design combines the two: anycast to reach a nearby edge, then the edge proxies over a private backbone to the right origin region.

### Client-side or application-level steering

Mobile apps and SDKs may carry a list of regional endpoints and measure or fail over themselves. This gives per-request control and fast failover (no DNS TTL), at the cost of client complexity and the slow rollout of client updates.

## Failover design

Questions to answer before drawing arrows:

1. **Active-passive or active-active?** Passive regions are simple but idle and untested; failovers into a never-used region frequently fail. Active-active exercises every region constantly but requires data that can be written in more than one place.
2. **What is the data story?** Traffic can move in seconds; data cannot. Asynchronous replication means a failover may lose the most recent writes (the replication lag, your RPO). Synchronous cross-region replication avoids loss but adds a cross-region round trip to every write. Multi-leader or per-user home-region schemes need conflict handling.
3. **Capacity**: if you run N regions and one fails, the others must absorb its load. With three equal regions, each should run below about 66 percent of its capacity so that two can carry the total.
4. **Health signal**: a region-level health check must reflect real user success (synthetic transactions from several vantage points), not just "the LB answers".
5. **Failback**: moving traffic back is also risky; ramp gradually and watch for overload as caches refill.

### Worked example

Three regions, 30,000 requests per second total, 10,000 each. Each region is provisioned for 16,000. Losing one region shifts 5,000 to each survivor, giving 15,000 each: 94 percent of the provisioned capacity, which is too tight, since a cold cache and retries will push it over. Target at most about 75 to 80 percent after failover, so provision about 19,000 to 20,000 per region (in effect 1.5x headroom over steady state). The cost of multi-region resilience is largely this idle headroom.

## Failure modes

- **Slow failover**: DNS TTLs and resolver stickiness leave some users on a dead region far longer than the nominal TTL.
- **Failover overload**: the surviving region collapses under redirected load plus retries; pair failover with load shedding and rate limits.
- **Flapping**: aggressive health checks bounce traffic between regions; use hysteresis.
- **Split-brain data**: both regions accept writes during a partition and diverge.
- **Correlated failure**: a bad config or software release rolled out to all regions at once defeats regional redundancy; stage rollouts region by region.

## Pitfalls

- Never testing failover. Run game days that actually drain a region.
- Assuming 99.99 percent from multi-region without accounting for the data tier and shared global dependencies (DNS, auth, config).
- Setting TTL to 30 seconds and assuming failover happens in 30 seconds.
- Using geo routing for compliance (data residency) without the data layer enforcing it.
