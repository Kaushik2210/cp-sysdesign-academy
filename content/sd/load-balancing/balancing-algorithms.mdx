## Intuition

Once a load balancer has a pool of healthy servers it must answer one question per request: *which one?* The answer sounds trivial ("take turns") but request costs are rarely equal. A cheap lookup and a 2-second report share the same URL space. If the algorithm ignores cost, a server that happens to collect several heavy requests builds a queue while its peers sit idle, and your p99 latency suffers even though *average* utilization looks fine.

## The algorithms

**Round robin.** Cycle through servers in order. Stateless, O(1), perfectly even in *request count*. Blind to request cost and to server capacity.

**Weighted round robin.** Each server gets a weight proportional to capacity (a 16-core box gets weight 2 next to an 8-core box). A smooth variant interleaves picks so a heavy server does not receive a long burst. Fixes heterogeneous hardware, not heterogeneous requests.

**Random (and power of two choices).** Pick uniformly at random. Simple and needs no shared state across multiple LB nodes. A well-known refinement, *power of two choices*, samples two servers and sends to the one with fewer in-flight requests; theory and practice show it removes most of the imbalance of pure random with almost no coordination.

**Least connections.** Send to the server with the fewest in-flight requests. Because slow requests keep a connection open longer, the policy naturally steers away from servers that are busy with heavy work. Needs per-server counters at the LB. A weighted form divides connections by weight.

**Least response time.** Combine observed latency (often an exponentially weighted moving average) with in-flight count. Adapts to a server that is degraded or in a slow zone. Risks: noisy measurements, and a fast-looking new server can be flooded ("herd effect") before its latency rises.

**IP hash / header hash.** `server = hash(client_ip) mod N`. Gives affinity with no cookie and no shared state, but spreads load only as evenly as your clients are distributed (NAT concentrates users) and changing N remaps most keys.

**Consistent hashing (preview).** Place servers (many virtual nodes each) on a hash ring; a key goes to the next server clockwise. Adding or removing a server moves only about 1/N of the keys instead of nearly all of them. This is the right tool when the choice must be *sticky by key*, such as routing to cache nodes, and it is covered again in the Caching and partitioning modules.

## A simulation you can run

The model: 5 servers, each a FIFO queue that works at one cost unit per time unit. Requests arrive every 0.725 time units; 90 percent cost 1 and 10 percent cost 20 (a heavy-tailed mix). Mean work is 2.9 units per request, so utilization is 2.9 / (5 x 0.725), about 80 percent. We compare latency (queue wait plus service) over 20,000 requests with the same request stream for every policy.

<CodeRunner language="python" code={`import random, hashlib

def make_requests(n, seed=7):
    rng = random.Random(seed)
    reqs, t = [], 0.0
    for i in range(n):
        t += 0.725
        cost = 20.0 if rng.random() < 0.10 else 1.0
        reqs.append((t, cost, rng.randrange(10_000)))  # arrival, cost, client id
    return reqs

class Sim:
    def __init__(self, k):
        self.free_at = [0.0] * k
        self.finishes = [[] for _ in range(k)]
        self.ewma = [1.0] * k
    def active(self, s, now):
        return sum(1 for f in self.finishes[s] if f > now)
    def assign(self, s, now, cost):
        start = max(now, self.free_at[s])
        end = start + cost
        self.free_at[s] = end
        self.finishes[s].append(end)
        self.finishes[s] = [f for f in self.finishes[s] if f > now]
        lat = end - now
        self.ewma[s] = 0.8 * self.ewma[s] + 0.2 * lat
        return lat

def run(policy, reqs, k=5):
    sim, lats, rr = Sim(k), [], 0
    rng = random.Random(1)
    busy = [0.0] * k
    for now, cost, client in reqs:
        if policy == "round_robin":
            s = rr % k; rr += 1
        elif policy == "random":
            s = rng.randrange(k)
        elif policy == "least_connections":
            s = min(range(k), key=lambda i: (sim.active(i, now), i))
        elif policy == "least_response_time":
            s = min(range(k), key=lambda i: (sim.ewma[i] * (sim.active(i, now) + 1), i))
        elif policy == "ip_hash":
            s = int(hashlib.md5(str(client).encode()).hexdigest(), 16) % k
        lats.append(sim.assign(s, now, cost))
        busy[s] += cost
    lats.sort()
    pct = lambda p: lats[int(p * (len(lats) - 1))]
    return sum(lats) / len(lats), pct(0.50), pct(0.99), max(busy) / (sum(busy) / k)

reqs = make_requests(20000)
print(f"{'policy':20s} {'mean':>8s} {'p50':>8s} {'p99':>8s} {'max/avg load':>13s}")
for p in ["round_robin", "random", "ip_hash", "least_connections", "least_response_time"]:
    m, p50, p99, imb = run(p, reqs)
    print(f"{p:20s} {m:8.2f} {p50:8.2f} {p99:8.2f} {imb:13.3f}")
`} />

| Policy | Mean latency | p50 | p99 | Max/avg work per server |
| --- | --- | --- | --- | --- |
| round robin | 24.43 | 17.37 | 126.37 | 1.029 |
| random | 25.76 | 19.90 | 107.70 | 1.040 |
| ip hash | 30.65 | 20.00 | 141.65 | 1.082 |
| least connections | 6.56 | 1.00 | 44.37 | 1.150 |
| least response time | 6.99 | 2.20 | 42.22 | 1.022 |

How to read it:

- **Total work is nearly balanced for every policy** (the last column is close to 1). Round robin even looks the *best* by that measure. Yet its mean latency is almost four times worse than least connections. Balancing *counts of requests* or *total work over time* is not the same as avoiding *queues at the moment a heavy request arrives*.
- Least connections and least response time react to instantaneous load, so a short request is rarely stuck behind a 20-unit one: p50 drops from about 17 to 1 to 2.
- IP hash is worst: no feedback at all, and a skewed client-to-server mapping on top.
- These are figures from one synthetic workload. Different mixes, utilization or service disciplines change the numbers; the *direction* (load-aware beats blind under heavy-tailed costs) is the transferable result.

<Callout type="pitfall" title="Stale information">
Least-connections only works if the LB sees all traffic. With several independent LB nodes, each sees only its own share and can all pile onto the same apparently idle server. Power of two choices or a shared load signal limits that herd.
</Callout>

## Consistent hashing versus mod N

When the same key must reach the same server (cache nodes, sharded stateful services), plain `hash(key) mod N` is fragile: changing N from 4 to 5 remaps most keys. Measured on 20,000 keys with MD5 and 100 virtual nodes per server:

<CodeRunner language="python" code={`import bisect, hashlib

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.ring = sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vnodes))
        self.points = [p for p, _ in self.ring]
    def get(self, key):
        i = bisect.bisect(self.points, h(key)) % len(self.ring)
        return self.ring[i][1]

keys = [f"user{i}" for i in range(20000)]
moved_mod = sum(h(k) % 4 != h(k) % 5 for k in keys)
r4 = Ring(["s0", "s1", "s2", "s3"])
r5 = Ring(["s0", "s1", "s2", "s3", "s4"])
moved_ring = sum(r4.get(k) != r5.get(k) for k in keys)
print(f"mod N: {moved_mod/len(keys):.1%} of keys moved going 4 -> 5 servers")
print(f"ring : {moved_ring/len(keys):.1%} of keys moved (ideal 1/5 = 20.0%)")
`} />

A local run printed about 80.1 percent moved for mod N and about 19.7 percent for the ring. The ring is near the theoretical minimum of one fifth because the new server takes over only the arcs it now owns.

## Failure modes

- **Hot server from hashing**: one popular key or a NAT gateway concentrates load; hashing cannot fix key skew.
- **Slow-start herd**: a freshly added or recovered server looks empty and instantly receives a flood. Many LBs have a slow-start ramp that gradually increases its share.
- **Weight misconfiguration**: weights not updated after a hardware change leave a big machine idle.
- **Measurement lag**: with least response time, latency data is old by the time you act on it.

## Pitfalls

- Choosing by the textbook name instead of measuring p99 on your own traffic mix.
- Using IP hash and then discovering that 40 percent of users share three egress IPs.
- Believing average CPU is a good balance metric; tail latency is what users feel.
- Forgetting that long-lived connections (WebSockets, gRPC streams) are balanced once, at connect time.
