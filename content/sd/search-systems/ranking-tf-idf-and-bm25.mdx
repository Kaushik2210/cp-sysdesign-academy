## Intuition

An inverted index tells you **which documents match** a query. A good search system also has to decide **in what order to show them**, because a query such as `python` can match millions of documents and the user will look at ten. Ranking turns the set of matches into a list ordered by how relevant each document is.

Relevance has no single definition, but a few intuitions drive almost every ranking function:

1. A document that mentions the query word **more often** is probably more about it (term frequency).
2. A word that appears in **almost every** document tells you little; a **rare** word is a stronger signal (inverse document frequency).
3. A word repeated 150 times does not make a page 150 times more relevant: returns **diminish**.
4. In a **very long** document a mention is less meaningful than in a short, focused one (length normalisation).

**TF-IDF** captures the first two and **BM25** captures all four. BM25 is the default scoring function in Lucene, Elasticsearch, OpenSearch and Solr.

## TF-IDF

For a query term `t` and a document `d`:

```text
tf(t, d)   = how many times t occurs in d
df(t)      = how many documents contain t
idf(t)     = log( N / df(t) )                    N is the number of documents
tf-idf     = tf(t, d)  *  idf(t)
```

For a multi-term query add up the score of each term. The `idf` factor makes a rare word worth much more than a common one: with `N = 1,000,000` documents, a word in 1,000 documents has `idf = log(1000) = 6.9`, while a word in 500,000 documents has `idf = log(2) = 0.69`, ten times less.

Raw term frequency over-rewards repetition, so many variants use a sub-linear function such as `1 + log(tf)`. That helps, but a document is still rewarded without limit for repeating a word, and long documents, which naturally contain more of every word, are favoured.

## BM25

BM25 fixes both problems with two tunable parameters:

```text
score(t, d) = idf(t) * ( tf * (k1 + 1) ) / ( tf + k1 * (1 - b + b * len(d) / avglen) )

k1  controls term-frequency saturation (typical 1.2): bigger means tf matters for longer
b   controls length normalisation (typical 0.75): 0 ignores length, 1 fully normalises
```

Two behaviours to notice:

- **Saturation:** as `tf` grows the fraction approaches `k1 + 1` and stops growing. The tenth mention adds far less than the second.
- **Length normalisation:** a document longer than average has a larger denominator, so the same `tf` earns less; a shorter one earns more.

BM25 uses a smoothed idf, `log(1 + (N - df + 0.5) / (df + 0.5))`, which never goes negative for words in more than half the documents. Because `k1` and `b` are knobs, they are tuned per corpus: short product titles want `b` near 0 (length carries no meaning), long articles want a higher `b`.

## Beyond text statistics

Text relevance is one signal among many. Real systems combine:

- **Field boosts:** a match in the title counts more than one in the body (BM25F scores fields with separate weights).
- **Freshness and popularity:** news wants recent items, shops want best sellers, with a decay so old items do not dominate or vanish.
- **Personalisation and context:** location, language, past behaviour.
- **Quality and authority signals:** link structure, ratings, spam scores.
- **Learning to rank:** a model trained on labelled examples or click data takes many features (including the BM25 score) and learns the best combination, typically applied to the top few hundred candidates.

### Semantic and hybrid search

Keyword matching misses synonyms and paraphrases (`cheap flights` and `low-cost airfare`). **Vector search** represents queries and documents as embeddings (dense vectors from a neural model) and retrieves the nearest ones by approximate nearest-neighbour indexes such as HNSW. It finds meaning but can miss exact tokens (product codes, names). **Hybrid search** runs both and merges the lists, commonly with **reciprocal rank fusion**: each document scores `sum of 1 / (k + rank)` over the lists it appears in, which needs no score calibration between the very different BM25 and vector score scales.

## Measuring relevance

You cannot improve what you do not measure. With human judgments or click data per query:

- **Precision at k:** the fraction of the top `k` that are relevant.
- **Recall:** the fraction of all relevant documents that were retrieved.
- **MRR (mean reciprocal rank):** the average of `1 / rank of the first relevant result`; good for "find the one right answer" queries.
- **NDCG (normalised discounted cumulative gain):** rewards putting highly relevant documents near the top, using graded relevance and a logarithmic position discount.

Run offline evaluation on a fixed query set before every ranking change, then confirm online with an A/B test, since offline gains do not always translate to user behaviour.

## Failure modes

- **Keyword stuffing and spam** rise to the top because text statistics are easy to game.
- **Popularity feedback loop:** popular results get more clicks, which makes them more popular; newer or niche results never surface.
- **Score incomparability:** adding BM25 to a vector similarity or a boost gives nonsense because the scales differ; use rank fusion or normalise.
- **Per-shard statistics skew:** document frequencies computed on small shards differ, so the same document scores differently depending on where it lives.
- **Overfitting to a test set:** tuning to a few queries that fail on real traffic.
- **Position bias in click data:** top results get clicked because they are on top, not because they are best.
- **Stale ranking features:** popularity or freshness computed daily make fast-moving items look old.

## Pitfalls

- Tuning `k1` and `b` once and never revisiting them as the corpus changes.
- Summing scores from different scales without normalisation.
- Measuring only clicks, not whether users found what they needed.
- Letting boosts overwhelm text relevance so unrelated promoted items win.
- Running expensive models on all matches instead of a small candidate set.
- Ignoring zero-result and abandoned queries, which show where recall fails.
