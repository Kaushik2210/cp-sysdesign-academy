## Intuition

A user types `cheap laptop with good battery` into a search box over 50 million product descriptions and expects an answer in a few tens of milliseconds. The obvious SQL, `WHERE description LIKE '%laptop%' AND description LIKE '%battery%'`, has to read every row. Even at a generous gigabyte per second that is far too slow, and it cannot rank results or tolerate typos.

Search engines solve this with the same trick as the index at the back of a book. A book does not make you read every page to find "photosynthesis"; it lists the pages where each word appears. A search engine builds that list for every word in every document **ahead of time**, so a query becomes a few list lookups and a merge instead of a scan. That structure is the **inverted index**, and it is the data structure behind Lucene, Elasticsearch, OpenSearch, Solr and the full-text features of most databases.

## The inverted index

Take three tiny documents:

```text
doc 1: "the quick brown fox"
doc 2: "the lazy brown dog"
doc 3: "the quick dog"
```

A normal (forward) index maps each document to its words. An **inverted** index maps each **term** to the documents that contain it:

```text
brown -> [1, 2]
dog   -> [2, 3]
fox   -> [1]
lazy  -> [2]
quick -> [1, 3]
the   -> [1, 2, 3]
```

Two parts:

- The **term dictionary**: a sorted set of all distinct terms, stored so you can look one up fast (a hash table, a sorted array with binary search, or a compact finite-state transducer that also supports prefix search).
- The **postings lists**: for each term, a **sorted list of document ids**. Real systems add to each posting the **term frequency** (how often the term occurs in that document, used for ranking) and optionally the **positions** (where in the document, needed for phrase queries like `"quick brown"`).

A query `quick AND dog` fetches the two postings lists `[1, 3]` and `[2, 3]` and **intersects** them to get `[3]`. The cost depends on the lengths of the lists, not on the size of the corpus.

## Text analysis: from raw text to terms

The terms are not the raw words. Before indexing (and identically before querying) text goes through an **analyzer**, a pipeline of steps:

1. **Character filtering:** strip HTML, normalise Unicode, fold accents (`café` to `cafe`).
2. **Tokenization:** split into tokens, usually on whitespace and punctuation, with rules for things like `e-mail`, URLs and `C++`.
3. **Lowercasing:** so `Laptop` matches `laptop`.
4. **Stop-word removal** (optional): drop extremely common words such as `the` and `of`. Modern engines often keep them because they matter for phrases and cost little once compressed.
5. **Stemming or lemmatization:** reduce words to a root so `running`, `runs` and `ran` can match. A stemmer (Porter, Snowball) chops suffixes by rule: fast but crude (`university` and `universe` can collide). A lemmatizer uses a dictionary and part of speech: more accurate and slower.
6. **Synonyms and expansion:** `tv` and `television`, `nyc` and `new york`.

**The same analyzer must run at index time and query time**, otherwise the query's terms will not match the stored ones. Changing an analyzer means **reindexing**, because the stored terms are baked in. Different fields get different analyzers: a product `sku` should be indexed as one exact token, a description with stemming, an autocomplete field with edge n-grams (`lap`, `lapt`, `lapto`, `laptop`) so prefixes match.

Language matters: English stemming does nothing for Chinese or Japanese, which have no spaces between words and need dictionary or n-gram tokenizers; German compounds need decompounding.

## What queries become

- **Single term:** read one postings list.
- **AND:** intersect lists. **OR:** union. **NOT:** subtract.
- **Phrase** (`"quick brown"`): intersect, then check that the **positions** are adjacent.
- **Prefix and wildcard:** walk the sorted term dictionary (`lap*` is a range) or use n-gram fields.
- **Fuzzy** (`laptpo`): find dictionary terms within a small edit distance, typically with a Levenshtein automaton, then union their postings.
- **Filters** (`price under 500`, `in stock`): usually separate structures such as sorted numeric columns or bitmaps that are combined with the text result.

### Intersecting postings lists

Merging two sorted lists is linear in their combined length. Two refinements matter when lists are very different in size:

- **Start with the shortest list.** For `rare AND common`, take each document of the rare list and **look it up** in the long one with binary search (or galloping search) instead of walking the whole long list.
- **Skip pointers / skip lists:** every few hundred postings keep a pointer so you can jump forward.

But binary-searching is not always better: for two lists of **similar** length a plain merge is cheaper, because each lookup costs `log(n)` steps instead of one. The simulation below measures both on a synthetic corpus, and also measures how much gap encoding saves.

## Compressing postings

Postings dominate index size, so they are compressed hard:

- **Delta (gap) encoding:** the ids are sorted, so store the **difference** from the previous id. A common term's gaps are tiny.
- **Variable-byte encoding:** write each gap in as few bytes as it needs (7 bits of data per byte). Small gaps take one byte instead of four.
- **Bit packing in blocks (frame of reference, PForDelta):** pack a block of 128 gaps using just enough bits for the largest, with exceptions handled separately; decodes very fast with SIMD.
- **Roaring bitmaps:** represent a dense postings list or a filter as a compressed bitmap, so AND and OR become fast bitwise operations.

rng = random.Random(8)

# a synthetic corpus: word ranks follow a Zipf-like law, so a few words are very common and most are rare

def draw():
    return min(bisect_left(cum, rng.random()), VOCAB - 1)

index = {}                                     # term id -> sorted list of document ids

# --- intersecting two posting lists: linear merge versus binary-searching the longer list ---
def merge_cost(a, b):
    i = j = steps = hits = 0
    while i < len(a) and j < len(b):
        steps += 1
        if a[i] == b[j]:
            hits += 1; i += 1; j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return hits, steps

def search_cost(short, long):
    hits = steps = 0
    lo = 0
    for x in short:
        l, h = lo, len(long)
        while l < h:                           # a binary search; every probe counts as one step
            steps += 1
            m = (l + h) // 2
            if long[m] < x: l = m + 1
            else: h = m
        lo = l
        if l < len(long) and long[l] == x: hits += 1
    return hits, steps

def varint_bytes(x):
    n = 1
    while x >= 128:
        x >>= 7

    for d in plist:

A local run on a synthetic corpus of 20,000 documents (Zipf-like word frequencies, 787,038 postings) printed: the most common term appeared in **19,946** documents, the median term in 44 and the rarest in 9. For a query joining a **rare term (23 documents) with the most common term (19,946)**, a linear merge took **19,303** steps while binary-searching each rare posting took **298**, with identical results. For two **mid-frequency terms (219 and 110 documents)** it was the other way around: the linear merge took **327** steps and binary search **1,300**. Storing postings as gaps with variable-byte encoding used **25%** of the raw 32-bit size for the most common term, 31% for a mid-frequency term, 47% for a rare term and **30% (953,439 bytes against 3,148,152) for the whole index**. Skewed lists want lookup-style intersection, balanced lists want merging, and compression is large and nearly free.

## Failure modes

- **Analyzer mismatch:** the query is analysed differently from the indexed text, so obvious matches are missed.
- **Analyzer change without reindex:** old documents keep their old terms and silently stop matching.
- **Index lag:** a new document is not searchable for a second or more; users who just posted something cannot find it.
- **Hot terms:** a term in nearly every document produces a huge postings list that is expensive to merge.
- **Out-of-sync copy:** the search index drifts from the database because an update event was lost.
- **Over-stemming or synonym explosion:** irrelevant documents appear.
- **Mapping explosion:** dynamic fields create thousands of terms or fields and bloat memory.

## Pitfalls

- Treating the search index as the source of truth instead of a derived, rebuildable copy.
- Forgetting that language and field type determine the right analyzer.
- Running leading-wildcard queries (`*phone`) on a large index.
- Indexing every field "just in case"; each indexed field costs space and indexing time.
- Not planning reindexing (use aliases and build a new index beside the old one).
- Expecting exactly-current results; search is near real time.
