## Intuition

Up to now a cache was an abstract box. In practice you choose a product, decide how data is spread over many nodes, and, for web content, lean on HTTP's own caching machinery and a CDN. This lesson covers the two dominant in-memory stores, how to shard them, and how `Cache-Control` and `ETag` let browsers and CDNs cache for you.

## Redis versus Memcached

| | Memcached | Redis |
| --- | --- | --- |
| Data model | Opaque key to byte-string value | Rich types: strings, hashes, lists, sets, sorted sets, streams, bitmaps and more |
| Operations | get, set, delete, increment, CAS | Hundreds of commands, atomic operations on structures, Lua scripts, transactions |
| Threading | Multi-threaded; scales across cores in one process | Command execution mostly single-threaded per instance (I/O threads in newer versions); scale by running more instances or cluster shards |
| Persistence | None; purely a cache | Optional: RDB snapshots, append-only file |
| Replication / HA | None built in (clients handle it) | Primary-replica replication, Sentinel for failover, Cluster for sharding |
| Eviction | LRU based, slab allocator | Configurable policies (LRU, LFU, TTL-based, none) |
| Typical use | Simple, large, high-throughput object cache | Cache plus counters, leaderboards, queues, rate limiters, pub/sub, locks, sessions |

Guidance:

- Need *only* a volatile object cache with the simplest operation and multi-core efficiency: Memcached is a good fit.
- Need data structures, persistence, replication, atomic counters, sorted sets or pub/sub: Redis.
- Do not treat either as a durable primary database unless you have deliberately designed and tested persistence and failover for it. Redis persistence has windows of loss.

Key points:

- **Mod N hashing** remaps almost every key when N changes (about 80 percent going from 4 to 5 nodes as measured in the load-balancing module's simulation), which at the cache layer is a miss storm. **Consistent hashing** with virtual nodes moves only about 1/N of keys, so the database sees a small additional load.
- **Redis Cluster** assigns each key to one of 16,384 hash slots by CRC16 of the key; each primary owns a range of slots, and the cluster migrates slots between nodes when resharding. Keys involved in multi-key operations must share a slot, which you control with **hash tags**: `{user42}:profile` and `{user42}:cart` hash only the part in braces.
- **Replication for availability**: a replica per shard promotes on failure. Replication is asynchronous, so a failover can lose the latest acknowledged writes, acceptable for a cache, a concern for anything else.
- **Failure of a node** loses that node's slice. With consistent hashing and no replicas, the database absorbs the slice's misses; plan capacity so a one-node loss does not tip it over, and warm replacements.
- **Capacity sizing example**: 200 million objects at an average 1 KB with roughly 50 bytes of per-key overhead is about 210 GB. At 32 GB usable per node that is 7 nodes before replicas; with one replica each, 14. Use real object sizes and overhead for your engine; these are planning estimates.

## CDN and HTTP caching

For web content, the first and cheapest cache is HTTP itself. Browsers and CDNs follow headers from the origin.

### Cache-Control

| Directive | Meaning |
| --- | --- |
| `max-age=N` | Fresh for N seconds in any cache; no revalidation needed during that time |
| `s-maxage=N` | Same, but only for shared caches (CDN, proxies); overrides `max-age` there |
| `public` / `private` | `private`: only the user's browser may store it (personalised data). `public`: shared caches may store it |
| `no-cache` | May be stored, but **must revalidate** with the origin before each reuse (despite the name) |
| `no-store` | Do not store at all (sensitive data) |
| `immutable` | Will never change during its freshness lifetime, so skip revalidation on reload |
| `stale-while-revalidate=N` | May serve a stale copy for N seconds while refreshing in the background |
| `stale-if-error=N` | May serve stale if the origin errors |

### Validators: ETag and Last-Modified

When a cached response goes stale, the cache can *revalidate* instead of downloading again:

1. The origin response carried `ETag: "v17"` (an opaque version) or `Last-Modified`.
2. The cache sends a conditional request: `If-None-Match: "v17"` (or `If-Modified-Since`).
3. If unchanged, the origin replies `304 Not Modified` with no body; the cache reuses its copy and resets freshness. Otherwise `200` with the new body and new validator.

This saves bandwidth, though not the round trip to the origin.

### The `Vary` header and cache keys

A cache keys responses by URL *plus* the request headers named in `Vary`. `Vary: Accept-Encoding` stores gzip and brotli copies separately. `Vary: Cookie` effectively disables shared caching (each user has a different cookie). Forgetting `Vary` on content that differs by language or device causes users to be served the wrong variant.

### Practical recipe

| Content | Headers | Why |
| --- | --- | --- |
| Fingerprinted assets (`app.3f9a2c.js`) | `Cache-Control: public, max-age=31536000, immutable` | Content change means a new URL, so cache forever |
| HTML shell | `Cache-Control: no-cache` plus `ETag` | Always revalidate cheaply so new asset URLs are discovered |
| Public API list, tolerates seconds | `public, max-age=30, stale-while-revalidate=60` | Smooths origin load; background refresh |
| Per-user data | `private, no-store` or `private, max-age=0` | Prevent shared caches from leaking user data |

CDN-specific concerns: **purge/invalidation** APIs are asynchronous and usually take seconds to minutes to propagate; prefer **versioned URLs** over purging; set `s-maxage` separately from `max-age` to let the CDN cache longer than browsers (so you can purge the CDN while browsers revalidate quickly); watch for cache poisoning through unkeyed inputs.

<Callout type="pitfall" title="no-cache does not mean no caching">
`no-cache` still stores the response and revalidates before reuse. To forbid storing, use `no-store`. Mixing these up is one of the most common HTTP caching mistakes.
</Callout>

## Failure modes

- **Cache node loss**: keys vanish, miss storm on the database; mitigated by replicas, consistent hashing and rebuild throttling.
- **Failover data loss**: asynchronously replicated writes lost when a Redis primary dies.
- **Big keys and slow commands**: a single huge value or an O(N) command blocks a single-threaded Redis instance, stalling every client.
- **Memory exhaustion** with `noeviction` or no TTLs.
- **CDN serves stale or wrong content**: missing `Vary`, or a purge that did not reach every PoP yet.
- **Leaking private data** through a shared cache because `private` was missing.

## Pitfalls

- Choosing Redis because it is popular when plain `get/set` with Memcached would do; or the reverse, bolting on counters and queues with ad hoc code.
- Using mod N sharding in clients and then adding a node during peak traffic.
- Multi-key operations in a cluster without hash tags, producing cross-slot errors.
- Long CDN TTLs on non-fingerprinted URLs, making rollbacks and fixes slow.
- Setting `Cache-Control` only on the CDN and not the browser, or the other way around.
