## Intuition

A cache is a smaller, faster copy of data kept close to whoever needs it. It works for two reasons that are properties of the *workload*, not of the cache:

- **Temporal locality**: data used recently is likely to be used again soon.
- **Skew** (popularity concentration): a small fraction of keys gets a large fraction of requests. Many real workloads are roughly Zipf-like, so the top few percent of items can account for most reads.

If every request touched a different item exactly once, no cache could help. Caching converts *repeated work* (a disk read, a network hop, a computation) into a memory lookup.

## Why bother: latency, load and cost

Approximate orders of magnitude (they vary by hardware, so treat them as ballparks): a main-memory reference is about 100 nanoseconds, a round trip inside a datacenter about 0.5 ms, an SSD random read about 100 microseconds, a database query that hits disk or does real work anywhere from a few milliseconds to hundreds, and a cross-continent round trip around 100 to 150 ms.

Caching therefore helps three things:

1. **Latency**: a cache lookup of about 1 ms replaces a 20 ms query.
2. **Throughput**: the backing store handles only the misses. If 90 percent of reads hit, the database sees a tenth of the read load.
3. **Cost and resilience**: fewer database replicas, and some reads survive a short backend outage.

## Hit ratio math

Let `h` be the hit ratio, `t_c` the cache lookup time and `t_s` the cost of going to the source on a miss. Expected latency (assuming a miss also pays the cache lookup, then the source):

`T = t_c + (1 - h) * t_s`

With `t_c = 1 ms` and `t_s = 20 ms`:

| Hit ratio | Expected latency | Database load vs no cache |
| --- | --- | --- |
| 0% | 21.0 ms | 100% |
| 50% | 11.0 ms | 50% |
| 90% | 3.0 ms | 10% |
| 99% | 1.2 ms | 1% |

Two lessons hide in this table. First, going from 90 to 99 percent hit ratio *divides the database load by 10 again* even though average latency improves only from 3.0 to 1.2 ms: for capacity planning, the **miss rate** is the number that matters, and small hit ratio changes at the high end are huge. Second, the average hides the tail: the 1 percent of misses still see 21 ms or worse, and if misses are slow enough to dominate p99, a 99 percent hit ratio does not make p99 fast.

### Worked example

A product page service receives 10,000 reads per second. The database can serve 2,000 reads per second. Required hit ratio: misses must be at most 2,000 per second, so `1 - h <= 0.2` and `h >= 0.8`. For safety margin and for cold-start periods, aim for 95 percent: misses are 500 per second, a quarter of the database capacity.

<CodeRunner language="python" code={`def expected_latency(h, t_cache=1.0, t_source=20.0):

    return rps * (1 - h)

for h in (0.0, 0.5, 0.8, 0.9, 0.95, 0.99):

## Where caches live

Layers from the user inward, each with a different owner, size and invalidation story:

| Layer | What it caches | Typical size and speed | Who controls it |
| --- | --- | --- | --- |
| Browser / client | Static assets, API responses via HTTP headers | Per user, MBs, zero network cost | `Cache-Control`, ETag (see the CDN lesson) |
| CDN / edge | Static files, sometimes whole pages and API responses | Many PoPs, TBs, tens of ms away | Origin headers plus CDN rules |
| Reverse proxy / gateway | Hot responses | Per node, GBs | Proxy configuration |
| Application, in-process | Parsed config, computed objects, hot rows | Per instance, MBs to GBs, nanoseconds | Your code |
| Distributed cache | Query results, sessions, objects (Redis, Memcached) | Shared cluster, GBs to TBs, sub-millisecond to a few ms | Your code and cache cluster |
| Database | Buffer pool of pages, query cache in some engines | Per node, as much RAM as available | DB engine |
| OS / hardware | Page cache, CPU caches | Automatic | Kernel |

Rule of thumb: cache **as close to the consumer as correctness allows**, and put the most expensive-to-recompute, most-shared data in the shared layers. Each additional layer multiplies the places a stale value can hide.

## What not to cache

- Data that is unique per request (low or zero hit ratio).
- Data where staleness is unacceptable and you cannot invalidate reliably (account balances during a transfer).
- Cheap-to-compute values where the cache lookup costs as much as recomputation.
- Highly personalised responses on shared caches (risk of leaking one user's data to another, a real class of CDN incident).

## Failure modes

- **Cold start**: after a deploy or cache restart, hit ratio is near zero and the database sees full load. Warm caches before shifting traffic, or limit traffic ramp.
- **Cache outage**: if the system *requires* the cache for capacity, the cache is a hard dependency. Know what happens at 0 percent hit ratio.
- **Stale reads**: users see old data. Decide an acceptable staleness bound per data type.
- **Memory growth**: no eviction or TTL means the cache fills and falls over.

## Pitfalls

- Reporting a high hit ratio computed over trivially cacheable traffic while the expensive requests miss; measure per endpoint.
- Caching before measuring: first check that the bottleneck is repeated reads of skewed keys.
- Forgetting negative caching (non-existent keys hammering the database) and its cost: cache the "not found" result with a short TTL.
- Letting the cache become the source of truth.
