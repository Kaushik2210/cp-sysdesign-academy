## Intuition

A well-known joke says there are two hard problems in computer science: naming things and cache invalidation. The second is hard because a cache is a *copy*, and a copy is correct only until the original changes. Invalidation is the work of making every copy notice. Doing it perfectly across independent systems is impossible without coordination, so the practical question becomes: **how stale may this data be, and how do we bound it?**

## Invalidation techniques

**1. TTL expiry.** Each entry carries a lifetime. Staleness is bounded by the TTL; no coordination needed. Simple and robust, but you choose between short TTLs (more misses and load) and long TTLs (staler reads).

**2. Explicit invalidation.** The writer deletes (or updates) the affected keys after changing the source. Fresh quickly, but you must know *every* key derived from the changed data, and failures between the database write and the cache delete leave stale entries. Mitigation: keep a TTL as a backstop, retry deletes from a durable queue, or publish invalidations from the database change log (change data capture).

**3. Versioned keys (cache busting).** Put a version or content hash in the key: `user:42:v17`, or `app.3f9a2c.js`. A change produces a *new* key, so nothing needs deleting and old entries age out through eviction. Excellent for immutable or derived data and for CDN assets. You store the current version somewhere authoritative (a small, cheap lookup), and it does not work when the identity must stay constant for external clients.

**4. Event-driven invalidation.** Services publish "entity changed" events and cache holders subscribe. Scales across services at the price of delivery guarantees (at-least-once, ordering, lost messages).

**5. Leases and tokens** (Facebook's memcache design): on a miss the cache hands one client a lease token; only that client may fill the key; if an invalidation arrives meanwhile, the token is invalidated so the stale fill is rejected. This addresses both the stale-set race and herd protection.

### The stale-fill race

Reader R misses and reads the old value `v1` from the database. Writer W commits `v2` and deletes the cache key. R then sets the cache to `v1`. The cache now holds stale data until TTL. Fixes: short TTL, leases, or versioned fills (only set if the version is not older than what the cache already knows).

## Consistency levels you can offer

- **Bounded staleness**: "at most TTL seconds old". The honest default.
- **Read-your-writes**: after a user writes, *that user* sees it. Achieve it by routing that user's reads to the database for a short period, or by updating the cache on their write path.
- **Strong consistency**: reads never stale. A cache fundamentally weakens this; if required, skip the cache for that data or use a design where the cache is the single owner (write-through with serialised access).

Always state the staleness contract per data type: product description (minutes is fine), stock count at checkout (must be fresh), follower counts (seconds to minutes).

## Cache stampede (thundering herd)

A hot key expires. In the next few milliseconds, hundreds of requests all miss, all go to the database to recompute the same expensive value, and the database falls over. Related situations: a cache node restart (a whole slice of keys missing at once), a deploy that clears the cache, or many keys sharing the same TTL expiring together.

Back-of-envelope: a key read 2,000 times per second whose recompute takes 300 ms. Without protection, about 2,000 x 0.3 = 600 concurrent recomputations pile up at the moment of expiry, each as costly as the original.

### Mitigations

| Technique | How it works | Cost |
| --- | --- | --- |
| Request coalescing (single flight) | In each process, concurrent misses for a key share one in-flight load | Per-process only; many processes still each load once |
| Distributed lock / lease | One caller acquires a short lock (for example `SET key NX PX`) and rebuilds; others wait briefly or serve stale | Lock expiry tuning; waiting latency; lock failure paths |
| Serve stale while revalidating | Keep a soft TTL (refresh time) and a hard TTL (drop time); after the soft TTL, return the old value and refresh in the background | Slightly stale reads; double memory lifetime |
| Jittered TTL | TTL = base plus random offset so keys do not expire together | Slightly uneven freshness |
| Probabilistic early expiration | Each reader may refresh *early* with probability rising as expiry nears; the formula (XFetch) uses recompute time and a random draw | Some extra recomputations; needs recompute-time estimate |
| Refresh-ahead / pre-warm | Background job refreshes known hot keys before expiry; warm caches before cutover | Wasted refreshes; must know the hot set |
| Load shedding | Cap concurrent recomputations; reject or degrade the rest | Some users get errors or defaults |

### Probabilistic early expiration, runnable

The XFetch rule: recompute early when `now - delta * beta * ln(random()) >= expiry`, where `delta` is how long a recompute takes and `beta` (default 1) tunes aggressiveness. Since `ln(random())` is negative, the left side adds a random positive amount, so the *chance of refreshing rises as expiry nears* and roughly one reader refreshes slightly early instead of all readers missing at expiry.

<CodeRunner language="python" code={`import math, random

def simulate(use_early, seed=1):
    rng = random.Random(seed)
    ttl, delta, beta = 10.0, 0.5, 1.0     # seconds
    expiry = ttl                           # when the cached value stops being valid
    done_at = None                         # when an in-progress rebuild finishes
    blocked = rebuilds = 0
    t = 0.0
    while t < 100:
        t += 0.001                         # about 1000 requests per second
        if done_at is not None and t >= done_at:
            expiry, done_at = done_at + ttl, None   # fresh value installed
        if t >= expiry:
            if done_at is None:            # first reader to miss starts the rebuild
                done_at, rebuilds = t + delta, rebuilds + 1
            blocked += 1                   # every reader meanwhile waits on the source
        elif use_early and done_at is None:
            if t - delta * beta * math.log(1 - rng.random()) >= expiry:
                done_at, rebuilds = t + delta, rebuilds + 1   # early refresh
    return blocked, rebuilds

print("no early refresh (blocked readers, rebuilds):", simulate(False))
print("early refresh    (blocked readers, rebuilds):", simulate(True))
`} />

A local run over 100 simulated seconds at about 1,000 requests per second printed 4,504 blocked readers and 9 rebuilds without early refresh, versus 0 blocked readers and 13 rebuilds with it. Early refresh trades a few extra rebuilds (the entry is refreshed slightly before its time) for removing the pile-up at expiry. The model is simplified: a single process, and readers that arrive while a rebuild runs are counted as blocked rather than served stale.

## Hot keys

A *hot key* is a single key so popular that one cache node, one shard or one database row saturates, even though the cluster as a whole has spare capacity. Sharding spreads *different* keys; it cannot spread one key. Examples: a celebrity profile, a flash-sale product, a global config.

Mitigations:

- **Local (in-process) cache** with a very short TTL (even 1 to 5 seconds) in front of the shared cache: each app instance fetches the key once per interval, cutting shared-cache QPS by the instance count.
- **Key replication / suffixing**: store the value under `key#0 ... key#N-1` and have readers pick one at random; the copies land on different nodes. Writers update or invalidate all copies.
- **Read replicas** for the hot shard.
- **Detect and promote**: count access frequency, automatically replicate keys that cross a threshold.
- **Request coalescing** to stop duplicates inside an instance.
- For hot *writes* (a counter incremented thousands of times a second): shard the counter into N sub-counters and sum on read, or batch updates with write-back.

## Failure modes

- **Delete lost**: the invalidation message is dropped; stale data until TTL. Always keep a TTL.
- **Herd on recovery**: after a cache outage the database receives a surge as everything misses; throttle rebuilds and warm gradually.
- **Lock held by dead process**: always use lock timeouts and fencing or idempotent rebuilds.
- **Negative stampede**: a missing key requested repeatedly bypasses the cache every time; cache the absence briefly.
- **Cross-region staleness**: invalidations arrive at different times in different regions.

## Pitfalls

- Believing "write to DB then delete cache" is atomic. It is two operations on two systems.
- Same TTL for everything, set by a cron-like deploy, producing synchronous expiry.
- Updating the cache in many code paths, so one forgotten path serves stale data forever.
- Caching authorization decisions with a long TTL.
