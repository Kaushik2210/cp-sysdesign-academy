## Intuition

A database is a promise about *what questions you can ask cheaply*. A relational database promises flexible questions over normalised tables ("join orders to customers, filter, aggregate"). Most NoSQL stores promise something narrower but faster or easier to distribute ("give me the value for this key", "give me everything for this partition key in order"). Choosing a store is choosing which questions you want to be cheap and which you accept as expensive or impossible.

"NoSQL" is a label for a loose group of different data models, not one technology. Treat each family on its own terms.

## Relational databases

Data lives in **tables** of rows and typed columns. Relationships are expressed with keys and joined at query time with SQL. The engine provides declarative queries, constraints (primary key, foreign key, unique, check), secondary indexes, and ACID transactions (next lesson).

- **Strengths:** ad-hoc queries, strong consistency inside one node, mature tooling, schema enforcement, transactions across rows and tables.
- **Limits:** scaling writes past a single primary needs sharding that the database does not do for you in the classic engines; schema changes on huge tables need care.

Examples: PostgreSQL, MySQL, SQLite, and managed offerings built on them.

## The NoSQL families

### Key-value stores

Data model: a map from key to opaque value. Operations: `get`, `put`, `delete` and sometimes scans. It is the simplest model and the easiest to partition by hashing the key.

Good for sessions, caches, counters, user profiles read by id. You cannot query by anything but the key unless you build your own index. Examples: Redis, Amazon DynamoDB (key-value and document modes), Riak.

### Document stores

Data model: self-contained documents (often JSON) stored under an id, with the engine able to see inside them and index fields. A document typically holds data you read together, such as an order with its line items.

Good when entities are naturally hierarchical, read as a unit, and have varying shape. Weak at many-to-many relationships and cross-document joins and transactions (support varies by product). Examples: MongoDB, Couchbase, Firestore.

### Wide-column stores

Data model: rows addressed by a partition key, with columns grouped into families and, inside a partition, rows kept sorted by a clustering key. Writes are typically appended and merged later (log-structured storage).

Good for very high write volume, time-series and event data, and queries like "all events for sensor 7 between two times". You must design tables around the queries; there are no general joins. Examples: Apache Cassandra, HBase, Google Bigtable.

### Graph databases

Data model: nodes and edges (relationships), each with properties. Queries traverse relationships ("friends of friends who like X").

Good when relationships are the main subject: social graphs, recommendations, fraud rings, dependency graphs. Multi-hop traversals that would need repeated self-joins in SQL become natural. Examples: Neo4j, Amazon Neptune.

<Callout type="tip" title="A good default">
Start with a relational database unless you can name the specific access pattern or scale that it cannot serve. A single well-indexed PostgreSQL or MySQL node goes a long way, and you can add specialised stores later for the parts that need them.
</Callout>

## What would you choose and why?

You are building (a) a shopping cart, (b) a social feed of followers' posts, (c) a store for 5 million sensor readings per second. Pick a family for each, write the primary access pattern, and name what you give up. Compare with the later lessons on partitioning and replication.

## Pitfalls

- Choosing a store by popularity instead of by access pattern.
- "NoSQL is faster": speed comes from giving up features such as joins and transactions, not from a magic ingredient.
- Using a document store for heavily relational data, then re-implementing joins in application code.
- Polyglot persistence without an owner for keeping the copies consistent.
