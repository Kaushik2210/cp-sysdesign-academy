## Intuition

**Normalization** means storing each fact once. If a customer's address appears in one place, updating it is one write and cannot go out of sync. **Denormalization** deliberately stores a fact in more than one place so that a read needs fewer joins or lookups. The first optimises for correctness and write simplicity, the second for read speed. Good schema design picks a point between them based on the access patterns.

## Normal forms, informally

- **1NF:** each column holds one atomic value; no repeating groups (no "tag1, tag2, tag3" columns or comma lists).
- **2NF:** every non-key column depends on the *whole* key (matters when the key has several columns).
- **3NF:** non-key columns depend only on the key, not on other non-key columns. "Every fact depends on the key, the whole key, and nothing but the key."

### Worked example

A single wide table:

| order_id | customer_id | customer_name | customer_city | sku | sku_name | qty |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 7 | Asha | Pune | A1 | Pen | 2 |
| 1 | 7 | Asha | Pune | B2 | Ink | 1 |
| 2 | 7 | Asha | Pune | A1 | Pen | 5 |

Problems: Asha's name and city repeat (update anomaly: change in one row only), a product with no orders cannot exist (insert anomaly), and deleting the last order of a product loses the product name (delete anomaly).

Normalised:

```sql
CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT, city TEXT);
CREATE TABLE products  (sku TEXT PRIMARY KEY, name TEXT);
CREATE TABLE orders    (id INTEGER PRIMARY KEY, customer_id INTEGER REFERENCES customers(id));
CREATE TABLE order_items (
  order_id INTEGER REFERENCES orders(id),
  sku TEXT REFERENCES products(sku),
  qty INTEGER,
  PRIMARY KEY (order_id, sku)
);
```

Each fact now lives once; a city change is one row update.

## Denormalization: when and how

Joins cost CPU and I/O, and in sharded systems cross-shard joins are expensive or impossible. Common denormalizations:

- **Copying a column** (store `customer_name` on the order so order pages never join).
- **Precomputed aggregates** (a `like_count` column, daily totals table).
- **Embedding** child data in the parent (document model: items inside the order).
- **Materialised views or read models** built from the source of truth.

Costs: more storage, writes touch more places, and copies can drift if an update path is missed. Mitigate with a single write path, transactions, or asynchronous rebuilds from the authoritative table.

<Callout type="note" title="Snapshots are not always a bug">
An order should usually keep the price and address *as they were at purchase time*. That is deliberate denormalization (a snapshot), not duplication to be normalised away.
</Callout>

## Schema design for access patterns

1. **List the queries first**: for each, its inputs, outputs, frequency and latency target.
2. **Model entities and relationships**, then normalise to a sensible baseline.
3. **Add indexes** for the key queries (previous lesson).
4. **Denormalize selectively** where measurements show joins or aggregations hurting.
5. **Re-check** when access patterns change.

In NoSQL stores the order flips: you often start from the queries and shape the data (and the partition key) to answer each with one lookup, accepting duplication.

## Failure modes

- A background job that maintains `like_count` crashes and counters drift; plan a reconciliation job.
- Updating a copied column in one place but not another produces contradictory pages.
- An embedded array grows without bound and a single document becomes huge.
- A migration to add a column locks a large table; use online schema change techniques.

## What would you choose and why?

Your feed page shows each post with author name and avatar. The author changes their avatar rarely. Would you join `users` on every read, copy the avatar URL into each post, or cache the author profile? Consider read volume of 50,000 per second and writes of a few per second to profiles. State the consistency you would accept.

## Pitfalls

- Denormalizing before measuring.
- Storing comma-separated lists in a column (violates 1NF; cannot index or constrain).
- Using one giant "everything" table with nullable columns.
- Forgetting that a snapshot of historical data (price, address) should not be normalised away.
