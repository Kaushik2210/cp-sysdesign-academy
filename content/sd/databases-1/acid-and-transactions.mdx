## Intuition

Moving 30 from Alice to Bob is two writes: subtract and add. If the machine dies between them, money vanishes. If another request reads between them, it sees a total that is 30 short. A **transaction** wraps a group of operations so the database treats them as one unit: either all of it happens or none of it, and (to the degree you configure) other transactions do not see a half-finished state.

## ACID

| Letter | Meaning | Plain version |
| --- | --- | --- |
| Atomicity | All operations of a transaction take effect, or none | Crash or error mid-way undoes everything |
| Consistency | A transaction moves the database from one valid state to another, respecting declared constraints | The database enforces rules like `balance >= 0`; the application defines the rest |
| Isolation | Concurrent transactions do not interfere in ways that break the illusion of running alone, to a degree set by the isolation level | Others do not see your partial work |
| Durability | Once committed, the data survives crashes | Written to a log on stable storage before the commit is acknowledged |

<Callout type="note" title="Consistency is the odd one out">
Atomicity, isolation and durability are properties the database provides. The "C" depends on the application declaring invariants (constraints, triggers) that the database can enforce. It is not the same consistency as in the CAP theorem or in replica consistency.
</Callout>

## A runnable demonstration: rollback in SQLite

This uses Python's built-in `sqlite3` module and is meant to run on your own machine (it is not run by the in-browser runner). A `CHECK` constraint keeps the balance non-negative. The second transfer fails in the middle; the earlier credit to Bob is rolled back.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, "
            "balance INTEGER CHECK (balance >= 0))")
con.executemany("INSERT INTO accounts (owner, balance) VALUES (?, ?)",
                [("alice", 100), ("bob", 50)])
con.commit()

def transfer(src, dst, amount):
    try:
        with con:  # commit on success, rollback on exception
            con.execute("UPDATE accounts SET balance = balance + ? WHERE owner = ?", (amount, dst))
            con.execute("UPDATE accounts SET balance = balance - ? WHERE owner = ?", (amount, src))
        print("committed")
    except sqlite3.IntegrityError as e:
        print("rolled back:", e)

transfer("alice", "bob", 30)
print(con.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall())
transfer("alice", "bob", 500)
print(con.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall())
```

Output (run locally with Python 3 and SQLite):

```text
committed
[('alice', 70), ('bob', 80)]
rolled back: CHECK constraint failed: balance >= 0
[('alice', 70), ('bob', 80)]
```

In the second transfer Bob was credited 500 first, then Alice's debit violated the constraint. Because both statements were in one transaction, the credit disappeared and balances are unchanged: atomicity in action.

## Anomalies (what can go wrong without isolation)

Suppose two transactions T1 and T2 run at the same time.

| Anomaly | What happens |
| --- | --- |
| **Dirty read** | T1 reads a value T2 has written but not yet committed; T2 then rolls back, so T1 acted on data that never existed |
| **Non-repeatable read** | T1 reads a row twice; T2 commits an update in between, so T1 sees two different values |
| **Phantom read** | T1 runs the same range query twice; T2 commits an insert matching the range, so new rows ("phantoms") appear |
| **Lost update** | T1 and T2 both read a counter, add one, and write back; one increment is lost |
| **Write skew** | T1 and T2 each read overlapping data, make decisions based on it, and write *different* rows; together they violate an invariant that each alone preserved |

### Write skew example

Rule: at least one doctor must be on call. Alice and Bob are both on call. Each transaction checks "are there at least two on call?", sees yes, and sets itself off call. They write different rows, so there is no direct write conflict, yet after both commit nobody is on call.

## Isolation levels

The SQL standard defines four levels in terms of which anomalies they must prevent. Real databases differ in the details, so check yours.

| Level | Dirty read | Non-repeatable read | Phantom | Write skew |
| --- | --- | --- | --- | --- |
| Read uncommitted | possible | possible | possible | possible |
| Read committed | prevented | possible | possible | possible |
| Repeatable read (standard wording) | prevented | prevented | possible | possible |
| Serializable | prevented | prevented | prevented | prevented |

Real-world notes (as documented by these products; verify for your version):

- **PostgreSQL** defaults to read committed. Its "repeatable read" is snapshot isolation, which also prevents phantoms but still permits write skew. Its read uncommitted behaves as read committed. Serializable uses serializable snapshot isolation and can abort transactions that you must retry.
- **MySQL InnoDB** defaults to repeatable read, using consistent snapshots plus locking.
- **SQLite** serialises writers, so its transactions are effectively serializable in the default mode.

<Callout type="pitfall" title="Serializable aborts are normal">
At higher isolation the database may abort a transaction to preserve correctness (a serialization failure or deadlock). Application code must be written to retry the whole transaction, not just the failed statement.
</Callout>

## Failure modes

- **Crash mid-transaction:** the log lets the database roll back uncommitted work on recovery.
- **Application crash after commit but before replying:** the client may retry; make the operation idempotent.
- **Long-running transactions:** hold locks or old snapshots, block cleanup and cause contention.
- **Distributed transactions:** spanning several databases needs two-phase commit or alternatives and is much slower and more fragile; avoid unless required.

## Pitfalls

- Believing "ACID" means the same thing in every database. Isolation levels differ by product.
- Assuming `read committed` stops lost updates; it does not.
- Wrapping network calls (payments, emails) inside a transaction, holding locks while waiting.
- Not retrying on serialization failures.
