## Intuition

A blob store is the building block behind almost every file upload feature. You give it bytes and a key, it gives you back the same bytes later, and it promises not to lose them. Everything else, such as folders, thumbnails, search and permissions, is built on top.

The interesting design questions are: how do big files get in without melting your app servers, how are bytes kept safe across disk and datacenter failures, and what do readers see right after a write?

## Core model

- **Bucket**: a named container with its own policy, region and settings. Bucket names are unique within the provider's namespace.
- **Key**: the string identifying an object within a bucket. Keys are flat; `a/b/c.jpg` is one key.
- **Object**: the bytes plus metadata (content type, size, ETag or checksum, user-defined headers).
- **Operations**: `PUT`, `GET` (optionally with a byte `Range`), `HEAD`, `DELETE`, `LIST` by prefix.
- **Limits** (S3 as an example, approximate and subject to change): a single `PUT` up to about 5 GB, multipart upload for objects up to about 5 TB, parts between 5 MiB and 5 GiB with at most 10,000 parts.

## Uploading large files: presigned URLs and multipart

Naive design: the client sends the file to your app server, which forwards it to the store. That doubles bandwidth, ties up your app threads for minutes, and makes the app server a scaling bottleneck.

Better design:

1. The client asks your API for permission to upload (authenticated, size and type checked).
2. The API creates a **presigned URL**: a URL with a signature and expiry baked in, produced with credentials the client does not have. Whoever holds the URL can perform that one operation on that one key until it expires.
3. The client uploads **directly** to the blob store using that URL.
4. The store notifies your system (event or callback), or the client confirms, and the API records the object in the metadata database.

For files larger than a few hundred MB, use **multipart upload**: split into parts, upload parts in parallel and retry only failed parts, then ask the store to complete the upload by listing the part numbers and ETags. Until completion the object does not exist, so readers never see a half-written file. Abandoned uploads should be cleaned up with a lifecycle rule or they keep costing storage.

<Callout type="pitfall" title="Validate on the server side">
A presigned URL authorises the bytes, not their meaning. Enforce key names, maximum size (conditions in a presigned POST policy, or check after upload), content type, and scan untrusted files before making them visible to others.
</Callout>

## Keeping bytes safe: replication and erasure coding

A blob store must survive disk, server, rack and datacenter failure. Two techniques:

**Replication.** Store N full copies (commonly 3) on different failure domains. Reads can come from any copy. Overhead is N times the data. Simple and fast to repair.

**Erasure coding.** Split an object into `k` data fragments and compute `m` parity fragments (Reed-Solomon is the classic scheme). Any `k` of the `k+m` fragments reconstruct the object. Example: `k=10, m=4` tolerates the loss of any 4 fragments with only 1.4x storage overhead, versus 3x for triple replication. The cost is CPU for encoding and decoding and more network traffic on repair and on reads when fragments are missing.

| Scheme | Overhead | Tolerates | Read path | Repair |
| --- | --- | --- | --- | --- |
| 3-way replication | 3.0x | 2 lost copies | Read one copy | Copy one full object |
| Erasure coding 10+4 | 1.4x | any 4 lost fragments | Read k fragments (or degraded decode) | Read k fragments, recompute |

Large providers publish durability targets such as "11 nines" (99.999999999% per object per year). That is a *design target* about not losing objects, not a guarantee about availability, and not protection against your own mistakes such as deleting an object.

## Consistency model

Older S3 behaviour was eventually consistent for overwrite and list operations. Since late 2020 Amazon S3 provides strong read-after-write consistency for `PUT`, `DELETE` and `LIST`. Other stores differ, so for any provider check: after a successful `PUT` returns, does a `GET` or `LIST` immediately reflect it? Concurrent writers to the same key still follow last-writer-wins, and there are no multi-object transactions, so "write the file, then write the pointer" must be designed by you (write the object first, then insert the metadata row, and run a reaper for orphans).

## Worked example: sizing an upload service

Assumptions: 2 million uploads per day, average 4 MB, 5% are videos averaging 400 MB.

- Photos: 1.9M x 4 MB = 7.6 TB per day. Videos: 0.1M x 400 MB = 40 TB per day. About 48 TB per day, or roughly 17 PB per year before replication.
- Average ingress: 48 TB / 86,400 s is about 0.55 GB/s, around 4.4 Gbit/s on average, several times that at peak. Sending it through app servers would require a large fleet; direct-to-store uploads move that bandwidth off your tier.
- With erasure coding at 1.4x the raw capacity is about 24 PB per year of raw disk; triple replication would be about 51 PB per year.

Numbers like these are why durability scheme and tiering (next lessons) dominate cost.

## Pitfalls

- **Sequential key names at high rate** (timestamps or incrementing ids as the leading characters) can concentrate load on one index partition on some stores. Check provider guidance; a short hash prefix is a common fix when needed.
- **Presigned URLs that live too long or are reusable** act like leaked credentials. Keep expiries short and scope them to one key and method.
- **Not verifying checksums** after upload. Send a content hash and let the store verify it.
- **Orphans**: an object written but the metadata insert failed (or the reverse). Always plan reconciliation.
- **Assuming `LIST` is a query engine.** It is a prefix scan; keep your own metadata index in a database.

## What would you choose and why?

Users upload 20 GB raw video files from home connections that drop frequently. Would you use presigned single PUT, presigned multipart, or proxy through your servers? Name the failure you are protecting against, how you resume after a drop, and how you clean up uploads that never complete.
