## Intuition

Two very different jobs hit your data:

- **OLTP** (online transaction processing): "update this order's status", "fetch user 42". Many small reads and writes touching a few rows each, low latency, strong correctness.
- **OLAP** (online analytical processing): "revenue per country per week for the past two years". Few queries, each scanning millions or billions of rows but only a few columns, tolerating seconds or minutes.

A system tuned for the first is usually poor at the second, so analytics gets its own storage and engine. The data flows from operational systems into an analytical store, usually through a pipeline.

## Row vs column layout

Take a table `events(user_id, country, device, amount, ts)` with a billion rows.

- **Row-oriented**: bytes of one row sit together. Fetching or updating a whole row is one seek. Ideal for OLTP.
- **Column-oriented**: all values of one column sit together. A query `SELECT SUM(amount) WHERE country = 'IN'` reads only `amount` and `country`, a fraction of the file. Similar values adjacent compress very well (run-length, dictionary and delta encoding), and engines can process vectors of values with CPU-friendly loops.

Writing a single new row to a column layout means touching every column's storage, so columnar stores batch writes and are bad at row-at-a-time updates.

**Parquet** (and ORC) are open columnar file formats. The idea: split the file into *row groups*; inside each, store each column as a *column chunk*; keep per-chunk statistics (min, max, null count) in the footer. A query engine reads the footer, skips row groups whose min/max cannot match the filter (predicate pushdown), and reads only the needed columns (projection pushdown).

| | Row store (OLTP) | Column store (OLAP) |
| --- | --- | --- |
| Access pattern | Few rows, all columns | Many rows, few columns |
| Writes | Single-row inserts and updates | Batch loads, append-mostly |
| Compression | Moderate | Strong (similar values adjacent) |
| Typical engines | PostgreSQL, MySQL | BigQuery, Snowflake, Redshift, ClickHouse, Parquet with Spark or Trino |

## Warehouse vs lake vs lakehouse

- **Data warehouse**: curated, schema-on-write, SQL-first, managed storage and compute tuned for BI. High quality and fast, less flexible for raw or unstructured data.
- **Data lake**: raw files (JSON, CSV, Parquet, images, logs) dumped cheaply in object storage, schema applied on read by whatever engine you point at it. Flexible and cheap, but can become a "data swamp" without cataloguing and quality checks.
- **Lakehouse**: open table formats (Apache Iceberg, Delta Lake, Apache Hudi) put transactions, schema evolution and snapshots on top of files in object storage, so one copy of data serves both styles.

## ETL vs ELT

- **ETL**: Extract, Transform, then Load. Clean and shape data in a separate processing tier before it reaches the warehouse. Good when the target is expensive or must hold only curated data, or for privacy filtering before landing.
- **ELT**: Extract, Load raw data, then Transform inside the warehouse or lake engine using SQL. Fits cheap storage and elastic compute; raw data is kept so transformations can be re-run when logic changes.

## Worked example: why columnar wins

A table has 1 billion rows and 20 columns, about 100 bytes per row uncompressed, so 100 GB. A query sums one 8-byte column filtered by one other 4-byte column.

- Row store: must read the whole 100 GB (ignoring indexes).
- Column store: reads about 12 bytes per row, so about 12 GB, and with 3x to 5x compression on those columns, roughly 2.4 to 4 GB. Add partition pruning by date and it may be a small fraction of that.

The exact ratios are workload dependent, but one to two orders of magnitude less IO is typical for narrow analytical queries.

## Pitfalls

- **Many tiny files.** Thousands of KB-sized Parquet files hurt listing and scan performance; compact into files of hundreds of MB.
- **Bad partitioning.** Partitioning by a high-cardinality column creates millions of directories; partitioning by something never filtered gives no pruning. Date is the common choice.
- **Running analytics on the production primary.** A single big scan can evict hot pages and spike latency.
- **Mixing definitions.** Two "revenue" numbers on two dashboards destroy trust; define metrics once.
- **Forgetting privacy.** Raw lakes copy personal data; plan deletion (GDPR-style erasure) and access control.
