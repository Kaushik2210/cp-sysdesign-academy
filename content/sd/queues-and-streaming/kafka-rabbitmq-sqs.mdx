## Intuition

Two designs sit behind most messaging products.

- A **broker with queues** (RabbitMQ, SQS) routes a message to a queue, hands it to a consumer, and *deletes it once acknowledged*. The queue is a to-do list: items disappear when done.
- A **distributed log** (Kafka) appends messages to a partitioned, ordered, retained file. Consumers track their own *position (offset)* and read; reading does not delete anything. The log is a ledger: entries stay until retention expires, and many readers can read the same entries at different positions.

That difference drives replay, ordering, fan-out and throughput characteristics.

## Core concepts side by side

### Kafka

- A **topic** is split into **partitions**. Each partition is an append-only ordered log, replicated across brokers (a leader plus follower replicas).
- Ordering is guaranteed **within a partition**, not across a topic. Producers choose the partition, usually by hashing a message key, so all events for one key stay in order.
- A **consumer group** shares a topic's partitions: each partition is read by at most one consumer in the group at a time. So maximum parallelism within a group equals the partition count. Different groups read independently, giving pub/sub.
- Consumers commit **offsets**. Retention is by time or size (for example 7 days), or by log compaction (keep the latest value per key), independent of whether messages were consumed. Replay means resetting an offset.

### RabbitMQ

- Producers publish to an **exchange**, which routes to **queues** by bindings and routing keys (direct, topic, fanout, headers). Consumers read from queues.
- Messages are acknowledged and removed. Rich routing, per-message TTL, priorities and dead-letter exchanges are built in.
- Typically a good fit for task distribution and complex routing at moderate throughput. Newer features (streams, quorum queues) add replicated and log-like options.

### Amazon SQS

- A fully managed queue. **Standard** queues offer very high throughput with at-least-once delivery and best-effort ordering; **FIFO** queues provide ordering per message group and deduplication within a window, at lower throughput limits (check current quotas).
- A received message becomes invisible for a **visibility timeout**; if not deleted in time, it reappears and is delivered again. Built-in dead-letter queue support via redrive policy. Retention up to 14 days.
- No broker to run; scales automatically; no replay of consumed messages.

## Worked example: choosing partitions

An order-events topic must sustain 30,000 messages per second, and a consumer instance can process about 2,000 messages per second. You need at least `30000 / 2000 = 15` consumers in the group, so at least 15 partitions. Add headroom for growth and for rebalancing (Kafka cannot easily reduce partitions, and increasing them changes the key-to-partition mapping), so choose a number like 24 or 32. Key by `order_id` so each order's events stay ordered. Partition counts are an approximation exercise; measure real consumer throughput first.

## Pitfalls

- Picking Kafka for a few hundred tasks a day because it is fashionable; a managed queue is far cheaper to operate.
- Picking SQS or a classic queue and later needing replay, multiple readers and ordering by key.
- Choosing a partition count by guess and a poorly distributed key.
- Assuming a topic is globally ordered; only partitions are.

## What would you choose and why?

You need (a) to send transactional emails, (b) to stream clickstream events to analytics, a fraud model and a search indexer, and (c) to run a nightly report job. Which system would you assign to each need and why? Would you use one broker for all three?
