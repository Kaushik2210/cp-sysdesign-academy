## Intuition

A producer sends a message, the network drops the acknowledgement, and the producer cannot tell whether the broker got it. Retry and you might duplicate; do not retry and you might lose it. A consumer processes a message and crashes before telling the broker; the broker cannot tell whether it was processed. Every messaging system must pick a side, and the names of the sides are the delivery semantics.

## The three guarantees

| Semantics | What it means | How it happens | Failure outcome |
| --- | --- | --- | --- |
| At-most-once | Delivered zero or one time | Acknowledge (commit offset) before processing; do not retry | Messages can be lost |
| At-least-once | Delivered one or more times | Process, then acknowledge; retry until acknowledged | Messages can be duplicated |
| Exactly-once | Effect happens once | Not a transport property on its own; see below | Needs cooperation end to end |

### What "exactly once" really means

Over an unreliable network, a receiver cannot be certain that a message was delivered exactly one time; this is a consequence of the two-generals problem. What systems offer is **exactly-once processing effects**: the *observable result* is as if each message were processed once. That is achieved by combining at-least-once delivery with deduplication or atomicity:

- **Idempotent producers** (Kafka): each producer has an ID and sequence numbers per partition, so the broker discards a retried duplicate within a session.
- **Transactions**: Kafka transactions write output records and the consumer's input offsets atomically, so a read-process-write pipeline *within Kafka* commits both or neither. Downstream consumers must read committed data only.
- **Idempotent consumers or sinks**: side effects outside the transactional boundary (an email, a payment API, a database in another system) are only safe if repeating them is harmless.

So the practical rule: exactly-once is "at-least-once plus idempotence". The guarantee ends at the boundary of the system that provides it.

## Idempotent consumers

An operation is **idempotent** if applying it repeatedly has the same effect as applying it once. `SET balance = 100` is idempotent; `balance = balance + 10` is not.

Techniques:

1. **Natural idempotence**: design the write as an upsert or "set to value" keyed by an ID.
2. **Idempotency key / dedup table**: store processed message IDs (with a TTL as long as the maximum redelivery window) and skip repeats. For atomicity, record the ID in the *same transaction* as the business effect, using a unique constraint.
3. **Conditional updates with versions**: apply only if the stored version is older (`UPDATE ... WHERE version < :v`).
4. **Pass the key downstream**: send an idempotency key to external APIs such as payment providers, which dedupe on their side.

### Worked example: crash between effect and ack

A consumer reads `{id: m-17, user: 5, amount: 10}`, adds 10 to a balance, then crashes before acknowledging. The broker redelivers; the consumer adds 10 again, so the balance is wrong by 10.

Fix: in one database transaction, `INSERT INTO processed(id) VALUES ('m-17')` (unique key) and update the balance. On redelivery the insert violates the unique constraint, the transaction aborts, and the consumer acknowledges the duplicate without effect.

## Ordering

- Brokers usually guarantee order only within a unit: a Kafka partition, an SQS FIFO message group, a single RabbitMQ queue with a single consumer.
- To keep related events in order, route them by key (`order_id`, `user_id`) to the same partition or group. Unrelated keys can proceed in parallel.
- Ordering breaks with: multiple competing consumers on one queue, retries that reinsert a failed message behind newer ones, producer retries without idempotence reordering in flight batches, and repartitioning that changes the key mapping.
- Global total order is expensive: one partition means one consumer's throughput. Prefer per-key order.
- When order cannot be guaranteed, make consumers tolerant: carry a version or timestamp in the event and ignore out-of-date updates.

## Pitfalls

- Believing a broker's "exactly-once" flag makes an email or payment safe.
- Dedup cache TTL shorter than the longest retry or replay window.
- Ordering by timestamp from different producers' clocks.
- Retrying a failed message to the back of the queue and breaking per-key order.

## What would you choose and why?

A payments consumer reads `charge` commands from a queue and calls a card processor over HTTP. Design the idempotency strategy: what key do you use, where do you store it, and what happens if your service crashes after the processor accepts the charge but before you record the result?
