## Intuition

A synchronous call chain makes every caller wait for, and depend on, everything behind it. A **message queue** puts a durable buffer in the middle: the producer drops a message and moves on; a consumer picks it up when it can. That one change buys three things.

1. **Decoupling**: producer and consumer do not need to be up at the same moment, use the same language, or know each other's addresses. They only agree on the message format.
2. **Buffering and load leveling**: a traffic spike fills the queue instead of overwhelming the consumer. The consumer drains at its own steady rate.
3. **Failure isolation and retry**: if the consumer is down, messages wait; if processing fails, the message can be retried.

You also gain independent scaling: add consumers to drain faster, without touching producers.

## Worked example: signup email

A signup request must create a user and send a welcome email. If the email provider takes 800 ms and is flaky, calling it inline makes signup slow and makes signup fail when email is down.

With a queue: the signup handler writes the user row, enqueues `{type: welcome, user_id}`, and returns in tens of milliseconds. A worker sends the email, retrying on failure. A spike of 5,000 signups in a minute (about 83 per second) becomes a short backlog drained by workers at, say, 20 emails per second per worker; 4 workers clear 5,000 messages in about 62 seconds. Users see instant signup either way.

## Queue vs pub/sub

| Property | Queue (point-to-point) | Pub/sub (topic) |
| --- | --- | --- |
| Delivery | Each message goes to one consumer in the group | Each message goes to every subscriber |
| Consumers | Competing workers sharing the load | Independent subscribers with their own progress |
| Typical use | Task distribution: send email, resize image | Event notification: order placed, many interested services |
| Scaling consumers | Add workers to drain faster | Each subscriber scales itself |

Modern systems blur the line. Kafka consumer groups give each *group* a copy of the stream and share work *within* a group, so one topic acts as pub/sub across groups and a queue within a group. SNS to SQS fan-out does the same: a topic publishes to several queues, one per subscribing service.

<Callout type="tip">
Rule of thumb: if the question is "who should do this job?", use a queue. If it is "who needs to know this happened?", use pub/sub.
</Callout>

## Trade-offs you accept

- **Eventual consistency**: the work is done later, so the user-visible effect lags. You must design the UX around that (pending states, notifications).
- **Operational complexity**: a broker to run, monitor and secure; lag and backlog become new things to alert on.
- **Harder debugging**: no single stack trace; use correlation IDs and distributed tracing.
- **Duplicates and reordering**: most queues deliver at least once, so consumers must tolerate duplicates (next lessons).
- **Backlog risk**: a queue hides overload until the backlog is hours old. Set limits and alerts.

## Pitfalls

- Using a queue where the user needs a synchronous answer; polling or callbacks then re-add the complexity.
- Dual writes (update DB, then publish) without an outbox, which drop or duplicate events when a step fails.
- Unbounded queues with no alert on age of the oldest message.
- Putting large payloads in messages; send a reference to object storage instead.

## What would you choose and why?

An image upload service must create thumbnails, scan for malware and update a search index. Is each of these a queue (one worker does it) or a pub/sub event (several systems react)? Which of the three can fail without blocking the upload response, and which must complete before the user sees the image?
