## Intuition

Batch processing answers questions about data that has stopped changing: "what were yesterday's sales?". **Stream processing** treats data as an unbounded sequence of events and keeps answers continuously up to date: "sales in the last 5 minutes, updated every second". You process each event as it arrives, hold a little state, and emit results with seconds of delay instead of hours.

## Building blocks

- **Event stream**: an append-only log of immutable facts (a click, a payment, a sensor reading), commonly in Kafka.
- **Stateless operators**: filter, map, enrich-from-a-static-table. Easy to scale and restart.
- **Stateful operators**: counts, joins, sessionisation. They keep state (in memory plus a local store with changelog backup) partitioned by key, so all events for a key reach the same worker.
- **Sinks**: another topic, a database, a search index, a cache, a dashboard.

## Use cases

| Use case | Example | Why streaming |
| --- | --- | --- |
| Real-time analytics | Live dashboard of orders per minute | Low latency aggregates |
| Fraud and anomaly detection | Flag more than 5 card attempts in 1 minute | Needs windows over recent history |
| Change data capture (CDC) | Mirror database changes to search or cache | Derived stores kept in sync from the DB log |
| Event-driven integration | Order placed triggers inventory, email, analytics | Decoupled reactions |
| ETL and enrichment | Join clicks with user profiles continuously | Replaces nightly batch |

### Change data capture

CDC reads a database's own transaction log (MySQL binlog, PostgreSQL WAL) and emits each row change as an event. Tools such as Debezium do this. It solves the dual-write problem: instead of the application writing to the database *and* a queue, the database is the source of truth and the stream is derived from it, in the same order the database committed. Consumers keep search indexes, caches and analytic stores in sync, and snapshotting plus log tailing lets a new consumer bootstrap.

## Windows and time

Aggregations over an infinite stream need bounded chunks, called **windows**:

- **Tumbling**: fixed, non-overlapping (every 1 minute).
- **Hopping or sliding**: fixed length, overlapping (5 minutes, advancing each 1 minute).
- **Session**: grouped by bursts of activity separated by an inactivity gap.

There are two notions of time:

- **Processing time**: when the processor sees the event. Easy, but results change with delays and replays.
- **Event time**: when the event actually happened, carried in the event. Correct, but events arrive late and out of order (a phone offline in a tunnel). Systems use **watermarks**, an estimate that "no events older than T will arrive", to decide when a window can close, and policies for late events (drop, side output, or update the previous result).

### Worked example: tumbling window counts

Events with event times (seconds): 3, 12, 58, 61, 64, 125, and a late event at time 55 arriving after 64. Using 60-second tumbling windows: window `[0,60)` has 3, 12, 58 and the late 55, so 4 if the window is still open or accepted via allowed lateness, or 3 if the watermark has passed and lateness is disallowed. `[60,120)` has 61, 64, so 2. `[120,180)` has 125, so 1. The choice of lateness policy is a trade between accuracy and latency.

## Correctness and operations

- **State and recovery**: processors checkpoint state and input offsets together so a restart resumes consistently (this is how engines such as Flink or Kafka Streams provide exactly-once state effects).
- **Reprocessing**: because the log is retained, you can fix a bug and recompute by replaying from an earlier offset into a new output.
- **Skew and hot keys**: a popular key makes one worker the bottleneck (see the hot keys lesson in Databases II).
- **Late data and schema evolution**: use a schema registry and compatible changes so old and new producers coexist.
- **Lag monitoring**: end-to-end latency is event time minus processing time.

## Pitfalls

- Using processing time when the business question is about event time.
- Unbounded state: windows without eviction, joins without time bounds.
- Treating the stream processor as the system of record; keep the log or a database as truth.
- Ignoring schema changes and breaking every downstream job at once.

## What would you choose and why?

You must show "orders in the last 5 minutes, per city" on a dashboard that updates every few seconds, and also produce an exact daily revenue report that finance relies on. Would you use the same pipeline for both? Which window type and time notion would you pick for the dashboard, and how would you handle late events for the finance report?
