## Intuition

A back-of-envelope estimate answers one question: *which order of magnitude are we in?* Is this 100 requests per second or 100,000? 50 GB or 50 PB? The answer decides whether one machine is enough, whether you need a cache, and whether the data fits in memory. Nobody needs the third significant digit; a factor of 10 changes the architecture, a factor of 1.3 does not.

To estimate quickly you need three tools in your head: powers of two (sizes), a few unit conversions (time and bytes), and a feel for how slow each kind of operation is.

## Powers of two

Computers count in powers of two, but humans round to powers of ten. The two are close enough that you can swap them when estimating:

| Power | Exact value | Round name | Handy reading |
| --- | --- | --- | --- |
| 2^10 | 1,024 | thousand | 1 KB |
| 2^20 | 1,048,576 | million | 1 MB |
| 2^30 | 1,073,741,824 | billion | 1 GB |
| 2^40 | about 1.1 x 10^12 | trillion | 1 TB |
| 2^50 | about 1.1 x 10^15 | quadrillion | 1 PB |

The error grows about 2.4% per step (1.024 per ten bits), so by 2^50 it is roughly 12.6%. For estimation that is noise; just say "1 GB is about 10^9 bytes".

Two useful corollaries:

- **n bits can name 2^n things.** A 32-bit ID covers about 4.3 billion items. If you expect 100 billion items over the system's lifetime, you need at least 37 bits (2^37 is about 137 billion), so a 64-bit ID is the natural choice.
- **Encoding length.** A 7-character code from the 62 characters `a-z A-Z 0-9` gives 62^7, about 3.5 x 10^12 distinct values. That is why URL shorteners can get away with 7 characters.

You can check these in the runner below.

<CodeRunner language="python" code={`for k in (10, 20, 30, 40, 50):
    print(f"2^{k} = {2**k:,}")
print("bits needed to name 100 billion items:", (100 * 10**9).bit_length())
print("7-char base62 space:", f"{62**7:,}")
`} />

## Units you must not mix up

| Quantity | Rule of thumb |
| --- | --- |
| Seconds per day | 86,400, which is about 10^5 (round to 100,000 for speed) |
| Seconds per month | about 2.5 million (30 days) |
| Seconds per year | about 31.5 million, roughly 3 x 10^7 |
| Per day to per second | divide by 86,400, so 1 million per day is about 12 per second |
| Bits vs bytes | Network speeds are quoted in **bits** per second; storage in **bytes**. 1 Gbps is about 125 MB/s |
| Availability | 99.9% allows about 8.8 hours of downtime per year; 99.99% about 53 minutes |

<Callout type="pitfall" title="Bits versus bytes">
A "10 Gbps" network card moves at most about 1.25 GB per second, before protocol overhead. Confusing Gbps with GB/s is a factor-of-eight error, and it is one of the most common in interviews.
</Callout>

Memorise one conversion: **1 million events per day is about 12 per second.** From it you can scale: 100 million per day is about 1,200 per second, and 1 billion per day is about 12,000 per second.

## Latency numbers

The table below is a descendant of the figures Jeff Dean popularised in talks and Peter Norvig published. Hardware keeps improving, and numbers vary by machine and workload, so treat every row as an **order of magnitude**, not a measurement. What matters is the *ratios*.

| Operation | Approximate time |
| --- | --- |
| L1 cache reference | about 1 ns |
| Branch misprediction | a few ns |
| L2 cache reference | a few ns (roughly 4 to 15 ns) |
| Mutex lock/unlock (uncontended) | tens of ns |
| Main memory reference | about 100 ns |
| Compress 1 KB with a fast compressor | a few microseconds |
| Send 1 KB over a 1 Gbps network | about 10 microseconds |
| Random read from an SSD | tens to a few hundred microseconds (use about 100 us) |
| Round trip within one datacenter | about 0.5 ms |
| Read 1 MB sequentially from SSD | roughly 0.2 to 1 ms |
| Spinning-disk seek | about 5 to 10 ms |
| Read 1 MB sequentially from spinning disk | roughly 5 to 20 ms |
| Round trip across continents | about 100 to 150 ms |

<Callout type="warning" title="Orders of magnitude only">
Do not quote these as facts about your hardware. Cloud network latency, SSD class (SATA vs NVMe) and disk caches move individual rows by factors of several. Use them to compare *kinds* of operations, never to promise a latency.
</Callout>

### Reading the table: the big takeaways

1. **Memory is fast, the network is slow.** One same-datacenter round trip costs about as much as several thousand memory references.
2. **Sequential beats random.** Disks, and to a lesser degree SSDs, are far better at reading a big contiguous block than at many small scattered reads.
3. **Avoid crossing the ocean on the hot path.** A cross-continent round trip is about 100 to 150 ms, and no engineering can beat the speed of light. This is why CDNs and regional replicas exist.
4. **Compress before you send** when the CPU time (microseconds) is far smaller than the network time saved.

Run a small ladder to feel the ratios:

<CodeRunner language="python" code={`ns = {
    "main memory read": 100,
    "SSD random read": 100_000,
    "same-datacenter round trip": 500_000,
    "HDD seek": 10_000_000,
    "cross-continent round trip": 150_000_000,
}
base = ns["main memory read"]
for name, t in ns.items():
    print(f"{name:28s} {t/1e6:10.4f} ms = {t//base:>10,} memory reads")
`} />

## Worked example: why batching round trips matters

A page needs 20 values. If each is fetched with its own call over the datacenter network, that is 20 round trips of about 0.5 ms, so roughly 10 ms of pure waiting even before any query work. If you batch all 20 into one request to an in-memory cache in the same datacenter, you pay about one round trip, so roughly 0.5 to 1 ms. The lesson is not only "memory is fast"; it is **count the round trips**, then batch them.

## What would you choose and why?

Your service must answer in under 100 ms at the 99th percentile for users on three continents, and the data is 2 TB that changes slowly. Which latency rows in the table drive the decision? Sketch where you would place the data and what you would do for users far from it. Write it down before reading the caching and CDN material later in the course.

## Pitfalls

- Treating the table as exact: quoting "SSD read is 16 us" as a fact about production.
- Forgetting that latency adds up along a request path while throughput is limited by the slowest stage.
- Mixing bits and bytes, or powers of two and ten, without noticing the factor of eight or the few percent.
- Estimating averages only: tail latency (p99) is usually what users and SLAs care about.
