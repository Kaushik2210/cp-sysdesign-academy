## Intuition

A wrong estimate that is *presented well* is still useful, because the reader can see the assumption and correct it. A right-looking number with hidden assumptions is dangerous. This lesson is about making estimates that are hard to get badly wrong, easy to check, and easy to challenge.

## Common mistakes

| Mistake | Why it hurts | Fix |
| --- | --- | --- |
| Using total users instead of daily active users | Overstates load several-fold | Ask for DAU or state a DAU:MAU ratio |
| Averages only | Systems fail at the peak | Apply a peak factor and say it |
| Forgetting replication and overhead | Storage off by 3x or more | Multiply by replication factor, add 10 to 50% for indexes and metadata |
| Unit slips (bits vs bytes, KB vs MB, day vs second) | Errors of 8x, 1000x, 86,400x | Write units on every line |
| False precision | Hides that inputs are guesses | Round to one or two significant figures |
| Ignoring read/write skew | Wrong component stressed | Always split reads and writes |
| Ignoring growth | Fine today, broken in a year | State a growth assumption (for example 2x per year) |
| Estimating without a goal | Numbers that decide nothing | Tie each number to a design choice |

<Callout type="pitfall" title="Precision is not accuracy">
"23,148 requests per second" built from "about 2 million" is a lie of precision. Say "about 23,000".
</Callout>

## Sanity checks

Before you commit to an answer, run these quick checks:

1. **Plausibility vs known systems.** One machine commonly handles thousands of simple requests per second, and a single well-tuned database node often handles thousands to tens of thousands of simple operations per second (very workload dependent). If you compute 5 QPS you do not need sharding; if you compute 5 million QPS you need a very large fleet.
2. **Dimensional analysis.** Do the units cancel to what you want? QPS x bytes per request must give bytes per second.
3. **Round-trip the answer.** Multiply the final per-second figure back to per day and see if it matches the starting assumption.
4. **Bounds.** Is the answer bigger than the whole planet's population or the size of the internet? Then a factor is off.
5. **Compare two routes.** Compute storage as users x per-user data and as writes x record size over time. If they disagree by 10x, find out why.
6. **Powers of ten.** If the result has a different order of magnitude from your gut feeling, rethink the assumptions, not just the arithmetic.

### A worked sanity check

You estimate a photo service stores 4 TB per day and bills 1.5 PB per year. 4 TB x 365 is about 1,460 TB, about 1.5 PB. Matches. You also estimate egress of 1.2 GB per second. A single 100 Gbps (about 12.5 GB/s) network link could carry it, so a few links or a CDN are plausible. If you had gotten 120 GB/s, you would pause and re-check.

## Presenting estimates in an interview

1. **State the assumptions first**, as a list, and ask the interviewer to confirm or change the important ones.
2. **Show the arithmetic compactly**: "100M per month / 2.6M seconds is about 40 per second".
3. **Round and say it**: "about 40 writes per second, 4,000 reads per second".
4. **Say what it means**: "so this is a read-heavy, small-payload problem; storage is only a few TB, so one big node could hold it, but I will still replicate for durability".
5. **Name the dominant dimension** and carry it through the design.
6. **Invite correction**: "if the ratio is 1000 to 1 instead, a cache becomes essential".

Do not spend more than a few minutes. The estimate exists to justify choices.

## Pitfalls

- Defending a number instead of its assumptions. The assumptions are the argument.
- Silently dropping a factor (replication, peak) when the number looks scary.
- Estimating things that do not influence any decision.
- Forgetting to revisit: when the design changes (for example adding a cache), update the numbers.
